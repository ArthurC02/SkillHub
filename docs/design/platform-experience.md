# 平台體驗模型

本文件描述 Skill Hub 的**目標體驗模型**：以 Skill 資產、不可變版本、驗證與發佈串成平台。單頁規則見[設計系統](./system.md)，頁與頁之間的現行路由與網址狀態見[資訊架構](./information-architecture.md)。

本文件的「目標」不代表已上線。現況以程式、契約、測試與兩份現行規格為準；新增入口、路由或可見能力時，必須同步更新 IA 與守衛。M5 創作入口仍受伺服器旗標與曝光邊界控制。

## 0. 設計方法

| 層次 | 問題 | 本文件落點 |
| --- | --- | --- |
| Strategy | 使用者與平台要得到什麼 | §1 |
| Scope | 提供哪些能力、哪些不進主導覽 | §2 |
| Structure | 物件如何關聯、如何移動 | §3～§4 |
| Skeleton | 導覽、工作區與操作如何排列 | §5 |
| Surface | 如何讓平台可信、可辨識、可及 | §6 |

這五層是產品推導，不是 `system.md` 的品質分層。

## 1. Strategy：平台替誰解什麼問題

平台依任務調整揭露深度，但共用同一份事實：

| 使用者狀態 | 首要問題 | 平台承諾 |
| --- | --- | --- |
| 學習者 | 能不能安全完成任務 | 先給用途、限制、來源、風險與試跑入口 |
| 改善者 | 哪裡沒達到要求、下一步是什麼 | 把 Test Case、Run、Evaluation、差異與修訂留在同一脈絡 |
| 精深者 | 判斷依據與執行證據是否可靠 | 保留不可變版本、Trace、強制者、識別碼與溯源 |

```text
發現或建立 → 納入工作區 → 建構版本 → 設計驗證 → 試跑 → 判定與改善 → 發佈或帶走 → 持續營運
```

平台以五種活動組織旅程，不等於五個同名導覽項目：

| 活動 | 語意 | 主要空間 |
| --- | --- | --- |
| Shopping | 探索與採用 | Catalog、公開 Skill 詳情 |
| Making | 建構與修訂 | Library、Studio、版本工作台 |
| Sharing | 發佈與交付 | 發佈空間、Publication、Bundle |
| Conducting | 試跑與驗證 | Test Case、Run、Activity |
| Governing | 治理與營運 | 獨立 Admin 空間 |

## 2. Scope：平台空間與能力

| 空間 | 回答的問題 | 包含 | 不包含 |
| --- | --- | --- | --- |
| Catalog | 外面有哪些可採用的能力 | 搜尋、瀏覽、比較、公開詳情 | 私人草稿、工作區管理 |
| Workspace | 我現在最值得處理什麼 | 待決策、續作、執行中、最近使用 | 一般指標牆、所有功能捷徑 |
| Library | 我擁有哪些資產 | 匯入、複製、創作、保存檢視 | Run 歷史、孤立下載清單 |
| Studio | 我正在創作或修訂什麼 | 會話、草稿、參考確認、驗收 | 無物件脈絡的生成表單 |
| Activity | 哪些工作在跑或等我決定 | Run、Evaluation、Creation、Packaging、Publishing 的跨物件投影 | 取代來源物件的完整證據 |
| 發佈 | 哪些成果正在準備或已對外 | Release、Publication、Bundle、曝光狀態 | Catalog 排名、自動發佈 |

匯入、建立 Test Case、上傳 Dataset、選版本試跑、比較 Run、打包與下載都是脈絡內指令，不因有表單就升格為穩定空間。全域命令列屬未落地目標；加入前必須先有真實指令、權限模型與確認流程。

## 3. Structure：概念模型

```text
平台空間
└─ Skill 工作台
   ├─ Draft／Creation Session
   ├─ 不可變 Skill Version
   ├─ Test Case／Dataset
   ├─ Run／Trace／Evaluation
   └─ Release／Publication／Bundle
```

- Skill 是持續演進的資產身分。
- Draft／Creation Session 是可修改工作，不是正式版本。
- Skill Version 是不可變快照；試跑、評估與發佈都指向精確版本。
- Test Case 描述任務與驗收條件，可重用於多次驗證。
- Run 是一次執行；Trace 是證據；Evaluation 是成果判定，三者不可合成一個狀態。
- Activity Item 是跨平台投影，不是新的領域真相或狀態機。

目標網址可保存可分享、可重開的身分與工作脈絡；顯示密度、展開狀態與個人排序不進網址。`/releases`、更完整的 Studio 與全域命令列仍是目標，不進現行 IA 路由表，直到程式、契約與測試一起落地。

### 3.1 目標資料與證據契約

- 每一筆可續作工作都必須可回到其 owner、Workspace、精確 Skill Version 與產生它的來源脈絡；不得以 Provider 臨時 id、前端暫存值或「最新版本」取代。
- Draft 與 Creation Session 可變；Skill Version、Test Case 快照、歷史 Run、Trace、Evaluation、Release 與交付成品不可變。改善永遠建立新草稿或新版本。
- 建立 Run 前，畫面必須顯示並確認精確內容、權限、成本或額度、同意與會使用的工具；模型服務只能提出內容，平台服務擁有授權、成本、狀態轉移與保存事實。
- Trace 是執行證據，Evaluation 是對驗收條件的判定；執行完成與成果符合分別呈現。讀不到或尚未產生的證據必須具名，不得補成通過。
- Activity 只能投影已由 Run、Evaluation、Creation、Packaging、Publishing owner 成功取得且已授權的 facts。任一來源不完整時，呈現來源狀態或拒絕部分聚合，不自行合成結論；完整證據仍回到來源頁。
- Publication、Release、Bundle 與 Catalog 曝光是不同事實。可取得、可散布與可見性各依 owner facts 呈現，未知不推定為可下載或公開。

## 4. Structure：使用者生命週期

### 4.1 發現與採用

```text
描述任務 → 候選與限制 → 比較證據 → 打開候選 → 試跑或複製到 Library
```

Catalog 先回答適用性、來源、相容性、依賴與風險；沒有結果時才出現受旗標保護的創作入口。

### 4.2 建立與修訂

```text
說明目標 → 確認參考 → 定義驗收 → 產生草稿 → 驗證 → 修訂 → 明確保存
```

Studio 顯示目前階段、已確認事實、待回答問題與草稿差異。模型只提出內容；平台服務保有會話、狀態與保存事實。

### 4.3 驗證與改善

```text
選版本 → 選 Test Case → 確認權限與成本 → 試跑 → 看兩軸結果 → 查看證據 → 修訂或保留
```

執行狀態與任務判定並列；改善建立新草稿或版本，不改寫歷史結果。進行中的評估顯示進度，不渲染任務判定報告；`無法判斷` 是終態未知，不是 pending 的替代詞。

### 4.4 發佈與帶走

```text
選版本 → 檢查再散布與風險 → 預覽交付 → 建立 Release／套件 → 發佈或下載
```

公開頁、套件取得條件與 Catalog 曝光分開回答。缺少 owner fact 時顯示未知，不把 `available` 推成「任何人可下載」。

### 4.5 六個生命週期檢查點

1. **探索**：先說用途、來源、限制、風險與證據覆蓋範圍，再提供採用、比較或試跑的下一步。
2. **接納**：匯入、Fork 或建立只在清楚的 Workspace 脈絡中開始；不可信內容在 Web／API 程序中不執行。
3. **創作**：會話保留已確認事實、待回答問題、草稿差異與保存目標；每次提交都可辨識目前步驟與是否可離開。
4. **驗證**：Test Case、Dataset、精確 Version、權限與成本在試跑前固定並可檢查；結果保留版本與證據的對應。
5. **判定與改善**：Run 狀態、Evaluation 判定與 Trace 分列；建議只導向可追溯的新草稿或新 Version。
6. **交付與營運**：Release、Publication、Bundle、下載與曝光的限制可檢查、可追溯，且不把交付完成描述成公開曝光。

## 5. Skeleton：平台殼層與工作區

桌面版以產品／Workspace、搜尋或指令、全域狀態、帳號組成頂列；主要平台空間與最近物件在側欄；目前物件的操作留在工作台。手機版保留可辨識的主要空間，不把側欄壓窄成不可掃讀的內容。

現行 `/`、`/workspace`、`/library`、`/activity`、`/workspace/runs` 與 `/workspace/downloads` 各自保有明確責任。工作台以 Skill、Version、Test Case、Run 與發佈脈絡連接各頁，不要求使用者反覆重選物件。Studio 的桌面並列與手機檢視切換是目標骨架，未宣稱所有 Studio 旅程已完成。

### 5.1 殼層、工作台與微互動契約

- 全域殼層只承載穩定平台空間、搜尋、帳號與跨頁狀態；一次性建立、匯入、試跑、打包與發布操作保留在其物件脈絡。
- 工作台先顯示目前回答的問題與判斷依據，再放操作；物件識別、Version、Test Case 與續作連結在跨頁時保持可辨識。
- 桌面 Studio 的會話清單與目前工作區是並列責任；手機改為可切換檢視，不能形成兩條競爭的文件捲軸。唯一可捲動的對話與固定輸入艙是目標行為，不代表所有會話流程已落地。
- 操作後的提醒只描述這次完成、失敗或等待的事實與可行下一步；草稿、目標或決定改變後，舊結果不得冒充目前結果。控制項被結果取代時，焦點必須移到可接續的目標。
- 動態工作必須說出目前步驟、是否會自行結束、是否能離開、可觀察的進度與最後更新；reduced motion、鍵盤與 375px 仍適用。

## 6. Surface：沿用現行設計系統

平台化不另建 token、元件庫或圖示系統。文字是狀態第一通道，顏色與圖示是輔助；識別碼與技術中繼資料退到進階層；動效只表示狀態轉移並尊重 reduced motion；主要路徑可用鍵盤與手機完成。所有頁內安全資訊遵守 `system.md` 的永不折疊清單、缺席型別、兩軸判定與強制者具名規則。

## 7. 不可破壞的邊界

1. M5 創作入口由伺服器旗標控制，不能由命令列、首頁或 Studio 繞過。
2. Run 建立前完成權限、成本與同意綁定，並綁定精確內容。
3. Skill Version、歷史 Run、Trace、Evaluation 與 Release 保持不可變。
4. Run 狀態由 Go 擁有；Activity 只是投影。
5. 執行成功與成果符合是兩個維度。
6. Publication 不等於 Catalog 曝光。
7. Secret、Trace 遮罩與 Workspace scope 不轉移到前端推測。
8. 不可信 Skill、Script 或資料不得在 Web／API 程序內執行。

## 8. 現況到目標的遷移

| 現行入口 | 目標落點 | 現況 |
| --- | --- | --- |
| `/workspace/skills` | `/library` | 舊網址只作相容導向 |
| `/workspace/creations` | Studio 與工作台建構 | 旗標後的現行入口；目標仍未全數落地 |
| `/lab/test-cases`、`/lab/test-cases/$testCaseId/datasets` | 工作台驗證 | 現行 canonical 脈絡已保留 |
| `/lab/run` | 驗證內的 preflight | 相容導向，不渲染第二份流程 |
| `/workspace/runs` | 試跑活動保存檢視 | 現行 Run-only 保存檢視 |
| `/workspace/downloads` | 發佈／交付活動 | 現行保存檢視，未宣稱 `/releases` 已上線 |
| `/admin/*` | 獨立營運殼層 | 現行後台路由保留 |

每個遷移方向只有在程式、契約、測試與 IA 同步後才可稱為落地。未實作的目標不得出現在現行路由表或封測入口。

### 8.1 分階段遷移驗收

每一階遷移都必須保留原有深連結或明確導向到 canonical URL，不能以第二份流程或靜默遺失脈絡取代。完成一階前，至少確認：權限與 Workspace scope 沒有由 UI 推測；精確 Version、Test Case、Run 與交付識別仍可續接；旗標關閉時沒有誤導入口；來源失敗、空白、無權與未知各有不同呈現；鍵盤、375px 與 reduced motion 的行為沒有退化。

## 9. 驗證方式

驗證要確認跨頁脈絡、空／失敗／無權／未測量狀態、鍵盤、375px、reduced motion、動態狀態宣告，以及背景工作離開後是否回到伺服器事實。代表性任務包括：從 Catalog 比較、採用並試跑；從失敗證據建立新草稿後重跑；由 Activity 回到來源工作；選定不可變版本建立交付；以及用手機與鍵盤完成同一流程。
