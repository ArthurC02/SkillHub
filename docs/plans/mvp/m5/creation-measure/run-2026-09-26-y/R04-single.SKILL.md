# GitHub issue 嚴重度分級與處理建議

當任務是把一批 GitHub issue 依嚴重度分成三級，並為每個 issue 各寫一句處理建議時，依下列流程處理。

## 1. 先確認輸入內容
- 取得每個 issue 的標題、描述、重現步驟、影響範圍、是否有錯誤訊息、是否影響核心功能。
- 如果資訊不足，先根據現有內容判斷；若無法判斷，標記為「需補充資訊」並說明缺少什麼。

## 2. 使用三級嚴重度
將每個 issue 分到以下三類之一：
- **高**：造成核心功能中斷、資料遺失、重大安全風險、廣泛使用者受影響，或沒有可行替代方案。
- **中**：功能受損但仍可部分使用、影響特定情境或部分使用者、存在明顯 workaround。
- **低**：不影響主要流程、屬於外觀/文案/小瑕疵、影響範圍小且可接受。

## 3. 判斷原則
- 先看**影響程度**，再看**影響範圍**，最後看**是否有 workaround**。
- 若 issue 同時符合多個等級，優先採用較高嚴重度。
- 不要只根據情緒化字眼判斷，必須依實際影響分類。

## 4. 為每個 issue 寫一句處理建議
每個 issue 只寫一句，內容要具體、可執行，格式可參考：
- **高**：建議立即排入修復並先做臨時緩解，避免影響擴大。
- **中**：建議納入近期修正排程，並確認是否有替代方案可先降低影響。
- **低**：建議列入一般待辦，於下一次整理或版本更新時一併處理。

## 5. 輸出格式
對每個 issue 輸出以下資訊：
- issue 標題
- 嚴重度：高 / 中 / 低
- 一句處理建議

可使用表格，格式如下：

| Issue | 嚴重度 | 處理建議 |
|---|---|---|
| 標題 A | 高 | 建議立即排入修復並先做臨時緩解，避免影響擴大。 |
| 標題 B | 中 | 建議納入近期修正排程，並確認是否有替代方案可先降低影響。 |
| 標題 C | 低 | 建議列入一般待辦，於下一次整理或版本更新時一併處理。 |

## 6. 品質檢查
- 每個 issue 都必須有且只有一個嚴重度。
- 每個 issue 都必須有一句處理建議。
- 建議句要和嚴重度一致，避免高嚴重度卻寫成延後處理。
- 若輸入是多個 issue，逐一處理，不要合併成單一結論。
