# GitHub issue 嚴重度三分級與處理建議

## 目的
將一批 GitHub issues 依嚴重度分成三級，並為每個 issue 寫一句處理建議。

## 適用時機
當你拿到 issue 清單、issue 摘要、標題或描述，需要快速做初步分級與回應建議時使用。

## 分級標準
使用以下三個等級：

- **高**：會造成服務中斷、資料遺失、資安風險、核心功能完全不可用，或沒有立即處理就會快速擴大影響。
- **中**：會影響主要功能、造成明顯錯誤或大量使用者受影響，但仍有替代方案或暫時可運作。
- **低**：不影響核心流程，屬於小錯誤、文字/版面問題、邊緣情境、改善建議或低風險技術債。

## 處理流程
1. **讀取每個 issue 的標題與描述**，先判斷影響範圍、是否阻斷流程、是否有安全或資料風險。
2. **選定一個嚴重度**：高、中、低。
3. **寫一句處理建議**，內容要具體、可執行，並符合嚴重度。
4. **若資訊不足**，以已知資訊做保守判斷，並在建議中指出需要補充的關鍵資訊，例如重現步驟、影響範圍、錯誤訊息或受影響版本。

## 輸出格式
對每個 issue 輸出一行或一段，格式固定如下：

- `Issue: <標題或編號>`
- `嚴重度: 高｜中｜低`
- `建議: <一句話處理建議>`

## 撰寫建議的原則
- 一句話即可，避免長篇說明。
- 要包含下一步動作，例如「先修復」、「補充資訊後再排程」、「納入下個版本」。
- 高嚴重度建議應偏向立即處理與止血。
- 中嚴重度建議應偏向排程修復與確認影響範圍。
- 低嚴重度建議應偏向記錄、排入待辦或與其他工作合併處理。

## 判斷優先順序
當多個因素同時存在時，優先考慮：
1. 資安與資料風險
2. 服務可用性與核心流程阻斷
3. 受影響使用者數量與頻率
4. 是否有替代方案
5. 是否只是外觀、文字或低風險改善

## 注意事項
- 不要把所有 issue 都判成同一級。
- 不要只根據標題做武斷判斷；若描述不足，保守分級並在建議中要求補充資訊。
- 不要輸出多句建議；每個 issue 只寫一句。
