## 目的

當你收到一段 Python 函式或方法程式碼，且任務是「審 docstring、補缺漏、改成 Google 風格」時，依照下列流程處理。

## 處理流程

1. **先辨識函式介面**
   - 找出函式名稱、參數、預設值、型別註記、`*args`、`**kwargs`、`self`、`cls`。
   - 找出回傳值型別註記與實際回傳行為。
   - 找出可能拋出的例外、side effects、屬性修改、I/O、狀態變更。

2. **檢查現有 docstring**
   - 判斷是否已存在 docstring。
   - 找出缺少的內容：
     - 函式用途摘要
     - 參數說明
     - 回傳值說明
     - 例外說明
     - `*args` / `**kwargs` 說明
     - 類別方法中 `self` / `cls` 是否需要說明（通常不必，除非有特殊意義）
   - 若內容與程式碼不一致，優先以程式碼為準修正。

3. **依 Google 風格補寫**
   - 使用以下結構：
     - 第一行：一句話摘要，簡潔描述函式做什麼。
     - 空一行。
     - `Args:`：逐一列出參數。
     - `Returns:`：說明回傳值；若回傳 `None` 也要寫明。
     - `Raises:`：列出明確可預期的例外。
     - 需要時可加 `Yields:`、`Attributes:`、`Examples:`，但只有在程式碼確實對應時才加。
   - 每個條目格式：`name (type): 說明。`
   - 若型別註記已存在，仍可在 docstring 中保留型別；若沒有型別註記，從程式碼推斷合理型別並標示。

4. **補齊缺漏時的原則**
   - 不要捏造程式碼沒有證據的行為。
   - 若無法確定某參數用途，根據名稱、預設值、使用位置推斷，並用保守措辭描述。
   - 若無法確定是否會拋出例外，不要硬加；只有在程式碼中可見或高度明確時才寫入 `Raises:`。
   - 若函式只是轉呼叫其他函式，docstring 應描述這個函式本身的責任，不要複製底層實作細節。

5. **格式與語言**
   - 輸出 docstring 必須是 Google 風格。
   - 保持與原始程式碼相同的語言；若原始內容是中文，則 docstring 也用中文，但結構仍維持 Google 風格標題。
   - 保持簡潔、精準、可讀。
   - 不要加入與函式無關的評論。

6. **若資訊不足**
   - 如果只提供函式名稱或片段不足以可靠補寫，先列出你需要的最少資訊：函式定義、參數、回傳、可能例外、相關程式碼。
   - 不要臆測完整 docstring。

## 輸出要求

- 直接產出修正後的 docstring，或在需要時產出可直接貼回原函式的完整 docstring 區塊。
- 若使用者要求「審」而非「改」，則先指出缺漏與不一致，再給出建議版 docstring。
- 不要改寫函式程式碼本身，除非使用者明確要求。
