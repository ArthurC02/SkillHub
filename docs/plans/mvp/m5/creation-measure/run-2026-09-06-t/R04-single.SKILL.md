# GitHub Issue 嚴重度三分級與處理建議

## 目的
將 GitHub issue 依嚴重度分成三級，並為每個 issue 寫一句處理建議，方便快速分流與排優先順序。

## 分級標準
使用以下三個等級：

- **高**：會造成核心功能不可用、資料遺失、資安風險、重大阻塞，或影響大量使用者。
- **中**：會影響主要流程、造成明顯錯誤或退化，但仍有替代方案或影響範圍有限。
- **低**：屬於小問題、文字/版面/體驗瑕疵、非阻塞性改善，或影響很小。

## 處理流程
1. **讀取 issue 內容**：標題、描述、重現步驟、影響範圍、截圖、標籤、留言。
2. **判斷影響程度**：優先看是否影響核心功能、資料安全、可用性、使用者範圍。
3. **判斷緊急性**：是否有立即風險、是否阻塞發版、是否需要先止血。
4. **分到三級之一**：高 / 中 / 低。
5. **寫一句處理建議**：用一句話說明下一步怎麼處理，避免空泛。

## 建議輸出格式
對每個 issue 輸出一行或一段，格式固定如下：

- `#<issue 編號>｜<標題>｜嚴重度：高/中/低｜建議：<一句處理建議>`

如果沒有 issue 編號，就用標題代替識別欄位。

## 寫建議時的原則
- **高**：建議以「立即處理、先止血、暫停發布、回滾、加上監控」為主。
- **中**：建議以「排入近期修正、補測試、確認影響範圍、安排修復」為主。
- **低**：建議以「納入一般待辦、視排程處理、可與相關優化合併」為主。

## 判斷優先順序
若資訊不足，依下列順序判斷：
1. 是否有資料遺失或安全風險
2. 是否造成核心流程中斷
3. 是否影響多數使用者或關鍵客戶
4. 是否有替代方案
5. 是否只是外觀、文案或小型改善

## 注意事項
- 不要把所有 issue 都判成高。
- 不要只重述 issue 內容；建議必須是可執行的下一步。
- 若 issue 描述不足，仍要依現有資訊給出最合理的分級，並在建議中提醒補充資訊或先確認影響範圍。
- 若同一批 issue 彼此相關，可先分級，再在建議中指出是否應合併處理。
