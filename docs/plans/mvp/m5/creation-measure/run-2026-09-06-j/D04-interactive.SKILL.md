# 伺服器 Log 錯誤分流

依下列流程在單次回覆中完成分析。所有輸入與輸出都只存在於目前對話；不讀取檔案、不連線 Jira、不傳送通知，也不寫入外部儲存空間。流程圖中的「讀取」、「建立」、「通知」與「寫入」均以處理使用者貼上的文字及產生 Markdown 草稿實現，不得聲稱已完成任何外部操作。

使用以下固定規則：

- 每筆 log 佔一行，格式為 `ISO-8601 時間戳 level service message`。
- 以前三個空白分隔欄位依序作為時間戳、level 與 service；該行其餘文字全部作為 message。
- 只有 level 欄位恰為大寫 `ERROR` 時才算 ERROR；`INFO`、`WARN` 或其他值都不算。
- ERROR 門檻是嚴格大於 10 筆；恰好 10 筆不觸發。
- 受影響服務只取 ERROR 記錄的 service，去除重複值並依首次出現順序列出。
- Jira 專案與通知管道未知，因此相關內容只能標示為草稿，供人工提交或傳送。
- 若使用者完全未提供 log 內容，不得虛構資料；只須明確說明缺少必要的 log 輸入，並請使用者直接貼上 log。除此情況外，不詢問追問問題，直接採用以下預設值完成處理：Jira 問題類型為 `Bug`、優先級為 `High`。

## 1. 起點：讀取伺服器 log 檔

將使用者訊息中直接貼出的每一行 log 視為一筆記錄。這裡的「log 檔」只是流程圖沿用的名稱；不得嘗試存取未提供的本機或遠端檔案。

解析每筆記錄的時間戳、level、service 與 message，並計算全部記錄總數。

## 2. 處理：篩出 ERROR 行

依固定規則保留 level 欄位恰為 `ERROR` 的完整原始行，維持輸入順序。計算 ERROR 記錄數，並從這些記錄整理受影響服務。

準備輸出的第一個區段：

```markdown
## 分流結果

- 總記錄數：{總數}
- ERROR 數：{ERROR 數}
- 門檻判定：{ERROR 數} {嚴格大於或不大於} 10，{已觸發或未觸發}處置
```

請用實際結果取代大括號內容，不要原樣輸出大括號。

## 3. 判斷：錯誤是否超過 10 筆

只判斷 `ERROR 數 > 10`：

- 是：先產生「Jira 建單草稿」，接著產生「值班通知草稿」，最後產生「每日摘要」。
- 否：略過 Jira 與通知草稿，直接產生「每日摘要」。

不得使用 `>= 10`，也不得依訊息嚴重程度、服務種類或其他條件改變分支。

## 4. 處理：建立 Jira 問題單

僅在 `ERROR 數 > 10` 時執行；否則略過本節。不得呼叫 Jira，而是緊接在「分流結果」後產生：

```markdown
## Jira 建單草稿

> 狀態：僅為草稿，尚未提交至 Jira。

- 摘要：伺服器 log 偵測到 {ERROR 數} 筆 ERROR
- 問題類型：Bug
- 優先級：High
- 描述：偵測到 {ERROR 數} 筆 ERROR；受影響服務為 {服務清單}。請調查錯誤原因並採取處置。

### ERROR 記錄

```text
{依原始順序列出全部 ERROR 行}
```
```

所有 ERROR 原始行都必須收錄且只能收錄一次。不得把 INFO、WARN 或其他非 ERROR 行放入 ERROR 記錄區塊。

## 5. 處理：通知值班工程師

僅在 `ERROR 數 > 10` 時執行；否則略過本節。不得實際傳送通知，而是在 Jira 草稿後產生：

```markdown
## 值班通知草稿

> 狀態：僅為草稿，尚未透過任何通知管道傳送。

偵測到 {ERROR 數} 筆 ERROR，受影響服務為 {服務清單}。請值班工程師立即調查錯誤原因、確認服務狀態並採取適當處置。
```

請將服務清單以清楚、自然的方式列出。

## 6. 終點：寫入每日摘要

無論是否超過門檻，都必須在最後產生「每日摘要」。這裡的「寫入」是指寫入目前回覆，不得宣稱已寫入外部系統。

```markdown
## 每日摘要

- 總記錄數：{總數}
- ERROR 數：{ERROR 數}
- 受影響服務：{服務清單；若沒有則寫「無」}
- 本次產生的草稿：{若已觸發則寫「Jira 建單草稿、值班通知草稿」；否則寫「無」}
```

# 回覆要求

整份回覆使用 Markdown。區段順序必須是：

1. `分流結果`
2. 若 ERROR 超過 10 筆，則為 `Jira 建單草稿`
3. 若 ERROR 超過 10 筆，則為 `值班通知草稿`
4. `每日摘要`

只輸出分析結果與所需草稿，不聲稱已建立 Jira 問題單、已通知值班工程師、已讀寫檔案或已完成任何其他外部服務操作。
