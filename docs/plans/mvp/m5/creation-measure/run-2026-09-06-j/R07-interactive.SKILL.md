## 任務

審查訊息中直接提供的 Python 函式程式碼，找出缺少或不完整的 docstring，並在一次回覆中補成 Google 風格。只修改 docstring；不得重構或改變函式簽名、裝飾器、註解及任何可執行陳述。

## 輸入要求

輸入必須包含可直接閱讀的 Python 函式程式碼，而不是只有檔名、路徑或對未提供內容的描述。

若訊息完全沒有提供 Python 函式程式碼，簡短說明無法審查，並請使用者貼上完整函式；不要猜測不存在的程式碼。除此之外，不要提出澄清問題：依現有程式碼採取保守且合理的假設，直接完成審查，並在摘要中說明會影響結果的假設。

## 處理步驟

1. 閱讀每個函式的簽名、型別註記、預設值、現有 docstring 與函式本體。
2. 判斷 docstring 是否缺少用途摘要、參數、回傳值、產生值或明確例外等資訊。
3. 僅根據程式碼中可觀察到的行為補寫 docstring。不得執行程式碼，也不得捏造外部契約、業務規則、副作用或呼叫端保證。
4. 將需要補正的 docstring 改為 Google 風格；若原 docstring 已完整且符合格式，保留其正確內容，只做必要修正。
5. 逐字保留 docstring 以外的程式碼，輸出補正後的完整程式碼。

## Google 風格規則

- 先寫一行簡潔、具體的用途摘要。
- 有參數時加入 `Args:`。每個參數都要記錄，名稱必須與簽名一致。
- 參數有型別註記時，使用該型別；沒有註記時，只有在函式內容足以可靠判定時才寫型別，否則採保守描述。
- 參數有預設值時，在其說明中明確寫出預設值。不要把沒有預設值的參數描述成可選。
- 一般函式有回傳值時加入 `Returns:`，記錄可由回傳註記或函式內容確認的型別與含義。
- 產生器使用 `Yields:`，不要以 `Returns:` 取代產生值的說明；只有程式碼確實另有具意義的回傳值時才額外使用 `Returns:`。
- 函式本體明確 `raise` 的例外應加入 `Raises:`，並說明觸發條件。相同例外型別若對應不同、可明確辨識的條件，分別記錄各條件。
- 僅在程式碼清楚支持時加入其他內容。無法可靠判定的細節使用保守措辭，不補造資訊。
- 沒有適用內容的區段不要加入。

Google 風格的基本形狀如下；實際輸出只保留適用區段：

```python
"""一句用途摘要。

Args:
    parameter_name (Type): 參數用途；如有預設值，明確說明。

Returns:
    ReturnType: 回傳值的含義。

Raises:
    ExceptionType: 明確的觸發條件。
"""
```

## 保留原始程式碼

- 允許的唯一變更是新增或替換函式 docstring。
- 不得修改函式名稱、參數、型別註記、預設值、裝飾器或回傳註記。
- 不得修改、增刪或重新排列任何可執行陳述。
- 不得順手格式化、重新縮排或改寫 docstring 以外的內容。
- 若輸入包含多個函式，依原順序處理，並在同一個完整程式碼區塊中保留其周邊內容。

## 輸出格式

輸出必須依下列順序完成，不要以問題結尾：

1. `審查摘要`：用簡短條列說明哪些函式的 docstring 被新增或補正、補了哪些區段，以及採用的任何保守假設。不要聲稱已執行或測試程式碼。
2. `補正後程式碼`：提供一個標示為 `python` 的程式碼區塊，包含補正後的完整輸入程式碼。不得只輸出 docstring 片段。

即使原 docstring 不需修改，也要依相同格式輸出摘要及完整程式碼，並在摘要中明確說明未發現需要補正之處。
