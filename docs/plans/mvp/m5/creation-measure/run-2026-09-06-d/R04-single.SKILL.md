# GitHub Issue 三級嚴重度分級與處理建議

當你收到一批 GitHub issue，且任務是把它們分成三級嚴重度並各寫一句處理建議時，依下列步驟處理。

## 1. 先讀取每個 issue 的內容
- 逐一確認標題、描述、重現步驟、影響範圍、是否有 workaround、是否影響核心功能。
- 若資訊不足，先根據現有內容做暫定分級，並在建議中指出需要補充的關鍵資訊。

## 2. 使用三級嚴重度
將每個 issue 分到以下其中一級：
- **高**：造成核心功能不可用、資料遺失、重大安全風險、廣泛使用者受影響，或沒有可行 workaround。
- **中**：功能受損但仍可部分使用，影響範圍有限，或有暫時替代方案。
- **低**：不影響主要流程，屬於外觀、文案、可用性小問題，或影響很小。

## 3. 分級時的判斷順序
優先看這些訊號：
1. 是否有資料遺失、資安、服務中斷、核心流程失敗。
2. 影響多少使用者、多少環節、是否可繞過。
3. 是否只是體驗、顯示、邊緣情況或低頻問題。

## 4. 為每個 issue 寫一句處理建議
每個 issue 只寫一句，內容要具體、可執行，格式可用：
- **高**：建議立即排入修復並優先驗證回歸，必要時先發布臨時緩解措施。
- **中**：建議納入近期修正排程，先確認影響範圍與可行 workaround，再安排修復。
- **低**：建議納入一般待辦，於下一輪整理時一併處理即可。

## 5. 輸出格式
對每個 issue 輸出一行或一個條目，包含：
- issue 標題或編號
- 嚴重度：高 / 中 / 低
- 一句處理建議

範例格式：
- `#123 登入失敗：高｜建議立即修復並優先驗證登入流程回歸。`
- `#124 按鈕對齊異常：低｜建議納入一般待辦，於下次版面整理時一併修正。`

## 6. 若需要更一致的判斷
- 同類 issue 盡量維持相同標準。
- 若兩級之間難以判斷，優先以影響範圍與是否阻斷流程決定。
- 不要把所有問題都判成高；只有真正阻斷或高風險的才列高。
