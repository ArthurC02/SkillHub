# GitHub Issue 嚴重度三分級與處理建議

當你收到一批 GitHub issue，且任務是把它們依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先確認輸入內容
- 逐筆讀取 issue 標題、描述、重現步驟、影響範圍、錯誤訊息、標籤與留言。
- 若資訊不足，先根據現有內容做暫定分級，並在建議中指出需要補充的關鍵資訊。
- 不要自行臆測未提供的事實；只能根據 issue 文字內容判斷。

## 2. 使用三級嚴重度
將每個 issue 分到以下三類之一：

### 高
符合以下任一情況時使用：
- 造成核心功能無法使用、服務中斷、資料遺失、資安風險或重大回歸。
- 影響多數使用者、正式環境，或沒有可行替代方案。
- 問題持續發生且阻礙主要流程。

### 中
符合以下任一情況時使用：
- 影響重要功能，但仍有替代方案或只影響部分使用者。
- 錯誤會降低體驗、造成明顯不便，或需要盡快修復但不屬於阻斷性問題。
- 需要排程處理，但不必立即中斷其他工作。

### 低
符合以下任一情況時使用：
- 影響輕微、邊緣情境、外觀/文案/小型改善，或僅是可接受的瑕疵。
- 不影響主要流程，且修復時程彈性較大。
- 屬於觀察、優化、技術債或非緊急需求。

## 3. 分級判斷原則
- 以「對使用者與系統的實際影響」優先，不只看 issue 標題。
- 若同時符合多個等級，採用較高嚴重度。
- 若 issue 是功能請求而非 bug，通常歸為低或中，視影響與急迫性而定。
- 若 issue 涉及安全、資料完整性、付款、登入、部署失敗或大範圍故障，優先評為高。

## 4. 為每個 issue 寫一句處理建議
每筆 issue 都要附上一句建議，格式要簡潔、可執行，並與嚴重度一致：
- 高：建議立即確認影響範圍、先止血，再安排修復與驗證。
- 中：建議排入近期修復，補齊重現條件並安排測試。
- 低：建議納入一般待辦或後續優化清單，視排程處理。

## 5. 輸出格式
對每個 issue 輸出以下資訊，保持一致：
- Issue：標題或編號
- 嚴重度：高 / 中 / 低
- 建議：一句話

### 範例格式
- Issue：登入頁面在 Safari 無法送出表單
  - 嚴重度：高
  - 建議：先確認受影響版本與範圍，暫時提供替代登入方式並優先修復。

- Issue：搜尋結果排序偶爾不符合預期
  - 嚴重度：中
  - 建議：補充重現條件後排入近期修正，並加入回歸測試。

- Issue：按鈕間距在小螢幕略顯擁擠
  - 嚴重度：低
  - 建議：納入介面優化清單，於後續版面調整時一併處理。

## 6. 最後檢查
- 每個 issue 都有且只有一個嚴重度。
- 每個 issue 都有一句處理建議。
- 用詞一致、簡潔，不要寫成長篇分析。
- 若需要對外輸出，優先使用使用者提供的語言與術語。
