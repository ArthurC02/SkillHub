# GitHub issue 嚴重度三分級與處理建議

## 目的
將 GitHub issue 依嚴重度分成三級，並為每個 issue 各寫一句處理建議。

## 分級標準
使用以下三個等級，並保持一致：

- **高**：會造成核心功能中斷、資料遺失、資安風險、重大錯誤，或沒有明顯替代方案。
- **中**：會影響主要流程、造成明顯不便、部分功能異常，但仍有替代方式或影響範圍有限。
- **低**：屬於小問題、文字/版面瑕疵、輕微體驗問題、優化建議，對使用影響有限。

## 處理流程
1. **先讀 issue 內容**，抓出：
   - 問題現象
   - 影響範圍
   - 是否阻斷使用
   - 是否有資料風險或安全風險
   - 是否有替代方案
2. **判定嚴重度**：
   - 若有資料遺失、資安、服務中斷、核心流程完全不可用，標為 **高**。
   - 若影響主要功能但仍可繞過，標為 **中**。
   - 若只是小瑕疵或改善建議，標為 **低**。
3. **為每個 issue 寫一句處理建議**：
   - 建議要具體、可執行、簡短。
   - 句子中可包含優先處理方向、驗證方式或下一步。
   - 不要寫成多句說明。
4. **輸出時保持一致格式**，讓人可以快速掃描。

## 建議輸出格式
對每個 issue 使用以下格式之一：

- `Issue #123｜高｜建議：先修復核心錯誤並補上回歸測試。`
- `Issue #124｜中｜建議：優先處理主要流程異常，確認是否有暫時替代方案。`
- `Issue #125｜低｜建議：排入後續優化，修正後再一起驗證介面細節。`

## 判定原則
- **以使用者影響為主**，不要只看技術難度。
- **同時有多個問題時**，以最嚴重的影響決定等級。
- **資訊不足時**，根據已知影響保守判定，並在建議中提醒補充資訊或驗證。
- **避免過度細分**，只使用高／中／低三級。

## 注意事項
- 不要把「難修」等同於「高嚴重度」。
- 不要把「很多人提到」等同於「高嚴重度」，仍以實際影響為準。
- 每個 issue 只輸出一個等級與一句建議。
