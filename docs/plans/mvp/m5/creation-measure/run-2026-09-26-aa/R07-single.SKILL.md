# 目的

當使用者提供 Python 函式、類別方法或模組片段，要求「補 docstring」或「把 docstring 改成 Google 風格」時，使用此技能。

# 工作原則

- 只處理 docstring，不改動程式邏輯、函式簽名或其他程式碼，除非為了讓 docstring 與實際程式一致而必須讀取上下文。
- 以程式碼本身為準：從函式簽名、型別註記、預設值、控制流程、回傳敘述、raise 敘述與呼叫關係推斷 docstring 內容。
- 若資訊不足，先從上下文找；仍不足時，保守描述，不要捏造不存在的行為。
- 使用 Google 風格 docstring：`Args:`、`Returns:`、`Raises:`、`Yields:`、`Attributes:`（若適用）、`Examples:`（只有在原始碼或需求明確需要時才加）。
- 保持語言一致：原始碼與使用者要求若是中文，就用中文寫 docstring；若原始碼慣例是英文，就用英文。

# 判斷流程

1. **確認目標範圍**
   - 找出要補 docstring 的函式、方法或類別。
   - 若使用者只貼一段程式碼，優先處理其中最明確的函式。
   - 若有多個函式，逐一處理，避免漏掉。

2. **讀取函式資訊**
   - 參數名稱、順序、預設值、型別註記。
   - 是否有 `*args`、`**kwargs`、keyword-only 參數。
   - 回傳值型態與條件。
   - 可能拋出的例外。
   - 是否為 generator、context manager、property、async function。

3. **補齊 docstring 內容**
   - 第一行用一句話總結函式做什麼。
   - 第二段補充必要的行為、限制、前置條件或副作用。
   - `Args:` 下逐一列出參數，包含型別與用途；若型別已在簽名中清楚標示，可在 docstring 中簡潔描述用途即可。
   - `Returns:` 說明回傳內容；若沒有明確回傳或回傳 `None`，寫明 `None` 或省略 `Returns:`，依專案慣例一致處理。
   - `Yields:` 用於 generator。
   - `Raises:` 只列出程式中實際可能拋出的例外，不要列推測的。
   - `Examples:` 只有在程式碼或使用者要求中有明確需求時才加入。

4. **處理缺漏與不確定性**
   - 若參數用途無法從程式碼判斷，寫成中性描述，例如「要處理的輸入資料」或「控制行為的旗標」。
   - 若回傳值依條件不同，清楚寫出條件分支。
   - 若函式名稱與實作不一致，以實作為準，必要時在說明中避免過度承諾。
   - 不要編造參數意義、商業規則或錯誤條件。

5. **格式要求**
   - 使用標準 Google 風格縮排與標題。
   - 每個區塊之間空一行。
   - 參數說明採 `name: description`。
   - 保持簡潔、精準、可讀。
   - 若原始碼已有部分 docstring，保留正確內容，只補缺漏並修正格式。

# 輸出方式

- 直接輸出補好的 docstring，或輸出包含 docstring 的完整函式片段，依使用者提供內容而定。
- 若使用者要求「審」或「檢查」，先指出缺漏與不一致，再提供修正版。
- 若程式碼不足以安全補寫，明確說明缺少哪些資訊，並列出需要補充的上下文。
