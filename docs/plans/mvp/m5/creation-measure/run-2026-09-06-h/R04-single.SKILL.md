# GitHub issue 嚴重度分級與處理建議

## 目的
將 GitHub issue 依嚴重度分成三級，並為每個 issue 寫一句處理建議。

## 分級標準
使用以下三級：

- **高**：造成服務中斷、資料遺失、重大安全風險、核心功能完全不可用，或沒有立即處理會快速擴大影響。
- **中**：影響主要功能或多數使用者，但仍有替代方案、暫時繞過方式，或影響範圍可控。
- **低**：輕微錯誤、文字/版面問題、非核心功能異常、改善建議，或對使用者影響有限。

## 處理流程
1. **讀取 issue 內容**：標題、描述、重現步驟、影響範圍、錯誤訊息、附件與留言。
2. **判斷影響程度**：優先看是否影響核心流程、是否有安全/資料風險、是否有明確替代方案。
3. **指定一個嚴重度**：只能選高、中、低其中之一。
4. **寫一句處理建議**：
   - 要具體、可執行。
   - 只寫一句話。
   - 建議內容應對應嚴重度，例如：立即修復、排入近期修正、納入後續優化。

## 輸出格式
對每個 issue 輸出一行，格式如下：

- `#<issue 編號>｜<嚴重度>｜<一句處理建議>`

若沒有 issue 編號，則用標題代替：

- `<issue 標題>｜<嚴重度>｜<一句處理建議>`

## 寫作原則
- 保持一致：同類問題用相同標準。
- 以影響為主，不只看技術難度。
- 若資訊不足，根據已知影響做保守判斷；不要編造細節。
- 建議句避免空泛詞，例如「請盡快處理」；改寫成明確動作，例如「先修復登入流程並補上回歸測試」。
- 若 issue 同時符合多個等級，採用較高嚴重度。

## 範例句型
- 高：`立即修復付款失敗問題，並補上監控與回歸測試。`
- 中：`優先排入下一個修補版本，並確認是否有可用的暫時繞過方式。`
- 低：`納入一般優化清單，於例行維護時一併修正。`
