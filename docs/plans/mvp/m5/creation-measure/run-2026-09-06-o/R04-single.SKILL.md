# GitHub issue 三級嚴重度分級與處理建議

## 目的
將 GitHub issue 依嚴重度分成三級，並為每個 issue 各寫一句處理建議。

## 適用情境
- 使用者提供一批 GitHub issue 文字、標題、描述或截圖轉寫內容
- 需要快速做初步 triage，而不是完整修復方案
- 需要輸出可直接貼回 issue 管理流程的簡短結果

## 分級標準
將每個 issue 分成以下三類之一：

### 1. 高嚴重度
符合以下任一情況時使用：
- 造成服務中斷、資料遺失、資安風險、金流/核心流程失敗
- 影響大多數使用者或所有使用者
- 沒有明顯替代方案，且問題持續存在

### 2. 中嚴重度
符合以下任一情況時使用：
- 影響主要功能，但仍有替代方式
- 影響部分使用者、特定環境或特定情境
- 會降低可用性、正確性或效率，但不至於立即阻斷核心服務

### 3. 低嚴重度
符合以下任一情況時使用：
- 文字、排版、文件、提示訊息、微小 UI 問題
- 不影響核心功能，或影響極小
- 改善性、可維護性、體驗優化類問題

## 判斷步驟
1. 逐一閱讀每個 issue 的標題與內容。
2. 找出影響範圍：是否影響核心功能、多少使用者、是否有風險或阻斷。
3. 依上方標準選定一個嚴重度。
4. 為每個 issue 寫一句處理建議，建議要具體、可執行、簡短。
5. 若資訊不足，根據已知內容做最保守的判斷，並在建議中指出需要補充的關鍵資訊或先做驗證。

## 輸出格式
對每個 issue 輸出一行或一段，格式如下：

- Issue：<標題或編號>
  - 嚴重度：高 / 中 / 低
  - 建議：<一句話處理建議>

## 寫作規則
- 嚴重度只能用「高 / 中 / 低」三種之一。
- 每個建議只寫一句話。
- 建議要以動詞開頭更清楚，例如「先…」、「立即…」、「安排…」、「補充…」。
- 不要寫長篇分析，不要展開成多步驟方案。
- 若多個 issue 類似，可分別判斷，不要合併除非使用者明確要求。

## 注意事項
- 這個技能只負責分級與一句建議，不負責實際修 bug。
- 若輸入不是 issue 內容，而是其他資料，先請使用者提供 issue 標題與描述再進行分級。
