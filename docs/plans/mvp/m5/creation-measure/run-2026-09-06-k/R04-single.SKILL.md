# GitHub issue 嚴重度三分級與處理建議

當你收到一批 GitHub issue，需要依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理出：
- 問題描述
- 影響範圍
- 是否阻斷主要功能
- 是否有替代方案
- 是否影響多數使用者或僅少數情境
- 是否有資料遺失、資安、金流、服務中斷等風險

如果資訊不足，先根據現有內容做保守判斷，不要自行補充未提供的事實。

## 2. 依嚴重度分成三級
使用以下標準分類：

### 高
符合任一情況即可列為高：
- 阻斷核心功能或主要流程無法完成
- 造成服務中斷、資料遺失、資安風險、金流錯誤
- 影響範圍大，或沒有可行替代方案
- 問題會持續擴大或造成重大營運損失

### 中
符合以下特徵：
- 主要功能仍可用，但有明顯缺陷、錯誤或降級
- 影響部分使用者、特定情境或次要流程
- 有替代方案，但會增加操作成本或風險
- 不處理會影響體驗或後續維護，但不至於立即中斷服務

### 低
符合以下特徵：
- 不影響核心功能
- 影響輕微、偶發、局部，或僅屬於改善項目
- 有簡單替代方式，且短期內風險低
- 屬於文字修正、UI 微調、文件更新、非阻斷性優化

## 3. 為每個 issue 寫一句處理建議
每個 issue 都要附上一句建議，格式要簡潔、可執行。

建議寫法原則：
- 高：優先立即處理，先止血再修復，必要時暫停相關變更
- 中：排入近期修正，先確認重現條件與影響範圍，再安排修補
- 低：納入一般排程，視版本規劃或批次優化處理

## 4. 輸出格式
請用固定格式輸出，方便直接貼回 issue 清單或報告：

- Issue 標題：
  - 嚴重度：高 / 中 / 低
  - 處理建議：一句話

若有多個 issue，逐條列出，不要混在同一條。

## 5. 判斷原則
- 以影響程度優先，不以描述語氣判斷
- 若介於兩級之間，優先選較高嚴重度
- 若 issue 同時包含多個問題，以最嚴重者為準
- 不要把「急」和「重要」混為同一件事；以實際影響為準

## 6. 若資訊不足
如果 issue 內容不足以判斷，先標為中，並在建議中要求補充重現步驟、影響範圍或錯誤紀錄，再決定是否升級。
