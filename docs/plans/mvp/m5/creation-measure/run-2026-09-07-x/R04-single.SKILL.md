# GitHub issue 三級嚴重度分類與處理建議

當你收到一批 GitHub issue，且任務是把它們分成三級嚴重度並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理出：
- 問題描述
- 影響範圍
- 是否阻斷主要功能
- 是否有資料遺失、資安、金流、當機風險
- 是否有明確重現步驟或大量使用者受影響

如果資訊不足，先根據現有內容做保守判斷，不要自行補假設；必要時在建議中寫明需要補充資訊。

## 2. 依嚴重度分成三級
使用以下標準：

### 高
符合任一情況即可列為高：
- 阻斷核心功能或主要流程無法使用
- 造成資料遺失、資料損壞、資安風險、金流錯誤
- 服務當機、重大性能退化、影響大量使用者
- 沒有可行替代方案，且需要優先處理

### 中
符合任一情況即可列為中：
- 影響重要功能，但仍有替代方式
- 問題會明顯影響使用體驗，但不致全面中斷
- 影響範圍有限，或只在特定條件下發生
- 需要排入近期修正，但不屬於立即危機

### 低
符合任一情況即可列為低：
- 文字、排版、提示訊息、文件、輕微 UI 問題
- 不影響主要流程或功能
- 影響很小、發生機率低，或屬於改善性需求

## 3. 為每個 issue 寫一句處理建議
每則建議要符合該嚴重度：
- **高**：建議立即處理、先止血、優先修復並補測試
- **中**：建議排入近期修正、確認影響範圍後處理
- **低**：建議納入一般排程、與其他優化一併處理

建議句要簡短、具體、可執行，避免空泛用語。

## 4. 輸出格式
對每個 issue 輸出以下三項：
- issue 標題或編號
- 嚴重度：高／中／低
- 一句處理建議

若需要處理多個 issue，逐筆列出，保持分類標準一致。

## 5. 判斷原則
- 以「對使用者與系統的實際影響」為優先，不只看字面嚴重詞彙。
- 同類問題要維持一致標準。
- 若介於兩級之間，優先採較高嚴重度，但在建議中說明原因。
- 不要把所有 issue 都判成同一級。
