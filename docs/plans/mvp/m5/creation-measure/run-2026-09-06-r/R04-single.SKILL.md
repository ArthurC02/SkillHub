# GitHub issue 嚴重度三分級與處理建議

當你收到一批 GitHub issue，需要依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理出：
- 問題描述
- 影響範圍
- 是否阻斷主要功能
- 是否有替代方案
- 是否影響多數使用者或僅少數情境
- 是否有資料遺失、資安、金流、服務中斷等風險

如果資訊不足，先根據現有內容做保守判斷，不要自行補假設；必要時在建議中寫明「需補充重現步驟／影響範圍」。

## 2. 依嚴重度分成三級
使用以下標準分類：

### 高
符合任一情況即可列為高：
- 主要功能完全不可用
- 造成服務中斷、資料遺失、資安風險、金流錯誤
- 影響大量使用者或所有使用者
- 沒有可行替代方案

### 中
符合任一情況即可列為中：
- 主要功能可用但明顯受損
- 影響特定流程、特定角色或部分使用者
- 有替代方案，但成本高、體驗差或容易出錯
- 需要盡快修復，但未達立即阻斷程度

### 低
符合任一情況即可列為低：
- 不影響核心功能
- 僅是外觀、文案、可用性小問題
- 影響範圍小且有簡單替代方式
- 屬於改善、優化、技術債或非緊急缺陷

## 3. 為每個 issue 寫一句處理建議
每個 issue 只寫一句建議，內容要包含：
- 優先順序或處理時機
- 建議的下一步

建議句型可參考：
- 高：`建議立即處理並優先修復，先確認重現條件與影響範圍，再安排 hotfix。`
- 中：`建議列入近期修復，先補齊重現資訊並評估替代方案後安排開發。`
- 低：`建議納入一般排程，待有空檔再修正並同步確認是否可接受現況。`

## 4. 輸出格式
對每個 issue 依序輸出以下欄位：
- Issue 編號或標題
- 嚴重度：高／中／低
- 處理建議：一句話

範例格式：
- `#123 登入失敗`
  - `嚴重度：高`
  - `處理建議：建議立即處理並優先修復，先確認重現條件與影響範圍，再安排 hotfix。`

## 5. 判斷原則
- 以使用者影響與業務風險為優先，不只看技術難度。
- 若介於兩級之間，採較高嚴重度。
- 保持分類一致，避免同類問題前後標準不一。
- 建議句要具體、可執行、簡潔，不要寫成長篇分析。
