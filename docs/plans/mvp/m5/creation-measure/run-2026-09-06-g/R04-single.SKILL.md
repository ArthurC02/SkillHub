# GitHub Issue 嚴重度分級與處理建議

當你收到一批 GitHub issue 時，依下列流程將每個 issue 分成三級嚴重度，並各寫一句處理建議。

## 1. 先讀取 issue 內容
對每個 issue，先確認：
- 問題是否會造成服務中斷、資料損壞、資安風險或主要功能不可用
- 影響範圍是單一使用者、部分使用者，還是大多數使用者
- 是否有明確替代方案或暫時繞過方式
- 是否只是體驗、文案、低風險錯誤或小型缺陷

## 2. 依嚴重度分成三級
使用以下標準：

### 高
符合任一條件即可列為高：
- 服務無法使用、核心功能失效
- 資料遺失、資料錯誤、不可逆損害
- 安全性、隱私、權限相關重大問題
- 影響大量使用者或所有使用者
- 沒有可行繞過方式，且需要優先處理

### 中
符合任一條件即可列為中：
- 主要功能受影響，但仍可部分使用
- 影響部分使用者或特定情境
- 有暫時繞過方式，但會明顯降低效率或體驗
- 需要修正，但不屬於立即危急

### 低
符合任一條件即可列為低：
- 小型錯誤、文案問題、排版問題、邊緣情境問題
- 不影響核心流程或僅有輕微影響
- 有明確且容易接受的替代方式
- 可排入一般排程處理

## 3. 為每個 issue 寫一句處理建議
每則建議要符合該嚴重度：
- 高：建議立即確認影響範圍、先止血，再安排修復與驗證
- 中：建議排入近期修正，先評估繞過方式與回歸風險
- 低：建議納入一般待辦，於例行排程中修正即可

## 4. 輸出格式
對每個 issue 輸出一行或一個條目，格式固定如下：

- Issue #編號｜嚴重度：高/中/低｜建議：一句話

如果沒有 issue 編號，就用標題或簡短描述代替編號位置。

## 5. 判斷原則
- 以實際影響為準，不只看字面上的急迫語氣
- 若資訊不足，先依已知影響做保守判斷；必要時標註「需補充資訊」
- 同一批 issue 的分級標準要一致
- 建議句要短、具體、可執行，不要寫成長篇分析
