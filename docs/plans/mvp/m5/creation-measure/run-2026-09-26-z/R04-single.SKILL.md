# GitHub issue 三級嚴重度分類與處理建議

## 目的
將一批 GitHub issues 依嚴重度分成三級，並為每一筆 issue 寫一句處理建議。

## 適用時機
當你拿到 issue 清單、issue 內容摘要，或一段包含多個 GitHub issue 的文字時，使用此流程進行快速分級與回覆建議。

## 分級標準
使用以下三個等級，並保持整批資料的一致性：

- **高**：會造成服務中斷、資料遺失、重大安全風險、核心功能完全不可用，或沒有立即處理就會快速擴大影響。
- **中**：會影響主要功能、造成明顯錯誤或工作受阻，但仍有替代方案、暫時可繞過，或影響範圍有限。
- **低**：屬於小問題、文字/版面/體驗瑕疵、非阻斷性錯誤、改善建議，或影響很小。

## 處理步驟
1. **先讀每個 issue 的標題與描述**，找出影響範圍、是否阻斷流程、是否有資料或安全風險。
2. **判斷嚴重度**：
   - 若有明顯中斷、資料風險或安全風險，標為 **高**。
   - 若會影響主要流程但可暫時繞過，標為 **中**。
   - 若只是小瑕疵或優化，標為 **低**。
3. **為每個 issue 寫一句處理建議**，建議要具體、可執行，避免空泛。
4. **輸出時保持一致格式**，讓人可以直接貼回 issue 清單或報告。

## 建議輸出格式
對每個 issue 輸出一行或一段，包含：
- issue 標題或編號
- 嚴重度：高 / 中 / 低
- 一句處理建議

範例格式：
- `#123 登入失敗：高｜先確認是否影響所有使用者，若是請優先修復並回溯最近變更。`
- `#124 按鈕文字錯誤：低｜先修正文案並在下一次例行更新中一併發布。`

## 判斷原則
- 以**使用者影響**優先，不只看技術難度。
- 若資訊不足，先根據已知影響做保守判斷；不要憑空補充不存在的細節。
- 同一批 issue 盡量使用一致標準，避免同類問題被分到不同等級。
- 建議句只要一句，重點放在下一步動作，例如：確認、修復、回歸測試、排程、觀察。

## 若資訊不足
如果 issue 內容太少，無法可靠判斷嚴重度，請先列出需要補充的資訊，例如：
- 影響範圍
- 是否可重現
- 是否有 workaround
- 是否涉及資料或安全

然後再暫定最可能的等級，並在建議中註明需補充資訊後再定案。
