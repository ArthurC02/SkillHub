# GitHub issue 嚴重度三分級與處理建議

當你收到一批 GitHub issue，需要依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理這些訊息：
- 標題
- 內文摘要
- 影響範圍
- 是否阻斷主要功能
- 是否有替代方案
- 是否影響多數使用者或僅少數情境
- 是否有資料遺失、資安、金流、服務中斷等風險

如果資訊不足，先根據現有內容做保守判斷，不要自行補假設；必要時在結果中標註「資訊不足，需補充」。

## 2. 使用三級嚴重度
將每個 issue 分到以下三類之一：

### 高
符合以下任一情況：
- 阻斷核心功能或主要流程
- 造成服務中斷、資料遺失、資安風險、金流錯誤
- 影響大量使用者或所有使用者
- 沒有可行替代方案

### 中
符合以下任一情況：
- 影響重要功能，但仍有替代流程
- 只影響部分使用者、特定環境或特定情境
- 會造成明顯不便、錯誤結果或工作延遲，但不至於全面中斷

### 低
符合以下任一情況：
- 僅是外觀、文案、微小體驗問題
- 影響範圍很小，且不妨礙主要功能
- 屬於改善、優化、可延後處理的事項

## 3. 判斷原則
- 以「實際影響」優先，不以標題字眼判斷。
- 若介於兩級之間，優先選較高嚴重度，但避免過度升級。
- 若 issue 同時包含多個問題，以最嚴重的影響為準。
- 若是重複 issue，仍可依內容分級，但可在建議中註明合併或關聯處理。

## 4. 為每個 issue 寫一句處理建議
每個 issue 都要附上一句簡短建議，格式要具體可執行，建議包含其中一種方向：
- 先修復或先排查
- 先確認重現條件
- 先補測試
- 先收斂影響範圍
- 可排入後續版本
- 可與相關 issue 合併處理

建議句要符合嚴重度：
- 高：建議立即處理、優先修復、先止血
- 中：建議排入近期修復、先確認影響範圍
- 低：建議納入例行優化或後續版本

## 5. 輸出格式
對每個 issue 輸出一行或一個條目，格式固定如下：

- `Issue #編號：嚴重度（高／中／低）｜處理建議：一句話`

如果沒有 issue 編號，就用標題代替：

- `Issue：標題｜嚴重度（高／中／低）｜處理建議：一句話`

## 6. 範例寫法
- `Issue #123：高｜處理建議：請立即修復並先確認是否影響所有登入流程。`
- `Issue #124：中｜處理建議：建議排入近期版本，並先釐清是否只發生在特定瀏覽器。`
- `Issue #125：低｜處理建議：可納入後續優化清單，與相關 UI 調整一併處理。`

## 7. 注意事項
- 保持每個建議只有一句話。
- 不要寫長篇分析，除非使用者另外要求。
- 若需要先看 issue 內容再分類，就先整理後再輸出，不要直接猜測。
