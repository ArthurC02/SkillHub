# GitHub Issue 嚴重度三分級與處理建議

當任務是把 GitHub issue 依嚴重度分成三級，並為每個 issue 寫一句處理建議時，依下列流程執行。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理以下內容：
- 問題描述
- 影響範圍：是否影響所有使用者、部分使用者、單一情境或僅是體驗問題
- 影響程度：是否造成服務中斷、資料錯誤、功能不可用、效能下降、或僅是小瑕疵
- 緊急性：是否有明確的截止時間、阻塞其他工作、或有安全/資料風險

如果資訊不足，根據現有內容做保守判斷，不要自行補充不存在的事實。

## 2. 使用三級嚴重度
將每個 issue 分到以下三類之一：

### 高
符合以下任一情況時使用：
- 造成核心功能不可用
- 影響大量使用者或所有使用者
- 有資料遺失、資料錯誤、資安風險、或服務中斷風險
- 阻塞主要流程或阻塞其他重要工作

### 中
符合以下任一情況時使用：
- 影響重要但非核心功能
- 只影響部分使用者或特定情境
- 有明顯錯誤、效能問題或工作流程受阻，但仍有替代方式

### 低
符合以下任一情況時使用：
- 只是文字、排版、微小 UX 問題
- 不影響主要功能
- 影響範圍小，且沒有立即風險

## 3. 為每個 issue 寫一句處理建議
每個 issue 只寫一句建議，內容要具體且可執行。依嚴重度調整語氣：
- **高**：建議優先處理、立即修復、先止血再補根因
- **中**：建議排入近期修正、安排在下一輪開發或修補版本
- **低**：建議納入一般待辦、與其他小項目一起處理

建議句要包含一個明確動作，例如：
- 先確認重現步驟並修復核心原因
- 優先排入本週修正並補上測試
- 納入一般 backlog，於下次整理時一併處理

## 4. 輸出格式
對每個 issue，輸出以下兩行：
- `嚴重度：高 / 中 / 低`
- `處理建議：` 後接一句話

若需要處理多個 issue，請逐一列出，保持每個 issue 的判斷一致且簡潔。

## 5. 判斷原則
- 以影響與風險為主，不只看字面上的抱怨強度
- 若介於兩級之間，優先選較高的嚴重度
- 不要把所有 issue 都判成同一級，應根據內容區分
- 不確定時，明確採取保守分類，避免誇大或低估風險
