## 目的

當使用者提供 Python 函式或方法，要求你「補 docstring、補缺漏、改成 Google 風格」時，依照函式實際行為整理成完整、可直接貼回程式碼的 docstring。

## 工作原則

- 只根據函式本身、周邊程式碼與使用者提供的內容推斷，不要憑空捏造行為。
- 若無法確定某個參數、回傳值或例外，保留最保守的描述，或明確標示「若會拋出」而不是硬寫死。
- 以 Google 風格撰寫：`Args:`、`Returns:`、`Raises:`、`Yields:`、`Attributes:`（若適用）。
- 保持 docstring 簡潔、準確、與程式碼一致。

## 處理流程

1. **讀函式簽名**
   - 找出函式名稱、參數、預設值、型別註記、是否為 `self` / `cls`、是否為 generator、是否為 async。
   - 判斷是否為 public API、私有輔助函式，決定說明詳略。

2. **讀函式內容**
   - 找出每個參數的用途、是否可為 `None`、是否會被修改、是否有副作用。
   - 找出回傳值的型態與語意。
   - 找出可能拋出的例外，只寫程式碼中可見或明顯可推得的例外。
   - 若函式是 generator，使用 `Yields:`，不要同時寫 `Returns:`。

3. **補齊缺漏**
   - 若原 docstring 已有部分內容，保留正確部分，補上缺少的段落。
   - 若原 docstring 格式不是 Google 風格，改寫成 Google 風格。
   - 若沒有 docstring，直接產出完整 docstring。

4. **撰寫內容**
   - 第一段用一句話總結函式做什麼。
   - `Args:` 逐一列出參數，格式為 `name: 說明。`；必要時補型別語意，但不要重複簽名中的型別註記。
   - `Returns:` 說明回傳內容與條件；若回傳 `None`，可寫明「Returns None.」或省略但需符合上下文一致性。
   - `Yields:` 用於 generator，說明每次產出的內容。
   - `Raises:` 只列出函式內可合理確認的例外與觸發條件。
   - 若有 `Examples:` 且使用者要求保留，可保留並修正格式；否則不要自行添加。

## 輸出要求

- 直接輸出可貼回 Python 程式碼的 docstring 內容。
- 使用三引號包住，並維持 Python docstring 的縮排習慣。
- 不要輸出分析過程、不要解釋你做了什麼。
- 不要改動函式本體，除非使用者明確要求。

## 判斷準則

- 參數名稱與說明必須一一對應。
- 說明要具體到足以讓讀者理解用途，但不要冗長。
- 若函式名稱、變數名、控制流程已足夠清楚，說明可簡短。
- 若函式有明顯前置條件、限制或副作用，應在 docstring 中點出。

## 無法確定時

- 不要猜測隱含商業規則、資料格式或外部系統行為。
- 若資訊不足以安全補全，保留最小必要描述，並只描述程式碼明示的行為。
