# GitHub Issue 三級嚴重度分級與處理建議

當你收到一批 GitHub issue，且任務是把它們分成三級嚴重度並各寫一句處理建議時，依下列流程處理。

## 1. 先確認輸入內容
- 逐筆讀取 issue 標題、描述、重現步驟、影響範圍、錯誤訊息、標籤與留言摘要。
- 若資訊不足，先根據現有內容做暫定判斷，並在建議中反映「需補充資訊」或「需確認影響範圍」。
- 不要憑空補寫不存在的事實。

## 2. 使用三級嚴重度
將每個 issue 分到以下三類之一：

### 高
符合以下任一情況：
- 造成核心功能不可用、服務中斷、資料遺失、資安風險。
- 影響大量使用者或所有使用者。
- 沒有明顯替代方案，且需要優先處理。

### 中
符合以下任一情況：
- 影響主要功能但仍有替代方案。
- 只影響部分使用者、特定環境或特定流程。
- 會造成明顯錯誤、阻礙工作，但不至於全面中斷。

### 低
符合以下任一情況：
- 只是小問題、文字錯誤、UI 瑕疵、可用性改善。
- 不影響核心流程或僅有輕微不便。
- 修正可延後，不影響主要交付。

## 3. 判斷原則
- 以「對使用者與系統的實際影響」為主，不只看技術難度。
- 若介於兩級之間，優先採用較保守但合理的判斷，並在建議中說明原因。
- 若 issue 同時包含多個問題，以最嚴重的影響為準，必要時可提醒拆分。

## 4. 為每個 issue 寫一句處理建議
每筆 issue 都要輸出：
- 嚴重度：高 / 中 / 低
- 一句處理建議：簡短、具體、可執行

建議句的寫法：
- 高：先止血、確認影響範圍、安排立即修復與驗證。
- 中：優先排入近期修正，補齊重現條件並驗證受影響範圍。
- 低：納入一般排程，視版本時程修正即可。

## 5. 建議輸出格式
對每個 issue 使用一致格式，例如：

- `#123：高｜先確認是否影響所有使用者，並立即修復後回歸驗證。`
- `#124：中｜補充重現步驟與受影響環境，排入近期修正。`
- `#125：低｜納入一般排程，於下個版本一併處理。`

## 6. 最後檢查
- 每個 issue 都有一個嚴重度。
- 每個 issue 都只有一句處理建議。
- 用詞一致，避免同一批結果出現不同標準。
- 若有不確定性，保留在建議中，不要硬判斷成確定事實。
