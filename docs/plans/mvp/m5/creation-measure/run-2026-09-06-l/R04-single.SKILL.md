# GitHub issue 嚴重度分級與處理建議

當你收到一批 GitHub issue，需要依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，整理以下內容：
- 問題描述
- 影響範圍：是否影響所有使用者、部分使用者、或僅特定情境
- 影響程度：是否造成服務中斷、功能不可用、資料風險、或僅有不便
- 是否有替代方案或暫時繞過方式
- 是否有明確的重現步驟、錯誤訊息、或受影響模組

## 2. 依嚴重度分成三級
使用以下標準分類：

### 高
符合以下任一情況時歸為高：
- 造成核心功能無法使用
- 服務中斷、資料遺失、資料損壞、資安風險
- 影響範圍廣，且沒有可行繞過方式
- 問題會阻斷主要流程或導致重大商業影響

### 中
符合以下情況時歸為中：
- 主要功能仍可用，但有明顯缺陷或錯誤
- 影響部分使用者、部分情境，或有暫時繞過方式
- 會降低效率、造成反覆失敗、或影響重要但非關鍵流程

### 低
符合以下情況時歸為低：
- 僅有輕微錯誤、文字問題、UI 小瑕疵、或非阻斷性問題
- 不影響主要流程，且對使用者影響有限
- 屬於改善體驗、可延後處理的項目

## 3. 為每個 issue 寫一句處理建議
每個 issue 都要輸出一句建議，格式要簡短、可執行，並與嚴重度一致：
- 高：建議立即處理、優先修復、先止血再補根因
- 中：建議排入近期修復、安排在下一輪開發或修補版本
- 低：建議納入一般待辦、視排程處理或與其他優化合併

## 4. 輸出格式
對每個 issue 使用以下格式輸出：

- Issue #編號：{高/中/低} — {一句處理建議}

如果沒有 issue 編號，就用標題或簡短識別名稱代替：

- {issue 標題}：{高/中/低} — {一句處理建議}

## 5. 判斷原則
- 以實際影響為準，不只看字面上的急迫語氣。
- 若資訊不足，根據已知影響先做保守分類，並在建議中指出需要補充資訊。
- 同一批 issue 的分類標準要一致，避免同類問題被分到不同等級。
- 若 issue 內容含多個問題，以最嚴重的影響作為分類依據。

## 6. 產出前檢查
在完成前確認：
- 每個 issue 都有一個嚴重度
- 每個 issue 都有一句處理建議
- 分級只有三級：高、中、低
- 建議語句簡潔且可執行
