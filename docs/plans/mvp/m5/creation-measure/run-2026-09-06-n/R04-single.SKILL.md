# GitHub issue 嚴重度三分級與處理建議

當你收到一批 GitHub issue，需要依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理出：
- 問題描述
- 影響範圍
- 是否阻斷主要功能
- 是否有資料遺失、資安風險、服務中斷
- 是否有替代方案或暫時解法
- 是否只影響外觀、文案、體驗或低風險功能

如果資訊不足，先根據現有內容做保守判斷，不要自行補造細節。

## 2. 依嚴重度分成三級
使用以下三類：

### 高
符合任一情況即可列為高：
- 造成核心功能無法使用
- 服務中斷、當機、資料遺失、資料損壞
- 安全性、隱私、權限問題
- 影響大量使用者或正式環境
- 沒有可接受的替代方案

### 中
符合任一情況即可列為中：
- 影響重要功能，但仍可部分使用
- 有明顯錯誤、效能問題或流程阻礙
- 有暫時解法，但會增加操作成本
- 影響範圍有限，但需要優先處理

### 低
符合任一情況即可列為低：
- 只影響外觀、文案、排序、細節體驗
- 不影響主要流程
- 有簡單替代方式，且風險低
- 屬於改善或優化性質

## 3. 為每個 issue 寫一句處理建議
每個 issue 都要附上一句建議，格式要簡短、可執行，並且和嚴重度一致。

建議寫法原則：
- 高：先止血、優先修復、必要時回滾或暫停相關功能
- 中：安排近期修復、補測相關流程、確認是否有替代方案
- 低：納入一般排程、視版本一起處理、可在有餘裕時修正

## 4. 輸出格式
對每個 issue 輸出以下欄位：
- issue 標題或編號
- 嚴重度：高 / 中 / 低
- 處理建議：一句話

可用條列或表格，但要保持一致。

### 範例格式
- #123 登入失敗：高｜先優先修復登入流程，必要時暫時回滾相關變更。
- #124 按鈕文字錯誤：低｜納入一般排程修正，與下一版一起處理即可。

## 5. 判斷原則
- 以使用者影響與風險優先，不只看技術難度。
- 若介於兩級之間，採較高嚴重度。
- 若 issue 描述含有「無法使用」「當機」「資料不見」「安全」等字眼，優先提高嚴重度。
- 若只是美觀或小幅體驗問題，通常列為低。

## 6. 若資訊不足
如果 issue 內容太少，無法可靠判斷，請：
- 先標為中或保守較高的一級
- 在建議中寫明需要補充重現步驟、影響範圍或錯誤訊息

不要編造不存在的細節。
