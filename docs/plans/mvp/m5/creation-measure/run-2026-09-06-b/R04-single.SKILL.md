# 目的
將一組 GitHub issue 依嚴重度分成三級，並為每一級各寫一句處理建議。

# 適用範圍
- 輸入可以是 issue 標題、描述、截圖文字、或整理過的 issue 清單。
- 若資訊不足以判斷嚴重度，先根據可見影響、範圍、是否阻斷流程來做保守分級，並在建議中明確指出需要補充的資訊。

# 分級標準
使用以下三級：

## 高
符合任一情況即可列為高：
- 造成核心功能不可用、流程中斷、資料遺失、資安風險、或大範圍使用者受影響。
- 沒有明顯替代方案，或問題會持續擴大。

## 中
符合任一情況即可列為中：
- 影響重要功能但仍可繞過。
- 影響範圍有限，或只在特定條件下發生。
- 會明顯降低使用體驗、效率或正確性，但不至於完全阻斷。

## 低
符合任一情況即可列為低：
- 文字、排版、提示、邊角案例、輕微不便、或不影響主要流程的問題。
- 影響很小、可接受，或主要屬於改善性需求。

# 處理步驟
1. 讀取每個 issue 的標題與描述，找出：
   - 受影響的功能
   - 影響範圍
   - 是否阻斷使用
   - 是否有資料、安全或營運風險
   - 是否有明確重現條件
2. 依上述標準將 issue 分到高、中、低其中一級。
3. 若同一批 issue 需要整體整理，先按高 → 中 → 低排序。
4. 對每一級寫一句處理建議，建議要具體、可執行，且符合該級別的優先順序。
5. 若輸入的是單一 issue，仍需輸出其所屬級別，並附上一句對應建議。

# 輸出格式
請用以下格式輸出：

- 高：<一句處理建議>
- 中：<一句處理建議>
- 低：<一句處理建議>

若某一級在這批 issue 中沒有對應項目，仍保留該級別，並寫「本批無此級別 issue，持續監控即可。」

# 寫作原則
- 建議句要短、直接、可執行。
- 不要寫成長篇分析。
- 不要只重述問題，要給出下一步動作。
- 若資訊不足，建議中要包含「先補充重現步驟／影響範圍／截圖或 log」之一。
