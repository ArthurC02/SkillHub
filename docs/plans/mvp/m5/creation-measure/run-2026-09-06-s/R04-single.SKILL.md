# GitHub issue 嚴重度三分級與處理建議

當你收到一批 GitHub issue，需要依嚴重度分成三級並各寫一句處理建議時，依下列流程處理。

## 1. 先讀取每個 issue 的關鍵資訊
對每個 issue，先整理以下內容：
- 問題描述
- 影響範圍
- 是否阻斷主要功能
- 是否有資料遺失、資安風險、服務中斷
- 是否有替代方案或暫時解法
- 是否只影響少數使用者或僅為體驗問題

## 2. 依嚴重度分成三級
使用以下固定分級：

### 高
符合以下任一情況時歸為高：
- 阻斷核心功能或主要流程
- 造成服務不可用、資料損壞、資料遺失
- 有明顯資安風險
- 影響大量使用者或所有使用者

### 中
符合以下情況時歸為中：
- 影響重要功能，但仍有替代流程或暫時解法
- 影響範圍有限，但會明顯降低可用性或效率
- 問題需要盡快處理，但不屬於立即中斷服務的等級

### 低
符合以下情況時歸為低：
- 只影響外觀、文案、微小體驗或非核心功能
- 影響範圍小，且不妨礙主要使用流程
- 可延後處理，對營運影響有限

## 3. 為每個 issue 寫一句處理建議
每個 issue 都要附上一句建議，格式要簡潔、可執行，並與嚴重度一致。

建議寫法原則：
- 高：優先立即處理，必要時先做緊急修補或回退
- 中：排入近期修正，並確認是否有暫時替代方案
- 低：納入一般排程，於資源允許時修正

## 4. 輸出格式
對每個 issue 輸出以下欄位：
- Issue 編號或標題
- 嚴重度：高 / 中 / 低
- 處理建議：一句話

範例格式：
- #123 登入失敗：高｜建議先緊急修復並確認是否需要回退版本。
- #124 按鈕樣式錯位：低｜建議納入一般排程，於下次 UI 修正時一併處理。

## 5. 判斷原則
- 以使用者影響與業務風險為優先，不只看技術難度。
- 若資訊不足，先依已知影響做最保守且合理的分級。
- 同一批 issue 的分級標準要一致，避免前後不一。
- 若 issue 敘述含糊，先抓最可能的實際影響，再給出分級與建議。
