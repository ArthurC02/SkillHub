# GitHub issue 嚴重度三分級

當收到一批 GitHub issue 時，依下列流程將每個 issue 分成三級，並各寫一句處理建議。

## 1. 先讀取 issue 內容
對每個 issue，先抓出以下資訊：
- 問題是否影響核心功能
- 影響範圍：單一使用者、部分使用者、全部使用者
- 是否有資料遺失、資安風險、服務中斷、金流錯誤、無法登入等高風險情況
- 是否有替代方案或暫時繞過方式
- 是否只是外觀、文案、體驗或低風險瑕疵

## 2. 依嚴重度分三級
使用以下標準分類：

### 高
符合任一條件即可列為高：
- 造成服務中斷、核心功能完全不可用
- 影響大量使用者或所有使用者
- 有資料遺失、資料損毀、資安、權限、金流或法規風險
- 問題無法繞過，且會阻斷主要流程

### 中
符合任一條件即可列為中：
- 影響主要功能，但仍有替代方案或部分可用
- 只影響部分使用者、特定情境或特定環境
- 會明顯降低使用體驗，但不至於全面中斷

### 低
符合任一條件即可列為低：
- 只影響外觀、文案、格式、微小體驗問題
- 不影響主要流程與資料正確性
- 可延後處理，短期內風險低

## 3. 為每一級寫一句處理建議
對每個嚴重度都寫一句固定風格的建議，要求簡短、可執行：
- 高：建議立即處理，先止血再修復，必要時暫停相關功能或回滾。
- 中：建議排入近期修復，先確認影響範圍與可行的暫時解法。
- 低：建議納入一般排程，於例行修正或版本整理時一併處理。

## 4. 輸出格式
對每個 issue 輸出以下格式，保持一致：
- Issue：<標題或編號>
- 嚴重度：高／中／低
- 建議：<一句處理建議>

## 5. 判斷原則
- 若資訊不足，根據已知影響先做保守判斷；若高風險與低風險特徵同時存在，以較高嚴重度為準。
- 不要只看抱怨語氣，要看實際影響。
- 同一批 issue 的分級標準要一致，避免前後不一。
- 若 issue 敘述含糊，優先依「影響範圍」與「是否阻斷流程」判斷。
