## 目標

為 Python 函式補齊缺失的 docstring，並統一成 Google 風格。重點是讓 docstring 與函式實作一致，而不是只套模板。

## 適用情境

- 使用者貼出一個或多個 Python 函式，要求補 docstring。
- 使用者要求改成或維持 Google 風格。
- 使用者要求補上缺少的 `Args`、`Returns`、`Raises`、`Yields`、`Examples` 等區塊。

## 處理步驟

1. 先讀函式簽名與函式本體。
   - 找出函式名稱、參數、預設值、型別註記、是否為方法、是否有 `*args` / `**kwargs`。
   - 判斷函式是回傳單一值、`None`、產生器、或可能拋出例外。
   - 觀察函式內部實際行為，不要只依賴名稱猜測。

2. 判斷現有 docstring 的狀態。
   - 若沒有 docstring，新增完整 Google 風格 docstring。
   - 若有 docstring 但缺欄位，補齊缺少的部分。
   - 若內容與程式不一致，修正為與程式一致。
   - 若使用非 Google 風格，轉成 Google 風格。

3. 撰寫摘要行。
   - 第一行用一句話說明函式做什麼。
   - 以動詞開頭，簡潔明確。
   - 不要重複函式名稱。
   - 不要寫冗長背景說明。

4. 補 `Args` 區塊。
   - 逐一列出所有參數，包含 `*args`、`**kwargs`、關鍵字專用參數。
   - 每個參數都要有名稱、型別說明（若程式碼未明示型別，依實際用途描述）、以及用途。
   - 若參數有預設值，說明預設行為。
   - 若某參數在函式內未使用但仍存在，仍需如實描述其用途或指出目前未使用。

5. 補 `Returns`、`Yields` 或 `Raises`。
   - 若函式有 `return`，寫 `Returns`，說明回傳型別與意義。
   - 若函式只做副作用且回傳 `None`，可省略 `Returns`，或明確寫出 `None`，依專案慣例一致處理。
   - 若函式是生成器，使用 `Yields`，不要寫 `Returns` 來混淆。
   - 若函式會拋出可預期例外，寫 `Raises`，只列出程式中實際可能發生且值得記錄的例外。

6. 補 `Examples`（只有在程式碼或上下文足以確定時）。
   - 若使用者要求範例，或函式用途明確且可安全示範，加入簡短範例。
   - 不要捏造外部依賴、檔案路徑或不可驗證的執行結果。
   - 若無法確定正確範例，省略此區塊。

7. 保持 Google 風格格式。
   - 使用標題：`Args:`、`Returns:`、`Yields:`、`Raises:`、`Examples:`。
   - 每個區塊下方縮排一致。
   - 參數說明採 `name: description`。
   - 多行描述要對齊縮排。
   - 保持簡潔，不要加入多餘段落。

8. 只輸出修正後的 docstring 或包含 docstring 的函式片段，依使用者要求而定。
   - 若使用者只要 docstring，就只給 docstring。
   - 若使用者提供整個函式並要求修改，就回傳修改後的函式。
   - 不要額外解釋你的判斷過程，除非使用者要求。

## 判斷原則

- 以程式實作為準，不以函式名稱或註解猜測。
- 不要憑空新增不存在的參數、回傳值或例外。
- 不要刪除原本仍然正確的資訊。
- 若資訊不足以安全補全，保留可確定部分，並省略不確定部分。
- 若函式本身有明顯問題但使用者只要求 docstring，仍只處理 docstring，不改程式邏輯。

## 輸出要求

- 使用繁體中文回答，除非使用者明確要求其他語言。
- docstring 內容可依原始程式語言與專案慣例使用英文，尤其是標題與技術名詞。
- 保持格式整齊，避免多餘空行。
