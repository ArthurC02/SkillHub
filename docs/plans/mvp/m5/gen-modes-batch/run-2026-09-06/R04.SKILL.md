## 目的
將 GitHub issue 依嚴重度分成三級，並為每個 issue 寫一句處理建議。

## 分級標準
使用以下三個等級：

- **高**：會造成服務中斷、資料遺失、資安風險、重大功能不可用，或影響大量使用者。
- **中**：會影響主要功能、造成明顯錯誤或工作受阻，但有替代方案或影響範圍有限。
- **低**：屬於小問題、文字/版面/體驗瑕疵、低風險改善，或不影響核心流程。

## 處理流程
1. 逐一閱讀每個 issue 的標題與內容，找出影響範圍、可用性、資料風險、是否有替代方案。
2. 依上面的標準判定為 **高 / 中 / 低** 其中一級。
3. 為每個 issue 寫 **一句** 處理建議，內容要具體、可執行，避免空泛描述。
4. 若資訊不足以判定，先以已知影響為準；必要時在建議中指出需要補充的關鍵資訊。

## 建議寫法
- 建議句要直接對應嚴重度。
- 高：優先修復、立即處理、先止血再補修。
- 中：排入近期修復、確認影響範圍後處理。
- 低：納入一般排程、視資源安排修正。

## 輸出格式
對每個 issue 輸出一行或一個條目，格式如下：

- `Issue 標題｜嚴重度：高｜建議：先暫停相關功能並優先修復，避免擴大影響。`
- `Issue 標題｜嚴重度：中｜建議：確認受影響流程後排入近期修復。`
- `Issue 標題｜嚴重度：低｜建議：納入一般排程，於下次迭代一併處理。`

## 注意事項
- 不要把同一個 issue 分到多個等級。
- 不要寫超過一句的建議。
- 不要加入與嚴重度無關的長篇分析。
