## 2. 「隨機手滑」這個判讀：一半對，而錯的那一半更重要

逐段比對兩輪：

| 描述 | A 輪 | B 輪 |
| --- | --- | --- |
| DOC-1 | **截斷（零產出）** | pass |
| DOC-3 | `frontmatter-invalid-yaml` | pass |
| DOC-4 | pass | `frontmatter-invalid-yaml` |
| WRI-2 | pass | `frontmatter-unknown-field` ＋ `description-missing` |
| DAT-1 | `frontmatter-invalid-yaml` | `frontmatter-unknown-field` ＋ `description-missing` |
| DAT-4 | `frontmatter-invalid-yaml` | `frontmatter-invalid-yaml` |

其餘 14 段兩輪都通過。

- **至少失敗一次：6／20**
- **兩輪都失敗：2／20**（DAT-1、DAT-4）
- **一次重試後成功：18／20 ＝ 90%**

### 2.1 對 ADR-047 決策 1 的判定：**結論成立，理由不成立**

決策 1 說「重試恰好一次」，理由逐字是「缺陷是隨機的排版手滑不是系統性的能力缺陷」。

- **結論成立**：把 A、B 當兩次抽樣，一次重試把 80% 帶到 **90%**。重試確實有用。
- **理由不成立**：**2／20 兩輪都失敗**。若純粹隨機且各段機率相同，20% 的單次失敗率下兩次都中的期望是 0.8 段，實測 2 段——樣本太小不足以作統計檢定，但它足以說明**「哪一段會失敗」不是均勻分布的**。
- **同一段的失敗碼會變**：DAT-1 兩輪是兩個完全不同的失敗。所以「同一個 bug 穩定重現」也不成立。

**綜合起來的正確說法**：**具體的缺陷是隨機的，但某些任務描述系統性地更容易產生缺陷。** 決策 1 不必改，但它的理由要換成這一句——**而且要寫明重試後仍有 10% 失敗，那不是趨近於零。**

### 2.2 A 輪「三次失敗全是同一個 code」是小樣本假象

A 輪三次全是 `frontmatter-invalid-yaml`，我在 ADR-046 的補記裡把它寫成一個發現。**B 輪三個不同的 code**（`invalid-yaml` ×2、`unknown-field` ×2、`description-missing` ×2），mini 又是第四種組合。

### 2.3 真正的共同點是**模型會弄壞 frontmatter 的鍵名**——三種形狀都很難看

| 輪 | 樣本 | 實際寫出來的東西 |
| --- | --- | --- |
| A | DAT-1／DAT-4／DOC-3 | `description` 前面多一個空格 |
| B | WRI-2 | `لdescription:`——鍵名前面黏了一個**阿拉伯字母 ل（U+0644）** |
| B | DAT-1 | 整份 SKILL.md **只有 38 個字元**：`name: csv-to-jsonl` 加一行 `说明: invalid`（簡體中文的鍵名，值literally 是 `invalid`），**本文完全是空的** |

三種都不是推理失敗，是**生成層的字元級瑕疵**：一個多餘空格、一個異國字母、一次語言崩壞。它們共同的性質是**落在 frontmatter 的鍵名上**——而那恰好是驗證器唯一擋得住的地方。

**DAT-1 B 那 38 個字元值得單獨記**：它花了 725 個 completion token（全批最少），交出一個語法正確、語意為零的檔案。**如果它的鍵名剛好對，它會通過驗證器**——那就是一個通過每一道檢查的空殼。A 輪報告說「空殼 0／19」，B 輪告訴我們那個 0 不是結構保證，只是那一批運氣好。

## 3. mini 對照：**通過率更高，便宜 21 倍**——但它寫的是另一種東西

| | flagship（A＋B 平均） | **mini** | 比 |
| --- | --- | --- | --- |
| 通過驗證器 | 16／20（80%） | **19／20（95%）** | mini 高 |
| 每次成本 | $0.1186 | **$0.00553** | **21.4×** |
| completion token 中位數 | 3571 | 1023 | 3.5× |
| 本文長度中位數（runes） | 3122 | 2440 | 1.3× |
| **產出多於一個檔案** | 6／20 | **0／20** | — |

mini 的唯一失敗是 DAT-2 的 `frontmatter-unknown-field`，與 flagship 的失敗同一家族。

**通過率的差異有一個看得懂的解釋**：失敗全部落在 frontmatter 鍵名的字元級瑕疵上，而 mini 每次少寫 3.5 倍的 token——**寫得少，弄壞的機會就少**。這不是「mini 比較聰明」，是暴露面比較小。

**但兩者產出的不是同一種東西。** mini **一次腳本都沒寫**，flagship 兩輪各有 6 段產出多檔（Python 與 shell）。抽樣讀過 mini 的 `DAT-1`：frontmatter 完整、`compatibility` 有加引號、本文是可執行的繁中步驟說明——**它是一份好的純指示型 Skill，不是一份被砍短的 flagship 產出**。

**這個差異本批量不到誰比較好。** 「一份帶腳本的 Skill 是否比一份純指示的 Skill 更有用」要靠試跑與人（`GEN-009` ③④），兩組在那件事上都是未知。

## 4. `possible-secret`：40 個新樣本仍然 0 命中

三輪合計 **0／59 個套件**（A 19 ＋ B 20 ＋ mini 20）。

[ADR-048](../../../adr/ADR-048-not-every-blocking-finding-is-a-random-slip.md) 的「成本與限制」已經預先寫了這件事：**若它其實從不發生，那條不重試規則就是一段沒有人走過的分支**。三輪之後這句話仍然成立，而且證據更強了。

**這不是撤回那條規則的理由**——它守的是 fail-closed 的方向，成本是一個 `if`。但它應該被誠實地標成「未觀測」，而不是被說成一條在保護什麼的規則。

## 5. `max_tokens` 16000：解得了，但機制與 ADR-047 決策 2 的理解不同

DOC-1 在 B 輪**通過**（3 個檔案）。但它的 completion token 是 **7552——低於 A 輪的 8000 上限**。

所以 A 輪那次失敗**不是「內容太長裝不下」**。查 A 輪的 usage：**8000 個 completion token 全部是 `reasoning_tokens`，`content` 是空字串**。`max_tokens` 同時涵蓋推理與輸出，一次推理花掉整個預算的呼叫，**在寫出第一個字之前就到頂了**。

ADR-047 決策 2 的理由寫「成功案例的最大輸出是 7506 tokens，上限就卡在觀測分布的頂端」——**那個推論的方向對，機制講錯了**。正確的說法是：**上限要蓋得住「推理 ＋ 輸出」的總和，而推理的變異數比輸出大得多**。同一段描述兩輪的推理花費可以差好幾倍。

## 6. 這批仍然答不了的

- **兩輪都失敗的那 2 段，第三次會不會過。** 沒有第三次觀察，所以「重試兩次能不能到 95%」不知道。
- **mini 的產出好不好用。** 只量了驗證器那道門。純指示 vs 帶腳本哪一種對使用者有用，是 `GEN-009` ③④。
- **DAT-1 B 那種「語法正確、語意為零」的產出有多常見。** 本批只有一例，而 harness 抓不到它（它是靠 `description-missing` 才被擋的，不是靠內容判斷）。
- **`possible-secret` 的真實發生率。** 0／59 只說明它罕見。

## 7. 邊界

- 每段每組**各一次**，n=20。§2 的「2／20 兩次都失敗」不足以做統計檢定，只足以否定「均勻隨機」這個描述。
- A 與 B 差一個 `max_tokens`。§2 的比較假設該參數對 frontmatter 品質無影響——合理但未驗證。
- mini 的成本取自 LiteLLM `/spend/logs` 的最後 20 筆 `openai/gpt-5.4-mini`（08:51:26–08:54:24），**該模型是平台的試跑預設，同日有其他批次在用**，時間窗是唯一的隔離方式。
- 語料與 A 輪完全相同，所以 A 輪 §6 記的兩個偏差（12 段來自閘門情境卡、生成端未走 `apps/llm`）在這裡一樣成立。

## 8. C 輪：第一次真的走過 `apps/llm` 端點的生成，與逐次成本分布（2026-08-25，`04` 丙-56／丙-53）

monkeypatch 掉 client。**於是端點與閘道之間那一段，在今天之前沒有任何一次執行覆蓋過**（[`04` 丙-56](../../04-backlog-and-handoffs.md)）。
這一輪走完整條：`POST /v1/generate-skill` → LiteLLM → OpenAI，`strict: true` 的真實 schema。

### 8.1 這條路通了

而在 08-24 它卡在額度用盡、**429 發生在 schema 驗證之前**，所以先前一次都沒驗到。
`prompt_version=generate-skill/v2`（strict-legal 的那版），`model=gpt-5.4-mini`。

語料：`gate-test/task-cards.md` §2 的 DOC-1～3／WRI-1～3／DAT-1～3 九張逐字，加一段自由描述。

### 8.3 一個這一輪才看得到的缺陷：strict 拿掉 pattern 之後，模型真的會寫出違規的 `name`

第一次呼叫回來的 `name` 是 **`scan-receipt-table整理`**——含中文，
而 `skillpkg.Validate` 的 `nameRule` 是 `^[a-z0-9]+(-[a-z0-9]+)*$`，**那個名字會被擋下來**。

**這不是模型變差，是約束搬家了**：strict `json_schema` 不接受 `pattern`（§5 與 `generate.py` 的註解都記著），
所以那六個約束從「模型產不出來」變成「下游要擋」。下游確實擋得住（`skillpkg.Validate` 逐字交出 finding，
`02:GEN-003`），**但代價是一次付了錢的呼叫換到一個阻擋級 finding**，而重試上限是 2。

**發生率 1／10**，九張情境卡全部合法（`name_legal` 9／9、`name_ascii` 9／9）。
**10 次不足以定一個率**，記在這裡是因為它是 A／B 兩輪結構上看不到的一類失敗——那兩輪沒有經過端點，
也就沒有經過 strict schema。

### 8.4 邊界

- **n=10，且全部是單次嘗試**。重試會讓實付變兩倍，8.2 的分布**不含**任何一次重試。
- 十段裡九段是閘門情境卡（與 A／B 輪同一份語料），繼承 A 輪 §6 記的同一個偏差。
- `cost_usd` 取自閘道**逐次回報**的 `usage`，不是時間窗切分的 `/spend/logs`——這一輪不需要 §7 第三條那種隔離。

### 9.2 分組差異的原因不是生成品質，是**我沒有給輸入檔**

照表面讀會得到一個結論：情境卡那一組表現最差（12 段裡 5 段拿到 `met`），非本類那一組最好（6 段裡 5 段）。
**那個讀法是錯的，而錯的原因在 harness 不在生成器。**

**五段拿到 `partially_met`／`not_met` 的，全部是 0 個產出檔案；十五段有檔案的，全部是 `met` 或 `undetermined`。**
換句話說這把尺實際上只在量一件事：**跑完之後 `/out/artifacts/` 裡有沒有東西**。

而那五段裡有四段（`DOC-1`／`WRI-4`／`DAT-1`／`DAT-4`）的卡片逐字寫著「你手上有一份匯出的 CSV」
「你手上只有那份大綱」「Someone sent you a guest post」——**那些檔案從來沒有被交給沙箱**。
`seedGen009TestCase` 只送任務描述，工作區是空的。**一個把 CSV 轉成 NDJSON 的 Skill，在沒有 CSV 的房間裡，
正確的行為就是產不出檔案。**

非本類那六段之所以好看，是因為它們要的是**方法、清單、模板**（排班方法、React 送出前清單、用藥時間表），
**那種東西不需要輸入就寫得出來**。這不是生成器對它們比較擅長，是**題目的形狀不同**。

**唯一一段可以歸給行為缺陷的是 `WRI-2`**（寫一封系統更換公告）：它不需要任何輸入檔，
提示詞也逐字要求「把產出的檔案寫到 `/out/artifacts/`」，**而它把公告寫在回覆裡沒有落檔**。

所以 ③ 這個數字的誠實形式是：**在有東西可做的十六段裡，十五段做出了檔案**；
**在沒有東西可做的四段裡，四段都沒有——那是對的。**

### 9.3 一個真的缺陷：**截斷一次，整份判定歸零**

三段（`DOC-2`／`DAT-3`／`OUT-6`）全部三條判準都是 `undetermined`，而**原因對三段完全相同**：

> the material sent for judgement was truncated (`trace_digest.entries[].excerpt`);
> criteria depending on it are undetermined rather than passed

`judge.go` 的規則是：只要 `truncation` 非空，**任何 `passed` 一律降成 `undetermined`**（失敗不降）。
`truncated` 是一個**整批的布林值**，不分判準。

**代價可以逐項看見**：這三段的 `deterministic_findings` 裡，
平台自己用 exact match 找到了 `skill_activation` 事件、也逐檔列出了產出的檔案
（`OUT-6` 有 5 個、另外兩段各 1 個）；**評審自己的 summary 三段都寫著「三項驗收條件都有可驗證的證據」**。
也就是說，**兩條判準的答案是平台機械查出來的、根本不依賴那段被剪掉的 trace 摘錄，卻一起被降成不確定。**

**發生率 4／20**（其中 3 段因此失去全部判定，第 4 段 `WRI-4` 三條都是 fail 所以規則沒有觸發）。
**而四段全部是長 Run**——`OUT-6` 跑了 296 秒、用掉 284,705 input token。
**這條規則系統性地拒絕評分最難的那些 Run。**

`judge.go` 那段的註解自己寫著這是未決的：「whether a trimmed tail deserves the same conservatism as a
missing event is a judgement about 丙-1's rule and is not decided by renaming it」。
**這一輪給了它一個發生率。** 裁定請求記在 [`05` R-18](../../05-pending-rulings.md)。

### 9.4 兩個順手量到的

- **`license-unknown` 20／20**：生成器產出的 `SKILL.md` **一次都沒有宣告授權**。今天不擋任何事
  （`skills.redistribution` 預設就不是 `allowed`），但依 [ADR-057](../../../adr/ADR-057-releasing-content-takes-named-evidence-not-a-button.md)，
  **一個沒有授權欄位的生成物永遠拿不到 `manifest` 這一級的證據**。要不要讓生成器寫入授權，是 M5 自己的題目。
- **5／20 的 Run 成功但零產出**：`the run reported success and no output files were recorded for it`——
  這條 finding 存在且說得清楚，**它就是 §9.2 那個分組差異的機械對應物**。

### 9.5 邊界（這一節的數字不能拿去回答什麼）

- **這把尺量的是「載入了並且產出了東西」，不是「做對了事」。** 選它是為了與精選那批（`CONTENT-008`）同軸可比，
  代價逐字寫在 harness 的檔頭。**沒有任何一段的判定代表那個 Skill 好用。**
- **那六段非本類描述不是 A／B 輪用的原文**。A／B 輪的六段從未進 repo（spike 的生成腳本是一次性的），
  這裡是**同樣六個題材、重寫的文字**。十四段情境卡則與 A／B 輪逐字相同。
- **每段只跑一次。** ADR-047 的 (甲)「每段至少兩次」是對 ①② 的要求，這一輪沒有對 ③ 重複——
  判定的變異數因此未知。
- **runtime 是 `runc` 不是 `runsc`**，這一輪不構成 `SEC-009` 的任何一項。
- **④ 仍然沒有數字。** 「人看了會不會留著」要人，`GEN-009` 整列因此維持不勾。
