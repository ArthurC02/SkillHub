# React 送出前自我檢查清單

在提交 React 程式碼前，先快速走完以下檢查。目標不是完美重構，而是避免把常見問題帶進主分支。

## 1. 載入中的狀態是否完整處理
- 是否有任何非同步資料請求、計算、圖片載入或頁面切換流程？
- 若有，畫面上是否清楚呈現 `loading / pending / fetching` 狀態？
- 載入中時，是否避免顯示空白、舊資料誤導使用者，或讓按鈕重複送出？
- 是否在適當位置顯示 skeleton、spinner、disabled 狀態，或其他明確回饋？
- 若有多段非同步流程，是否每一段都有自己的載入處理，而不是只在最外層包一層？

## 2. 錯誤有沒有被吞掉
- 是否有 `try/catch`、promise chain、事件處理、API 呼叫、hook effect？
- 任何錯誤是否都有被記錄、顯示，或轉成可理解的 UI 狀態？
- 是否避免只有 `catch {}`、空的 `catch`、或直接忽略失敗？
- 若錯誤是預期內的，是否有明確分類與對應訊息？
- 若是非預期錯誤，是否至少保留 log、上拋、或交給 error boundary / 全域處理？
- 是否確認錯誤處理不會讓畫面卡在 loading，或讓使用者不知道發生了什麼？

## 3. 元件是不是太大，該拆了
- 單一元件是否同時處理：資料取得、狀態管理、表單邏輯、格式化、渲染、互動？
- 是否出現明顯的「一個檔案太長、太多條件分支、太多 props」的跡象？
- 是否有可抽出的區塊：
  - 重複的 UI 區段
  - 複雜的表單欄位群
  - 資料轉換邏輯
  - API / hook 邏輯
  - 可重用的小元件
- 若元件讀起來需要來回跳很多段才能理解，是否應拆分成更小的元件或自訂 hook？
- 拆分後是否能讓責任更單一、命名更清楚、測試更容易？

## 4. 快速自問
送出前，用下面三句話確認：
- 這個畫面在載入中時，使用者知道自己在等什麼嗎？
- 出錯時，使用者和開發者都看得到問題嗎？
- 這個元件的責任是否已經接近上限，該拆就拆？

## 5. 如果任何一項不通過
- 先修正再送出。
- 如果一時無法修正，至少在提交說明中註明：
  - 哪一項尚未完成
  - 原因是什麼
  - 之後要怎麼補

## 6. 使用方式
每次送出前，逐項快速過一遍；如果你在 review 時發現同樣問題，也用這份清單反查是否在開發時就漏掉了。
