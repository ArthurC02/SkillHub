## 2. `EVAL-011` 為什麼不勾（唯一的退回，逐步寫清楚）

**準則原文**：`02:EVAL-003` 第 1 條「**使用者可**使用同一 Test Case 對新 Skill Version 重新執行」。

**已成立的部分，先說完整**：

1. **刻意不新增重跑端點**，這是對的且要記下來為什麼對。重跑就是既有的 `POST /skills/{id}/runs` 帶新 `skill_version_id` 與同一個 `test_case_id`，所以 preflight 與 `confirmed_summary_hash` 一定在路徑上。多開一個「一鍵重跑」端點，它與既有那條唯一可能的差別就是**繞過權限確認畫面**——`TEST-009` 存在的全部理由。整合測試 `TestRerunningTheSameTestCaseOnANewVersionGoesThroughPreflight` 直接反證繞不過去：新版本內容雜湊不同 → 摘要 hash 變 → 舊確認自然失效 → 422。
2. **比較畫面已經給了一條合格的路**：`RunCompare.tsx` 的 `RerunCell` 把 `skill`／`version`／`test_case` 三個 id 都填好連到 preflight，且 `inputs_available: false` 時**整條連結拿掉**而不是給一個壞掉的（ADR-003：已刪除的輸入不得暗示仍可重跑）。
3. **Test Case 詳情頁也連得過去**，帶 `skill` 與 `test_case`。

**缺的那一步，也說清楚**：

- `RunPreflight.tsx` 沒有 Skill Version 選擇器。`version` 只能從 URL query 進來，該檔的 scope 註解自己寫了這件事（「Skill Version id 目前仍需自行填入」）——**填在哪裡？網址列。頁面上沒有這個欄位。**
- 而 M3 的主路徑是「評估 → 採納建議 → 建出新版本 → 用同一個 Test Case 重跑新版本」。走到第四步時，`AppliedResult` 只顯示版本序號與內容雜湊，連到 Skill 頁；使用者要在 Skill 頁抄下版本 ID，回到 Test Case 頁點連結，再手動把 `&version=<抄來的 id>` 加進網址。
- 比較畫面那條合格的連結**解不了這一步**：它要求兩個 Run 都已經存在，而這裡正是要產生第二個。這是循環，不是替代路徑。

**為什麼這一次要退回，而 `TEST-008`／`TEST-009` 當初在同樣的 URL query 形態下可以勾**：那兩項的準則主詞是系統（「執行前必須揭露」「權限異動後必須重新確認」），本項的主詞是使用者。這正是 §9 那把尺要分辨的東西，不是嚴格與寬鬆的差別。

**補法與代價**：preflight 頁加一個版本選單（讀既有的版本清單），或 `AppliedResult` 直接連到帶著新 `version` 的 preflight。任一都不需要新端點、不需要新決策。補上即依允收重新勾選——與 `TEST-004`（缺顯示面被退回、補上 `/lab/datasets` 後重勾）、`TEST-003`（缺操作面被退回、補上 `TEST-012` 後重勾）**同型的第三次**。殘項見 `04` 丙-11。

## 3. 兩項已勾項目的覆核

### 3.1 `EVAL-013`：維持勾選，範圍註記誠實

**結論：同意原勾選，範圍註記不需要修改，也不建議刪減。**

覆核的重點不是「六條允收有沒有滿足」（有，[report-judge-regression.md §9](report-judge-regression.md) 逐條對照且逐條有可重跑的產出），而是**那個 100% 有沒有被寫成別的意思**。沒有：

- 報告 §1 的一句話結論之後緊接著寫「**但這個 100% 要照它的範圍讀，不能當成『Judge 準』的通稿**」，§2 用一張「測到了／沒測到」的對照表把三個空格攤開（主觀判定、注入抵抗、證據殘缺下的保守性），§9 的勾選建議後面直接寫「**勾選同時要講清楚它不代表什麼**」。
- 更關鍵的一句在 §2 末：那兩條可計分驗收條件的**正確答案平台自己用規則就算得出來**，所以這是一個**下界檢查**——能證偽「Judge 連讀得到的事實都會讀錯」，不能證實「Judge 判得動它真正存在的那一類問題」。這句話比任何一個百分比都重要，而它已經在文件裡。
- §6 的差異歸因沒有硬套 `02:EVAL-013` 給的兩個類別（「Judge 判錯」／「標註可議」）。兩類實測都是 0，作者**另立第三類「平台缺陷」並具名根因**，而不是把 45 筆塞進其中一格。這是對的處置：準則給的分類不夠用時，誠實的做法是加一類並說明，不是選一個比較像的。
- v1 → v2 的處置也對：prompt **升版不就地改寫**，兩輪同存於 `results.jsonl` 並以 `regression_id` 區分，舊列一個位元組未改（ADR-026 決策 1 的實作演練）。

**`03` 行內的範圍註記**（「勾選的範圍是『回歸集與驗證流程建立且跑過』，不含主觀判定、注入抵抗與證據殘缺三類的覆蓋」）與報告一致，**不退回**。

**這一項最值得留下的一句**：v1 的 45 筆全數降級，形態是「判定正確、理由正確、引用的 id 正確，只有引文多了一個 `事件型別: ` 前綴」，而呈現出來與「Judge 沒把握」**無法區分**。沒有這次回歸，線上會呈現的是「Judge 對啟用類條件永遠說不知道」，每一份判定的 `reason` 卻都寫著正確答案。`02:EVAL-013` 在第一次執行就付清了自己的成本——這件事應該被 M4 的任何一個「要不要為驗證再花一次錢」的討論引用。

### 3.2 `CONTENT-007`：維持勾選，兩項保留意見同意

**結論：同意原勾選，兩項保留意見誠實且應該保留在行內。**

四個缺口（G1 資料層／G2 Go 接線／G3 UI／G4 harness）逐項查證：

| 缺口 | 查證 |

**保留意見二（A 輪查出的 G7）**：同意記在 `04` 乙-13 而不是留著擋本項。判準是「這個缺口與 rubric 內容有沒有關係」——沒有：`verify()` 對 `kind = artifact` 只檢查路徑在 manifest 上、**引文不比對**，這對任何帶 `evidence_required` 的 rubric 一視同仁，屬 `EVAL-001`／ADR-026 defence 3 的判準而非內容供應。**它需要拍板**（兩個選項動的是防線 3 本身），所以歸乙不歸丙。

## 5. 歷史 M2 Run 的 `artifacts` 表全空——這一項單獨寫

`artifacts` **全表 0 列**：M2 的管線沒有寫這些列，封存本身還在物件儲存（`run-artifacts/<run_id>/<attempt_id>/artifacts.tar`），`EVAL-013` 的 harness 是以 SigV4 直接讀封存的索引才拿到 manifest 的（回歸報告 §3.2 規則 5）。M3 的 `recordArtifacts` 從此會寫，所以**新的 Run 沒有這個問題**。

**為什麼要單獨寫**：`deterministic.go` 的 `artifactFindings()` 在 `len(m.artifacts) == 0` 且 Run 為 `succeeded` 時會產出「這個 Run 回報成功而沒有記錄到任何產出檔案」——那正是丙-5 `date-wrangling` 那個實例要抓的東西。**對 M2 的歷史 Run 評估時，這句話會對 43 筆確實有產出的 Run 說出來，而且是錯的。** 送給 Judge 的 `artifacts[]` 也會是空陣列。

**裁定：記為已知限制，不在 M3 修。** 三個理由：

1. **它今天不會發生。** 評估只由終態轉移排入，M2 的 73 筆 Run 早已終態，沒有任何路徑會自動評估它們。ADR-025 已明文把它們定為「永久停在未評估，除非有人另行決定補評」。
2. **它一旦發生就是靜默的錯**，所以不能只留在程式碼註解裡——要補評 M2 歷史 Run 的人必須先看到這一條。已入 `04` 丙-13 並寫明前置動作。
3. **修法是資料回填不是程式修改**：從封存的 tar 索引回填 `artifacts` 列，`EVAL-013` 的 harness 已經證明讀得到（不解壓、不依副檔名解析，設計 §2.2 允許的那條路）。

**要補評 M2 歷史 Run 的人，順序是：先回填 `artifacts`，再評估。** 反過來會得到 43 份帶著一句錯誤指控的評估——而評估是 append-only 的，錯的那一份會永遠留在 revision 清單裡。
