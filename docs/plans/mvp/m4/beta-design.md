## 0. 一句話

> 封測要回答的不是「能不能跑」，而是「**一個沒看過這個產品的人，會不會自己走完一次並覺得值得**」——因此本設計的每一項機制，都要能在事後回答漏斗的某一段為什麼斷掉。

## 2. B-1 准入：邀請制 vs 純 OAuth

ADR-020 的待決策第 2 條逐字問的就是這件事：「封閉測試（`BETA-001`）是否需要邀請碼／白名單閘門疊在 OAuth 之上」。

| 選項 | 內容 | 評價 |
| --- | --- | --- |
| **A（建議）：允許清單疊在 OAuth 之上** | 登入仍走 GitHub OAuth；`user_identities.provider_user_id` 命中部署設定的允許清單才建立 Workspace 並開放私有功能。**未在清單內：可搜尋、可看詳情，不可 Fork、不可 Run、不可下載** | 與 `DISC-010`（公開搜尋不要求登入）天然一致——「未受邀者看得到目錄」本來就是既有行為，不是為封測新開的。實作是一個 middleware ＋一份設定，**比照 `SEC-011` 的 `OPERATOR_USER_IDS` 既有前例**（該項刻意不做 DB 角色表，理由逐條寫在 `03` SEC-011，此處完全適用） |
| B：邀請碼 | 發一次性碼，兌換後綁定帳號 | 需要碼的產生、保管、兌換、撤銷與過期，外加一個兌換頁。**它解決的問題（防止不請自來的人用掉配額）在允許清單下已經被解決**，而它自己是一組新的機密材料 |
| C：純 OAuth，不設閘門 | 任何有 GitHub 帳號的人都能用 | 封測的成本模型（PDM-010 §8.2：30 人 900 Run／月）在人數不可控時失效；且 `BETA-002` 的漏斗會混入非受測者，`BETA-005` 的複審失去樣本邊界 |

**取 A**，並沿用 `SEC-011` 的三個既有裁定：清單來自部署設定（`BETA_ALLOWLIST` 之類）、每次啟動寫一筆 roster audit event（答「誰現在在名單上」，**不答「誰在何時被加入」**——後者的事實在部署設定的變更歷史裡）、寫不成該筆事件時 fail-closed。

**未在清單內的使用者看到什麼**：不是 404，是一句說明 ＋「回報你的使用情境」入口——那正是 PDM-010 §8.1 為「額度耗盡」設計的同一個需求訊號蒐集管道，兩處共用一個表單。

> **這需要一份 ADR（建議 ADR-028）**，因為它回答的是 ADR-020 明文掛著的待決策，而且它與 B-2 的強制點是同一個問題的兩半。

## 3. B-2 配額與成本上限

### 3.1 值（PDM-010 提案，**未追認**）

| 項目 | 值 | 備註 |
| --- | --- | --- |
| 首個 30 天窗口 | **20 次 Run**（`min(20, 30)`） | 提案自己標了「**或 20+30=50，請負責人明確擇一，不要留給實作推斷**」 |
| 第 31 天起每月滾動 | 30 次 Run | |
| 每日 | 5 次 Run | |
| 同一 Workspace 並行 | 2 | **已強制**（`internal/run/gateb.go`，交易內 advisory lock ＋非終態計數） |
| 計數起點 | 進入 `preparing` 狀態的 Run | 資源真正被佔用之後才計 |
| 自動退還 | 平台原因終止（Provider 不可用、清理失敗、平台側 `failed`、閘門 B 基線未過） | **不退還**：Skill 執行失敗、驗收未通過、使用者主動取消 |
| 耗盡行為 | 阻擋建立新 Run，顯示重置時間 ＋「回報你的使用情境」入口 | 與 §2 共用同一個表單 |
| 未登入 | 可搜尋、可看詳情、不可 Run | `DISC-010` 既有行為 |

### 3.2 強制點在哪一層——**這一題本專案已經答錯過一次**

`04` 乙-2 的教訓要逐字帶到這裡：PDM-005 的 token 上限被寫進 `policy_snapshot`、**顯示在執行前權限摘要上並要求使用者確認**，而平台與沙箱都不強制。那個狀態被判定為「兩者中最壞的一種」——讓使用者確認一個平台不會執行的上限，直接踩 `NFR-001`「UI 不得誤導」。最後的處置是找出**唯一看得到那個數字的地方**（沙箱內的 harness）並在那裡強制。

配額有同一個陷阱，形狀不同：

| 看起來像煞車、實際上不是的東西 | 為什麼不是 |
| --- | --- |
| LiteLLM Virtual Key 的 `max_budget` | 它是**每 Run 一把新鑰匙**（`skillhub-attempt-<id>`），管的是單次 Run 的金額，**不會跨 Run 累加**。三十次 $0.30 的 Run 全部合法通過 |
| `tpm_limit` | 速率不是總量 |
| Workspace 並行 2 | 同時只能跑兩個，不代表一個月不能跑三百個 |
| 牆鐘 | 單次時長 |

**因此配額的強制點必須是平台自己的一個計數器**，落在 `internal/run` 的 `Create`（＝閘門 B 現在住的地方），與並行上限同一處、同一個交易、同一個 advisory lock。理由不是方便：那裡是**唯一一個「Run 即將被建立」且還沒有花任何錢的位置**。

**計數用的表**：不新增「餘額」欄位——餘額是可以漂移的快取。改為對既有的 Run 列做時間窗計數（比照並行上限用的是「非終態計數」而不是一個 counter 欄位）。退還因此不是「加回一格」，而是**計數查詢排除那些 failure_class**——退還語意變成一個查詢述詞，不是一次會漏掉的寫入。

### 3.3 顯示與強制必須成對

`TEST-011` 已經在執行前權限摘要上放了「預估成本區間」。配額要加的是**剩餘次數與重置時間**，而依乙-2 的教訓，**顯示它的前提是它真的會被執行**。因此第 5 批的順序是硬的：先做強制點與測試，再做顯示。

## 4. B-3 漏斗量測

### 4.1 現況：沒有任何工作項承接

`01` §11.2 列了七段漏斗，`03` `BETA-002` 要量其中三段，但**平台沒有產生使用者行為事件的任何機制**：

| 既有的東西 | 它答什麼 | 為什麼不能拿來當漏斗 |
| --- | --- | --- |
| `O11Y-001`／`002`／`003` 的 Prometheus 指標 | 平台健康（搜尋延遲、Run 排隊、成功率、清理失敗） | 是**聚合計數**，沒有使用者維度，答不出「同一個人有沒有從詳情走到試跑」 |
| `CORE-008` 的 audit event | 合規紀錄：誰、做了什麼、對哪個資源、何時 | PDM-006 提案給它 400 天、**只存 actor／動作／資源 ID／時間戳、不含內容**。拿它當分析來源，要嘛得往裡面塞內容（破壞它的隱私設計），要嘛答不出「使用者輸入了什麼意圖卻沒點任何結果」 |
| Run Trace | 一次 Run 內發生什麼 | 漏斗的前兩段（搜尋 → 詳情）根本還沒有 Run |
| Langfuse | 工程調優，**明文非事實來源**（ADR-017） | 同上，且只看得到模型呼叫 |

**結論：漏斗事件是一個新的資料類別。** 建議新增工作項（`README` §7 差-4，建議 `O11Y-004`），並**在寫第一行事件產生程式碼之前**立 ADR-029 劃清邊界——因為鐵律 11 明文「Secrets 不得出現在套件、Log、Trace 明文或**分析事件**」，而目前全 repo 沒有任何文件定義「分析事件」是什麼。

### 4.2 建議的形狀（細節留給 ADR-029）

**七段漏斗對應的事件**（`01` §11.2 逐條）：

| 漏斗段 | 事件 | 已有的資料 |
| --- | --- | --- |
| 輸入意圖後查看至少一個詳情 | `search_performed`、`skill_detail_viewed` | 無 |
| 查看詳情後 Fork 或啟動試跑 | `skill_forked`（可由 audit 推）、`run_created`（已有 `runs` 列） | 部分 |
| 建立 Run 後成功完成 | — | **`runs` 表已足夠**，不需要事件 |
| 完成 Run 後認為結果有幫助 | — | **`evaluations.feedback_helpful` 已存在**（`EVAL-006`） |
| 改善建議被採用 | — | **`evaluation_suggestions.decision` 已存在** |
| 完成試跑後打包下載 | — | **`download_records` 會有**（`WS-004`，M4 第 4 批） |
| 首次使用後再回來 | `session_started` | 無 |

**只有四個事件是真的要新做的**：`search_performed`、`skill_detail_viewed`、`session_started`，加上一個 `download_started`（若要區分「按了下載」與「下載成功」）。其餘五段**用既有的領域資料表就答得出來**——這一點很重要，因為它把「新增一個分析管線」縮小成「新增四個事件 ＋ 一組跨表查詢」。

**三條必須寫進 ADR-029 的界線**：

1. **分析事件不是事實來源。** 領域問題一律查領域表（同 ADR-017 對 Langfuse 的既有立場、同鐵律 5 對 `run_lifecycle` 的既有立場）。
2. **不記自由文字內容。** `search_performed` 記查詢的**長度、語言、是否有結果、結果數**，**不記查詢原文**——查詢原文可能含個資（`gate-test/recruit.md` §5.2 第 6 項已為閘門的逐字稿點名同一個風險）。要看原文得走 `BETA-003` 的質性管道，那條路徑有使用者的明示同意。
3. **保存期限與遮罩要有值。** 沿用 PDM-006 的分級表形式；未定值前不得上線收集（＝`NFR-002` 的既有要求，不是新規則）。

### 4.3 `01` §11.3 的體驗目標怎麼量

| 目標 | 量法 |
| --- | --- |
| 10 分鐘內完成第一次「搜尋到下載」 | `session_started` → 第一筆 `download_records` 的時間差（同 workspace） |
| 所有「通過／未通過」都能展開查看依據 | **不是量的，是 `QA-006`（評估可解釋性測試）** |
| 所有執行都能追溯到版本、輸入、Runtime 與 Provider | **不是量的，是 `RELEASE-002` 的檢查** |

## 5. B-4 回饋收集

三個管道，各自回答不同的問題，**不要合併成一個表單**：

| 管道 | 回答什麼 | 形式 | 需求 |
| --- | --- | --- | --- |
| 逐次評估的有幫助／無幫助 ＋ 文字 | 「這一份評估報告有沒有用」 | **已存在**（`EVAL-006` 的 `PUT /runs/{id}/evaluation/feedback`） | `BETA-003` |
| 阻斷回報 | 「我卡在哪裡」 | 全站可及的入口，帶當前頁面路徑與（若有）`run_id`；**不自動抓畫面** | `BETA-004` |
| 需求訊號 | 「我想要但沒有的東西」 | 與 §2 的「未受邀」與 §3 的「額度耗盡」共用同一個表單（PDM-010 §8.1 已這樣設計） | `BETA-005` |

**`BETA-004`「記錄所有阻斷首次成功旅程的問題」的判定尺**：一個問題算「阻斷」的條件是**使用者在該段停下且沒有自行繞過**——這需要漏斗事件（§4）與阻斷回報對得起來，所以兩者要能用同一個 session 識別串起來。這是 §4 的四個事件裡 `session_started` 存在的理由。

## 6. 招募與受測者資料：可重用的與必須新做的

### 6.1 可整套重用（來自 [`../gate-test/recruit.md`](../gate-test/recruit.md)）

招募文案兩版（公開版 ＋ 個別邀請版）、「文案不可以寫的三件事」的前兩條（不提搜尋引擎、不舉具體例子——**第三條「不暗示會找不到」是干擾卡專用，封測不適用**）、5 題篩選問卷與分層規則、三層受測者定義（學習者／改善者／精深者，用行為問不用標籤問）、硬性與排除條件、篩選作業流程（分層取人、同層優先類別互補、每層留候補）、報酬設計四原則（不用產品額度折抵、對應 1 小時市場價、當下無條件給付、未完成場次照給全額）。

**要改的只有框架**：閘門是「40 分鐘一對一主持」，封測是「一段時間內自己用」。因此封測還要決定：測試期長度、期間內的接觸頻率、以及**是否要一次 onboarding 通話**。

### 6.2 必須從零做的唯一一項：同意書與受測者資料的保存政策

全 repo **沒有任何同意書模板**，只有兩處掛勾（`moderator-guide.md` §1 的檢核項、`recruit.md` §5.2 第 5、6 項待決）。第 6 項已經自己點名了對齊對象：**M0 的資料保存政策（PDM-006）與 `NFR-002` 的遮罩要求**，理由是「受測者查詢原文可能含個資」。

**做一次，M1 閘門與 M4 封測共用。** 內容至少要涵蓋：蒐集什麼（帳號識別、使用行為、查詢原文？逐字稿？錄影？）、保存多久、存在哪、誰能讀、怎麼撤回、以及**平台已有的使用者資料刪除承諾（`NFR-002`／`CORE-007`）與封測資料的關係**——後者是新問題：使用者刪除帳號時，他的封測回饋要不要一起刪？（建議：質性回饋去識別化保留，與 PDM-006 §6.1 對 Run metadata 的既有處理同型。）

**文件本體 agent 寫得出來**（`README` §5.1 P-12）；**簽署與法務確認是人的動作**。

### 6.3 兩批受測者不可混用

`gate-test/recruit.md` §5.2 第 11 項已建議「9 位閘門受測者不計入 PDM-009 的封測人數」，理由是他們已知答案。**反向也成立**：封測者若先看過產品就不能再當閘門受測者。這是 `README` §5.3「先跑閘門、再跑封測」的第二個理由。

## 7. PDM-009 是 M4 唯一一個連提案都沒有的決策

`m0/pdm-proposals.md` 有 PDM-001～006、008、010，**沒有 PDM-009**。而兩份既有文件已經各自假設了一個數字：`pdm-proposals.md` §8.2 用 30 人、`cost-estimation.md` 用 20 人。**兩者互斥且都沒有依據。**

`PDM-009` 要回答三件事，缺一則 `BETA-001`／`BETA-005`／`RELEASE-009` 全部不可判定：

| 要回答 | 為什麼不能事後定 |
| --- | --- |
| **人數** | 它決定成本模型（PDM-010 §8.2 的整張表以 30 人為前提）與節點數（cost-estimation 的 N+1 下限效應：封測規模下 Sandbox 成本**對 Run 量不敏感**，想省錢只能省節點規格） |
| **招募方式** | 材料可重用（§6.1），但**通路**要決定（社群、電子報、個別邀請） |
| **成功門檻** | **事後定門檻等於沒有門檻。** `gate-test/README.md` §2.2 的做法是現成的形狀：一個主判準 ＋ 一個分佈判準 ＋ 一個否決判準，每個門檻都寫出推導 |

**建議**：把「補一份 PDM-009 提案」排在第 1 批之前。**提案 agent 寫得出來**（依 `01` §11 的漏斗與 `gate-test/README.md` §2.2 的門檻推導形式），**拍板仍在人**。提案至少要包含「不通過時做什麼」——`gate-test/analysis.md` §4 的三類決策樹（搜尋／內容／呈現）是現成的形狀，封測版的分類軸應該是漏斗的哪一段斷掉。
