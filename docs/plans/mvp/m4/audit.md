## 2. 逐項對帳

> 逐項的完整理由**已就地寫進 `03-work-items.md` 的每一行**（那是勾選狀態的事實來源）。本節只記**裁定為什麼是這一個而不是另一個**，以及對帳過程中新發現的東西。不重複 `03` 已有的證據清單。

### 2.1 §15 `PACK-*`：六勾三不勾

**三個不勾各自代表一種不同的失敗，值得分開讀**：

- **`PACK-003` 是「四項裡少一項，而且少的那項沒有落點」。** `download-manifest.schema.json` 全文沒有任何 author 欄位；作者資訊只能靠來源套件的 `SKILL.md` frontmatter 被白名單逐位元組複製而存活。**這個推理是對的，但它是推理。** 同一份設計自己要求打包的具名測試要對匯出的位元組斷言（尺-3），而這一格目前對意圖斷言。**補法二選一，都很小**：manifest 加一個 additive 的 author 欄位（動 schema，major/minor 依 `contracts/packaging/README.md` 的規則判），或在 `02:PACK-001` 就地寫明「作者資訊隨套件位元組保留、不另立 manifest 欄位」並補一支測試。
- **`PACK-007` 是「宣稱大於實作」，而且那句宣稱隨每一個 `standard` 套件出貨。** `standard.json` 的 `known_limitations` 第 3 條寫著 INSTALL.md 會列出「including the ones Skill Hub's own runtime image refuses」，而 `dependencyNotes()` 從不查那張拒收表。**這正是乙-2 記下來的形狀**：讓使用者相信一件平台不執行的事。另兩個缺口（`undeclared-dependency` 不進 INSTALL.md、`targetView` 不送 `env_vars` 與依賴）讓 `02:PACK-002` 第 1 條的字面也不成立。
- **`PACK-009` 是「最後一哩要人，而且已經被預告過」。** [README.md §13.5 出-1](README.md) 早就寫著這件事，本次對帳只是把它從「出入清單」升格為「不勾的理由」。**另有一個純程式的缺口**：`packaging-design.md` §2.3 具名要求的 round-trip 測試不存在，而 `standard.json` 的 `verification_steps` 第 4 條正是叫使用者做那件事——**平台要求使用者做一個自己沒有自動驗過的檢查**。

**六個勾選裡，兩個值得單獨記一句**：

- **`PACK-002` 是 M4-1 接點最乾淨的落地。** 打包側沒有自己的「阻擋級」定義，severity 全取 `skillpkg`；preview 與 create 由同一個 `Plan` 回答，所以「預覽說可以、建置說不行」在結構上不可能。**兩套判準會漂移，而漂移的方向必然是打包側比較鬆**——這個風險被關掉的方式是不讓第二套存在。
- **`PACK-004` 的白名單設計讓 M4-4 由「一條要被記得的規則」變成「一件不可能發生的事」。** 評估建議的 prose、證據引文、rubric、Trace、Run artifact 從來就不是 Skill Version 套件位元組的一部分，所以它們不進包不是因為有人擋，是因為它們不在來源集合裡。**黑名單漏一項就是洩漏，白名單漏一項只是少一個檔案。**

### 2.2 §17 `QA-*`：四勾五不勾

**`QA-002` 是本里程碑最完整的一項交付，理由不在於它綠**：它查出了三個真缺陷，而且**把它們記成 `gap` 而不是調鬆期望**——「一個期望值被調鬆的語料，下次就沒有人知道它曾經抓到過什麼」。三個缺陷同日修畢（丙-15），期望清單隨**行為改變**更新而不是反過來。

**`QA-003`／`004`／`005` 三項勾選共用一個保留意見**：測試都存在、都具名、都跑得起來，**但沒有一份把它們對回需求 ID**——它們分別掛在 `RUN-*`／`SBX-*`／`TRACE-*`／`TEST-*` 名下。**那份對照表就是 `RELEASE-001` 的交付物**，不是這三項的缺口，已記進 [release-checklist.md](release-checklist.md)。

**`QA-006` 的不勾是本次最需要解釋的一個**，因為它的測試面確實齊備：不勾的是**「可解釋性」這件事本身有一個已實測的破口**（乙-13 G7），A 輪 9 筆 `passed` 裡有 6 筆只靠一種從未被回驗的引用。**測試齊備不等於被測的東西是對的**——這是 `EVAL-013` 存在的同一個理由。

**`QA-008` 是唯一一項連基礎設施都沒有的**，而它的缺席直接造成 `QA-009` 的第三個不勾理由（沒有真瀏覽器 ⇒ 對比只能手量 ⇒ 沒有自動守門）。**這兩項要一起決定**。

### 2.3 §17 `BETA-*` 與 §18 `RELEASE-*`：十五項全不勾

**不逐項重複理由，只記一件事**：這十五項裡有相當多的**程式面已經完成**（准入閘門、配額強制、四個漏斗事件、回饋端點、`SEC-012` 的開關、打包與下載的全套測試）。**把它們勾起來會讓帳面看起來像 MVP 完成了**，而 `02` §7 DoD 的第一條與最後一條要的是「一位新使用者走完旅程」與「至少一輪封閉測試」。

[README.md §5](README.md) 的整節就是為了這一刻寫的：**M0～M3 的殘項一再證明，把「人的動作」寫成工作項會讓帳面看起來在前進而實際沒有。** 本次對帳把那一節的分界原樣執行。

### 2.4 跨章節的四項：`CORE-007`／`CORE-008`／`WS-004`／`O11Y-004`

這四項掛在 M1／M2 的章節裡但由 M4 承接（[README.md §7](README.md) 的差-3／差-4／差-5 已裁定不搬章節）。**本次是它們第一次被真正判定**：

- **`CORE-008` 勾了，而且它是本次唯一一個從 M1 拖到現在才成立的項目。** 判定尺是 `02` NFR-001 第 4 條的字面五項——**不是 ADR-007 的完整清單**。這個選擇要寫明：ADR-007 的清單更長（含來源變更、清理），但 `02` 的允收準則是 NFR-001 那一條，而工作項的允收準則不能比 `02` 更嚴。**三處沒有事件源的動作已具名交棒到丙-23**，其中「權限確認的拒絕側」最值得注意——**通過有紀錄、被擋沒紀錄**，而安全事件回溯要看的往往是後者。
- **`CORE-007` 不勾的關鍵不是帳號刪除（那做得很完整），是 Run Artifact 沒有單項刪除路徑。** `02:WS-002` 第 3 條與 `02:SEC-006` 第 1 條都把 Artifact 列為使用者可刪的東西，而目前只有 Download Artifact 有 `DELETE`。
- **`WS-004` 是同一種退回的第四次**（`TEST-004` 缺顯示面 → `TEST-003` 缺操作面 → `EVAL-011` 缺交接面 → 本項缺列表面）。**四次都是同一個根因**：後端把能力做完了，而 `02` 的準則主詞是使用者。
- **`O11Y-004` 的產生與儲存做得比 `02` 要求的更嚴**（白名單是 schema 本身、全表無自由文字欄、未定值不收集），**不勾的是「查詢」與「揭露」兩項**。其中「使用者可在資料保存政策中看到」那一條，缺的是產品內的一個頁面——[gate-test/consent-and-data-policy.md §2](../gate-test/consent-and-data-policy.md) 已經把逐欄揭露的內容寫好了，那份是給受測者簽的，不是產品裡的。

### 2.5 §16 `SEC-012`：開關做完了，觸發沒有

**這一項的不勾要單獨記，因為它很容易被讀成「沒做」。** 做了的部分是完整的：一張表、兩個觸發者共用、三個動作齊備、每個讀者 fail-closed、解除不是自動的、incident 接管 threshold 且不被降級、operator 端點 404、暫停與解除各有具名測試。

**缺的是本項字面的第一個動詞**：「**偵測到** P1 判準即立即停止派送……不等人接告警」。五個 P1 判準沒有任何一個會自動翻這個開關。commit 自陳的「刻意不做」對其中三條成立（逃逸疑慮是判斷、P-02 探針在別處、停擺的 Reconciler 不會發現自己停擺），**但 `TraceMaskingStopped` 與「Reconciler 停擺 > 10 分鐘」是平台自己看得見的兩條**，它們沒有接上。

**這條準則的價值全在「不等人」**——`SEC-009` 通過、開放外部使用者提交 Skill 執行的那一刻，P1 若仍需要人手動停派送，`02:SEC-010` 的設計前提（團隊是一個人，等人接的最高級告警等於沒有 SLA）就直接落空。
