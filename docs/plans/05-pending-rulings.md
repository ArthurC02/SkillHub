## 1. 現在要簽什麼

**六項。** 沒有一項在擋正在執行的工作——擋著整條路徑的是 §2 的三件事，而那三件都不是簽名。

### R-22｜M6 算不算 MVP 完成度

- **要決定的是什麼**：受限環境下的可攜執行（M6）要不要計入 MVP 完成度。今天 [`01` §7.3](01-goals-and-plan.md) 依 M5 的先例把它排除在外，而那個排除本身沒有被簽過。
- **已經查到的事實**：淨測試模式那份決策已經有一項落地（派送閘門從黑名單改成白名單），**而那一項不等這個簽名就做了，因為它修的是既有缺陷**。
- **建議**：不計入，並把上述那一項一併歸入同一半。理由不是折衷——它不新增能力，它讓一個**已經存在的允收**恢復可信。把「畫面全綠而實際少跑三成七」留在完成度之外，才是誠實的記法。
- **不決定的代價**：`01` §10 M6 那一格會一直帶著「惟該判定待裁定」這句話。
- **決定之後誰動**：Agent 改 `01` §7.3 與 §10 該格一句話。

### R-25｜purge 與資料庫層的清除權限屬於誰

- **要決定的是什麼**：要不要在部署裡真的切到最小權限的清除角色，並對 API 角色收回 DELETE。
- **已經查到的事實**：**角色與授權已經在 repo 裡**——`0059_skillhub_purge_role.sql` 建 `skillhub_purge` 並逐表授權，`maintenance` 讀 `SKILLHUB_PURGE_DATABASE_URL`，沒設時退回 API 角色並在啟動日誌說出這件事，切換與回退步驟在[清除角色切換](../runbooks/purge-role-cutover.md)。**沒有被做的是操作者那兩步**：`0059` 刻意不指派登入帳號、也不 revoke 任何東西，而 `.env.example` 裡那個變數是空的——所以今天七個 purge 子命令仍跑在與 API 相同的角色上，**那個角色對每一張表都有 DELETE**。清除路徑是這個系統唯一會不可逆銷毀使用者資料的東西，而它與服務請求的路徑共用同一組憑證。
- **原本反對拆角色的理由已經不成立**：退回機制讓淨測試模式那條唯一連線維持不變（變數不設，行為與今天一樣），所以「拆角色會撞出例外」不再是代價。
- **選項**：(a) 照 runbook 切過去並收回 API 角色的 DELETE；(b) 維持退回 API 角色，**把理由寫下來**，並說明 repo 裡那套角色是為誰準備的。
- **建議**：(b)。封測 12 人、operator 一人，(a) 的縱深買不到相稱的風險降低。
- **不決定的代價**：不擋任何人。**它擋的是「有沒有人想過」這件事被記下來**——而現在多一層：機制已經在 repo 裡而沒有人用，文件沒說那是刻意的。
- **決定之後誰動**：(a) 由操作者照那份 runbook 走；(b) 由 Agent 把理由寫進對應的 ADR。對應 [`04` 乙-27](04-backlog-and-handoffs.md)。

### R-78｜營運後台要不要有漏斗儀表板、要不要依帳號排行

**一、漏斗儀表板**

- **要決定的是什麼**：`/admin/trends` 要不要多一組分析事件的漏斗圖（搜尋 → 看詳情 → 試跑 → 下載）。
- **已經查到的事實**：分析邊界那份決策寫「讀取面是後台查詢，**不做即時儀表板**」，`02` §4.12 的範圍表也排除它；但營運後台的圖是打開頁面才查一次、不輪詢，形狀上不是「一直開著的畫面」。漏斗的數字有既記的限制：session 粒度讓第一段的分母**系統性高估**，百分比只能讀作量級。
- **建議**：做。形狀照既有的圖（按需、UTC 日分桶、只有計數），每一段旁邊寫明分母高估；分析邊界補記一句「按需查詢的圖不算即時儀表板」。
- **不決定的代價**：看漏斗仍要貼 SQL 進 psql。

**二、依帳號或工作區的排行與下鑽**

- **要決定的是什麼**：趨勢圖要不要能看「誰花最多」「誰的點數最多」，以及從一格點進某一個帳號。
- **已經查到的事實**：成本與分錄兩張表永久保存、帶使用者識別、沒有清除路徑；營運後台的既有決策要求**指向特定帳號的讀取每查一次就在同一交易裡寫一筆 audit**；同意書「營運人員看得到你的 email 與點數紀錄」要不要揭露仍待法務。
- **建議**：先不做排行。要找某個帳號，從「帳號與點數」頁以 email 查（已經有 audit）。若要做，排行**只列 workspace id、不列 email**，每次載入寫一筆 audit，對象是整份排行。
- **不決定的代價**：找「異常花費的帳號」只能先在成本圖看到哪一天偏高，再去資料庫查。
- **決定之後誰動**：法務（同意書）→ Agent。

### R-82｜判定失敗的評估要不要跟判定完成的一樣凍結

- **要決定的是什麼**：一版評估有兩個結局，判定完成與判定沒跑完。兩者都不能再結算。要決定的是**失敗的列要不要跟完成的一樣整列凍結**。
- **已經查到的事實**：
  1. 不可變 trigger 只在舊值是 completed 時作用——completed 的列只剩回饋兩欄與兩個時間欄可以改，也不能刪除。
  2. **failed 的列沒有這道 trigger**：任何欄位都能被 UPDATE，也能被刪除。今天 Go 沒有這樣的寫入路徑（結算與失敗的 WHERE 只接 pending，回饋只寫回饋欄），**所以這是資料庫層少了一道保證，不是已經發生的改寫**。
  3. failed 的評估會被下一版取代，它的內容是「那次為什麼沒有結論」的紀錄，而評估的既有決策把它當成可重新判定、但每一版不可改寫的歷史。
- **建議**：凍結。一支 migration 把 trigger 的條件擴及 failed，放行的欄位不變。
- **不決定的代價**：沒有使用者看得到的差別；少的是資料庫層的第二道保證，未來某條直接寫入 failed 列的程式不會被擋。
- **決定之後誰動**：Agent（一支 migration，把一條特徵化測試改成規則，並證明會紅）。對應 [`04`](04-backlog-and-handoffs.md) 的評估凍結那一列。

### R-83｜帳號刪除要不要改成領域事件

- **要決定的是什麼**：aggregate 之間只用領域事件、各自的 Mailbox 最終一致，是既有決策。**帳號刪除今天不是這個形狀**：identity 在一個交易裡依序呼叫各 context 的清除，全有全無。要決定它維持同交易，還是改成發一則「帳號到期刪除」、各 context 各自清。
- **已經查到的事實**：
  1. **同交易是被測試守住的產品承諾**：讓最後一步失敗，斷言前面每一步都回滾、身分去識別化也沒生效。
  2. **順序是 load-bearing 的**：registry 必須先刪版本，ingest 才刪得掉沒有版本引用的匯入來源。事件化之後這個順序要改由事件鏈表達。
  3. 刪除版本靠交易級的放行機制通過不可變 trigger；各 context 各自開交易時，這個放行要重新設計。
  4. 事件化會把「一個交易清完」換成「陸續清完」，硬刪除承諾的「清完了」判準與負責對帳的人都要重新定義。
  5. **全有全無只涵蓋資料列，不涵蓋位元組**：物件儲存沒有回滾，所以它的刪除刻意排在交易開始之前，失敗時留下的是指向已消失檔案的列（下一輪清理會收），不是沒有任何列指名的孤兒檔。守著回滾的那支測試用的是假的物件儲存，只斷言資料列。
- **選項**：(a) 維持同交易——帳號刪除是作用在整個 workspace 的合規流程，不是 aggregate 之間的溝通；(b) 改成事件——要定義判準、補對帳與逾時告警、重做 trigger 的放行。
- **建議**：(a)。事件化在同一個資料庫裡買到的是未來拆分時比較好搬，付出的是今天就成立的全有全無；而觸發服務拆分的壓力條件沒有出現。
- **不決定的代價**：沒有；照現況運作。
- **決定之後誰動**：(a) 沒有工作；(b) 由 Agent 開事件與 Mailbox，並改寫硬刪除的允收準則。

### R-86｜使用者該不該看得到自己的花費明細，以及看得到哪一種數字

**工程面可以直接做，但其中三個問題是產品決定，不自行裁定。**

- **已經查到的事實**：真正被扣的分錄指回一筆成本事件，兩張表都不可變，查詢已經存在；**但這份真實明細只有營運者看得到**。一般使用者的端點只回滾動餘額與下一場的事前估計。使用者側確實還看得到一些數字，**但散在四個畫面、而且沒有一個是從真實分錄算出來的**。允收準則只要求「餘額＝分錄代數和」與分錄可追溯，**從來沒有要求任何使用者可讀的明細畫面**——這是準則層的缺口，不是實作漏做。
- **三個要裁定的問題**：
  1. **明細要不要能點回去看是哪一筆花費。** 現有的分錄回應連營運者都只看得到種類、看不到 id。要做到「花在哪」通常就是要能點進那個 Run；那要新增欄位，並且要先決定反查已刪除的、或已經不屬於這個 Workspace 的 id 時給什麼——**實作鐵律 3 說使用者查詢預設要求 Workspace Scope**。
  2. **要給使用者看哪一種數字。** Trace 頁上的「用量」是事件疊算的**下界估計**，分錄才是真正扣掉的點數，兩者在加成與面額快照之下不會剛好相等。**兩個數字同時出現在一個畫面上，看起來就像平台自相矛盾。**
  3. **要不要出現美金。** 契約描述明寫美金是平台自己的帳本、**永遠不出現在這條路由上**——Credit 是對使用者的唯一計價單位。明細畫面若要顯示美金，等於推翻這條既有決定。
- **不裁定就不動的理由**：這三題任何一個答錯，補出來的畫面都會製造新的挫敗（點不進去的連結、兩個互相矛盾的數字、或一個講不清楚單位的帳單），**而它們都不是工程判斷**。
- **決定之後誰動**：Agent。對應 [`04`](04-backlog-and-handoffs.md) 的花費明細那一列。

## 3. 一條刻意不動的線

**「先閘門、再封測」不重排。**

甲類與封測並行、M5 與 M4 並行這兩項決策已經拆掉兩條線性鏈，所以要明寫**第三條為什麼不拆**——否則下一個人看到前兩條被放行，會順手推這一條。三個理由沒有一個被時間侵蝕：

1. 在未結案的閘門上勾封測准入項，是把兩個相反結論寫進同一份文件。
2. **看過產品的人不能再當閘門受測者，反之亦然。**
3. 閘門凍結的是搜尋與內容。

**第 2 條在單人團隊下還更硬**——兩場使用者研究並行不是排程問題，是主持人只有一個。
