**規則**：

## 1. 現在要簽什麼

**三項**，都是產品化的前提（R-92～94）：**沒有它們，「發佈」這個動作在產品裡不存在**，任何交付形狀都沒有出口。擋著封測那條路徑的是 §2 的三件事，而那三件都不是簽名。

### R-92｜平台要不要產出 Agent Plugin（推翻兩處已簽的決定）

- **要決定的是什麼**：作者能不能挑選自己的多個 Skill Version、組成一份可版本化的 Bundle，並以 Agent Plugin 形狀匯出。它推翻兩處已簽的東西：`02:PACK-001` 的允收準則「平台不產出 Plugin」，以及[打包、授權溯源與散布](../adr/README.md#打包授權溯源與散布)決策 9 最後一條「我們產出的仍然只有標準 Agent Skill 套件」。
- **已經查到的事實**：那條 ADR 自己就把這件事定性為「把 N 個 Skill 重新組回一個 Plugin 是一個**發佈功能**，不是匯入的對稱操作」——它排除的是匯入的對稱操作，不是這個功能本身。今天的散布單位只有一個 Skill Version：打包路由是 `POST /skills/{id}/versions/{versionId}/packaging`，下載紀錄逐筆對一個 Skill，沒有任何一次取得多個的路徑。匯入端已經認得 Plugin，所以**同一個使用者放進來的一套東西，出不去**。組合的規則已寫成[發佈、發佈者與組合散布](../adr/README.md#發佈發佈者與組合散布)決策 6～8（釘住成員版本、匯出只含 Agent Skill、信任取最壞）。
- **選項**：(a) 授權產出，Bundle 是發佈物（有名稱、版本、成員清單，可更新）；(b) 只做一次性匯出（挑 Skill → 下載一包 zip，不留任何記錄）；(c) 維持現狀。
- **建議**：(a)。(b) 的成本只低一點，但它拿不到唯一真正的差別——**消費端看得到「這一版把哪個成員升到哪一版」**；沒有版本的組合等於一張快照，使用者第二次還是要自己重組。(c) 讓匯入與匯出永久不對稱。
- **不決定的代價**：使用者手上「一套」的概念在平台裡不存在：分享要給 N 個連結、對方要裝 N 次、讀 N 份安裝說明。而他自己匯入的那一整包，平台還原封不動存著，只有沙箱拿得到。
- **決定之後誰動**：(a)／(b) 由 Agent 改寫 `02:PACK-001` 那一條並新增需求 ID 與允收準則、改寫打包 ADR 決策 9 最後一條，然後依分期實作；(c) 由 Agent 把「不產出」的理由補進那條 ADR，並在匯入畫面說清楚使用者永遠拿不回整包。

### R-93｜平台內「分享」的最小形態，以及它要不要越過封測准入

- **要決定的是什麼**：一個作者要把東西給別人，平台內要提供什麼動作。連帶要決定這個動作要不要對**未受封測邀請**的人開放。
- **已經查到的事實**：**平台今天沒有分享動作。** 決定曝光的是 Workspace 上的 `is_catalog` 旗標，而整份 SQL 只有一條讀它的查詢、沒有任何 UPDATE 或路由——要讓東西進目錄只能直接下資料庫。沒有分享連結、沒有複製連結、沒有公開切換。未登入者只看得到已在目錄裡的 Skill，別人私有的一律 404。**取得只有一條路**：Fork（`RequireSession` ＋ `RequireInvited`）→ 進自己工作區才能打包下載（同樣 `RequireInvited`）。也就是說，**沒有邀請的人連下載都不行**。而治理那一側四個動詞（限制、可散布、策展層級、下架）都已經有營運者端點。
- **選項**：(a) 公開連結：發佈產生一個可分享的公開位址，未登入可讀、可下載該發佈物；(b) 定向分享：指定收件人才可讀，不進目錄；(c) 維持平台外傳遞，但把這件事在畫面上說清楚。**准入另外一問**：(i) 發佈與取得都不要求邀請、(ii) 發佈不要求、取得要求、(iii) 兩者都要求（現狀）。
- **建議**：(a) ＋ (i)。Catalog 是三個核心之一，而定向分享解決不了「被發現」；把取得綁在封測邀請上，等於產品化的主路徑對外關著。**曝光仍然要過內容審核**——分享與曝光是兩件事（[發佈、發佈者與組合散布](../adr/README.md#發佈發佈者與組合散布)決策 2）。
- **不決定的代價**：任何交付形狀都沒有出口。先做完 Bundle 也只會得到一包只能用平台以外的方式寄出去的檔案，而「發佈」這個動詞在產品裡仍然不存在。
- **決定之後誰動**：(a) 由 Agent 新增 Publication 的狀態機與公開位址、把四個治理動詞接到它上面、`is_catalog` 退場為「平台自己是一個發佈者」；准入的選擇由 Agent 改 `RequireInvited` 的掛點並補路由測試。曝光資格的判準等丙-285 的四個定義。

### R-94｜命名空間的三條規則

- **要決定的是什麼**：對外識別字的唯一性卡在哪一層、改名的下場、以及審核卡在發佈還是曝光。三條一起簽，因為它們互相決定。
- **已經查到的事實**：查過五個成熟市集（VS Code Marketplace、npm、GitHub Actions Marketplace、Docker Hub，以及 Claude Code 的 plugin marketplace；Codex 的官方自助發佈尚未開放，只有社群自建的 git-backed 形式）。**四條共通做法**：識別字是命名空間前綴加本體名稱；命名空間綁帳號或組織、自助註冊、驗證是事後加值；改名不原地覆寫而是保留舊識別字並轉址或標示棄用；不可變引用只能靠內容位址。**三處分歧**：唯一性卡在全站（VS Code／npm／GitHub Actions）或只卡在命名空間內（Docker Hub）；審核在發布前（Docker Official Images）或完全不審（GitHub Actions）；舊名字燒毀永不重用（VS Code）或轉址棄用（npm／GitHub Actions）。另外查到一條可以直接省掉自家機制的事實：宿主會把一個 Plugin 的元件掛在以 Plugin 為名的命名空間下（`deploy-tools:reviewer`），所以**安裝端的同名衝突不需要平台處理**。
- **選項**：①唯一性 (a) 發佈者內唯一、跨發佈者可同名／(b) 全站唯一。②改名 (a) tombstone ＋ 轉址／(b) 名字燒毀永不重用。③審核 (a) 審曝光不審發佈／(b) 審發佈／(c) 都不審。
- **建議**：①(a)②(a)③(a)。①：通用名稱不能先到先得地燒掉，而我們的引用一律帶發佈者。②：我們的核心價值是可追溯，而冒名風險已由發佈者前綴擋掉大半。③：分享不該被審核卡住，目錄品質要守住，而我們已經有掃描、授權事實與策展層級可以據以判斷。名稱字元規則沿用 Agent Skill 規格那一套，不另造一套；保留字清單連近似拼寫一起擋。
- **不決定的代價**：命名空間一旦開放就無法回頭——每個註冊過的名字都永久佔用。**這三條的成本隨目錄成長而上升**，晚一天決定就多一批要遷移的識別字。
- **決定之後誰動**：由 Agent 把三條寫進[發佈、發佈者與組合散布](../adr/README.md#發佈發佈者與組合散布)（決策 3～5 已按建議值寫下，簽了就成立、改了就改寫那三條），並補保留字清單與字元規則的測試。

## 2. 不是簽名，但在等人的三件事

**這一節排在所有簽名之前。** 它們不需要本頁的任何一項。

1. **一台節點真的被開出來。** 供應商與規格已定值（R-43），cloud-init 的輸入契約已定案（R-17c），三種角色的 IaC 都已進 repo 並在模擬環境跑到服役。**缺的是有人去把那台機器開出來**——`04` 甲類五項全部在等它，而甲類擋著封測。
2. **同意書送出去簽名之前，先走一次法務確認。** 三件真人動作有順序：①**法務再確認一次**——第一次已在 2026-08-23 過關，之後同意書正文改過（保存期限、跨境傳輸、逃逸驗收揭露、首次揭露「刪帳號不刪回饋文字」與 Test Case 的刪除路徑），而那份文件自己的規則是**正文一改就要重走**，並明寫「在重新確認完成之前不得送交受測者簽署」；要看的五件與移交材料都已備妥（`04` 乙-16）。②**填入聯絡方式**——§9 的其餘佔位都已定值，剩下的是一個真人的姓名與信箱，不是一個決定。③**12 位受測者簽名。**
3. **`m5/ask-5.md` 的五個人。** 材料已備，由負責人自己去問。它是 M5 最貴的那個未對沖假設（「使用者搜不到會想要生成一個」）唯一的證據來源，而今天的證據量是零。

## 3. 一條刻意不動的線

**「先閘門、再封測」不重排。**

甲類與封測並行、M5 與 M4 並行這兩項決策已經拆掉兩條線性鏈，所以要明寫**第三條為什麼不拆**——否則下一個人看到前兩條被放行，會順手推這一條。三個理由沒有一個被時間侵蝕：

1. 在未結案的閘門上勾封測准入項，是把兩個相反結論寫進同一份文件。
2. **看過產品的人不能再當閘門受測者，反之亦然。**
3. 閘門凍結的是搜尋與內容。

**第 2 條在單人團隊下還更硬**——兩場使用者研究並行不是排程問題，是主持人只有一個。
