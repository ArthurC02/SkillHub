## 1. 現在要簽什麼

擋著封測那條路徑的仍是 §2 的三件事，而那三件都不是簽名。下面這一項不擋封測。

### R-58 創作出的 Skill 要能呼叫哪些外部工具（`04` 丙-239）

- **要決定的是什麼**：Skill 除了自帶 `scripts/`，還要能宣告並在試跑與正式執行時呼叫 MCP 工具。要裁三件：①平台提供哪些 MCP server（例如行事曆、郵件、試算表、公司內部系統），以及 Skill 用什麼名字引用它們；②憑證由誰持有、怎麼注入沙箱、試跑時是真連還是替身；③試跑時的 egress 與費用歸屬。
- **已經查到的事實**：Skill 規格的 `allowed-tools` 欄位目前只被套件驗證讀來顯示，沒有進入試跑的權限；試跑沙箱的工具是固定一組，沒有 MCP server，容器沒有外網；憑證不得出現在套件、Log、Trace（現行紅線）；創作提示明令模型不得捏造不存在的工具，所以在 ① 定下來之前，創作出的 Skill 不會寫任何 MCP 呼叫。
- **建議**：(a) 先做「宣告」——平台維護一份可引用的 MCP 工具清單（名稱、用途、參數摘要），創作提示只准引用清單上的名字，試跑時以替身回應並在輸出標明「此步驟需要 X 工具」；正式執行的憑證注入與 egress 另案。(b) 一步到位，沙箱直接掛 MCP server 與憑證——要同時動沙箱契約、egress 與計費，且把外部副作用帶進試跑。建議 (a)。
- **不決定的代價**：Skill 只能把「寄出」「上傳」「查系統」交回給人做，效用受限；同時創作提示會持續被要求「不要捏造工具」，兩邊拉扯。
- **決定之後誰動**：主 Agent 改創作提示與套件驗證（清單比對）；沙箱替身進 `apps/sandbox` 與 `run.mjs`；清單本身由負責人給。

以下五項來自非功能性需求的逐條對照（`03` §25），R-100 來自同時在線 1000 人的容量目標（`02:NFR-008`、`03` §26）。**都不擋封測**，但每一項不裁，對應的工作項就只能做到一半；R-96、R-97 也因容量目標多了一層要考慮。

### R-95 資料壞了，要多快、救回到哪一刻

- **要決定的是什麼**：資料庫的 RPO（最多可以丟幾分鐘的資料）與 RTO（多久要恢復服務）；物件儲存（Artifact、套件、上傳檔）要不要備份、備在哪裡。
- **已經查到的事實**：資料庫有連續 WAL 封存（約 60 秒）、每日完整備份、每月還原演練，CI 每次都跑一次還原演練；系統脈絡那份 ADR 把 RPO／RTO 列為待決。物件儲存沒有任何備份；備份與主資料是否在不同儲存位置沒有規定；備份裡留著已被使用者刪除的資料多久，與「使用者可刪除」沒有對帳。
- **建議**：資料庫 RPO ≤ 5 分鐘、RTO ≤ 4 小時，還原演練量到的時間超過就讓 CI 紅；物件儲存每日備份到與主資料不同的位置，每月演練加一步「還原後資料庫引用的每個物件都存在」；備份保留 35 天，寫進同意書的刪除說明。
- **不決定的代價**：一次磁碟故障就會發現 Artifact 與套件救不回來，而資料庫救得回來——兩邊對不上，畫面上會出現指向不存在檔案的紀錄。
- **決定之後誰動**：主 Agent 補 `02` 新的資料復原條目與演練腳本；同意書的刪除段要重走法務確認（`04` 乙-16）。

### R-96 平台一天最多花多少錢，花完了怎麼辦

- **要決定的是什麼**：模型閘道全域每日總額的數值；以哪個時區計日；用盡時已在跑的 Run 怎麼處理；誰收到通知。
- **已經查到的事實**：每個 Run 有自己的 Virtual Key 預算，Credit 有三道閘，創作每場有上限；閘道另有一條全域每日總額（目前 50 美元，**以 UTC 日計**），2026-09-27 量測時撞到兩次——撞到後每一筆呼叫都被拒，使用者看到的是「模型回傳無法使用的輸出」，平台沒有任何紀錄或告警。數值寫在閘道設定，不在 `02`。平台自己的 Agent 各有每日上限（目前只有每日報告，0.20 美元），但沒有任何檢查要求這些上限的總和留在全域總額之內；Agent 一多，它們可以一起把全域總額吃光，使用者的呼叫就跟著被拒。
- **建議**：保留閘道全域總額當最後一道保險，數值寫進 `02` 新的成本條目；計日改用台北時間或在畫面上寫明 UTC；用盡時新呼叫回「今日額度已用完、明天幾點恢復」，已在跑的 Run 跑完當前這一步；達 80% 時告警給營運者（`03` HARDEN-009 落地顯示與指標的那一半）。平台 Agent 的每日上限總和不得超過全域總額的一個固定比例（建議 10%），登記時超過就拒絕啟動並點名。
- **同時在線 1000 人時**：匿名搜尋每次最多三次模型呼叫、目前沒有快取（`03` SCALE-008 會補），每日 50 美元的總額依這個人數必定撐不過一天；總額要依入口分開試算——匿名搜尋、創作、試跑、Judge 各自的每日上限與加總，其中一個入口燒完不該連帶停掉其他入口（`03` SCALE-020）。
- **不決定的代價**：保險絲存在但沒人知道它燒了；下一次燒斷時，使用者與營運者都會以為是模型壞了。
- **決定之後誰動**：主 Agent 改閘道設定、補告警與 `02` 條目。

### R-97 全平台同時能跑幾個 Run，滿了是排隊還是拒絕

- **要決定的是什麼**：平台全域的同時執行上限；滿了的時候建立 Run 是排進佇列還是立刻拒絕；一個工作區的負載能不能拖慢別人。
- **已經查到的事實**：每個工作區同時只能有 1 個 Run，次數配額與並行上限同一交易；沙箱節點以「執行槽」計遺留資源。全域沒有上限、沒有佇列深度的告警、沒有公平性的量測。
- **建議**：全域上限＝節點執行槽總數，滿了排入佇列並在畫面顯示前面還有幾個；佇列深度與等待時間各一條告警；公平性等真節點上線後用負載測試量（`03` HARDEN-023 同一批）。
- **同時在線 1000 人時**：每個試跑預設 2 vCPU／4 GiB，沙箱節點每台預設 2 個執行槽，部署文件寫的是第一批 1 台；`02:NFR-008` 的負載模型是 100 個 Workspace 同時要求試跑。全部同時跑需要約 50 台節點，所以實際要裁的是「同時跑幾個、其餘排隊等多久可以接受」——建議先定 20 個執行槽（10 台），尖峰時排隊，畫面顯示前面還有幾個，平均等待超過 10 分鐘時告警，再以負載測試與費用報價校準。
- **不決定的代價**：封測人數一多，沙箱節點被塞滿時的行為沒有人定義過，第一次發生就在使用者面前。
- **決定之後誰動**：主 Agent 補 `02` 容量條目與實作；量測等 `04` 甲類的節點。

### R-98 「外部即時搜尋」這個功能存不存在

- **要決定的是什麼**：`02:NFR-001` 第 5 條要求「外部即時搜尋」端點有速率限制，`02:NFR-004` 第 1 條把它排除在搜尋延遲之外——但程式裡沒有這個功能，規格也沒有任何一段描述它。
- **已經查到的事實**：搜尋只查已索引內容；互動創作有一個「連網抓取」工具（連網前先問人、被擋只報不重試），那是創作的一步，不是搜尋。
- **建議**：(a) 刪掉兩處字面，改成「互動創作的連網抓取」並確認它已有的限制；(b) 保留字面，另開需求做外部即時搜尋。建議 (a)。
- **不決定的代價**：兩條允收準則永遠有一半不可驗證。
- **決定之後誰動**：主 Agent 改 `02` 兩處字面。

### R-99 保存與刪除的兩處字面落差

- **要決定的是什麼**：①Trace 按月整個分區丟棄，實際保存是 90 天到約 120 天，而 Run 產出精確 90 天——第 90 到約 120 天之間重新評估，會在「這個 Run 沒有產出」的前提下判定，正是 `02:NFR-002a` 第 2 條要避免的情形。②`02:NFR-002` 寫「使用者可主動刪除 Run 輸入」，但已被 Run 凍結的 Test Case 快照依不可變原則刻意保留，能刪的只有 Dataset 與 Test Case 本身。
- **已經查到的事實**：保存下界的機器檢查比的是名目值，不是有效值；改任何保存期限都要重走法務確認（`02:NFR-002a`）。快照保留已寫在同意書。
- **建議**：①Run 產出保存期改為「Trace 名目值＋一個月」，或讓 Trace 的月分區等該月所有 Run 產出都過期才丟；兩者擇一，檢查改比有效值。②改 `02:NFR-002` 字面為「Dataset、Test Case 與 Run 產出」，並寫明凍結快照為何保留。
- **不決定的代價**：①每月有約一個月的窗口，重新評估的輸入是錯的，而評估紀錄只增不改；②一條允收準則字面上永遠做不到。
- **決定之後誰動**：主 Agent 改常數、SQL 與檢查；同意書改期限要重走法務確認。

### R-100 平台壞一台機器時要不要停

- **要決定的是什麼**：控制平面與資料庫的部署拓撲。`02:NFR-008` 寫的目標是每月可用性 99.9%、任一節點故障 15 分鐘內自動恢復、資料最多遺失 5 分鐘；現行架構決策是刻意的單節點，資料庫壞了就全平台停到人工還原。兩者不相容，必須改其中一個。
- **已經查到的事實**：API、Worker、能力服務、PostgreSQL、監控都在同一台機器，每個只有一份，沒有資源上限；資料庫有約 60 秒的 WAL 封存、每日備份、每月還原演練；物件儲存用供應商的受管服務；架構決策列出的升級條件之一是「團隊至少有一名能負責 Kubernetes 升級的成員」，這是必要條件。程式面要能多開，還要先完成 `03` SCALE-004～007、009、015，與拓撲怎麼選無關。
- **建議**：分兩步，不上 Kubernetes。(a) 先把應用層變成可多開，兩台控制平面節點放在供應商的負載平衡器後面，各跑一份 API／Worker／能力服務，單一節點故障時流量自動轉走；(b) PostgreSQL 一主一備串流複寫，加一個自動切換的管理程式（三個小節點做共識），切換後應用自動重連。(b) 的維運成本是三台小機器與一套要演練的切換流程；不想自己維運，替代方案是供應商的受管 PostgreSQL，代價是資料不在自有節點、月費較高。
- **不決定的代價**：`02:NFR-008` 的可用性那一條永遠無法驗收；1000 人在線時一次資料庫或主機故障，就是全平台停機直到有人醒來處理。
- **決定之後誰動**：主 Agent 改寫架構決策中單節點與升級條件那兩段、部署組合與 runbook；開機器與付費由負責人。

下面兩項來自在 gVisor（runsc）節點上量測沙箱資源上限，以及對照容器與 gVisor 的強化指引。**都不擋封測**。

### R-101 試跑的「磁碟」上限要不要和記憶體分開

- **要決定的是什麼**：要不要讓試跑的「磁碟」成為獨立於記憶體的上限，寫滿時工作負載收到「磁碟已滿」，而不是撞記憶體上限結束。撞到上限時怎麼歸類已裁定（見 §4 R-102）。
- **已經查到的事實**（量測與程式皆已查證）：沙箱的 `/work`、`/out`、`/tmp` 都是 tmpfs（`apps/sandbox/internal/dockerdrv/docker.go`）；gVisor release-20260921.0、systrap、cgroup v2 上寫入 128 MiB 檔案，容器記憶體用量增加約 135 MB。現在預設磁碟等於預設記憶體 4 GiB（`apps/sandbox/internal/sandbox/contract.go`、`apps/platform/internal/trial/execution/service.go`），試跑前的資源摘要註明暫存檔計入記憶體上限（`apps/web/src/features/lab/preflight/components/ResourceLimitsFacts.tsx`），撞到時以「撞到資源上限」結束且不計配額——這是記憶體後盾沙箱的常見做法（Cloud Run、E2B 都明說檔案計入記憶體）。要讓兩個上限獨立，做法是 gVisor 的 `--overlay2=root:self,size=N`（節點層級的 runsc 參數，大小不能逐請求設定）或 Docker 的 `--storage-opt size`（需要節點的 overlay2 落在掛了 `pquota` 的 xfs 上）；CI 的 runner 是 ext4，兩者都無法在 CI 驗證。
- **建議**：(1)，有大檔案需求的證據時再做 (2)。(1) 維持現狀：數字與說明已經一致，代價是可寫入量要和程式記憶體共用。(2) 節點改用 xfs＋`pquota`，driver 以 `--storage-opt size` 給每次 Run 獨立的磁碟上限，暫存路徑改走可寫的根檔案系統：兩個上限真正獨立、寫滿時回「磁碟已滿」，但要改節點部署、隔離驗收與 driver，並另找能驗證 xfs 配額的環境。
- **不決定的代價**：需要寫大量暫存檔的 Skill，可寫入量被程式的記憶體用量吃掉一部分；不扣配額，但時間與模型花費照付。
- **決定之後誰動**：選 (2) 由負責人配合節點部署與驗收環境，主 Agent 改 driver、契約與資源摘要。

### R-103 握有 Docker 的 `sandboxd` 等同節點 root，要不要再加一道限制

- **要決定的是什麼**：`sandboxd` 被攻破時的影響範圍。它目前能叫 dockerd 做任何事；要不要讓「它能叫 dockerd 做的事」也只剩它的程式本來就會做的那幾種。
- **已經查到的事實**（程式皆已查證）：`sandboxd` 以非 root 使用者加入 docker 群組執行（`infra/deploy/sandbox/systemd/skillhub-sandboxd.service` 的 `SupplementaryGroups=docker`），Docker 官方與 OWASP 都把能操作 dockerd 視同主機 root；架構決策已明文接受這個形狀，理由是把 `sandboxd` 放進容器只會變成掛 `docker.sock`，隔離沒有變好。它的入口只接受帶權杖的結構化請求（`apps/sandbox/internal/sandbox/http.go`），容器的安全欄位全部寫死在驅動裡、請求改不到（`apps/sandbox/internal/dockerdrv/docker.go` 的 `HostConfig`），所以要利用這份權限，必須先在 `sandboxd` 本身找到程式漏洞，或偷到平台給它的權杖。節點上沒有 Docker 的授權外掛、socket proxy 或 rootless Docker。
- **建議**：(1)，節點數變多或 `sandboxd` 的入口變寬時再做 (2)。(1) 維持現狀：已有的縮小入口就是業界對這類服務的首要建議，成本為零。(2) 在 `sandboxd` 與 dockerd 之間放一個只放行固定 API 的 proxy，並檢查建立容器的請求必須符合沙箱基線（`runsc`、非特權、無掛載、丟掉全部 capability）：`sandboxd` 被攻破也開不出特權容器，代價是多一個要維護的元件，且它本身也握有 Docker。(3) 改成 rootless Docker 或直連 containerd：rootless 與 gVisor 的組合官方支援有限，要先實測；直連 containerd 仍需 root 級權限，只是少一層 dockerd。
- **不決定的代價**：維持現狀的風險已被架構決策接受；不裁定不會讓任何東西變差，只是沒有第二道防線。
- **決定之後誰動**：選 (2) 或 (3) 由主 Agent 實作並補節點准入檢查，部署由負責人配合。

## 2. 不是簽名，但在等人的三件事

**這一節排在所有簽名之前。** 它們不需要本頁的任何一項。

1. **一台節點真的被開出來。** 供應商與規格已定值（R-43），cloud-init 的輸入契約已定案（R-17c），三種角色的 IaC 都已進 repo 並在模擬環境跑到服役。**缺的是有人去把那台機器開出來**——`04` 甲類五項全部在等它，而甲類擋著封測。
2. **同意書送出去簽名之前，先走一次法務確認。** 三件真人動作有順序：①**法務再確認一次**——第一次已在 2026-08-23 過關，之後同意書正文改過（保存期限、跨境傳輸、逃逸驗收揭露、首次揭露「刪帳號不刪回饋文字」與 Test Case 的刪除路徑），而那份文件自己的規則是**正文一改就要重走**，並明寫「在重新確認完成之前不得送交受測者簽署」；要看的五件與移交材料都已備妥（`04` 乙-16）。②**填入聯絡方式**——§9 的其餘佔位都已定值，剩下的是一個真人的姓名與信箱，不是一個決定。③**12 位受測者簽名。**
3. **`m5/ask-5.md` 的五個人。** 材料已備，由負責人自己去問。它是 M5 最貴的那個未對沖假設（「使用者搜不到會想要生成一個」）唯一的證據來源，而今天的證據量是零。

## 3. 一條刻意不動的線

**「先閘門、再封測」不重排。**

甲類與封測並行、M5 與 M4 並行這兩項決策已經拆掉兩條線性鏈，所以要明寫**第三條為什麼不拆**——否則下一個人看到前兩條被放行，會順手推這一條。三個理由沒有一個被時間侵蝕：

1. 在未結案的閘門上勾封測准入項，是把兩個相反結論寫進同一份文件。
2. **看過產品的人不能再當閘門受測者，反之亦然。**
3. 閘門凍結的是搜尋與內容。

**第 2 條在單人團隊下還更硬**——兩場使用者研究並行不是排程問題，是主持人只有一個。
