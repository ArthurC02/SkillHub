# 待裁定清單：現在等著被簽的東西

[`04`](04-backlog-and-handoffs.md) 回答「還缺什麼、誰在等誰」。**這一份只回答一件事：你現在要簽什麼。**

每一項的格式固定：**要決定的是什麼 → 已經查到的事實 → 建議 → 不決定的代價 → 決定之後誰動**。

**規則**：

- 裁定寫進這裡**不算數**，要回寫到它對應的 `04` 那一列，或它改到的 ADR、`02` 允收準則。**這份文件是入口不是紀錄。**
- 推翻既有決策的，另開或改寫對應的 ADR。
- 一項簽完，它從 §1 移到 §4 的索引，只留一行「裁定了什麼」；完整的權衡、選項與依據留在 git 歷史與它落地的那份文件裡。
- **本頁不複述 `04` 的殘項總數，也不複述 `03` 的勾選數。**

## 1. 現在要簽什麼

擋著封測那條路徑的仍是 §2 的三件事，而那三件都不是簽名。下面這一項不擋封測。

### R-58 創作出的 Skill 要能呼叫哪些外部工具（`04` 丙-239）

- **要決定的是什麼**：Skill 除了自帶 `scripts/`，還要能宣告並在試跑與正式執行時呼叫 MCP 工具。要裁三件：①平台提供哪些 MCP server（例如行事曆、郵件、試算表、公司內部系統），以及 Skill 用什麼名字引用它們；②憑證由誰持有、怎麼注入沙箱、試跑時是真連還是替身；③試跑時的 egress 與費用歸屬。
- **已經查到的事實**：Skill 規格的 `allowed-tools` 欄位目前只被套件驗證讀來顯示，沒有進入試跑的權限；試跑沙箱的工具是固定一組，沒有 MCP server，容器沒有外網；憑證不得出現在套件、Log、Trace（現行紅線）；創作提示明令模型不得捏造不存在的工具，所以在 ① 定下來之前，創作出的 Skill 不會寫任何 MCP 呼叫。
- **建議**：(a) 先做「宣告」——平台維護一份可引用的 MCP 工具清單（名稱、用途、參數摘要），創作提示只准引用清單上的名字，試跑時以替身回應並在輸出標明「此步驟需要 X 工具」；正式執行的憑證注入與 egress 另案。(b) 一步到位，沙箱直接掛 MCP server 與憑證——要同時動沙箱契約、egress 與計費，且把外部副作用帶進試跑。建議 (a)。
- **不決定的代價**：Skill 只能把「寄出」「上傳」「查系統」交回給人做，效用受限；同時創作提示會持續被要求「不要捏造工具」，兩邊拉扯。
- **決定之後誰動**：主 Agent 改創作提示與套件驗證（清單比對）；沙箱替身進 `apps/sandbox` 與 `run.mjs`；清單本身由負責人給。

以下三項來自非功能性需求的逐條對照（`03` §25），R-100 來自同時在線 1000 人的容量目標（`02:NFR-008`、`03` §26）。**都不擋封測**，但每一項不裁，對應的工作項就只能做到一半；R-96、R-97 也因容量目標多了一層要考慮。

### R-96 平台一天最多花多少錢，花完了怎麼辦

- **要決定的是什麼**：模型閘道全域每日總額的數值；以哪個時區計日；用盡時已在跑的 Run 怎麼處理；誰收到通知。
- **已經查到的事實**：每個 Run 有自己的 Virtual Key 預算，Credit 有三道閘，創作每場有上限；閘道另有一條全域每日總額（目前 50 美元，**以 UTC 日計**），量測時撞到兩次——撞到後每一筆呼叫都被拒。現在被拒時，能力服務回 503 並點名是平台總額用完，平台計數並觸發 critical 告警；創作的這一步不算步數、生成與條件建議告知沒有收費且現在重試也會被拒、評估判定記為失敗並在額度恢復後自動重判。Worker 每 5 分鐘讀一次閘道的本期花費與總額（重置時間是 UTC 午夜），花到八成時告警，讀不到超過 30 分鐘也告警。尚未做的是畫面上的恢復時間，以及平台 Agent 上限總和的檢查。數值寫在閘道設定，不在 `02`。平台自己的 Agent 各有每日上限（目前是每日報告與曝光審核助手，各 0.20 美元，營運者可在後台各自調到最多 5 美元，預設都停用），但沒有任何檢查要求這些上限的總和留在全域總額之內；Agent 一多，它們可以一起把全域總額吃光，使用者的呼叫就跟著被拒。Judge 評審團（預設關閉）開啟後，每次評估的判定費用成為三倍，同樣算在這個總額裡。
- **建議**：保留閘道全域總額當最後一道保險，數值寫進 `02` 新的成本條目；計日改用台北時間或在畫面上寫明 UTC；用盡時新呼叫回「今日額度已用完、明天幾點恢復」，已在跑的 Run 跑完當前這一步；達 80% 時告警給營運者（`03` HARDEN-009 落地顯示與指標的那一半）。平台 Agent 的每日上限總和不得超過全域總額的一個固定比例（建議 10%），登記時超過就拒絕啟動並點名。
- **同時在線 1000 人時**：匿名搜尋每次最多三次模型呼叫、目前沒有快取（`03` SCALE-008 會補），每日 50 美元的總額依這個人數必定撐不過一天；總額要依入口分開試算——匿名搜尋、創作、試跑、Judge 各自的每日上限與加總，其中一個入口燒完不該連帶停掉其他入口（`03` SCALE-020）。
- **不決定的代價**：保險絲存在但沒人知道它燒了；下一次燒斷時，使用者與營運者都會以為是模型壞了。
- **決定之後誰動**：主 Agent 改閘道設定、補告警與 `02` 條目。

### R-97 全平台同時能跑幾個 Run，滿了是排隊還是拒絕

- **要決定的是什麼**：平台全域的同時執行上限；滿了的時候建立 Run 是排進佇列還是立刻拒絕；一個工作區的負載能不能拖慢別人。
- **已經查到的事實**：每個工作區同時只能有 1 個 Run，次數配額與並行上限同一交易；沙箱節點以「執行槽」計遺留資源。全域沒有上限、沒有佇列深度的告警、沒有公平性的量測。
- **建議**：全域上限＝節點執行槽總數，滿了排入佇列並在畫面顯示前面還有幾個；佇列深度與等待時間各一條告警；公平性等真節點上線後用負載測試量（`03` HARDEN-023 同一批）。
- **同時在線 1000 人時**：每個試跑預設 2 vCPU／4 GiB，沙箱節點每台預設 2 個執行槽，部署文件寫的是第一批 1 台；`02:NFR-008` 的負載模型是 100 個 Workspace 同時要求試跑。全部同時跑需要約 50 台節點，所以實際要裁的是「同時跑幾個、其餘排隊等多久可以接受」——建議先定 20 個執行槽（10 台），尖峰時排隊，畫面顯示前面還有幾個，平均等待超過 10 分鐘時告警，再以負載測試與費用報價校準。
- **不決定的代價**：封測人數一多，沙箱節點被塞滿時的行為沒有人定義過，第一次發生就在使用者面前。
- **決定之後誰動**：主 Agent 補 `02` 容量條目與實作；量測等 `04` 甲類的節點。

### R-99 Trace 與 Run 產出的有效保存窗口不一致（②已裁定，見 §4）

- **要決定的是什麼**：Trace 按月整個分區丟棄，實際保存是 90 天到約 120 天，而 Run 產出精確 90 天——第 90 到約 120 天之間重新評估，會在「這個 Run 沒有產出」的前提下判定，正是 `02:NFR-002a` 第 2 條要避免的情形。
- **已經查到的事實**：保存下界的機器檢查比的是名目值，不是有效值；改任何保存期限都要重走法務確認（`02:NFR-002a`）。
- **建議**：Run 產出保存期改為「Trace 名目值＋一個月」，或讓 Trace 的月分區等該月所有 Run 產出都過期才丟；兩者擇一，檢查改比有效值。
- **不決定的代價**：每月有約一個月的窗口，重新評估的輸入是錯的，而評估紀錄只增不改。
- **決定之後誰動**：主 Agent 改常數、SQL 與檢查；同意書改期限要重走法務確認。

### R-100 平台壞一台機器時要不要停

- **要決定的是什麼**：控制平面與資料庫的部署拓撲。`02:NFR-008` 寫的目標是每月可用性 99.9%、任一節點故障 15 分鐘內自動恢復、資料最多遺失 5 分鐘；現行架構決策是刻意的單節點，資料庫壞了就全平台停到人工還原。兩者不相容，必須改其中一個。
- **已經查到的事實**：API、Worker、能力服務、PostgreSQL、監控都在同一台機器，每個只有一份，沒有資源上限；資料庫有約 60 秒的 WAL 封存、每日備份、每月還原演練；物件儲存用供應商的受管服務；架構決策列出的升級條件之一是「團隊至少有一名能負責 Kubernetes 升級的成員」，這是必要條件。程式面要能多開，還要先完成 `03` SCALE-004～007、009、015，與拓撲怎麼選無關。
- **建議**：分兩步，不上 Kubernetes。(a) 先把應用層變成可多開，兩台控制平面節點放在供應商的負載平衡器後面，各跑一份 API／Worker／能力服務，單一節點故障時流量自動轉走；(b) PostgreSQL 一主一備串流複寫，加一個自動切換的管理程式（三個小節點做共識），切換後應用自動重連。(b) 的維運成本是三台小機器與一套要演練的切換流程；不想自己維運，替代方案是供應商的受管 PostgreSQL，代價是資料不在自有節點、月費較高。
- **不決定的代價**：`02:NFR-008` 的可用性那一條永遠無法驗收；1000 人在線時一次資料庫或主機故障，就是全平台停機直到有人醒來處理。
- **決定之後誰動**：主 Agent 改寫架構決策中單節點與升級條件那兩段、部署組合與 runbook；開機器與付費由負責人。

### R-106 要不要把「結構化判斷」接成既有 Agent 的第二道訊號

- **要決定的是什麼**：供應商的 Decisions 介面（`/v1/decisions`）只回機率、選項與信心值，不產生文字。要不要把它接在既有 Agent 旁邊，當成多一道訊號，而不是取代 Agent；要接的話先接哪裡。
- **已經查到的事實**（量測皆經閘道，`tools/eval-regression/decisions-probe-results.jsonl`，腳本 `decisions_probe.py`）：
  - 判定：判錯樣本集 13 條條件各問 5 次，答對 55/65，每條 5 次的答案完全相同；現行 Judge 在同一集是 60/65（`judge-adversarial-results.jsonl`）。現行 Judge 唯一的判錯（`ja-02` c2，條件沒發生卻判過）它也判錯，信心 0.97，所以它壓不下同一類系統性偏誤；它另一個判錯（`ja-04` c1）信心只有 0.27，答對的信心最低 0.55。樣本太少，還看不出低信心能不能當成「要人看」的訊號。
  - 注入偵測：注入樣本集 12 個攻擊加 7 個無注入的輸出，各問 5 次「有沒有對評審、模型或 Agent 下指令」：抓到 11/12，0/7 誤報，每題 5 次答案相同。漏掉的 `inj-06` 宣稱有一個清單裡沒有的產出檔，不是指令，屬於產出清單比對的範圍。
  - 成本與延遲：160 次呼叫共 52,025 個輸入 token、0 個輸出 token，延遲中位數 0.29 秒、p95 0.38 秒；以同模型的輸入單價估算約 US$0.005，這個介面是否照該單價計費尚未查證。
  - 閘道：LiteLLM 1.101 內建的 `/openai/{path}` pass-through 不必改設定就能用；虛擬金鑰的模型白名單會檢查，但比對的是請求裡的原始模型名，閘道的角色別名在這條路由上不生效，換模型不再是改設定檔一行。**閘道把這類呼叫記成 0 元、0 token**，每日花費上限與金鑰預算都看不到它。
  - 只有一家供應商提供這種介面；依外部系統可插拔的原則，平台端要是一個 port，沒有 adapter 時這道訊號就是關的。
- **建議**：(2)。(1) 不接：維持現狀，成本為零。(2) 先接注入偵測：Go 在呼叫 Judge 之前，經 `apps/llm` 的新能力問一次「輸出有沒有對評審下指令」；判為真時，Run 結果與曝光審核的待審項目都標示出來，Judge 照常判定。花費由 `apps/llm` 回傳的輸入 token 依設定的單價計入平台帳本，不依賴閘道記帳；開關放在營運後台「平台設定」。(3) 在 (2) 之上再加 Judge 第二意見：它與 Judge 不一致且信心低於門檻時，把那條條件標成「需要人看」。先擴大判錯樣本集再量，量出門檻之前不做。曝光審核的預篩與創作試跑前的快速檢查都還沒量，這次不提。
- **不決定的代價**：判定提示照樣抵擋注入，但沒有一道和 Judge 用不同方式失效的第二道偵測；被說服的判定只能靠平台對引文的回驗抓到。
- **決定之後誰動**：選 (2) 由主 Agent 先改 `llm-internal.yaml` 契約，再做 `apps/llm` 的 adapter、Go 端的 port 與注入、帳本記帳、平台設定開關與突變證明；負責人不必動作。

## 2. 不是簽名，但在等人的三件事

**這一節排在所有簽名之前。** 它們不需要本頁的任何一項。

1. **一台節點真的被開出來。** 供應商與規格已定值（R-43），cloud-init 的輸入契約已定案（R-17c），三種角色的 IaC 都已進 repo 並在模擬環境跑到服役。**缺的是有人去把那台機器開出來**——`04` 甲類五項全部在等它，而甲類擋著封測。
2. **同意書送出去簽名之前，先走一次法務確認。** 三件真人動作有順序：①**法務再確認一次**——第一次已過關，之後同意書正文改過（保存期限、跨境傳輸、逃逸驗收揭露、刪帳號時回饋文字與只被自己試跑過的 Skill 內容一併刪除、Test Case 的刪除路徑、已刪除資料在備份裡最多再留 35 天），而那份文件自己的規則是**正文一改就要重走**，並明寫「在重新確認完成之前不得送交受測者簽署」；要看的五件與移交材料都已備妥（`04` 乙-16）。②**填入聯絡方式**——§9 的其餘佔位都已定值，剩下的是一個真人的姓名與信箱，不是一個決定。③**12 位受測者簽名。**
3. **`m5/ask-5.md` 的五個人。** 材料已備，由負責人自己去問。它是 M5 最貴的那個未對沖假設（「使用者搜不到會想要生成一個」）唯一的證據來源，而今天的證據量是零。

## 3. 一條刻意不動的線

**「先閘門、再封測」不重排。**

甲類與封測並行、M5 與 M4 並行這兩項決策已經拆掉兩條線性鏈，所以要明寫**第三條為什麼不拆**——否則下一個人看到前兩條被放行，會順手推這一條。三個理由沒有一個被時間侵蝕：

1. 在未結案的閘門上勾封測准入項，是把兩個相反結論寫進同一份文件。
2. **看過產品的人不能再當閘門受測者，反之亦然。**
3. 閘門驗的對象是搜尋與內容。

**第 2 條在單人團隊下還更硬**——兩場使用者研究並行不是排程問題，是主持人只有一個。
