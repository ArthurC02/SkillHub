### 0.3 這次重排推翻了什麼

**原本的 R-1「一次過完十項」把一個擋住整個量測的決策，和九個不擋任何東西的追認綁在一起排隊。**

這正是本專案在 M4 對帳時反覆找到的那個缺陷形態的**鏡像**：過去發現的是「**一段不需要決策的工作，被掛在一個真的要人拍板的東西旁邊一起等**」（丙-21、丙-25、丙-26 三次同型）；這一次是反過來——**一個真的擋事情的決策，被埋在九個不擋事情的追認裡一起等**。同一個病，方向相反，代價一樣。

`m4/README §5.3` 的「**先閘門、再封測**」**不重排**。

| PDM-006 | 三個保存窗口 | **追認發生在 2026-08-23**（上表），2026-08-27 只是補打 §9.1 的勾 |

**這一批的性質，一句話**：**十一列裡沒有一個值被改，程式碼與測試一行未動。** 追認補的是簽名——這正是 R-1b 開頭就寫著的那件事，它花了四天不是因為難。

**追認之後解除了什麼，以及沒有解除什麼**：

- **解除**：`02` 與 `m0` 對「是否已定案」的永久不一致。任何人回頭查一個值的來源，不會再落在一個未勾的方塊上。**這是 `04` 乙-9 唯一剩下的內容**，故同日結案。
- **解除**：[ADR-028](../adr/ADR-028-beta-admission-and-quota-enforcement-points.md) 決策 4 的「未追認的數字不得出現在畫面上」，對 PDM-010 的四個數不再成立。
- **沒有解除**：`RUN_QUOTA=off`（[ADR-055](../adr/ADR-055-the-run-allowance-is-turned-off-and-that-took-an-action.md)）。**解除的是禁令，不是開關**——本次封測畫面上仍然沒有額度可顯示，而理由從「數字沒簽名」換成「沒有東西在被強制」（`04` 乙-2：顯示跟著強制）。ADR-055「受測者不得被告知有額度」那一節逐字仍然成立。

**三列刻意不追認，各自在等不同的東西**（記在這裡，因為「整批」這個詞最容易吃掉例外）：

- **`PDM-007`**（Local Runner 首批 OS）：後 MVP，`m0/pdm-proposals.md` 從一開始就不涵蓋它，等的是需求訊號。
- **`PDM-009`**：產品面已於 2026-08-22 追認，**報酬金額與受測者簽署**仍等 R-2（`04` 乙-15）。
- **`SBX-002` 實測項**：它自己寫著「仍待實測：CLI 內建 Skill 與內建工具的裁減幅度」，而**那件事一次都沒有做過**。部分完成保持未勾（AGENTS.md）。**勾它的代價很具體**：harness 19.4K／次 API 呼叫的固定前綴是全表唯一真正的成本槓桿，勾掉之後不會再有人回頭找它。

**追認時查出三處記載錯誤，逐條記下來，因為三處都會讓下一個人做錯事**：

1. **`03` 的 PDM-006 那列寫著「Run、Trace、Artifact 的保存期限本身仍無值」——過期了。** 三個變數自 2026-08-23 起有值。已就地換成查證後的事實，並保留兩件仍然開著的：**Run 本身**沒有期限值；**Run Artifact 的 30 天違反 `02:NFR-002a` 第 2 條**——那是 R-11，**本次追認沒有回答它**，也是 `SEC-006` 至今不勾的真正理由。
2. **`m0` §9.1 的 PDM-008 第二列措辭比它的來源鬆**：它寫「source-available 打包政策已由負責人與法務確認」，而 §2 風險表逐字說的是「**放寬**需負責人與法務明確確認後才可改」。**法務是放寬的前置，不是維持保守預設的前置**——今天追認的是保守預設本身，只需要負責人。`04` 乙-10（anthropic-sa 法務終判）仍開著，不受影響。
3. **`01` §13 去向表的兩列 ID 是對調的**：「封閉測試人數」那列寫 PDM-010（應為 PDM-009）、「免費 Run 額度」那列寫 PDM-009（應為 PDM-010）。**兩列正好是本次追認要動的那兩列**，所以在寫下追認之前先改正——否則追認會被寫在錯的 ID 旁邊，而那比原來的錯更難查。

## R-19｜使用者自行匯入的 Skill 屬於哪一類，由誰決定（`04` 丙-76 的鄰居，`02:DISC-002` 類別維度）

**2026-08-28 新增，與精選層同一批查出來的，而兩者的結局不同**：來源層級今天上線了（`0042`），**類別沒有**，因為它卡的不是欄位是一個問題——`skill/discovery/http.go` 的停用理由逐字寫著：「the import path takes a package, not a category, and **a user-imported skill would have none at all**」。

**要決定什麼**：PDM-001 的三個類別（`documents`／`writing`／`data`）今天只存在於 `tools/content/seed-skills.json`，`skills` 表沒有這個欄位，`?category=` 回 400。要讓 `02:DISC-002` 的類別維度成立，得先回答「**不是策展來的那些 Skill，類別從哪來**」。三個答案落在三張不同的表，所以這不是實作者能挑的。

**已查到的事實**：

- 45 筆策展內容各有 `category`（`data` 25／`documents` 10／`writing` 10），從未跨過 API 邊界——`tools/content/import_seed.py` 只把它印進本地報告，`POST /skills/import/upload` 的 body 只有 zip bytes。
- `02:DISC-002` 的篩選維度表把類別的啟用條件寫成「需 CONTENT-003 先決定類別是否成為平台欄位，**以及使用者自行匯入的 Skill 如何取得類別**」——**後半句就是這一項，而它從 2026-08-15 寫下來到今天沒有被回答過**。
- 對照組：來源層級的啟用條件只有前半句（「產出至少兩種 tier 值」），所以它今天做得完而類別做不完。**兩個維度在同一張表上並列，讀起來像同一種阻礙，其實不是。**

| 選項 | 落點 | 代價 |
| --- | --- | --- |
| **(a) `skills.category` nullable，只有策展內容有值** | `skills`（同 `curation_tier`） | 使用者匯入的一律「未分類」。DISC-004 要求缺值顯示未知、不得推定，所以篩選器會長期有一個「大部分東西都不在任何分類裡」的狀態——**而那個狀態會隨封測使用者增加而變糟** |
| **(b) 索引期由模型判定，並標為模型產出** | `search_documents`（與 `tags`／`limitations` 同區） | 值錯了用 reindex 修、不用 migration（`0015` 自己的理由）。代價是**分類是模型寫的**，要在 UI 上標示，而 ADR-013 已經要求模型產出的文案必須標記——這條路是既有慣例的延伸不是例外 |
| **(c) operator 指派** | 同 `curation_tier` | 使用者內容永遠沒有分類，等於這個篩選器只對策展內容有效。**與 (a) 的差別只在誰按按鈕**，涵蓋率一樣差 |

**建議**：**(b)**。理由不是省事：這個維度存在的目的是**幫一個不知道要搜什麼的人縮小範圍**（`01` §1 的第一個問題），而 (a) 與 (c) 都讓「使用者自己帶進來的東西」永久缺席這個維度——**封測第一天起，缺席的比例只會上升**。(b) 的代價是誠實可揭露的（標成模型判定），而 (a)／(c) 的代價是一個會隨時間變大的空洞。

**不決定的代價**：低而確定。`02:DISC-002` 的類別維度**在此之前無法啟用**，那格停用控制項會繼續掛在搜尋頁上——而它的停用理由（「類別尚未存入平台」）是**真的**，所以不會像來源層級那樣變成一句不實陳述。**這一項不會腐爛，只是不會前進。**

## R-20｜北極星指標的「通過使用者驗收」是資料庫裡的哪一欄（`01` §11.1）

**2026-08-28 新增。這一項的特別之處是它擋住的東西比它看起來大**：`01` §11.1 的北極星是「**每週通過使用者驗收並完成打包的 Skill 數量**」，而**這個數字今天寫不出來，缺的不是資料是定義**。

**要決定什麼**：「通過使用者驗收」映到哪一個既有欄位。

**已查到的事實**：

- 「完成打包」那一半**查得到**：`download_records.downloaded_at` join `download_artifacts.skill_version_id`，逐週逐 Skill 算得出來。
- 「通過使用者驗收」**沒有任何欄位對應**。最接近的兩個都不是它：
  - `evaluations.overall`（`met`／`partially_met`／`not_met`／`undetermined`）是 **Judge 與規則的判定**，ADR-025 明文寫它不是使用者的。
  - `evaluations.feedback_helpful` 問的是「**這次判定有沒有幫助**」，那是漏斗第 4 段，不是「這個 Skill 通過了我的驗收」。
- `tools/analytics/` 目前只有 `funnel.sql` 一個檔，**沒有任何北極星查詢**。
- `01` §11 開頭自陳「這一節目前一個數字都沒有」，理由記的是「封測未開始」。**那個理由對七段漏斗成立，對北極星不成立**——就算明天有一百位受測者，這個分子仍然寫不出來。

| 選項 | 分子 | 代價 |
| --- | --- | --- |
| **(a) `overall = 'met'`** | 機器判定符合 | 最好算，**但它不是「使用者驗收」**，是平台自己的判定。ADR-025 明文劃過這條線，用它等於讓北極星量平台對自己的評價 |
| **(b) `feedback_helpful = true`** | 使用者說有幫助 | 是使用者的聲音，**但問的是評估報告有沒有幫助，不是 Skill 通不通過**。而且它只有回答的人才有值 |
| **(c) (a) 且有下載** | 機器判定符合＋使用者真的帶走了 | **「帶走」是使用者用行動表示的驗收**，兩半都有資料。代價是它比字面嚴格，會低估 |
| **(d) 新增一個明確的動作** | 使用者在評估頁按一個「這個可以用」 | 最貼字面，**但要新增 UI 與欄位**，而且會多一個沒人按的按鈕（`funnel.sql` 第 5 段的採用率今天是 `0 \| 0`，那不是缺陷是還沒有人按過） |

**建議**：**(c)**，並在報表列上明寫它是下界。理由：北極星的用途是**每週看一個數字判斷產品有沒有在前進**，(c) 的兩半都是既有事實、不新增任何要人按的東西，而且它量到的是**這條價值閉環真的被走完了**——`01` §4.2 的五項使用者成果，最後一項正是「一個可下載的標準套件」。(d) 更準但它把量測變成一個新功能，而**這一節今天連一個數字都沒有，先要有數字**。

**不決定的代價**：**這是全表唯一一個「封測開始也不會自己好起來」的**。七段漏斗有四段明天就能給數字，剩下三段是純 SQL；北極星不是——它在有人回答之前連分子都寫不出來，而它是 `01` §11.1 唯一的一列。**封測跑完之後回頭補，補到的是一份沒有北極星的封測報告。**

**決定之後**：一支 `tools/analytics/north-star.sql`，形狀照 `funnel.sql`（`\set` 區間、每列自帶精確度限制的 note），並補一支對真 schema 跑的整合測試——`funnel.sql` 的五支測試就是模板。

## R-21｜套件裡的巢狀壓縮檔要不要拒（PDM-005 §5.1b 說拒，程式沒有拒）

**2026-08-28 新增。這一項是程式自己記下來的，而它從未進過任何清單。** `apps/platform/internal/shared/skillpkg/archive.go` 的註解逐字寫著：巢狀壓縮**不拒**，而且「that one is **a real gap** rather than a resolved disagreement」。

**要決定什麼**：PDM-005 §5.1b 明訂「禁巢狀壓縮」，理由是它是繞過解壓上限的標準手法。程式沒有實作，理由也寫在同一段：**依副檔名拒絕會同時拒掉一個合法地把 zip 當範例資料附上的 Skill**。要嘛接受那個誤殺，要嘛承認這條禁令不做。

**已查到的事實**：

- §5.1b 的另一條（symlink 一律拒）**也沒有照字面做**，但那一條是**已解決的分歧**不是缺口：`04` 丙-15 D-3 裁定改為揭露，理由是該條的前提（TOCTOU）對這個實作不成立——**這個實作從不解析連結**，所以沒有 check 與 follow 之間的窗口。**巢狀壓縮沒有那樣的理由，它就是沒做。**
- 既有的解壓防護仍然在：解壓後總量 100 MB、2000 檔、深度 10、單檔上限，四道都有測試。**巢狀壓縮繞過的是「解壓後總量」那一道**——平台只解一層，所以內層的量不會被算進去。
- 45 個策展套件裡**有幾個真的附了壓縮檔**：**策展紀錄裡一個都沒有**——`tools/content/seed-skills.json` 與 [content-summaries.md](mvp/content/content-summaries.md) 全文沒有出現 `.zip`／`.tar`／`.gz`／「壓縮」任何一次（2026-08-28 查）。**這是紀錄層的答案不是位元組層的答案**：真正的答案要對 45 份套件的檔案清單掃一次，而那份清單今天只存在於物件儲存裡。**但它已經把「這條規則今天會不會誤殺我們自己的內容」的機率壓得很低。**

| 選項 | 內容 | 代價 |
| --- | --- | --- |
| **(a) 照字面拒**（依 magic bytes，不依副檔名） | 套件內出現任何壓縮檔即擋 | 誤殺合法的範例資料。**但 magic bytes 比副檔名準**，而這個 repo 的型別判定已經是 magic bytes（`filetype.go`） |
| **(b) 揭露不拒**（同 symlink 的處置） | 掃描出一個 finding，說出哪一個檔是壓縮檔 | 與 symlink 的處置一致、可解釋。**但它不擋那條繞過路徑**，只是讓人看得見 |
| **(c) 拒巢狀但放行「不會被解開的」** | 只擋平台自己會遞迴解開的形態 | **今天不成立**：平台根本不遞迴解開，所以這個選項等於 (b) 換一個說法 |
| **(d) 改允收** | 把 §5.1b 那一句收斂成「揭露」 | 與丙-74 同日的處置方式一模一樣（收斂允收句而不是改機制），**而丙-74 收斂得起來是因為責任有別的機制承接；這一條要先說出承接者是誰** |

**建議**：**(a)，依 magic bytes**。原本的建議是「先查那個數字再選」，而那個數字查了：策展紀錄裡零筆提到壓縮檔。**誤殺的對象目前是空集合，而繞過的路徑是實在的**——平台只解一層，內層的量完全不進 100 MB 那道閘。用 magic bytes 而不是副檔名，因為型別判定在這個 repo 已經是 magic bytes（`filetype.go`），而改副檔名是繞過裡最便宜的一種。<br>**選 (b) 也站得住**，它與 symlink 的處置一致；差別是 (b) 讓人看得見而不擋，**而這一條擋的是一個量的問題不是一個知情的問題**——一個讀者看見「這裡面有一個 zip」，仍然不知道解開之後有多大。

**不決定的代價**：中等，而且**與封測同時到期**。今天目錄是團隊自己收的 45 筆，沒有人有動機繞過解壓上限；封測第一天起匯入的是別人的套件，而這條路徑是**已知的、已被寫在自己程式註解裡的**繞過方式。**`04` 乙-23 那一列已經示範過同一種期限**：一個往下調的上限，代價在第一個超過它的封測套件進來之前是零。

## R-23｜Pitch 現場要不要能真的跑一次（[m6/report-sandbox-options.md](mvp/m6/report-sandbox-options.md)、`02:PORT-010`）

**2026-08-28 新增，2026-08-29 更新前提。** 本項原本寫著「M6 規劃出來的是唯讀的一半，`02:PORT-006` 明文把開始一次 Run 列為清單外」——**那兩句今天都不成立**：`PORT-006` 已撤回，而 [ADR-059](../adr/ADR-059-the-clean-mode-execution-driver-is-honest-about-not-being-a-sandbox.md) 開出了 `clean` 等級與本機行程 Driver，**策展過的展示素材可以在那台機器上真的跑完一次生命週期**（`PORT-010b`，尚未實作）。

**所以這一項要問的東西縮小了，但沒有消失**：現場能跑的是**策展素材**；**不受信任的內容仍然一律不行**，由派送閘門強制。要決定的是 Pitch 現場需不需要跑**觀眾當場出的題目**。

**要決定什麼**：Pitch 現場**需不需要跑觀眾當場出的題目**。這不是工程判斷——它取決於那場簡報要說服的是什麼。

**已查到的事實**：

- **沒有 PGlite 等價物，而卡住的不是隔離技術的品質。** 逐項查證見報告：白名單管的是哪顆 PE 能執行，**任何要你自己帶一顆 `.exe` 的方案都在門口出局**——包括 Windows 自己那套（Windows 建立 AppContainer profile 的那個 API 其實**不需要管理員**，微軟文件與 Chromium 的沙箱設計文件都這樣寫，但你得先有一顆 launcher）。
- **只剩兩條縫**，代價都不小：①瀏覽器分頁內的 WASM——**但能跑的那個 Python 沒有 subprocess、沒有 pip、沒有原生套件**，而沙箱裡實際要跑的是完整 Debian ＋ numpy／lxml ＋ `python foo.py`；②唯一通得出去的那條網路上的託管沙箱——**真 Debian、真 shell，但邊界不歸你管，而且資料離開機構**。
- **`02` §7 的 DoD 第一條**要求走完含「試跑」的六段。**一個不能試跑的 Skill Hub，示範的是它的搜尋引擎，不是它的價值主張。**

| 選項 | 內容 | 代價 |
| --- | --- | --- |
| **(a) 播放真實錄下的 Run，或以本機 Driver 現跑策展素材** | `02:PORT-007` 已允許取用 [m2 的 45 筆逐筆試跑](mvp/m2/content-baseline-report.md)、[m5 的生成基線](mvp/m5/)（20 份生成 Skill ＋人工判定） | **不需要沙箱，今天就能做，而且是真資料**。代價是現場不能改題目——問「那如果我要它做 X 呢」時只能說「這是我們跑過的」 |
| **(b) 先爭取多開一個網域** | 把 Run 送回自己的 gVisor 節點 | **隔離與生產一模一樣、不必生第二套安全論述、資料不離開機構。** 這是**一次行政溝通**，其他每一條路都是一套要維護的新架構。代價是它可能被拒絕，而被拒絕之前不知道 |
| **(c) 用託管沙箱** | 走那條唯一通的路 | 機器上什麼都不裝，跑真的任意程式碼。**但邊界的所有權不在你手上，且不受信任的內容與測試資料會送出機構**——在金融機構這一條可能比技術問題難過 |
| **(d) 瀏覽器內 WASM 現場跑** | — | **要縮小「不受信任的 Skill」的定義到沒有 subprocess／沒有 pip／沒有原生套件——那等於改產品。** 不建議 |

**建議**：**(b) 先問，(a) 同時做。** 兩者不互斥，而且 (a) 的成本已經沉沒——那些 Run 都跑過了。(b) 的價值不只在 Pitch：它同時解掉 `01` §10 那三條 ⛔ 邊界背後的同一個東西。

**不決定的代價**：**中等，而且會晚一步才痛。** M6 不會停住（唯讀那一半的規格都寫好了），但**如果 Pitch 前一週才發現簡報需要現場跑一次，(b) 那條行政路徑已經來不及了**——它的前置時間不由我們決定。

**✅ 2026-08-29 負責人答覆：(b) 否決——防火牆無法多開網域。** 同時給了三個之前沒有人問出來的事實，而它們的方向與 (b) 相反：

## R-24｜Langfuse 要不要做：做／不做／縮限（ADR-017 的另一半）

## R-25｜purge 與資料庫層的清除權限屬於誰（要不要對 API 角色收回 DELETE）

**2026-08-29 新增。**

**要決定什麼**：`cmd/maintenance` 的七個 purge 子命令用的是與 API 相同的資料庫角色，**所以那個角色對每一張表都有 DELETE**。要不要把清除工作拆到一個獨立角色，並對 API 角色收回（SQL 的 revoke）它不該有的刪除權？

**已查到的事實**：

- **清除路徑是這個系統唯一會不可逆地銷毀使用者資料的東西**，而它今天與服務請求的路徑共用同一組憑證。
- **既有的紀律走的是另一條路**：不可變性由 migration `0005_immutability.sql` 的 trigger 強制（`UPDATE skill_versions` 會失敗，`devctl automation-check` 有 `immutable table write` 檢查器在守），**那是資料庫層的強制，而它有效**——M6 的整個資料庫候選判準（判準一）就建立在它身上。所以「用資料庫權限擋」在這個 repo 不是新概念。
- **代價落在部署與淨測試模式**：多一個角色就多一組憑證要保管，而淨測試模式（`PORT-010`）只有**一條連線**，多角色在那個形態下要嘛不成立、要嘛要一個例外。
- **今天沒有已知的濫用路徑**：`OPERATOR_USER_IDS` 目前只會是負責人自己，而 API 沒有任何端點會整批刪。

| 選項 | 內容 | 代價 |
| --- | --- | --- |
| **(a) 拆角色 ＋ 收回權限** | maintenance 用自己的角色；API 角色對 append-only 表收回 DELETE 權限 | 縱深最好，且與既有的 trigger 紀律同源。**淨測試模式要一個明文例外** |
| **(b) 明文不拆** | 寫下「單一角色是刻意的」與它的補償控制（trigger、audit、單人團隊） | 成本零。**但它要被寫下來，否則下一個人會以為沒人想過** |

**建議**：**(b)，但要寫下來。** 封測是 12 個人、operator 是一個人，(a) 的縱深買不到相稱的風險降低，而它會在淨測試模式上撞出一個例外——**而例外正是這份 repo 反覆記載的那種東西**。MVP 之後、第一次有第二個 operator 時重開。

**不決定的代價**：低。**但它與 R-21 是同一種**：一個沒有人想過的可能，和一個想過並拒絕的可能，在文件上長得一模一樣。

## R-26｜策展的範例 Dataset 事實上永遠到不了下載者手上（`02:PACK-001` 第 5 條、`CONTENT-007`）

**2026-08-29 新增，由稽核逐行追出來。這一項不是缺陷回報，是一條允收準則今天不可交付。**

**要決定什麼**：`02:PACK-001` 第 5 條寫「使用者可選擇是否包含**可散布的** Test Case 與範例資料」，第二層表格明列「平台策展產生的範例 Dataset」可以進包。**實際上這條路只有 operator 走得通。** 要嘛改機制，要嘛把允收縮回它實際成立的範圍。

**已查到的事實**：

- `skill/delivery/testcase.go` 的 `selectTestCases` 判準是 **`ws.IsCatalog`**：非策展工作區的每一個 Test Case 一律排除，理由碼 `not_curated` 或 `user_uploaded_dataset`。
- `delivery/packaging.go` 的 `Plan` 讀 skill／version 都用**呼叫者自己的個人工作區** ID。所以只有**目錄工作區的擁有者（operator）**打包時 `ws.IsCatalog` 才為真。
- 一般使用者要拿到策展 Skill 只能先 Fork（`library/registry.go`），**Fork 進的是個人工作區，於是 `IsCatalog = false`**。
- 結果：一般使用者拿到的永遠是 `include_test_cases=true` 加一份「not_curated」的排除清單。**M2 為 45 個精選做的範例資料，對下載者是零價值**，而 `CONTENT-007` 的允收理由逐字就是「供 `PACK-001` 選用」。

## R-30｜`packaged_at` 這個欄位名說的不是它裝的東西（`download-manifest.schema.json` 已是 1.1）

**2026-08-29 新增（A5）。低優先，但它是一個契約問題不是一個註解問題，所以放在這裡而不是只放 `04`。**

**要決定什麼**：交付物 manifest 的 `packaged_at` **裝的是來源版本的建立時間**（`delivery/packaging.go`：`p.Version.CreatedAt`），不是打包發生的那一刻。要改名（＝ schema 變更），還是改描述並留著這個名字？

**已查到的事實**

- **值是刻意的，不是 bug。** 它必須是**決定性的**：同一個版本重打兩次要得到同一份 manifest。若它是「打包的那一刻」，兩次 byte-identical 的建置就會有不同的 manifest——而 `manifest_hash` 存在的整個目的正是回答「這兩包的**內容**是不是一樣」。schema 自己在兩處長描述裡把這件事寫清楚了。
- **A5 已修掉會誤導的註解**（`delivery/export.go`），並在原地寫明「這個欄位該不該叫 `packaged_at` 是一個命名問題」。**程式面到此為止是誠實的。**
- **改名的代價是 schema 版本**：`contracts/packaging/download-manifest.schema.json` 目前是 **1.1**，而 `packaged_at` 在 `required` 裡。改名 ＝ 對已下載過套件的人破壞相容。
- **不改名的代價是誤讀**：讀 manifest 的人（**包括不會來讀 schema 描述的下游工具**）會把它當成打包時間戳。這是 `NFR-001`「UI 不得誤導」在交付物上的同一條紀律——只是這一次讀者不是使用者，是拿到 zip 的人。

| 選項 | 內容 | 代價 |
| --- | --- | --- |
| **(a) 不改名，改 schema 描述**（建議） | `description` 一句話說明它是**來源版本的建立時間**與**為什麼必須是決定性的** | 成本近乎零、不破壞相容。**代價是名字仍然會被瞄一眼的人讀錯**——但瞄一眼的人本來也不會讀描述 |
| (b) 改名為 `source_version_created_at` 之類 | 名實相符 | **schema 破壞性變更**（1.1 → 2.0）＋ 產生器、測試與已發出的套件三邊不同步 |
| (c) 兩個欄位都給 | 保留舊名、加新名 | 最糟：**兩個欄位裝同一個值**，而下一個人要決定信哪一個 |

**建議**：**(a)**。這個欄位的**值是對的、理由是硬的**，錯的只有名字，而名字的破壞成本高於它造成的誤讀。**若日後 schema 因別的原因走到 2.0，這一項應該搭那班車**——記在這裡就是為了那時候不必重新查一次。

**不決定的代價**：低而持續。**讀 manifest 的人會推論出一個時間戳，而那不是它說的那個東西**；今天唯一擋著這個誤讀的是 schema 裡的兩段長描述，而 `04` 已經為「宣告了卻沒有消費端／說了卻沒人讀」這個形狀記過三次。

**決定之後**：(a) 動一行 `description`（`contracts/` 由主 Agent 序列化）；(b) 要同一批動 schema、`manifest.go` 的 struct tag、`packaging.go` 的賦值與 golden test，**並且要一支斷言舊名不再出現的測試**。

## ~~R-31~~｜三個 judge／旗艦層的取樣事實上沒有被釘住，而 ADR-026 的前提建立在它被釘住 — ✅ **已裁定 2026-08-30：(a) 承認，並讓紀錄說實話**

## ~~R-32~~｜淨測試模式的節點該怎麼宣告自己的出口（今天它只能說謊或不跑）— ✅ **已裁定 2026-08-30：(a) 抄資源上限那個形狀**

## ~~R-3~~｜`skills.redistribution` 的寫入路徑（`04` 乙-17）— ✅ **三個子項全部裁定完畢**（R-3c 2026-08-23；R-3a／R-3b 2026-08-27 → [ADR-057](../adr/ADR-057-releasing-content-takes-named-evidence-not-a-button.md)）

**先講一件會改變這一項急迫性的事**：[ADR-045](../adr/ADR-045-self-supplied-content-is-not-redistribution.md)（2026-08-23）已經把最痛的那一半移走了——**使用者現在下載得了自己上傳的 Skill**（匯入時直接寫第四個值 `self_supplied`，不需要任何人去改任何東西）。

所以這一項剩下的是**別人的內容**：誰能把它標成可散布、要什麼證據。**沒有人在等它才能用產品**，但治理強度的不對等每天都在跑。

### R-3a｜誰能改 ✅ **已裁定（2026-08-27）：只有 operator** → [ADR-057](../adr/ADR-057-releasing-content-takes-named-evidence-not-a-button.md) 決策 1

| 選項 | 代價 |
| --- | --- |
| **(a) 只有 operator** | 使用者匯入第三方內容而授權判定不足時，他看到的是「你的 Skill 不能下載」而**沒有任何自助路徑**。以現況的 `unknown` ＝ 擋為預設，這會是常態 |
| **(b) Skill 擁有者對自己匯入的內容也能改** | 把一個**授權判定**交給沒有義務做那個判定的人。ADR-021 §5.3 記著本次查核最重要的單一發現：**兩個 repo 的根目錄 `LICENSE` 是合法的 MIT 檔，但它涵蓋的內容並非該作者所有**——「repo 根有 MIT ⇒ 子目錄是 MIT」是錯的，**而且錯在放行方向** |

**建議 (a)**，理由不是保守而是 §5.3 那個發現：**這個判斷連做過查核的人都會錯，交給按下按鈕的人不會更準。** (b) 的真實需求訊號要等封測——`N-2` 的第一個訊號就是它。

**✅ 2026-08-27 取 (a)。程式一個字都沒有改，因為路由從 2026-08-23 起就是 operator-only**——當時取窄的理由是「之後放寬是加呼叫者，先放寬再收回是拿走東西」，**那是一個暫代的形狀，不是一個決定**。本次把它變成決定。
**(a) 的代價照樣要付，寫在 ADR-057 決策 1 而不是消失**：使用者匯入第三方內容而授權判定不足時，沒有任何自助路徑，而以 `unknown` ＝ 擋為預設，這會是常態。

### R-3b｜改成 `allowed` 要什麼證據 ✅ **已裁定（2026-08-27）：具名證據，且必須與凍結快照相符** → [ADR-057](../adr/ADR-057-releasing-content-takes-named-evidence-not-a-button.md) 決策 2～4

**ADR-021 已經給了一半判準**：誤判必須錯在**擋**的方向。所以「放寬的門檻不能只是一個按鈕」不是意見，是那條規則的直接推論。

**建議**：沿用 ADR-021 已經定義的**來源層級（license source tier）**——要把一個 Skill 從 `unknown` 改成 `allowed`，必須附上**該層級可接受的證據**，而不是一個確認框。這不需要新的概念，只需要讓端點要求它。

**✅ 2026-08-27 依建議落地，而落地時長出三件建議裡沒有的東西：**

1. **證據不只是「附上」，是要能被平台當場否定。** 請求帶的 `license_expression` ＋ `license_source` 必須**與該 Skill 最新版本凍結的快照相符**；不符就拒絕，並在訊息裡說出快照記的是什麼。**這道檢查買到的不是「證明」，是「可以被反駁」**——一個確認框沒有任何人能說它填錯了。
2. **三種拒絕刻意是三句不同的話**：沒填（漏填）／**快照什麼都沒記**（重新匯入才有）／填了但不符（在描述另一個套件）。壓成一句「授權證據無效」，會讓中間那一個讀起來像表單錯誤，**而它是唯一一個不該被繞過的**。
3. **稽核記的是快照的值，不是操作者打的字。** 這一條是**測試先發現的**——第一次跑就以 `MANIFEST` 進了 audit，而「所有以 `repo-license-file` 為據放行的 Skill」那句 SQL 比不到那一列。

**只有 `allowed` 要證據**：為了「擋」而先做一次授權判定，等於**對「拒絕做判定」收費**，而 ADR-021 §5.3 說誤判必須錯在擋的方向。

**沒有做而且刻意留著的兩件**（ADR-057「已知邊界」）：判定黏在 Skill 上，**日後匯入的新版本不會使它失效**；`repo-license-file`（正是 §5.3 誤判的形狀）**仍可作為放行依據**——先讓上面那句 SQL 查得出來，再決定要不要禁。

### R-3c｜治理強度 ✅ **已落地（2026-08-23），這一格不再等任何人**

`redistribution` 是**全庫唯一一個沒有稽核就能改的閘門欄位**——`access_restriction` 有 `PUT`／`DELETE /admin/skills/{id}/restriction` 與 audit event，這一個只能直接跑 SQL。

**兩道鎖擋的是同一件事，而治理強度差一整級。** 加端點與 audit 的技術補法很小（沿用 `SEC-011` 同一組形式），**而且它不依賴 R-3a 的答案**——不論最後是誰能改，都應該留下紀錄。

**已補**：`PUT /admin/skills/{id}/redistribution`——operator-only、`note` 必填、before／after／note 與欄位寫入**同一個交易**（稽核 action `skill.redistribution_set`），沿用 `access_restriction` 的同一組形式。

**它刻意沒有回答 R-3a 與 R-3b**，而這一點值得寫下來：路由取 operator-only 是因為那是 R-3a 兩個選項裡**較窄的那一個**——之後放寬是加呼叫者，先放寬再收回是**拿走東西**；請求帶的是自由文字 `note`，**不是 R-3b 可能會要求的來源層級證據**，因為**半套的證據要求讀起來和整套一樣**，那個誤會比缺一個端點貴。

**順帶多了一個守門**：`self_supplied` 不接受。0036 定義它是「誰帶進來的位元組」這個**事實**、由匯入路徑建立，不是任何人能斷言的**判定**——接受它等於讓 operator 用「這是擁有者自己的內容」把別人的內容放出去。反方向（`self_supplied` → `blocked`）允許，因為擁有者自己上傳的東西仍可能是平台必須停止交還的。

**原本的「不決定的代價」**：一個閘門欄位可以被沒有紀錄地改動，而它決定的是「內容能不能交出去」。**這一句現在不成立了。**

## R-8｜產品願景那句話還剩四個動詞，而現在做的是五個

**要決定什麼**：`01` §3 的長期願景是「成為個人與團隊**探索、驗證、改善及發佈** Agent Skill 的可信任基礎平台」。M5 加了第五個動詞——**生成**——而且已經全面開工（ADR-046／052／054）。願景句要不要納入它？

**已查到的事實**：

- `01` §7.3 已經正確處理了範圍層：「從零生成 Skill」列在「MVP 不包含」，並明文寫著**那是時程不是永久排除**。所以**範圍沒有矛盾，矛盾在定位句**。
- 生成入口已經在畫面上（旗標後面，[資訊架構 §2.4](../design/information-architecture.md)），程式面不等定位句。
- ADR-046 決策 2 已經替生成物劃了一條線：**不進公開目錄、不進搜尋索引**。

**這不只是加一個詞。** 前四個動詞的受詞都是**別人寫的 Skill**，第五個的受詞是**平台自己寫的**。「可信任」在這兩種情況下要證明的東西不一樣：

- 對別人的 Skill，可信任 = 來源可追溯、授權清楚、有試跑證據（現行三層內容策略＋信任三軸）。
- 對平台生成的東西，可信任 = **誠實說出它沒有那些**。`02:GEN-004` 已經要求詳情與列表寫出「沒有經過任何人工檢視、沒有任何試跑證據」，`01` §12 最後一列也把它列為風險。

**建議措辭（三選一，不是我來選）**：

| 選項 | 措辭 | 代價 |
| --- | --- | --- |
| (a) 納入，並列 | 「探索、**生成**、驗證、改善及發佈」 | 最直接。但把生成放在驗證**之前**，讀起來像在推薦「先生成再說」，與 ADR-046 決策 7「先搜尋、搜不到再生成」的產品主張相反 |
| (b) 納入，但附屬 | 「探索、驗證、改善及發佈 Agent Skill——**必要時從任務描述生成起點**」 | 措辭保住了決策 7 的順序。長一點 |
| (c) 不納入 | 維持四個動詞 | 表示生成永遠只是探索失敗的補救、不是產品主張之一。**這也是一個立場，只是要有人說出來**——目前的狀態是沒人說過，而不是選了 (c) |

**⚠️ 2026-08-29 一則必須記下來的誤植，因為它差一點讓這一項被當成已簽**：負責人當天的裁示訊息把「Run Artifact 與 Trace 保存期統一為 90 天」寫成 **R-8**，而**那個內容對應的是 R-11**（保存期限），不是本項（願景句）。**本項至今未簽，狀態不變。** 記下來的理由與這一頁存在的理由相同——`04` 乙-24／乙-25 的教訓逐字是「殘項清單漏掉的不是難的事，是不在清單上的事」，而**一個被別人的編號蓋掉的待簽項，比一個沒人提過的更難被發現**：它看起來像已經處理過了。

**不決定的代價**：低，但會持續累積成同一種東西。願景句是新加入者（人與 Agent）讀的第一段，也是 ADR-038 §3 規則 5「新產品用語必須先能回對 `01` 的使用者成果」所指向的那份文件。**生成現在回不到它。** 於是每一份談 M5 的文件都要自己解釋一次它為什麼存在——這正是本專案反覆出現的「一個事實好幾份定義」的上游。

## ~~R-9~~｜M5 生成額度的四個數字（`04` 乙-22）— ✅ **已追認 2026-08-27：照提案值**

**2026-08-23 新增。** 這一項與其他九項不同的地方是：**它今天不擋任何人**，因為 `GENERATE_QUOTA=off`（[ADR-056](../adr/ADR-056-the-generation-allowance-is-its-own-switch-and-it-is-off.md)）。它進這份清單的理由是**這份文件是「我現在要簽什麼」的唯一入口**，而 `04` 乙-22 記著一個等簽名的東西——一個只活在另一本帳裡的簽名，就是 `QA-008` 那個病。

**要決定什麼**：生成額度的四個數字。`policy.DefaultGenerateQuotaLimits()` 目前給 **每日 10／每窗 30／首窗 20／窗長 30 天**，四個全部標「待追認」。

**已查到的事實**：
- 一次生成實測 **$0.00553**（預設 mini）與 **$0.1186**（flagship，~~$0.113~~ 是 spike 報告訂正前的數），見 [m5/report-generate-baseline.md](mvp/m5/report-generate-baseline.md)。
- 一次 Run 的閘道實付**中位數 $0.0382**（ADR-055 訂正後）。**生成比試跑便宜一個量級。**
- PDM-010 §8.1 只給了 Run 的數，生成當時還不存在。

**建議**：**照提案值追認**。每日比 Run 的 5 高，理由是使用者不滿意會改寫描述再跑一次；每窗不高，理由是生成不該取代搜尋。

**不決定的代價**：[ADR-028](../adr/ADR-028-beta-admission-and-quota-enforcement-points.md) 決策 4 允許強制點先建，但**禁止未追認的數字出現在畫面上**。`02:GEN-001` 要求生成前顯示「本次將消耗的額度」——**那句話在追認前不能顯示額度**（成本那一半也還顯示不出——見 R-10）。`off` 之下這條自動成立，**但開關一旦打開，這個限制要有人記得**。

**✅ 2026-08-27 追認：每日 10／每窗 30／首窗 20／窗長 30 天，照提案值，`04` 乙-22 結案。**

**依據沒有重新推導，讀的就是 `generate_quota.go` 註解裡已經寫好的三個數**——生成實測 $0.00553（mini）與 $0.1186（flagship），Run 的閘道實付中位數 $0.0382。**這正是 [ADR-056](../adr/ADR-056-the-generation-allowance-is-its-own-switch-and-it-is-off.md) 決策 3 把估算依據寫進程式碼的目的**：讓追認是複審而不是重來。`policy.DefaultGenerateQuotaLimits()` 與它的四個常數**一個值都沒有改**。

**追認解除的是一條禁令，不是一個開關**——這個分別是本項唯一容易被讀錯的地方：

| | 追認前 | 追認後 |
| --- | --- | --- |
| ADR-028 決策 4「未追認的數字不得出現在畫面上」 | 對這四個數成立 | **不再成立** |
| `GENERATE_QUOTA` | `off`（ADR-056 決策 4） | **仍然 `off`** |
| 畫面上有沒有額度可顯示 | 沒有 | **仍然沒有** |

**所以 `02:GEN-001` 的「本次將消耗的額度」今天還是空的，但理由換了**：不再是「數字沒有簽名」，純粹是**沒有東西在被強制**——`04` 乙-2 的既有紀律（顯示跟著強制），不是本次追認的遺留。成本那一半已於 2026-08-25 補上（R-10 已關閉，畫面印「約 US$0.003–$0.03」）。

**上面那句「開關一旦打開，這個限制要有人記得」現在可以放下**：開關打開時，數字已經有簽名了。這一項當初進清單的理由——「一個只活在另一本帳裡的簽名就是 `QA-008` 那個病」——**在它自己身上驗證了一次**：它躺了四天，而它本來就不擋任何人。

## ~~R-10~~｜生成前的「預估成本」：單價、上限，還是一個有出處的區間（`04` 丙-53）— ✅ **2026-08-26 關閉：它等的是資料不是簽名，資料已進來**

**2026-08-24 新增。** `02:GEN-001` 逐字要求「生成前顯示預估成本」。畫面上現在有三個**被強制的界**（描述 4,000 字、推理加輸出 16,000 token、最多嘗試 2 次，副本由 `one-number:` 機械比對），成本的位置印的是 `尚未定值`。

**要決定什麼**：那個位置怎麼變成一個金額。三條路，**前兩條要簽名，第三條要資料**：
- **(a) 把單價釘進部署設定**——一個每千 token 的輸入／輸出單價（今天連 `GENERATE_SKILL_MODEL` 都不在 `.env.example` 裡，只在 `generate.py` 的 `os.getenv` 預設），由它與三個界算出「一次最多約 $X」。**平台因此對一個會變的供應商數字背書**；漂掉時要出聲（設定與閘道回報的 `usage.cost_usd` 對不上就記一筆）。算出來的也只是**估計的上界**，不是被強制的上限——輸入界是 runes 不是 token、且不含 system prompt。
- **(b) PDM 給一個每次上限並強制它**——「一次生成最多花 $X」，超過即停。那才是一個被強制的數字，但要有人簽，而且強制點要寫（今天沒有）。
- **(c) 照 Run 的既有形式：一個有出處的區間＋一句 basis，標示「估計值，非報價」**——`RunPreflight` 就是這樣做的（`preflight.go` 的三個量測常數 `$0.01／$0.06／$0.30`，`Basis` 開頭寫「估計值,非報價」），而 [m0/pdm-proposals.md](mvp/m0/pdm-proposals.md) 的 PDM-005 §5.3 **接受了這個形式**。它**不需要任何人簽名**。**今天做不到的原因是資料**：B 輪只記下 mini **每次平均 $0.00553**（[m5/report-generate-baseline.md](mvp/m5/report-generate-baseline.md) :7、:80），沒有逐次分布，印不出區間；印平均值當預估就是 `04` 丙-53 說的那種承諾。

**已查到的事實**：
- flagship 每次 **$0.1186**（B 輪，[report-generate-baseline.md](mvp/m5/report-generate-baseline.md) :80；spike 報告的 08-23 訂正是 A 輪的 $0.1184）。R-9 與 `04` 丙-53 先前寫的 $0.113 是 spike 報告**訂正前**的數。
- Run 那一側的「預估成本」是**量測分布**（45 次，中位 $0.0566／均 $0.0702／最大 $0.2367）寫成三個常數加來源句；它**不是**上限——`preflight.go` 自己逐字這樣寫。Run 另有一把帶 `max_budget` 的短效 key，那是另一件事。
- `04` 乙-2 與設計系統 §2.2：**沒被強制的數字不得出現在畫面上**——而 (c) 的形式已被接受為例外：**有出處、標示估計值、不進 `summary_hash`**。

**2026-08-25 訂正一個會讓建議 (c) 落空的前提**：這一項一直寫著「成本分布是丙-56 那次呼叫的**副產品**」，而**在同日之前那不成立**——`GenerateSkillResponse.Usage` 一直存在，`generate.go` 從來沒有讀過它，每一次生成的成本在 `generateOnce` return 之後就地蒸發。**丙-56 就算今天跑完，也不會留下任何一筆逐次成本。**同日補上兩半（失敗寫進 `skill.generate_failed`（**2026-08-26 訂正拼法**：常數是 `audit.ActionSkillGenerateFailed = "skill.generate_failed"`，底線不是點；照這一頁原本的拼法去查 `audit_events` 會查到零筆，然後看起來像沒有在記）、成功寫進它那一列 `skill.import` 的 metadata），**兩半必須同時有**：只有失敗那半的話，分布全部來自「付了一通、然後沒能打包」的呼叫，而成功的可能付了兩通，用它估成本會系統性低估。**建議不變，前提現在才真的成立。**

## ~~R-15~~｜`QA-008` 的最後一格：macOS runner 要不要加（ADR-036 待決策 1）— ✅ **已裁定 2026-08-27：不加**

**2026-08-26 新增，理由與 R-14 同**：[ADR-036](../adr/ADR-036-real-browser-verification-tier.md) 待決策 1 逐字寫著
「**在做這個決定之前 `QA-008` 不得勾選**」，而那句話寫在 ADR 裡，不在這一頁上。

**要決定什麼**：`.github/workflows/ci.yml` 的 `web-browser` 矩陣要不要加 `macos-latest`。

**已查到的事實**：

- **矩陣已經有四格**：ubuntu × chromium／firefox／webkit ＋ windows × chromium。`QA-008` 的
  「主要瀏覽器」那一半**已經滿足**，剩下的是「目標作業系統」。
- **windows 那一格是有理由的**：`system-ui` 在 Windows 解析成 Segoe UI、在 Linux runner 上是 DejaVu／Cantarell，
  換行寬度不同；Windows 的傳統捲軸吃 15–17px 版面，macOS 與 Linux 的覆蓋式捲軸吃 0。
  **一個在 Linux 上不橫向捲動的頁面，在 Windows 上可能會捲。**
- **macOS 那一格買不到它看起來買得到的東西**：Playwright 在 macOS 上跑的一樣是**它自己編譯的 WebKit**，
  「真 Safari」不在任何一格裡，加了也不在。它真正多出來的是第三種字型度量（SF），
  而捲軸行為與 Linux 那一格相同。
- **價格**：macOS runner 計價是 Windows 的 5 倍（相對 Linux 的 10 倍）。

**建議**：**不加，並把這個「不加」寫成 ADR-036 的補記，然後勾 `QA-008`。**
理由不是省錢：**這一項的字面判準是「主要瀏覽器與目標作業系統」，而目標作業系統的兩個會影響版面的變因
（字型度量、捲軸佔位）已經各有一格覆蓋到極值**——Windows 是捲軸佔位的那一端，Linux 是不佔位的那一端，
macOS 落在已被覆蓋的那一端。**買第三種字型度量要付 5 倍價，而它與已有兩格不構成新的失敗模式。**
**若裁定「加」，那也是一個合法的答案**，只是要接受它買不到真 Safari，並把這句話寫進 job 註解。

**✅ 2026-08-27 裁定：不加，矩陣到此為完整。** ADR-036 待決策 1 已回填理由與重評條件，`03:QA-008` 同日勾選。**要寫清楚它沒有買到什麼**：加 macOS 也得不到真 Safari（Playwright 在 macOS 上一樣是自編 WebKit），所以那個缺口不是被這個裁定關掉的，是被寫明它關不掉——**它要換驗證層的形態才關得掉，不是換一格 runner**。

**~~不決定的代價~~**：`QA-008` 結構上不可勾，而 `RELEASE-001` 把 `QA-008` 列在自己的不勾理由裡。
**注意這一項與其他各項相反的地方**：不決定不會讓任何東西壞掉，**但它會讓一個已經做完 4/5 的東西永遠記成沒做**。

## R-17｜閘門 A 探針寫出來之後，發現驗收表有三個地方沒有辦法照字面執行（`04` 甲-1／甲-4）

**2026-08-27 新增，由兩件實際跑起來的東西查出**：[T5 網路實驗室](mvp/m4/sec-009-acceptance/2026-08-27-nested-dev-container-t5/)與[閘門 A 節點准入探針](../../tools/sec009/t8-node-probe.py)。**三項都不是「還沒做」，是「照字面做會得到一個沒有用的結果」。**

### R-17a｜`C-01` 的執行期半邊，閘門 A 看不到，而 `unknown` ＝ fail ⇒ **一台完全正確的節點也會紅**

**事實**：`C-01` 是「每個 Run 使用獨立環境與獨立暫存工作區，**不與其他 Run 共用可寫路徑**」——後半句是一個關於**兩個並行 Run** 的敘述。閘門 A 拍的是**一台還沒有任何 Run 的閒置節點**的照片，那半邊在那個時點不存在。ADR-022 §2 的覆蓋表把 `C-01` 整條指給 `T8`。

**後果不是理論的**：探針照 ADR-022 的 fail-closed 規則把它報成 `unknown`，而 `unknown` 視同 fail，所以**探針對一台設定完全正確的節點也會 exit 2**。**一個永遠紅的閘門，第一週就會被值班的人關掉**——那比沒有閘門更糟，因為關掉之後沒有人記得它曾經該擋什麼。

**建議**：把 `C-01` 拆成**宣告面**（閘門 A：sandbox runtime 有註冊、沒有共用的可寫 host 掛載、每 Run tmpfs 的設定存在）與**執行期**（`SBX-005` 的整合測試，那裡真的有兩個 Run）。**兩邊都要有承接者，不是把後半句刪掉。**

### R-17b｜`T5-5` 的節點 loopback 這一項，**在結構上留不下 nftables 紀錄**

**事實（實測，不是推論）**：從沙箱送往 `127.0.0.1` 的封包**不會離開那個 namespace**；即使在沙箱側加一條 `via` 節點的路由、兩側都把 `route_localnet` 設成 `1`，再在 `prerouting` 掛一條 raw 優先權的計數規則，**計數仍然是 0**——封包連 nftables 都沒進到。forward 鏈裡那條 `ip daddr 127.0.0.0/8 drop` 對這個方向永遠不會觸發。

**而 T5 的判準寫著**：「每一次嘗試都要在 nftables 記錄中留下一筆 drop，**沒有記錄 ＝ N-06 未成立，即使流量確實被擋**」。照字面，這一項永遠是 `unknown`，也就是永遠 fail。

**建議**：為這一項寫一個**具名例外**——判準改成「被拒絕，**且**沒有任何 nftables 計數器動過（即拒絕發生在核心路由層）」。腳本已經按這個形式實作（評分等級 `kernel`），**它是一個可以被推翻的斷言**：哪一天有東西計到了，那一列就會紅。

### R-17c｜`node.json` 的三個欄位是探針自己定的，而 repo 裡沒有任何東西會產生它

**事實**：閘門 A 要判 `P-01`／`P-03` 就得知道「這台是什麼角色」與「它是什麼時候被建出來的」，而這兩件事**不能由節點自己當下推斷**（ADR-022 §1 逐字要求 `node_created_at` 來自 cloud-init 寫入的建置時戳）。探針因此定義了 `/etc/skillhub/node.json` 與 `role: sandbox-exec`，**而那個字串是實作者挑的，不是任何人裁定的**；`infra/compose/sandbox-node.yml`（ADR-022 §Q1 引用）**根本不存在**。

**還有一個探針推不出來的**：「時戳是不是節點自報的」目前用 2 秒容差當啟發式。**正確的修法是讓 cloud-init 另外寫一個 boot id 或建置階段標記**，那是輸入契約要多一個欄位，不是探針能推出來的。

**建議**：把 `/etc/skillhub/node.json` 的欄位（`node_id`／`role`／`node_created_at`／`iac_commit` ＋一個 build-phase marker）連同 `role` 的字面值一起定案，寫進節點 IaC 的需求。**這一項不需要節點就能定。**

**不決定的代價**：R-17a 讓閘門 A 從第一天起就是一個永遠紅的燈；R-17b 讓 46 項裡有一項結構性地停在 `unknown`，而 ADR-022 §3 明文「任一項 `unknown` → 不得開放外部使用者」——**兩者都會在部署當天才被發現，而那天沒有人有時間裁定驗收表**。R-17c 不擋任何東西，但沒有它，IaC 寫出來的節點與探針要讀的檔案不會對上。

**決定之後**：ADR-022 §2 的覆蓋表與 §T5 判準各補一句（**不是改寫決策，是補對帳**，形式比照該 ADR 2026-08-26 的 N-08 補記）；`node.json` 的欄位進節點 IaC 的需求清單。

## R-18｜評審的截斷規則是整批的，而它讓 4／20 的評估交不出判定（`03` GEN-009 ③、丙-1 那條規則）

**2026-08-28 新增，由 [GEN-009 ③ 那批 20 段實跑](mvp/m5/report-generate-baseline.md#9-d-輪③-生成物完成第一次試跑後的評估判定分布2026-08-272803-gen-009-③)查出。**
**這不是一個缺陷回報，是一條刻意寫成保守的規則第一次有了發生率。**

**事實**：`judge.go` 的 `merge()` 收一個布林值 `truncated`——只要送去評審的材料**有任何一處被剪過**，
所有 `passed` 一律降成 `undetermined`（`failed` 不降）。那個布林值**不分判準**：
剪掉的是 trace 摘錄的尾巴，被降級的是全部三條。

**這一批量到的**：20 段裡 **4 段觸發**（`trace_digest.entries[].excerpt`），
其中 **3 段因此三條判準全部 `undetermined`、整份評估等於沒有結論**（第 4 段三條都 fail，規則沒有觸發）。
**四段全部是長 Run**，最長的一段 296 秒、284,705 input token。

**代價不是理論的**：那三段的 `deterministic_findings` 裡，**平台自己**用 exact match 找到了
`skill_activation` 事件、也逐檔列出了產出的檔案；**評審自己的 summary 三段都寫著「三項驗收條件都有可驗證的證據」**。
**兩條判準的答案是平台機械查出來的、完全不依賴那段被剪掉的摘錄，卻一起被降成不確定。**

**這是一個已知未決，不是新發現**——`judge.go` 那段的註解逐字寫著：
「whether a trimmed tail deserves the same conservatism as a missing event is a judgement about 丙-1's rule
and is not decided by renaming it」。**缺的一直是「它多常發生」，現在有了：20 分之 4。**

**三個選項**

- **(a) 維持現狀。** 保守到底，代價是**越難的 Run 越評不出來**，而封測要看的正是難的那些。
- **(b) 把 `truncated` 從整批改成逐判準**：一條判準若其verdict的證據全部落在**未被剪的來源**
  （exact-match 的 trace 事件、artifact manifest 列），就不降級。**這需要 `merge()` 知道每條 citation 的來源分類**，
  而那個資訊已經在 `EvidenceRef.Match` 裡。
- **(c) 只降級「依賴被剪那個欄位」的判準**：比 (b) 弱一級，把 `truncation` 的欄位名當作過濾條件。
  **實作最小，但它假設判準與欄位的對應關係看得出來**，而那個對應目前沒有任何地方宣告。

**建議 (b)**：它是唯一一個能同時保住「不讓看不到的東西支撐 pass」與「平台自己查到的事實算數」的形狀，
而且它要的資料已經在 row 裡。**(a) 不是安全的預設**——一個永遠對難題沉默的評審，
與一個亂給分的評審在封測裡會造成同一種結果：沒有人相信那個分數。

**不決定的代價**：封測的評估判定會有一段比率固定是 `undetermined`，
而**那段比率與任務難度正相關**——受測者會看到「越認真的題目越評不出來」。
這件事在封測開始之後才發現，就沒有時間改了。

**2026-08-28 補一項證據，方向與「保守是安全的」相反**：那三段被沉默掉的評估，其中**兩段（`DAT-3`／`DOC-2`）的文件經負責人逐份看過後判定「留」**（[報告 §10.2](mvp/m5/report-generate-baseline.md)；第三段 `OUT-6` 未標）。**這條規則沉默的是長 Run，而長 Run 通常是模型多做了事——它沉默掉的不是壞東西。**

**決定之後**：改 `judge.go` 的 `merge()`；`02:EVAL-*` 的截斷句補一行說明降級的粒度；
[m5/report-generate-baseline.md §9.3](mvp/m5/report-generate-baseline.md) 的發生率是重測的基準線。
