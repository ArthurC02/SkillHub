# Skill Hub MVP：目標與計畫內容

## 1. 背景

Agent Skill 生態正在成長，但個人創作者仍面臨四個主要問題：

1. 知道想完成的任務，卻不知道該搜尋哪個 Skill。
2. 找到 Skill 後，難以判斷是否可信、是否適合自己的 Agent 與環境。
3. 單看 `SKILL.md` 無法證明 Skill 在真實 Prompt、資料與工具下有效。
4. 即使完成試跑，也可能不知道如何改善、打包與安裝到目標 Agent。

Skill Hub MVP 將以「探索、試跑、評估、下載」建立第一個完整價值閉環。

## 2. 目標使用者

### 2.1 主要 Persona：個人創作者

個人創作者可能處於不同成熟度階段，而非固定角色：

- 學習者：有明確任務意圖，但不了解 Skill 規格與建立方式。MVP 內他的路徑是「永遠不從零寫」——系統自動建議驗收條件、改善建議直接回完整檔案內容，他不必打開編輯器。「從零生成一個 Skill」列 M5，見 §7.3 與[從描述生成 Skill](../adr/README.md#從描述生成-skill)。
- 改善者：已有或找到 Skill，但不知道如何判斷問題與改善效果。
- 精深者：能自行調整 Skill，希望降低搜尋、比較、測試與維護成本。

MVP 預設介面以非技術使用者可理解的任務語言呈現，並提供可展開的進階技術資訊。

## 3. 產品願景與 MVP 承諾

長期願景：

> 成為個人與團隊以 Catalog 探索、輕鬆創建、私人訂製並在明確治理下公開散布 Agent Skill 的可信任平台。

產品三個核心是 **Catalog、輕鬆創建、私人訂製／公開散布**；AuthZ、Workspace、版本、追溯、驗證、成本、隱私與治理是支援主旅程的平台能力。公開散布須經另行明確確認與既有治理，本批不開放生成物曝光或擴充商業 Marketplace。互動創作的允收見 [`02` GEN-007～012](02-specifications-and-acceptance-criteria.md)，設計見[互動創作](../adr/README.md#互動創作)。

MVP 承諾：

> 個人創作者能在 10 分鐘內找到一個可能符合需求的 Skill，用自己的 Prompt 與測試資料驗證效果，並下載可安裝的版本。

## 4. MVP 目標

### 4.1 產品目標

- 驗證使用者是否願意透過自然語言描述任務來探索 Skill。
- 驗證「可先試跑」是否能提高使用者選擇及下載 Skill 的信心。
- 驗證 Trace 與具體改善建議是否能幫助使用者修正 Skill。
- 建立從網路來源到可追溯、可驗證、可下載套件的基本流程。
- 建立可替換 Sandbox Provider 的執行邊界，避免綁定單一執行環境。

### 4.2 使用者成果

使用者完成核心旅程後，應獲得：

- 一個與任務意圖相符的候選 Skill。
- 一份可理解的來源、授權、依賴、權限與相容性摘要。
- 一次使用自有 Prompt 與測試資料的執行結果。
- 一份說明成功、失敗、限制與改善方式的評估報告。
- 一個可下載的標準 Agent Skill 套件與安裝說明。

### 4.3 平台成果

- 所有執行皆可追蹤至特定 Skill 版本、輸入與執行環境。
- 未受信任的 Skill 不直接在 Web/API 主機程序中執行。
- Skill 的原始來源、版本、授權與修改關係可被追溯。
- Cloud Sandbox、第三方 Sandbox 與 Local Runner 可透過共同介面被調度。

## 5. 產品原則

1. 使用任務語言：使用者不需要先理解 Skill 規格才能開始。
2. 證據優先：品質判斷以來源、試跑與驗收證據為主。**全域評分與排行榜永久不做**——名次要求可比較，而本產品的證據天生不可比較，A 的驗收條件不是 B 的驗收條件（[設計系統、信任訊號與畫面用語](../adr/README.md#設計系統信任訊號與畫面用語)）。替代品是帶分母、非預設排序、有 k 門檻的試跑證據彙總，見 §7.3。
3. 權限透明：執行前說明預計使用的資料、工具、MCP 與網路權限。
4. 可解釋改善：每項建議都需指出原因、位置與可能影響。
5. 可攜但不過度承諾：分開呈現規格有效、能力相容與**執行環境相容**。第三軸是一條規則的結論——「這個映像有沒有提供套件腳本宣告的執行環境」——不是一次觀察；平台不查那次 Run 裡腳本有沒有真的執行成功。「已測試」這個語意由[打包、授權溯源與散布](../adr/README.md#打包授權溯源與散布)三層相容性的第三層承擔，它的鍵是 (Skill Version × Runtime Image)，換映像即回未驗證。
6. 使用者可帶走成果：Skill、測試案例與必要安裝資訊可被匯出。**評估的正文刻意匯不出去**：套件 manifest 只帶建議的類別與目標路徑，`problem`／`proposed_content`／`expected_impact` 與證據摘錄是引用某次 Run 私有輸入的模型文字，依實作鐵律 11 不可表達。評估只在站上可讀。
7. 漸進式揭露：一般模式提供白話資訊，進階模式提供檔案、Trace 與技術細節。

## 6. MVP 核心旅程

### 6.1 探索

1. 使用者以自然語言描述想讓 Agent 完成的任務。
2. 系統分析輸入、輸出、工具、資料與環境需求（`02:DISC-005`、`03:DISC-011`）。這一步是「意圖搜尋」與「一個搜尋框」的全部差別。
3. 系統顯示候選 Skill，並解釋符合原因與限制。
4. 使用者查看詳情、來源、授權、風險與相容性。
5. 使用者選擇 Skill 並 Fork 到個人工作區。

### 6.2 試跑

1. 使用者選擇快速 Demo 或自己的測試情境。
2. 使用者輸入 User Prompt，並視需要加入資料集。
3. 系統提出可編輯的驗收條件。
4. 系統顯示預計使用的權限、執行環境與可能成本。
5. 使用者確認後啟動 Run。
6. 系統顯示一般進度，並提供可展開的進階 Trace。

### 6.3 評估、改善與下載

1. 系統依驗收條件將結果分成符合、部分符合、未符合或無法判斷。
2. 系統列出格式、啟用、執行、效果、相容性與成本問題。
3. 使用者檢視並選擇是否採用改善建議。
4. 使用者使用相同 Test Case 重新試跑並比較結果。
5. 使用者選擇目標 Agent，取得標準套件與安裝說明。

### 6.4 互動創作（已接線，完整驗收待收齊）

創作者在私人 Workspace 開始會話，補足需求或確認流程圖理解與參考材料；確認 brief 與驗收後取得草稿，依 Go 驗證或經授權試跑的回饋修訂，最後確認所見 revision／雜湊保存。資料不足時可直接說明限制或替代方案；未試跑的保存明示未驗證。公開散布是保存後獨立、受治理的明確動作。

## 7. MVP 功能範圍

### 7.1 必須包含

- 自然語言意圖搜尋。
- 精選、已索引及外部 Skill 的基本來源分級。
- Skill 結果列表、詳情、來源、License、依賴、權限與風險摘要。
- Skill Fork 與個人工作區。
- Skill 格式驗證與基本靜態檢查。
- User Prompt 與可編輯驗收條件。
- 測試資料上傳與執行期間存取。
- 自建 Cloud Sandbox Provider。
- 標準 Run 狀態、取消、逾時與清理流程。
- Tool Call、MCP Call、Log、錯誤、延遲及成本 Trace。
- 結果評估、具體改善建議與重新試跑。
- 標準 Agent Skill 套件與安裝說明下載。
- 基本帳號、Run 歷史及使用者主動刪除資料。
- operator 營運後台（`/admin/*`）：帳號與點數的查詢及授予、Skill 治理、派送煞車、名冊（唯讀）、operator 動作紀錄、成本統計與每日趨勢圖；不含名冊編輯，也不讀 `SEC-011` 列為私有的資料（[營運後台](../adr/README.md#營運後台)、`02` §4.12）。

### 7.2 MVP 可簡化

- 初期只提供少量人工整理的 Skill 類別與內容。
- 初期只設定一個主要 Agent Runtime 作為平台驗證基準。
- Skill 比較可先採用靜態比較，不必同時平行執行多個 Skill。
- 改善建議可先提供差異預覽與人工確認，不必支援完全自動改寫。
- 驗收條件可先純手動建立，自動建議為可選強化。
- 目標 Agent 打包可先支援標準套件與少量安裝 Profile。

公開散布是核心產品方向，正式發佈／審核流程仍屬後續範圍。創作與發佈均不改既有封測樣本、曝光或安全邊界。

### 7.3 MVP 不包含

- Local Runner 與本機工具絕對路徑存取（架構決策已成立，見[系統情境、平面與部署路徑](../adr/README.md#系統情境平面與部署路徑)；實作依 M2 後需求訊號啟動）。
- 遠端 MCP Server 整合（同上，依需求訊號啟動）。
- 完整公開發佈與創作者 Marketplace。
- 付費 Skill、收益分成與創作者結算。
- 團隊協作、企業組織與進階多租戶管理介面。
- 社群留言。
- 完整評分機制與排行榜——**這一項不是時程，是定位**（[設計系統、信任訊號與畫面用語](../adr/README.md#設計系統信任訊號與畫面用語)）：名次必須可比較，而本產品的證據天生不可比較，所以全域評分與排行榜**永久不做**。社會證明的替代品是 MVP 之後的試跑證據彙總（帶分母、非預設排序、k 門檻、需同意書與逐工作區 opt-in）。
- GPU、長時間工作或任意自訂基礎映像。
- 所有 Agent 的行為一致性保證。
- 大規模、無限制的全網爬取。
- 多個 Skill 的大規模平行 Benchmark。
- 從任務描述**從零生成** Skill——**這一項不是永久排除，是時程**（[從描述生成 Skill](../adr/README.md#從描述生成-skill)）：需求 ID 與允收準則已立於 [`02` §4.9](02-specifications-and-acceptance-criteria.md)（`GEN-001`～`004`），實作列 M5。排在 MVP 之外的理由是時序不是意願——封測漏斗第一段量的正是「輸入意圖後查看至少一個 Skill 詳情的比例」，那個數字要在「沒有第二條出路」的條件下量才有意義。

## 8. 初期內容策略

Skill 內容分為三層：

| 層級 | 定義 | MVP 行為 |
| --- | --- | --- |
| 精選 | 已人工檢視來源、License、內容與至少一次試跑 | 可直接查看並進入試跑 |
| 已索引 | 已取得來源並完成規格及靜態檢查，尚未驗證效果 | 顯示未試跑標示，試跑前再次確認 |
| 外部結果 | 即時或透過 URL 找到，尚未進入平台管理流程 | 先匯入、掃描與建立來源紀錄後才能試跑 |

首批類別為 `documents`／`writing`／`data`（PDM-001）。

三層的收錄政策、白名單制與各層判準的允收準則見 [`02` 第 4.7 節「內容供應與策展」](02-specifications-and-acceptance-criteria.md)（`CONTENT-001`～`009`）。精選層的「至少一次試跑」由 `03:CONTENT-008` 承接，列 M2。

## 9. 執行環境策略

### 9.1 控制平面

Skill Hub 管理：

- 權限、Secrets 與資源政策。
- Run 狀態機。
- Trace、評估與歷史資料。
- Sandbox Provider 選擇。

### 9.2 執行平面

MVP 先提供：

- `SelfHostedProvider`：執行上傳資料與公開資源。

### 10.2 ⛔ 三條仍然生效的邊界

## 11. 成功指標

> **這一節目前一個數字都沒有。** 量測管線在 M4 落地（四個漏斗事件、[產品分析與稽核邊界](../adr/README.md#產品分析與稽核邊界)、`ANALYTICS_RETENTION` 已追認為 365 天），但封測未開始，沒有任何一位受測者產生過事件；M1 閘門的 G1～G4 同樣沒有讀數。<br>所以下面三小節現在的身分是**假設，不是指標**——包含「10 分鐘」這個數字，它在 §3 與 §11.3 各出現一次而兩處都沒有被量過。第一個讀數會來自閘門的 9 場，第二個來自封測的漏斗；在那之前不要拿這一節的任何一句話當成已達成的證據。

### 11.1 北極星指標

> 每週通過使用者驗收並完成打包的 Skill 數量。

**分子 ＝ 同一週內，某個 Skill Version 既有一次 `overall = 'met'` 的評估，又有一筆下載紀錄**（`05` R-20）。兩半各自映到既有欄位，不新增欄位、不新增事件：

- **「通過使用者驗收」→ `evaluations.overall = 'met'`**（機器判定符合，逐 Skill Version）。
- **「完成打包」→ `download_records.downloaded_at` join `download_artifacts.skill_version_id`**（真的被下載走）。
- **兩者以 Skill Version 為鍵、以 UTC 週界（同 `funnel.sql` 的半開區間）為窗口取交集**；分母週次同樣以 UTC 週界切。

**為什麼不新增欄位或新事件**：`evaluations.feedback_helpful` 問的是「這次判定有沒有幫助」，不是「這個 Skill 通過了我的驗收」，兩者不可互代；一個為北極星量身打造的新按鈕或新表，會是**第三個記錄「使用者怎麼看這個 Skill」的地方**，而封測期 12 人的量級養不起一個沒人維護的新真相來源。用既有兩張表的交集，代價是**它是下界而不是字面**——`overall = 'met'` 是平台的判定不是使用者親口說的驗收，這個落差要在報表列上明寫。

**查詢尚未落地**：形狀照 `funnel.sql`（`\set` 區間、每列自帶精確度限制的 note），需對真 schema 跑的整合測試，承接工作項待開。

### 11.2 核心漏斗

- 輸入意圖後查看至少一個 Skill 詳情的比例。
- 查看詳情後 Fork 或啟動試跑的比例。
- 建立 Run 後成功完成的比例。
- 完成 Run 後認為結果有幫助的比例。
- 改善建議被採用的比例。
- 完成試跑後打包下載的比例。
- 首次使用後再次回來試跑或重新驗證的比例。

### 11.3 體驗目標

- 使用者能在 10 分鐘內完成第一次「搜尋到下載」的成功旅程。
- 所有「通過」或「未通過」結論都能展開查看依據。
- 所有執行都能追溯到 Skill 版本、輸入、Runtime 與 Provider。

## 12. 主要產品風險

| 風險 | 影響 | MVP 對策 |
| --- | --- | --- |
| 搜尋結果多但難以選擇 | 無法進入試跑 | 顯示符合原因、限制與可比較摘要 |
| 初期內容品質不足 | 失去信任 | 精選優先、來源分級、限制全網內容 |
| 評估結果過度主觀 | 改善建議缺乏價值 | **三項**：結構檢查、執行結果、驗收條件。`trial/improvement/deterministic.go` 六類問題中五類由平台自有紀錄判定，只有「任務效果」進模型且引用逐條重驗。**「其他工作區的試跑證據」不在這三項裡**——它沒有欄位、query 或端點，前置是同意書與逐工作區 opt-in 的資料模型 |
| Skill 符合規格但無法執行 | 下載後失敗 | 分開呈現規格、能力與執行環境相容性 |
| 未受信任程式碼或 MCP 外洩資料 | 造成安全事件 | 隔離執行、權限預覽、Secrets 隔離及預設封鎖網路 |
| Sandbox 成本不可持續 | 無法提供足夠試跑額度 | 資源上限十一項在 preflight 上、預估是真區間、額度機制（`entitlements/quota.go`）已存在。**成本顯示的是下界不是用量**：平台沒有 Run 層級的成本欄位，畫面合計自 Trace 的用量事件，權威來源是模型閘道對這個 Run 的 per-key 實付，而 Trace 受 `TRACE_RETENTION` 規範——**保存窗口過了就沒有了** |
| Local Runner 權限過高（後 MVP） | 影響使用者電腦 | 明確授權、限制路徑、顯示命令與可中止執行 |
| **內容涵蓋不到使用者的任務** | 學習者 persona 走不完第一步：精選只有三類，落在三類外就掉到「外部結果」層，而那一層要使用者自己提供 URL——不會寫 Skill 的人通常也不知道去哪找 | MVP 內只有誠實：無結果狀態說出下一步而不是只給改寫建議。封測要看的數是漏斗第一段；M5 的生成路徑是它的解，但刻意排在讀數之後 |
| **生成物看起來像一個 Skill，但沒有任何人或任何 Run 檢視過** | 使用者把一份沒有證據的產出當成與精選內容同級 | 三道：不進公開目錄也不進搜尋索引、Script 的揭露與匯入物逐字相同不享寬待（[從描述生成 Skill](../adr/README.md#從描述生成-skill)）、詳情與列表必須說出「沒有經過任何人工檢視、沒有任何試跑證據」（`02:GEN-004`） |
