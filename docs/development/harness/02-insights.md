# 洞見：十二條，每條附證據與後果

排序不是重要性，是**依賴順序**——後面的條目建立在前面的之上。

## 1. 判準不是「agent 勤不勤勞」，是「文件有沒有在通往程式碼的路上」

**證據**：子代理啟動保證只有約 19 KB 進 context；`docs/` 4.38 MB；16 條死連結全部「讀起來是對的」。
**後果**：不要再寫「請 agent 務必閱讀 X」。把 X 放在動到那段程式碼時**必然經過**的位置（分區卡、按路徑觸發的 rule），並在路的盡頭放會叫的機器。

## 2. Claude 專屬的層只是提早發現，不是保證

**證據**：repo 同時有 Claude Code 與 Codex 在同一棵工作樹；Codex 讀不到 `.claude/`，也不受 `permissions.deny` 管。模型規則第一次寫在 `.claude/` 裡，對 Codex 等於沒寫。
**後果**：規則本體一律放跨工具的位置（根 `AGENTS.md`、`docs/`）；`.claude/` 只放「同一條規則的 Claude 版早期預警」。任何「只有 Claude 吃得到」的機制都不得成為唯一的守衛。

## 3. 知識放哪一層，問「換一個 repo 還成立嗎」

**證據**：技能一旦引用 `docs/` 或 ADR 編號，就隨那份文件過期；負責人明言「doc 是權威文件，skill 要輕量高可複用」。
**後果**：成立 → `.claude/skills/`；不成立 → `docs/`（判準）＋ `AGENTS.md`（路由）＋ rules（觸發）＋ deny／CI（攔阻）。這條有機器：`harness` 檢查拒絕技能出現 `docs/`、ADR 編號、需求 ID。

## 4. 每一層只放一種東西；每條規則只有一個作者

**證據**：五個角色檔各抄一份禁令，而根 `AGENTS.md` 已在每個子代理的 context 裡——這是本 repo 記了三次的「數字有多個作者」換成規則版。
**後果**：角色檔只留一行「以根 `AGENTS.md` 第 3 條為準」＋真正角色專屬的一兩句。新增規則前先問「它已經在哪裡了」。

## 5. 角色按風險切，不按目錄切

**證據**：web／platform 兩個角色的差異只有「先讀哪份」與「哪些檔屬於 coordinator」——兩者都是那個目錄的事實，本來就該住在該目錄的 `AGENTS.md`；而下一階段的工作不在這兩個目錄。
**後果**：三個角色——writer（路徑範圍由簡報給）／verify（唯讀）／mutation（證明測試會紅）——**永不新增**。新增區域是三步配方：目錄 `AGENTS.md`、一條 rule、根表一列。

## 6. 一句正確的話旁邊要有那台機器——harness 自己也不例外

**證據**：放置規則寫好的當天沒有機器；隔天審視就找到兩份技能沒有 `name:`。而這個產品本身就是 Skill 驗證器，`skillpkg.Validate` 跑在 `.claude/skills/` 上當場抓到。
**後果**：`automation-check` 名冊第 25 條 `harness`（技能不引用本地文件、角色指定 `model`、根 `AGENTS.md` 有上限）＋ dogfood 測試。**每台新機器落地前先種一個違規確認它會紅**。

## 7. 串在一起的檢查不是檢查，只是輸出

**證據**：`git add X && git diff --name-only --staged && git commit` ——清單印出來了，但 commit 已在同一條鏈裡執行；掃進 25 個別人的檔案。
**後果**：「看索引」是獨立的一步，讀完結果再決定要不要 commit。推廣：任何「檢查 → 動作」的組合，檢查必須有機會**改變後面的動作**，否則它不是檢查。

## 8. 每一條 deny 要親自撞一次，並且要有對照組

**證據**：`Bash(*git add .*)` 誤擋 `git add .claude/…`（寫完幾分鐘內撞出）；`commit -a`／`restore`／`checkout .` 漏擋（審視時撞出）；`Write(...)`／`Glob(...)` 路徑規則被接受但永不查詢。
**後果**：加規則 → 用會被擋的指令撞 → 用結構相同但合法的指令確認通過。沒有對照組的「擋住了」可能是別的東西擋的。

## 9. 送達要用儀器量，不要用推論

**證據**：`InstructionsLoaded` hook 寫下 `file_path`＋`load_reason`（`session_start`／`nested_traversal`／`path_glob_match`／`include`／`compact`）；我曾說它「從沒觸發」，其實已有 16 列——同一個錯誤（沒去看紀錄就下結論）。
**後果**：「agent 有沒有讀到某份文件」是可以查的，去查。新建的巢狀 `AGENTS.md` 有發現延遲，這也是儀器量到的，不是猜的。

## 10. `AGENTS.md` 是心智模型，不是施工日誌

**證據**：22 KB 裡一半是日期、刪除線、括號套括號；它自己第 11 行寫「狀態變動改 `01` §10，不改這裡」——**規則落地的檔案自己違反了那條規則**。缺的是「系統怎麼跑」那一段。
**後果**：入口文件的順序是「這是什麼 → 系統怎麼跑 → 現在在哪（三行，無日期）→ 地圖 → 技術棧 → 鐵律 → 紅線各一句 → 去哪看（一張表）」。上限是棘輪（16 KiB），貼著現況而不是懸崖。

## 11. 模型按「需要多少推論」選，用特性不用名字

**證據**：禁 Fable 之後九成指定 Opus（負責人不認同）；Luna／Terra 是 Codex 的名字；名字會換、每個工具各一套。
**後果**：四級——旗艦（派工者自己用，子代理禁用）／深度推論／快速執行／機械執行——各自寫「派給它的事」；名稱只在表的「現行對應」欄與檢查器。從能做完的最低一級起，升級要寫理由。

## 12. 借了現況便宜的設計，三週後要先拆再蓋

**證據**：按目錄切的角色、抄五份的禁令、永遠碰不到的上限——每一個在建置當天都「合理」，對照路線圖（閘門期、demo、封測、Local Runner）就不合理。
**後果**：任何 harness 變更做完，對照一次路線圖問「下一階段的工作在哪個目錄、哪種任務」；答案不在現有結構裡，就是借了便宜。

---

**這十二條的共同底層**：沒有量測的判斷，對的和錯的長得一模一樣。本歷程被推翻的六個判斷（見 [01-journey.md](01-journey.md) 末表）全部是「讀了文件就相信」或「沒去看紀錄就下結論」。
