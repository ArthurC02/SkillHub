# Harness 原則

## 文件與規則

1. **文件必須在工作路徑上。** 不以「請閱讀」取代路由；由根與目錄 `AGENTS.md`、適用 rules、brief 與機器檢查共同交付。
2. **跨工具的規則要有跨工具的權威。** 工具專屬設定只能作為提早發現，不能是唯一守衛。
3. **可攜方法與專案事實分開。** 可重用的工作方法放 skill；專案規則、架構與狀態放它們的權威文件。
4. **每條規則只有一個作者。** 角色只保留角色專屬責任，區域事實只放區域指示，避免多處副本漂移。

## 協作與風險

5. **角色按風險分工。** writer 依明確 allowlist 寫入；verify 預設唯讀；mutation 證明測試能偵測回歸。
6. **檢查必須能改變下一步。** 將檢查和 commit、reset、格式化或其他寫入分開；否則輸出不是防護。
7. **共享工作樹保留未知差異。** 不以 `stash`、`reset`、`clean` 或 checkout 消除其他 Writer 的工作。
8. **模型依任務的推論需求選擇。** 先使用能完成工作的最低等級；旗艦級保留給主線，升級需說明理由。

## 可證偽的自動化

9. **每個護欄都要有負例與對照例。** 負例證明規則會攔截；對照例排除是其他因素造成的假紅。
10. **以觀測確認送達與執行。** 讀設定檔或看到 exit 0 不等於規則命中、指示載入或測試實際執行。
11. **先證明測試會紅。** 行為修正必須還原關鍵改動並讓對應測試因目標斷言失敗；語法錯誤、空輸入與前置失敗不算證據。
12. **定期對照下一階段。** 新區域、新工具與新流程加入後，確認路由、唯一權威、跨工具守衛與可證偽檢查仍完整。

共同原則是：沒有可重跑觀測的判斷，正確與錯誤看起來沒有差別。
