# Harness 的工作方式

Harness 讓文件、角色與自動化規則實際進入開發路徑，並以可重跑的檢查證明它們仍有效。它不是施工紀錄；目前適用的 repo 規則以根目錄 `AGENTS.md`、區域指示與 `docs/development/automation.md` 為準。

## 從需求到可驗證規則

1. **把權威放在正確層級。** 專案特有的規則放在 `AGENTS.md`、文件或 ADR；可攜的方法才放進 skill。不得用 skill 複製或取代專案文件。
2. **讓規則在路徑上。** 依目錄路由的 `AGENTS.md`、按路徑套用的 rules 與明確的 brief，缺一不可。工具對巢狀指示的送達方式不同，不能把任何單一工具專屬機制當成唯一守衛。
3. **每條規則只維護一份。** 根規則、區域事實、角色責任與檢查器各自只描述自己的責任；角色不重抄共同禁令。
4. **以風險而非目錄分工。** writer 的路徑範圍由 brief 限定；verify 預設唯讀；mutation 只負責證明行為測試能抓到回歸。區域規則由目錄指示提供。

## 安全的多人協作

共享工作樹採單一 Writer。任何檢查與後續破壞性動作必須分開執行：看過索引、diff 或範圍後，才能決定是否進行下一步；把檢查與 commit、reset 或其他寫入串在同一條命令中，不是有效檢查。

看到不屬於自己的差異時保留並回報，禁止用 `stash`、`reset`、`clean` 或 checkout 清掉它。高衝突區、generated 檔與 lockfile 依根 `AGENTS.md` 的序列化規則處理。

## 護欄要能證偽

每一條 deny rule、path rule 或檢查器都要有兩種驗證：

- 一個應受阻擋的違規輸入；
- 一個結構相近、預期可通過的對照輸入。

只看到「被擋」不足以證明是哪條規則在作用；只看到綠燈也不足以證明檢查真的覆蓋目標。新增機器檢查前先設計可讓它失敗的最小變異，並確認失敗是目標判定，而非語法錯誤、空輸入或其他前置失敗。

## 觀測與維護

工具是否載入指示、規則是否命中、測試是否執行，都應以各工具的輸出或儀器記錄確認，不可由設定檔存在推論。文件入口必須維持精簡：描述系統、現行規則與權威連結；狀態、數字與里程碑結論留給其指定的計畫文件。

任何 harness 變更完成後，對照下一階段的工作範圍檢查：新區域是否有路由、規則是否仍跨工具可用、是否有唯一權威來源，以及自動化是否能證明新護欄有效。
