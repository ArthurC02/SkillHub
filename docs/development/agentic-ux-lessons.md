# 從五層模型到平台體驗：Skill Hub 的 Agentic UX 開發經驗

這是一份給接手產品設計與前端開發的人看的**經驗總結**，不是另一份畫面規格。它記錄我們如何從 Jesse James Garrett 的五層模型出發，走過「把工具頁換成平台殼層」到 Catalog、色彩、回饋與 Studio 對話的調整，以及 Agent 在下一輪工作中該如何避免只修表面。

要判斷**現在應該做什麼**，仍以[平台體驗模型](../design/platform-experience.md)管產品方向、[資訊架構](../design/information-architecture.md)管頁與頁之間、[前端設計系統](../design/system.md)管一頁之內；功能是否真的存在，以[目標與里程碑](../plans/01-goals-and-plan.md#10-里程碑)、程式和測試為準。本文提到的「我們做了」只描述已檢查的迭代，不表示每個頁面都已完成平台化，也不替代真人易用性研究。

## 一、最大的轉折：從「做功能」改問「人在平台上做什麼」

早期介面容易以後端能力或表單動作命名：匯入、試跑、打包、建立。每個頁面各自可用，使用者卻要記得自己剛才選的是哪個 Skill、哪個不可變 Version，以及下一步去哪裡。把這些頁面統一換色、加陰影，不能解決迷路。

我們先把使用者活動整理為 **Shopping、Making、Sharing、Conducting、Governing**，再把能力安放在 Catalog、Library、Studio、Activity 等穩定空間與精確物件脈絡中。這不是把選單項目改名：一個人從 Catalog 看見候選，進入 Skill，建立或試跑，離開後從 Activity 回來，仍要看得出自己在處理同一件事。平台感首先來自這種連續性，然後才是視覺風格。

回頭看，幾輪工作大致沿著同一條線往內收斂：

| 當時追問 | 帶來的改變 | 留下的教訓 |
| --- | --- | --- |
| 為何像一堆工具？ | 用五層模型重建平台活動、空間與物件旅程。 | 先找產品中心，不從選單或表單起稿。 |
| 為何首頁不像平台、卡片看不完？ | Catalog 成為探索入口，卡片改為可掃讀的商品格線。 | 清單幫初選，詳情才負責查證。 |
| 為何有配色仍顯廉價？ | 建立品牌層級與語意色角色。 | 顏色服務資訊與後果，不能拿來粉飾未知。 |
| 為何操作不夠滑順？ | 重看首屏、缺席狀態、停用原因與跨頁續作。 | 好看不等於能做決定；每個狀態都要有出口。 |
| 為何等待與對話不像熟悉的產品？ | 調整提醒時機、長工作狀態與 Studio Chat UI。 | 借互動慣性，但不假造進度、預算選擇或領域結論。 |

後續幾次調整暴露出另一個問題：**平台骨架成立，不代表每個決定都容易做。** 首頁曾把創作入口放得太前面，像工具而不像可逛的 Catalog；商品卡曾塞滿資訊，一次只能讀一張；統一的色彩雖有科技感，卻未必能說清成功、危險、等待或未知；Studio 即使有對話紀錄，也未必像使用者熟悉的 Chat UI，長工作更可能讓人懷疑是否還在進行。於是工作重心從宏觀的空間與旅程，移到微觀的資訊密度、狀態時機、操作暗喻與手機上的可達性。

這段歷程留下的判準很簡單：**看起來像平台，是必要但不充分的條件；使用者能判斷、能續作、知道系統目前掌握什麼，才是體驗。**

## 二、用 Garrett 五層定位問題，不要把它當瀑布流程

[Garrett 的《The Elements of User Experience》](https://www.pearson.com/en-us/subject-catalog/p/Garrett-Elements-of-User-Experience-The-User-Centered-Design-for-the-Web-and-Beyond-2nd-Edition/P200000000272)把問題從抽象的 Strategy 推到具體的 Surface。它幫我們辨認「這個抱怨到底發生在哪一層」，不是要求一層做完才能碰下一層。Surface 測試失敗時，常常要往下追到 Scope 或 Structure；下層改變時，也必須回頭重看畫面。

| 層次 | 在 Skill Hub 要先回答什麼 | 這段歷程給的提醒 |
| --- | --- | --- |
| Strategy | 使用者此刻想做哪個決定？平台希望促成哪段旅程？ | 首頁若先推製作，會搶走「先發現合適 Skill」的任務；漂亮的建立表單不能補救方向錯置。 |
| Scope | 哪些內容、能力與可信事實已存在？哪些仍未量測或不能曝光？ | 不能為了補滿卡片臆造採用數，也不能讓尚未開放的生成入口藉視覺重設進入封測動線。 |
| Structure | Skill、Version、Run、Session、Release 等物件怎麼關聯？使用者如何回來？ | 一條深連結要帶回精確物件和階段；Activity 是來源事實的續作入口，不是另一套前端猜測的狀態機。 |
| Skeleton | 第一眼先看到什麼？資訊如何分組、導覽、捲動和操作？ | Catalog 要能一眼掃過多個候選；Studio 要讓目前決定、工作狀態與輸入區各有固定位置。 |
| Surface | 色彩、字級、密度、文字和動態傳達什麼？ | 色彩有語意但不能單獨承擔語意；「綠」不能代替真正的成功證據，也不能把執行完成誤寫成任務通過。 |

每次改版都可以從最刺眼的現象切入，但交付前要把五層串成**一條可反駁的推導**。例如「卡片太擠」表面上是排版問題，往下追會發現 Skeleton 沒分清「清單上做初選」與「詳情頁查證據」，Scope 又把所有可得資訊都當成必須在卡片上展示。只改 padding，下一批欄位仍會把卡片擠回去。

五層也不能取代領域權威。畫面需要一個事實時，先確認它由誰擁有、契約是否提供、缺席代表什麼；不讓 React 從零值、URL 或幾個 API 回應自行拼出新的產品事實。詳見[領域邊界](../adr/README.md#platform-bounded-context-與-context-map)與[設計系統的「未知不是空白」](../design/system.md#21-未知不是空白)。

## 三、四個案例：我們如何從外觀追到使用者決定

我們曾向 Bootstrap、Material UI 等成熟設計系統尋找元件質感，也看過電商與 Chat UI 的實際呈現。真正可搬回來的，是元件狀態的完整性、字級與間距的層級、語意色角色，以及操作如何隨情境揭露；不是把別人的 CSS、依賴、品牌或所有功能一起搬進來。[現行設計系統](../design/system.md#48-外部範例庫只取技法不取套件負責人明示)列出可參考的來源與「不安裝額外視覺套件」的邊界。

### 1. Catalog：從「首頁有搜尋」到「首頁可逛、可比較」

電商展示給我們的啟發，不是照抄服飾攝影或促銷語氣，而是把**清單視為一次同時比較多個候選的工作**。首頁先給可瀏覽的 Skill 探索畫廊，再讓搜尋和篩選縮小集合；卡片只留下初選需要的身份、用途和少量判斷訊號。較長的符合原因、來源、限制與驗證證據，在詳情或展開的脈絡內查。資訊沒有被刪掉，只是按決定時機分層。原本期待「熱門技能」，但目前沒有可信的人氣量測，畫面便不能把目錄排序或人工精選假稱為熱門。

這裡有一道不能被美感蓋過的界線：會改變安全或信任判斷的資訊，仍須在使用者作決定前可見；人氣不等於可信，未知也不等於零。若為了讓第一屏更好看而藏掉必要風險，畫面是變輕了，決策卻變差了。[設計系統的優先序](../design/system.md#0-優先序)說明了這種衝突誰先誰後。

### 2. 配色：從「有科技感」到「看得懂後果」

統一品牌色能改善廉價感，但單靠一組主色無法告訴人「可繼續」「有風險」「正在處理」「目前無法確認」。我們改以語意角色思考色彩：哪些動作值得強調、哪些要警告、哪些表示完成；背景和邊框則維持安定，不讓每張卡都爭奪注意。顏色是**第二訊號**，要和文字、圖示或狀態說明一致，並接受對比與鍵盤焦點檢驗。

最容易犯的錯是把「綠色＝成功」用得太廣：Run 結束是一件事，驗收條件是否通過是另一件事；發佈成功、能下載、能在 Catalog 被找到，也可能是三個不同事實。語意色只幫助掃視，不能把多個領域狀態壓成一個好看的 badge。現行角色與用法由[設計系統的色彩角色](../design/system.md#461-色彩角色)維護，本文不另訂一套 token。

### 3. 提醒與長工作：從「有訊息」到「在對的時間說對的事」

一個送出動作至少有幾個時刻：尚未送出、等待回應、背景處理、需要使用者決定、完成或失敗。靜態提示、短暫 notice、持續狀態和 Activity 項目各服務不同時刻。把同一句話到處重複，會製造噪音；只在按鈕旁閃過一次，長工作離開頁面後又找不到，會製造不安。

我們因此把提醒綁回**事件與下一個決定**：送出後要確認系統已接手，等待時要顯示目前已知的工作狀態，需使用者介入時要給明確操作，結束後留下可回訪的物件與證據。不能用前端動畫假裝有真實進度，也不能把網路失敗當成工作失敗。Activity 的續作入口與來源頁的完整證據各司其職；詳細時機見[設計系統的提醒原則](../design/system.md#214-提醒要跟著決定與事件走)。

### 4. Studio Chat UI：借熟悉的操作慣性，不借別人的產品承諾

對話式創作若只是把每則訊息都做成厚卡片，仍像表單紀錄。參考開源的 [Hugging Face Chat UI](https://github.com/huggingface/chat-ui) 與 [assistant-ui](https://github.com/assistant-ui/assistant-ui) 後，我們吸收的是**會話閱讀與操作節奏**：訊息主次清楚、輸入區安定地靠近底部、目前工作狀態佔小而明確的位置，工具性選項按需揭露，未送出的草稿不因等待或切換而消失。這些模式可以由現有 React 與 CSS 落地，並不等於要安裝它們的套件或複製其視覺商標。

熟悉感也有邊界。Skill Hub 的創作會牽涉成本檔位、候選版本、確認動作與不可變成果，不能因為想「像一般聊天」就自動選預算、自動確認或把工作進度畫成生成器編造的百分比。桌面與手機需要不同的資訊安排，但都要能找到目前決定、歷史對話、工作清單與可送出的輸入。[平台體驗模型的 Studio 切片](../design/platform-experience.md#82-分階段落地)記錄了這種五層推導。

這一輪也提醒我們：元件測試與一般 E2E 綠燈，仍可能漏掉**既有真實瀏覽器腳本與新揭露方式的衝突**。當預算選項改成按需展開，舊腳本仍直接點擊隱藏選項，整體檢查就會失敗。修正必須讓測試走使用者真的能看見的路徑，再看同一條 CI 回綠；不能因為產品程式的測試通過，就把瀏覽器失敗歸類成無關噪音。

## 四、讓 Agentic 開發可重複的工作路徑

Agent 的優勢是能同時閱讀產品文件、程式、測試與外部模式；弱點是很容易在取得一張參考圖後，直接跳到 CSS。以下是一個**每次切片可重跑的短循環**，不是要求先做完整大改造才交付。

1. **定任務與邊界。** 用一句話寫出「誰、在哪個物件脈絡、要做什麼決定」。先讀適用的 `AGENTS.md`、產品現況、契約與設計規範；確認旗標、權限、不可變性、缺席語意和未量測的部分。記下已知、未知、假設，不把假設寫成產品事實。
2. **從五層提出假說。** 每層只回答這個切片真正需要回答的問題。若 Surface 的要求會迫使 Scope 虛構資料，停下來改設計；若 Structure 沒有回到精確物件的路，先處理導覽而不是再加一個漂亮卡片。
3. **帶著問題研究外部。** 問「這個平台如何讓人掃描候選／恢復工作／理解等待／避免誤操作」，再讀官方文件、開源實作與可操作畫面。記錄吸收的模式、不要吸收的功能假設、授權與依賴代價。現有原生元素和元件能做到時，不為了外觀裝新套件。
4. **做一條垂直切片。** 連同入口、空態、載入、失敗、成功、返回和深連結一起做；前端有新事實需求時，先找 owner 與契約。不要只讓 demo 資料或一條 happy path 看起來成立。
5. **看真畫面，也操作它。** 在桌面與手機寬度檢查第一屏、資訊密度、捲動、焦點、鍵盤和長文案；讓等待、失敗、未知、無權與已完成各走一遍。靜態截圖只驗證一個瞬間，不能證明易用性或長工作連續性。
6. **讓主張有證據。** 先跑最貼近改動的測試，再跑受影響的瀏覽器流程與專案閘門。若宣稱「修好某行為」，要證明對應測試在拿掉修正時會紅、恢復後會綠；純文案不必做這種突變。記下實際成功、失敗和 skipped 數，不把「本機沒報錯」當成 CI 綠。
7. **收斂來源與交接。** 更新應更新的現行規格、測試與狀態，不在回顧文裡發明新規則；交接說清已落地、仍未落地、尚欠真人驗證的地方。一次切片完成後，再選下一個最影響使用者決定的問題。

如果使用 SubAgent，把工作拆成**查證、批判、實作、驗證**等可交接的責任；共享工作樹仍只留一個 Writer，給精確路徑與交付條件，不讓多個 Agent 同時改同一組檔。模型依任務推論量選擇，而不是用模型等級代替 brief。具體操作和閘門以[開發自動化](./automation.md)及[分層與派工](./agent-instructions.md)為準。

### 可複製的切片 brief

```text
使用者與情境：誰從哪個入口來，正處理哪個 Skill／Version／Run？
眼前決定：他現在要比較、確認、等待、修訂，還是返回？
五層推導：Strategy／Scope／Structure／Skeleton／Surface 各改什麼、不改什麼？
權威與邊界：哪些事實有 owner？哪些未知、未量測、受旗標或權限限制？
外部參考：學到哪個互動模式？哪些功能／依賴／視覺不照搬？
代表性路徑：正常、等待、空、錯誤、無權、手機、鍵盤、離開再回來。
可反駁證據：哪個測試會因修正消失而紅？哪些瀏覽器畫面／操作要人工看？
交付：程式、契約、現行設計文件、CI、仍未驗證的主張各在哪裡？
```

這份 brief 的目的不是增加文件量，而是讓下一位 Agent 能問對問題。若一個欄位無法回答，這通常比「先開 CSS 檔」更值得處理。

## 五、如何判斷完成，如何承認還沒完成

我們逐漸學到三種證據不能互相冒充。**程式與測試**能證明某個狀態、路由或互動在指定條件下成立；**真實瀏覽器與人工檢視**能發現首屏、焦點、密度、捲動與既有腳本的問題；**真人任務研究與產品量測**才能檢驗人是否找得到、看得懂、願意用。尤其「有美感」「像平台」「易用」不是一條 snapshot 或一張截圖能蓋章的結論。

下一階段的工作仍要在兩個尺度上驗證：宏觀看跨空間旅程是否連續、能力是否有唯一主要落點；微觀看一個狀態是否說清發生什麼、為何如此、接下來能做什麼。[平台體驗模型的代表性任務](../design/platform-experience.md#93-代表性任務)與[設計系統 checklist](../design/system.md#3-評估準則checklist)提供現成的檢查入口。尚未取得的封測與使用者研究數字，不能用 Agent 的信心、UI 的完成感或自動化綠燈補上。

把這份經驗帶到下一個功能時，最有用的不是複製這次的顏色或版型，而是保留這條追問：**使用者在做什麼決定？畫面依據哪個真實事實幫他做決定？如果答案不成立，應該回到五層的哪一層重想？**
