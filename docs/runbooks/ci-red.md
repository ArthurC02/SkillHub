# CI 紅了，而訊息只說「exit code 1」

## 先建立共同模型

一次 CI 失敗不會直接出現在你面前，它要**穿過通道**才會到；每一層通道各丟掉一些東西，而你手上有哪幾層，取決於 repository 可見性、使用的 API 與憑證。以下的「無憑證」只指公開 repository 可讀的 API 視角；private repository 一律先確認讀取權限。

| 通道 | 拿得到什麼 | 丟掉了什麼 | 要憑證嗎 |
| --- | --- | --- | --- |
| workflow run 的結論 | 綠或紅 | 哪一個 job、哪一步 | 否 |
| job 與 step 的結論 | **哪一步**失敗 | 為什麼 | 否 |
| check-run 的 annotation | 那一步**自己publish 的文字**（尾端數 KB） | 它沒 publish 的一切 | 否 |
| step summary | 該 step 寫出的較完整報告 | 它沒有寫出的內容 | 依 repository 與 endpoint；不要假定匿名一定讀得到 |
| 完整 log | 全部 | — | 依 repository 與 endpoint；通常需要可讀取 Actions 的權限 |

這張表的重點不是層數，是**第三層的那句「自己 publish 的」**：annotation 不是 GitHub 去翻 log 翻出來的，是那一步主動送出去的。**沒有主動送的步驟，在沒有憑證的視角裡就是一句「Process completed with exit code 1.」**——那句話不代表失敗訊息很短，只代表沒有人把它送出來。

所以在這個 repo 裡，**需要靠命令輸出判斷產品、測試或驗收失敗的 step 都要包在 [`tools/ci/report-failure.sh`](../../tools/ci/report-failure.sh) 裡**。它 tee 住輸出，失敗時同時寫 step summary 與一則 `::error::` annotation。checkout、安裝或單純設定等基礎 step 不必假裝有同樣的診斷內容；它們失敗時應保留原始輸出，並從本機重現或有權限的 log 查原因。新增或修改 step 時，先判斷它屬於哪一類，不能只因未包報告器就宣稱它在無憑證視角可診斷。

借本機 Git 憑證庫的權杖讀完整 log 是最後手段：先窮盡 `task ci:status`、匿名 REST 與本機重現。多數情況下你根本不需要走到那一步——**把「看不見」修好，比猜根因便宜**，而且下一次失敗會自己說出原因。

## 四件會騙你的事

這四件都不是罕見陷阱，是這套通道的固有性質。判讀任何 CI 訊號前先過一次。

- **`continue-on-error: true` 會把那一步的 `conclusion` 一律記成 `success`。** 不論命令做了什麼。所以**帶這個旗標的步驟，不能用 job/step API 的結論判斷成敗**；可讀的訊號是「有沒有出現 failure annotation」。把這種步驟的 success 當成通過，會得到一個完全反過來的結論。
- **annotation 取的是輸出的尾端**（`tail -c 3000`；step summary 是 60 KB）。任何在收尾時大量列印的東西——容器日誌、狀態傾印——都會把真正的判決擠出那個範圍。**腳本要把「哪一條斷言失敗」印在所有傾印之後**，否則你拿到的 annotation 會是一整片 Postgres 啟動訊息。
- **把結果緩衝到最後一次印出的子程序，會被同一件事埋掉。** 瀏覽器腳本（`stack-browser.mjs`、`stack-credit.mjs`）把每一條檢查累積起來、結束時一次 `console.log`。要讓它們的逐條結果活到 annotation，得把那次執行 `tee` 進檔案，收尾時再把 `^FAIL` 撈出來重印。
- **送進 `/dev/null` 的輸出救不回來。** 安裝、下載、探測的 stderr 一旦丟棄，一次網路抖動就只會呈現成「某條測試失敗」。CI 腳本裡不要有 `>/dev/null 2>&1`，除非那段輸出在失敗時也確定沒有價值。

## 診斷順序

每一步都有它能回答與不能回答的問題；答不出來就往下一步，不要跳著猜。

1. **`task ci:status`**（`devctl ci-status [ref] [--wait]`）。得到：哪些 workflow run、哪個 job、哪一個 step 失敗、哪些 job 被 path filter 跳過。**驗證**：它列出的 step 名稱要和你預期動到的區域對得上；對不上就先懷疑你的改動與這次失敗無關。
2. **在可用存取範圍內讀那個 job 的 annotation。** 公開 repository 可先用匿名 REST；private repository 用可讀取它的憑證。得到：那一步自己送出來的文字。**驗證**：annotation 裡如果只有 `Process completed with exit code 1.`，**結論不是「查不到」，而是「那一步沒有發布可讀的診斷」**——跳到第 4 步。
3. **本機以相同輸入重現。** 映像要自己建、環境變數照抄 workflow。**驗證**：跑得出同一個失敗才算重現；一次綠不代表不存在，間歇性失敗要多跑幾次。
4. **把那一步改成會自己說話**，推上去，讓下一次失敗回答你。包 `report-failure.sh`、停止丟棄輸出、把判決印在傾印之後。這一步**不是繞路**：它一次修好所有後續的同類失敗，而猜根因只修這一次。
5. **最後才是借權杖讀 log。**

## 讓下一次的失敗自己說話

改 CI 腳本讓它更會報告時，有一個地方會把紅燈改成假綠，動之前先驗：

- **在管線裡加 `tee` 之前，先確認失敗狀態傳得出來。** `set -o pipefail` 之下 `cmd | tee f` 會回傳 `cmd` 的失敗，但這件事**值得用一次兩行的實驗證實**，而不是憑記憶——寫錯的代價是往後所有失敗都變成綠燈。
- **等待迴圈數的是次數，不是秒。** `for _ in $(seq "$limit"); do ...; sleep 1; done` 的實際牆鐘是 `limit ×（探測耗時 ＋ 1 秒）`；如果每次探測是一個 `docker run`，那可能是宣稱值的兩三倍。訊息要嘛報實測秒數，要嘛別講秒。**放寬或縮緊這個預算是行為改變**：縮緊會把「比較慢的 runner」變成新的失敗，不要順手做。
- **放棄之前多探測一次、並把輸出印出來。** 迴圈裡的探測通常靜音，最後那一次不該靜音。

## 綠燈也要能分辨兩種狀態

看不懂的綠燈與看不懂的紅燈一樣沒有用。這一節和上面是同一個道理的另一半：**訊號要能分辨兩種狀態，否則它不是證據。**

- **整批跳過的測試會報成功。** 缺 daemon、缺 node、缺可寫的 cgroup 子樹時，測試跳過而 job 是綠的。這個 repo 用 `SKILLHUB_REQUIRE_DOCKER=1`、`SKILLHUB_REQUIRE_CGROUP=1` 把「環境不支援」由跳過變成失敗——**在該有那個能力的工作上一定要帶這些旗標**，否則綠燈只證明測試檔存在。
- **反方向也要守。** `sandbox-nodocker` 把 `DOCKER_HOST` 指向沒人在聽的位址，讓新長出來的容器依賴當場變紅而不是靜默跳過。兩個方向合起來才說得出「這套測試不需要容器，而且它的上限真的攔得住」。
- **沒有 path filter 觸發的 job，等於被靜音。** 一個區域長期沒被改到，它的 job 就不會跑；`task ci:status` 會列出「被跳過」的 job，那不是綠燈。一份紅了一陣子的測試可以這樣藏很久，直到某次不相干的改動把它喚醒。判斷「main 是綠的嗎」要看**跑過的 job 有哪些**，不是只看最後那個結論。
