# ADR-046：從任務描述生成 Skill——生成物是工作區私有，不是目錄的第四層

- 狀態：Accepted
- 日期：2026-08-23
- 相關：[ADR-013](./ADR-013-intent-search-architecture.md)（檢索與無結果）、[ADR-016](./ADR-016-language-and-framework-selection.md)（Go／Python 分工）、[ADR-017](./ADR-017-model-gateway-and-llm-observability.md)（唯一模型閘道）、[ADR-021](./ADR-021-skill-license-provenance.md)（License 溯源）、[ADR-027](./ADR-027-download-artifact-shape-reproducibility-and-integrity.md)（四道鎖）、[ADR-028](./ADR-028-beta-admission-and-quota-enforcement-points.md)（配額強制點）、[ADR-044](./ADR-044-agent-skills-specification-conformance.md)（規格釘選）、[ADR-045](./ADR-045-self-supplied-content-is-not-redistribution.md)（同一把尺的第一個案例）、`01` §2.1／§7.3／§10／§12、`02` §4.9（`GEN-001`～`004`）、`03` §19、`04` 乙-21、丙-38

## 背景：一個 persona 走到一半就沒有路了

`01` §2.1 把三種成熟度都列為主要 persona，第一種逐字是「**學習者：有明確任務意圖，但不了解 Skill 規格與建立方式**」，產品原則 1 也承諾「使用者不需要先理解 Skill 規格才能開始」。

產品給這個人的路不是「教你寫」，是**你永遠不從零寫**：`/suggest-criteria` 幫他出驗收條件，`/suggest-improvements` 回的是 `proposed_content`（完整檔案內容，不是 diff），他從頭到尾不必打開編輯器。這條路是真的，但它有兩個前提：

1. **三類精選內容涵蓋得到他的任務。** 精選只有 `documents`／`writing`／`data`（PDM-001）。落在三類之外就掉到「外部結果」層，而那一層**要使用者自己提供 URL**——一個不會寫 Skill 的人，通常也不知道去哪找 Skill 的 URL。
2. **Fork 來的 Skill 與目標只差微調。** 改善迴圈能把一句話改對，**不能長出新的檔案**：`evaluate.py` 的 prompt 寫死「Propose content only for a file whose current content you were given」。

兩個前提都不成立時，使用者看到的是 `Home.tsx` 的「沒有夠接近的 Skill」加一句改寫建議，**然後就沒有了**。

而在此之前，這件事的狀態是第四種：**沒人決定過**。`01` §7.1 沒收、§7.2 沒收、§7.3 沒排除、`02` 六十四個章節沒有一個是它（`04` 乙-21）。本 ADR 結束這個狀態。

**這不是在推翻 MVP 承諾。** `01` §3 的承諾逐字是「找到一個可能符合需求的 Skill……下載可安裝的版本」，沒有一個字說「做出一個新 Skill」——所以 MVP 沒有違約，本 ADR 開的是 MVP 之後的路（決策 1）。

## 決策 1：這條路開，列 **M5**，MVP 範圍一個字都不動

`01` §10 新增 M5 里程碑。**`01` §7.1／§7.2 不動**，§7.3 補一列指向這裡。

理由是時序不是意願：M1 的驗證閘門 D 日仍未宣告，`03` §18 的 `RELEASE-001`～`010` 十項全部不勾。**封測漏斗的第一段量的正是「輸入意圖後查看至少一個 Skill 詳情的比例」**——那個數字要在「沒有第二條出路」的條件下量，才知道搜尋本身夠不夠好。此時把生成插進 MVP，等於在自己要買的資訊上先加一個變數。

**但「列 M5」不等於「先不寫規格」。** 照 `TEST-003`／`TEST-004` 的既有慣例：ID 在、允收準則在、標明啟動條件。規格先立的成本是幾頁文件，晚立的成本是下一個人重新問一次同樣的四個問題。

## 決策 2：生成物只在個人工作區，**不進公開目錄**——`tier` 不新增第四態

`discovery/tier.go` 的三態 `curated`／`indexed`／`external` 全都是**「經過多少人工檢視」的階梯**，不是「東西從哪來」的分類。生成物在這把尺上一個格子都不符合：沒有人檢視過（不是 curated），不是從平台外匯入的（`tier.go` 的 `TierIndexed` 逐字是「imported and passed static validation」——**2026-08-23 訂正：原文誤寫成它「帶『已取得來源』」，那個性質其實掛在 `TierCurated` 底下**；結論不變，生成物沒有經過匯入），也不是從平台外找到的（不是 external）。

**不進目錄，這個問題就整個不存在**：不必新增第四態、不必進搜尋索引、不必回答 `DISC-002` 的來源層級篩選要不要多一個值、不必碰 `CONTENT-001`～`009` 的收錄政策。這也與 §7.3「MVP 不包含完整公開發佈與創作者 Marketplace」一致。

使用者對自己生成的 Skill 能做的事，與他對自己匯入的 Skill 能做的事完全相同：看得到、試跑得了、改得動、下載得了。**別人看不到。**

**代價寫在這裡而不是留給下一個人踩**：這表示生成物**不會**在搜尋結果裡出現，包括生成它的人自己搜尋時。工作區的 Skill 列表是它唯一的入口。若日後要讓它進目錄，那是一條新路徑，本 ADR 只保證它出現時必須先回答「誰檢視過」。

## 決策 3：新增獨立的 `POST /v1/generate-skill`，**不放寬改善迴圈的 prompt**

`apps/llm` 已有六個單次閘道端點（`embed`／`enrich-skill`／`match-reasons`／`suggest-criteria`／`judge-run`／`suggest-improvements`），每一個都是「收結構化請求、回結構化結果」，政策與狀態全在 Go（鐵律 6）。加第七個是同一個模子。

**否決「放寬 `evaluate.py` 的 prompt 允許新增檔案」**，儘管 `apply.go` 的 `patchArchive` 早就處理得了套件原本沒有的檔案、門只是 prompt 關的。理由是那條路的防線整條落空：`suggest.go` 的 `suggestionEvidence` 要求提案的引文逐字出現在平台放進 digest 的 excerpt 裡（ADR-043、丙-38），**從零沒有既有版本、沒有 Run、沒有 excerpt**。在同一個端點裡養兩套語意，等於讓那條防線變成「有時候成立」——而丙-38 剛剛才示範過，一個沒有跟任何東西對帳的判準，失敗起來長得跟「模型真的沒話說」一模一樣。

**推論（不是額外規則，是這個決策的一部分）**：生成**不以任何既有 Skill 版本為輸入**。以既有版本為起點的事叫改善，那是 `EVAL-002` 的地盤，走 `suggest-improvements`。兩條路在輸入上就分開，不必靠註解維持。

**不引入 agent framework**——沿用丙-38 同批的裁定：若「生成 → 打包 → 驗證 → 沒過帶錯誤碼重來」這個迴圈要做，**它寫在 Go**（Go 已經有 zip、有 `skillpkg.Validate`、有重試政策），呼叫 `apps/llm` N 次，Python 端一行都不用改。而 Go 裡的那個迴圈是一個 `for`。

## 決策 4：`skills.redistribution` 新增第五個值 `generated`

ADR-045 決策 4 的判準逐字是「**平台有沒有多加一個散布環節**」。生成物：位元組是平台的模型應這個使用者的要求產生的，只落在他自己的私有工作區，只有他讀得到。交還給他，平台沒有多做出一個他自己做不到的散布動作。**同一把尺，同一個答案：下載得了。**

**但它不共用 `self_supplied` 這個值**，因為兩者在 ADR-045 留下的那個待決策上答案不會一樣：「`self_supplied` 的內容要不要能發佈到目錄」問的是「這份別人寫的東西你有沒有權利散布」；生成物問的是「模型寫的東西的權利歸屬是什麼」。**兩個不同的問題共用一個值，日後只會有一方被錯誤地一起放行。** 一行 CHECK 的成本，換一個未來分得開的狀態。

`generated` 與 `self_supplied` 一樣**刻意不寫成 `allowed`**：任何未來的發佈路徑都必須停下來要求判定。

## 決策 5：生成器**不得寫 `license` 欄位**

生成物沒有上游，所以 `SKILL-004` 的多層溯源在它身上沒有東西可以溯。剩下的問題只有一個：frontmatter 的 `license` 填什麼。

**答案是不填。** 模型寫出來的 `license: MIT` 是一個**編出來的宣告**，而 `02` §3 的 License 狀態三態（未知／已宣告／已人工確認）裡，「已宣告」的意思是**有人宣告過**。讓模型佔用那個狀態，就是把平台自己造的字串當成使用者的意思表示。

生成物的 License 狀態預設 `unknown`，由使用者在建立後自行宣告。**`unknown` 在這裡不擋下載**（決策 4 已經開了那道鎖），但它擋住每一條未來的發佈路徑，而這正是我們要的。

## 決策 6：唯一的門是 `skillpkg.Validate`，而生成的 Script 不享有任何寬待

生成物走 **admission 的同一條驗證路徑**寫版本——與 `apply.go` 的 `validatePatched` 同一把尺：**一條不過，整個生成結果拒絕，不建版本**。ADR-044 釘選的 Agent Skills 規格對它一體適用。

不另立品質規則。理由是我們沒有能力在建立時判斷「這個 Skill 有沒有用」——**那正是試跑存在的原因**，而使用者手上已經有那條路。

**這道門是語法門，不是品質門——寫在這裡，免得下一個人把它讀成保證。**（2026-08-23 同批查證補記，非決策變更）`skillpkg.go` 的**阻擋級**檢查全部是結構性的：`SKILL.md` 在不在、frontmatter 是不是合法 YAML、有沒有規格外的欄位、`name` 的大小寫格式與長度、`description` 在不在與長度、壓縮檔的路徑逃逸。**一個被告知格式的模型幾乎必定全數通過。**

**⚠️ 2026-08-23 第三次訂正：上面那句列舉漏了一個，而漏掉的那個不是結構檢查** → [ADR-048](./ADR-048-not-every-blocking-finding-is-a-random-slip.md)。`SeverityError` 實際有 **12 個 code**，第 12 個是 **`possible-secret`**（`skillpkg.go:900`）——它對**每個檔案的內容**跑六條憑證樣式 regex，命中即阻擋，而 `Validate()` 一定會呼叫 `scanTree`。spike 的 20 個樣本剛好沒撞到它，所以這個錯誤沒有在數字上留下痕跡，**只留在句子裡，而句子被抄了三份**。正確的說法是：**11 條結構／語法檢查，外加一條內容檢查**。這一條直接影響決策 6「生成的 Script 不享有任何寬待」——**它是唯一一條會因為 Script 內容而阻擋的規則**，而原文偏偏漏了它。

**⚠️ 2026-08-23 稍晚實測：這句話錯了，是 80%** → [report-generate-spike.md](../plans/mvp/m5/report-generate-spike.md)（20 段任務描述，`gpt-5.6-sol`，閘道實付 $2.3684）。**但錯的方向有用**——四次失敗沒有一次是「模型答不出來」：**三次是同一個 YAML 縮排手滑**（frontmatter 第二個鍵前面多一個空格，`frontmatter-invalid-yaml`），**一次是 `max_tokens=8000` 截斷**（整個結果化為零，不是一個品質差的套件）。下面兩個推論的第 1 點因此推翻，第 2 點被證實且比預期嚴重。兩個推論：

1. ~~**「待決策」的第 2 項（重試次數上限）大概率是一個不存在的問題**——沒有東西可重試。~~ **實測推翻**：問題存在（3／19 撞同一個 code），但**很便宜**——那是隨機的排版手滑不是系統性的能力缺陷，**單次重試就夠**。
2. **真正的風險方向與原本設想的相反**：不是「生成物一直被擋、使用者卡住」，而是**「幾乎什麼都擋不住，而使用者已經付過錢了」**。**實測證實，而且有一個比預期更難看的案例**：gate-test 的兩張干擾卡（日本機票＋租車、正時皮帶）——**一個 Skill 本來就做不到的兩件事**——各自產出套件且**兩個都通過**。X-1 產出的 `japan-flight-car-planner` 自己的 `compatibility` 欄位寫著它需要網路，**而平台的 Sandbox 預設封鎖網路**（ADR-005／022）：一個付過錢、通過每一道檢查、寫進工作區、在這個平台裡結構性跑不起來的 Skill。決策 6 的第一句「整組拒絕」讀起來像品質保證，**它不是**；擋住壞東西的是試跑與 `GEN-004` 那句「沒有經過任何人工檢視、沒有任何試跑證據」，不是這個驗證器。

這一段不改變決策（門仍然是 `skillpkg.Validate`，也仍然不另立品質規則），它改的是**這個決策可以宣稱到哪裡**——同 ADR-044 對「符合規格」那句話的處理方式。

**Script 的處理逐字與匯入相同**：靜態掃描、`SKILL-003` 的 `SKILL.md` 內嵌程式碼揭露、Sandbox 執行（鐵律 1）。畫面上**不得因為「這是平台生的」而少一個警告**——平台的模型不是可信來源，它只是一個沒有上游的來源。

## 決策 7：入口是「沒有夠接近的 Skill」那一格

`Home.tsx` 的 `no_results` 分支現在只有一句話加一句伺服器給的改寫建議。生成的入口接在那裡，以及工作區的 Skill 列表。

**首頁不放一個對等的「生成」按鈕。** 那會把一個十分鐘旅程的第一步變成二選一，而其中一條是要花錢、沒有任何證據、且使用者還沒有任何判斷依據的那條。先搜尋、搜不到再生成，這個順序本身就是產品意見。

## 影響

### 正面

- 學習者 persona 第一次有一條走得完的路，而且是產品原則 1 承諾的那一種（不必先理解 Skill 規格）。
- 生成物與匯入物在版本、驗證、試跑、評估、打包上**共用同一套機制**，新增的只有生成那一步。
- 「這條路存不存在」不再是一個要靠讀 `04` 的旁註才答得出來的問題。

### 成本與限制

- **多一個花錢的入口。** 生成是一次模型呼叫，走 LiteLLM 閘道（ADR-017），套用 ADR-028 的既有配額強制點。封測期間它會與試跑競爭同一份免費額度。
- **`redistribution` 的第五個值**：`delivery`／`discovery`／`registry` 各有一份這組字串的副本（既有狀況，非本批引入），真正綁住它們的是資料庫的 CHECK。
- **生成品質沒有基線。** 丙-38 量的是**改善提案**的品質（53 次評估 → 37 筆提案 → 24 筆存下，`ApplyPreview` 16/16 `applicable`），那個數字**不能外推到生成**：改善有既有內容當骨架，生成沒有。M5 開工前要有自己的一批（`03:GEN-009`）。
- **生成物看起來像一個 Skill，但它從來沒有被任何人或任何 Run 檢視過。** 這是本 ADR 引入的最大的新風險，已補進 `01` §12 風險表。決策 2（不進目錄）與決策 6（不寬待 Script）是它的兩個緩解，**但畫面上還必須說出來**——`GEN-004` 的準則。

### 原文（2026-08-23 裁定前）

- **生成物要不要能發佈到目錄，以及那條路徑要求什麼。** 與 ADR-045 的同名待決策是**兩個問題**（決策 4）：這一個問的是模型產出的權利歸屬。今天沒有這條路徑。
- **生成失敗幾次算失敗。**（~~2026-08-23 補記：優先序下修，這個問題可能不存在~~ **同日稍晚的實測推翻了那個下修**，見決策 6 的實測補記。）第一次就過的比率是 **16／19**，三次失敗**全部**是 frontmatter 第二個鍵多一個空格。**單次重試就夠**，這一項的剩餘問題縮小為一個政策問題：**平台要不要直接把那個空格修掉再打包？** 那不是 bug fix ——它是平台去改模型交出來的位元組，而生成物的來源紀錄要說得出「這份東西是誰寫的」。三個選項（純重試／重試前先修／不修不重試由使用者按按鈕）都成立，本 ADR 不代決。
- **`max_tokens` 上限與截斷的處置。** 實測 1／20 在 8000 output token 被截斷，結果是零而不是一個較差的套件。`02:GEN-001` 需要一條準則：上限是多少、截斷時使用者看到什麼、**那次呼叫的錢已經付了要不要算進額度**。
- **生成的單次成本高於一次試跑。** 實測 $0.113／次（flagship 級），而試跑預設是 mini 級（PDM-003）。ADR-028 的配額設計假設「額度的主要消耗者是 Run」，這條路開了之後不再必然成立。
- **生成物能不能當 Fork 的來源。** `WS-001` 的 Fork 準則預設有原始 Skill 與 License 關係；生成物兩者皆無。M5 範圍內不提供，但沒有機制阻擋它日後成立。
