# ADR-022：淨測試模式

- 狀態：Accepted
- 相關：[ADR-002](./ADR-002-data-ownership-and-core-infrastructure.md)（資料所有權與核心基礎設施）、[ADR-003](./ADR-003-run-orchestration-and-async-workflows.md)（Run 編排與非同步工作流程；Provider Port／Adapter 的既有形狀）、[ADR-004](./ADR-004-sandbox-isolation-and-execution-security.md)（Sandbox 隔離與執行安全；`isolation.level` 的既有紀律）、[ADR-006](./ADR-006-identity-workspace-admission-and-allowances.md)（身分、Workspace、准入與額度；「授予＝改部署環境」的既有先例）、[ADR-007](./ADR-007-packaging-license-provenance-and-redistribution.md)（打包、授權溯源與散布；「自帶內容不等於可信」「放行要具名證據」的既有先例）、[ADR-016](./ADR-016-platform-bounded-contexts-and-context-map.md)（Platform Bounded Context 與 Context Map；`cmd/api`／`cmd/worker` 兩個 deployment unit 的既有規則）

## 背景

系統的完整跑法依賴 Docker、PostgreSQL 與容器 runtime；在一台只能執行白名單內程式、不能安裝軟體、對外網路除模型供應商外不保證的機器上，今天一行都跑不起來。這類機器不只是展示現場的特例，也是部分開發者的日常環境——而在沒有資料庫的環境下，控制平面套件的多數測試不是失敗，是**靜默跳過**，看起來全綠的畫面量的其實只是一部分行為。

問題收斂成：在這樣一台機器上，如何跑起同一套產品程式（資料庫、檔案儲存、沙箱三個依賴），而不是另外造一個示範用的系統；以及跑起來之後，凡是與正式環境不同的地方（沒有隔離、單連線、不驗證物件授權），必須讓使用它的人看得見，不能靠文件或記憶維持誠實。

## 決策

### 決策 1：淨測試模式是同一套產品程式，以單一旗標切換三個實作，不是另一個系統

資料庫存取、檔案存取、沙箱三條軸各自是一個 Port 兩個 Strategy（生產實作／淨測試實作）；旗標 `SKILLHUB_CLEAN_MODE` 未設時，行為與生產**逐位元相同**，這是「平行、不干擾」的可檢驗形式。

不得為三條軸各自開一個環境變數：三者描述的是同一件事（這台機器裝不了東西），分開開關會讓「一半淨測試、一半生產」成為一個沒有人設計過、也沒有人會測的可達組態。

合併入口是既有二進位（`cmd/api`）加這一個旗標，不是第三個二進位：淨測試模式下 `cmd/api` 額外在同一個行程裡啟動 worker。選擇點只有一個，在 composition root（`cmd/api` 的 main），不在任何 Generic 套件內部分支（例如不進 `objstore.FromEnv()` 內部）——三條軸的實作在那裡被選定一次，往下注入。

這是 [ADR-016](./ADR-016-platform-bounded-contexts-and-context-map.md)「`cmd/api` 與 `cmd/worker` 是兩個 deployment unit、共享零個物件」的唯一例外，且只在旗標開啟時發生：生產路徑的兩個二進位一個字不改；worker 的組裝根（無 I/O、無環境變數讀取）與 `cmd/api` 對稱地放在 `internal/entrypoint/worker`。

### 決策 2：資料庫這一軸用 PGlite，前提是單行程 ＋ 佇列改為 poll-only

資料庫的候選必須通過同一個判準：**能不能讓對不可變版本（如 `skill_versions`）的 `UPDATE` 真的被資料庫擋下**——這是最便宜、也是唯一能分辨「真資料庫」與「行為相似的假資料層」的測試；純 Go 手寫的資料層與 SQLite 都通不過這個判準（前者不存在資料庫強制的規則，後者連 schema 本身都套不上）。PGlite（PostgreSQL 編譯為 WASM）是在不安裝任何東西的前提下仍然通過此判準的候選，migration 全套可套用。

另一個同樣通過此判準的候選是在模擬環境中執行未經修改之 PostgreSQL 主程式；不採用的原因不是它通不過判準，而是隨附版本缺少 pgvector 擴充、移植風險難以評估。它被留在這裡而非捨棄，是作為單行程形狀一旦無法成立時的已知備援。

讓它在有後端的形狀下成立的條件是：

- 單一行程內同時承載 API 與 Worker，而不是生產的兩個獨立二進位。
- 連線池 `pool_max_conns=1`；PGlite 的 multiplexer（一條實體連線偽裝成多個 session）必須關閉——multiplexer 打開會讓多條連線同時拿到同一把 advisory lock，使本專案賴以互斥的機制安靜失效，因此是禁用組態。
- 佇列客戶端以 `PollOnly` 模式啟動（不發 `LISTEN`），使單一連線的池子足以同時服務查詢與工作領取。
- Outbox 的 publisher 不得跨越整段投遞流程持有那唯一一條連線：在 advisory lock 下批次領出後即釋放連線，再逐筆投遞；否則會與 consumer 對同一個池子搶連線造成死鎖。
- PGlite 與其 pgvector 擴充的版本需與 CI 使用的 PostgreSQL 主版本一致，並在工具鏈版本清單中對帳。

工作負載（`run.mjs`）的環境變數契約在兩個 Driver（本機與容器）各自維護一份，不抽成共用套件。

### 決策 3：檔案存取這一軸用行程內承載，並揭露它不驗證物件授權

`apiserver.ObjectStore` 介面已存在；淨測試模式的實作是行程內承載，選擇點與其餘兩軸相同，在 composition root。此承載必須明文宣告它不驗證 presigned URL，且不得被引用為安全驗收（沙箱物件授權相關項目）的證據——同一組驗證斷言對正式的 S3 相容儲存全數通過、對此承載全數落空，差異本身就是宣告的依據。

### 決策 4：沙箱這一軸用本機行程 Driver，宣告等級為「沒有邊界」

`sandbox.Driver` 介面已存在，淨測試模式新增第二個實作：在主機上直接 spawn 與容器內相同的單一工作負載（`node run.mjs`），把容器目錄換成主機目錄。它向派送邏輯宣告 `isolation.level = "clean"`——**這個名字讀作「沒有邊界」，不是「比較弱的邊界」**，只承載策展過的展示素材，永遠不承載不受信任的內容。

隨此新增等級，派送閘門從黑名單改為白名單：`gvisor` 各處可用、`container` 需要開發登入旗標、`clean` 需要 `SKILLHUB_CLEAN_MODE`，其餘任何值一律拒絕；新增等級從此必須先被明確列入白名單才能通過派送檢查。

不引入第三方行程管理依賴——沒有成熟、活躍、真正跨 Windows／Linux 的現成方案；改用已在依賴樹中的 `golang.org/x/sys`（Windows Job Object API）加約 120 行，以及標準庫 `archive/tar`。

四個平台限制以型別宣告，並由測試對照宣告斷言，不寫在註解裡：

1. **淨測試模式下 `Adopt()` 回空**：服務重啟會終止所有進行中的 Run。取捨是刻意的——留下孤兒行程樹比丟掉一次 Run 的代價更高。
2. **資源上限兩平台不對稱**：Windows 的 Job Object 可在不需管理員權限下限制記憶體、行程數與 CPU；Linux 在無 root 時沒有等價機制（需要 systemd 委派 cgroup 才能使用，須執行時偵測後降級），共同的最低保障是工作負載本身的記憶體上限旗標。宣告必須反映實際偵測到的能力，不是意圖。
3. **行程樹回收不對稱**：一個刻意讓自己脫離行程群組的子孫行程，Windows 上會被連帶回收，Linux 上不會（更貼近的修法成本都高過此 Driver 的用途）。介面以 `Reaping()` 回傳 `{Descendants, Detached}`（Windows 皆為真、Linux 僅前者為真），測試按此宣告逐項斷言，日後若某平台被修好，變動會反映在宣告上而不是被默默吃掉。
4. **`Stop(grace)` 的等待時間在兩個平台都不是合作式關閉窗口**：工作負載本身沒有訊號處理常式，這是既有行為而非本 Driver引入；真正用來收集執行結果的機制是既有的完成標記檔案。

本 Driver 與 `clean` 等級是為特定機器限制而存在的暫時性設計，不是永久架構：當展示需求不再需要在受限機器上執行，或該機器的白名單改為接受可自帶的啟動器（使真正的隔離變得可部署）時，應重新評估移除；移除不需要新的 ADR，只需要清空這裡列出的三個接縫（新增的 Driver、白名單項目、依賴）。

### 決策 5：不受策展限制內容的執行，以逐版本、具名理由的方式在部署設定裡個別放行

派送前的強制檢查只放行目錄工作區的內容，或指定 curation 等級且正是那一版的內容；使用者自行上傳、Fork 或生成的 Skill 版本預設無法在此模式下執行——這道限制是刻意的，因為此模式的 Driver 沒有任何隔離邊界，而平台無法分辨「自己寫的」與「從別處取得再上傳的」內容（見 [ADR-007](./ADR-007-packaging-license-provenance-and-redistribution.md)），所以「這是我自己的」不能作為「可以在無沙箱環境執行」的依據。

放行規則：

- **放行單位永遠是一個 Skill Version，不是一個 Skill**——否則下一次推版會自動放行一批沒有人看過的位元組。
- **放行的宣告在部署設定裡，不在產品 UI 裡**：具體形式是一個檔案，一行一筆 `<skill_version_id> <理由>`。此模式下任何到得了頁面的人都能以任何身分登入（含最高權限身分），所以一個長在 UI 裡、按得下去的放行按鈕，按得動它的人就包含剛上傳那個版本的人——這正是本限制要擋的對象；讓放行只能透過改部署設定並重啟達成，與 [ADR-006](./ADR-006-identity-workspace-admission-and-allowances.md) 對單人團隊自我提權已給過的答案一致。
- **具名理由就是控制本身，不是附加的文件工作**：沒有理由的一行不算放行。使用時另外留下一行執行期警告，記錄 Run、版本與放棄了什麼；刻意不寫進資料庫層的稽核事件——此模式的資料庫是關機即消失的記憶體內執行個體，比終端機裡的那一行更不可靠。
- **拒絕訊息必須指名那一版的 id、放行檔案的路徑，並說明沒有理由的一行不算放行**；變數未設定與已設定但未放行，要給出可區分的訊息。
- **此機制只在淨測試模式內存在**：生產環境下即使誤設了對應的檔案與變數，判斷邏輯在更早的分支就已經返回，一行都不會被讀取，並由測試證明「讀得到就會出聲」以避免兩種情況都是綠燈。
- **放行不會過期，也不隨後續版本變動而擴大**：它綁定一個不可變的版本 id；要收回就刪除那一行。

## 影響

### 正面

- 在完全無法安裝軟體的機器上，也能展示一次完整的 Run 生命週期（開始、執行、取回產出、清理），且資料庫查詢是真的執行、搜尋排名是真的算出來，不是預先排好的順序。
- 旗標未設時，生產路徑的行為與程式碼路徑完全不受影響。

### 成本與限制

- **單連線是永久性質，不是暫時缺陷**：淨測試模式下的併發語意與生產不同，任何「在淨測試模式下沒有重現的問題」，都必須先排除這項差異才能下結論。
- 此模式完全沒有執行隔離；唯一的防線是決策 5 的具名逐版本放行機制，且該機制刻意設計得不方便使用。
- 資源限制與行程樹回收在 Windows／Linux 兩平台的能力不同，以型別宣告並由測試鎖定，而不是隱藏在文件裡。
- 依賴一個目標機器上必須存在、但不由本專案控制的事實（該機器的白名單是否接受所需的執行環境）；此事實不成立時，此 ADR 的資料庫與沙箱兩軸都無法運作。

## 待決策

- 淨測試模式產生的 Run，要不要寫入正式的 Run 歷史——它們是真的 Run，但跑在沒有隔離、單連線的環境下，混入既有歷史會讓「歷史 Run 可追溯 Provider 與 Runtime」這句話多一種讀法。
- `Adopt()` 在此模式下回空這件事，要不要在畫面上呈現，而不只是終端機看得到。
- 決策 5 的放行被用到時，要不要也在 Run 的畫面上說出來——今天只有終端機知道這一版是被放行跑的，讀 Trace 的人看不出這次執行沒有經過策展。
- 決策 5 的策展限制判斷，要不要提前到使用者投入多個步驟之前（例如上傳或 Fork 當下）就先擋下，而不是在派送當下才拒絕。
