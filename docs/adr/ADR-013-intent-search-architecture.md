# ADR-013：意圖搜尋採混合檢索與索引時 LLM 增強

- 狀態：**Accepted**（2026-08-14 定案；原定案條件「PDM-011 Spike 結果、PDM-001 首批類別確認」皆已滿足，見文末「定案紀錄」）
- 日期：2026-08-13（提出）／2026-08-14（定案）
- 決策者：產品負責人、架構規劃

## 背景

DISC-001 要求使用者以任務描述搜尋 Skill，並顯示每個候選的符合原因。這是產品風險表的第一條（搜尋結果多但難以選擇），也是整條漏斗的入口。

限制條件：

- 使用者的任務語言與 `SKILL.md` 的技術詞彙往往不重疊，純關鍵字比對召回率差。
- NFR-004 要求已索引內容搜尋 p95 小於 2 秒，排除每次查詢都讓 LLM 閱讀候選內容的作法。
- 初期語料很小（三個類別、每類少量精選 Skill），不需要獨立搜尋引擎的規模。
- 搜尋索引依 ADR-003 是可重建投影，不是事實來源。

## 評估選項

### 選項 A：純全文檢索（BM25 / Postgres FTS）

- 優點：實作最簡單、延遲最低、無模型成本。
- 缺點：任務描述與 Skill 內容詞彙不重疊時召回率差，正是本產品的核心查詢型態；無法生成有意義的符合原因。

### 選項 B：純向量檢索（Embedding）

- 優點：語意相近查詢召回好；語料小，嵌入成本可忽略。
- 缺點：無法精確過濾結構化條件（來源層級、是否含 Script、驗證狀態）；對精確名稱／工具查詢反而不如 BM25；分數無法直接解釋為符合原因。

### 選項 C：查詢時 LLM 即時閱讀候選並排序

- 優點：品質上限最高，符合原因最自然。
- 缺點：每次查詢的延遲與成本最高，違反 NFR-004；未登入搜尋開放時成本不可控。

### 選項 D：混合檢索＋索引時 LLM 增強（建議）

把 LLM 成本移到索引時（每個 Skill Version 一次），查詢時只做輕量處理。

## 決策

採選項 D，分三段：

### 1. 索引時增強（每個 Skill Version 執行一次）

- LLM 讀取 `SKILL.md` 與套件結構，生成：任務導向白話摘要、適用任務範例句、輸入／輸出／工具／依賴標籤。
- 產出寫入 Skill Search Document（ADR-003 的可重建投影），連同 Embedding 一併保存。
- 生成內容標示為模型產出，錯誤可由人工修正並觸發重建。

### 2. 查詢時檢索

- 輕量 LLM 查詢改寫：使用者意圖 → 任務關鍵詞＋結構化過濾條件；改寫失敗或逾時直接用原句降級。
- 混合檢索：pgvector 向量相似度＋Postgres FTS（BM25）以 RRF 融合。
- 規則過濾與排序調整：來源層級、驗證狀態、相容性（DISC-002 的可解釋排序）。

### 3. 符合原因生成

- 預設由命中欄位以模板生成（「此 Skill 宣告支援＿＿，與你的＿＿需求相符」），零額外延遲。
- Top-N 結果可選 LLM 潤飾；逾時或失敗降級為模板版本，不阻塞回應。

### 搜尋基礎設施

初期使用 PostgreSQL（pgvector + FTS）承載，不引入獨立搜尋引擎。拆分觸發條件依 ADR-010：搜尋規模或查詢演進速度成長時再評估 Elasticsearch／Typesense 等專用引擎；因索引是可重建投影，遷移不涉及事實來源。

## 驗證方式

- PDM-011 Spike：每個首批類別建立至少 20 條任務描述的 golden query set，量測 recall@5 與符合原因可理解性；Spike 不通過則回到本 ADR 重新評估選項。
- p95 延遲量測涵蓋查詢改寫降級路徑。
- 索引重建流程可從 Skill Version 事實來源完整重生 Search Document。

## 影響

### 正面

- LLM 成本與 Skill 數量成正比而非查詢量，未登入搜尋可負擔。
- 符合原因有真實依據（命中欄位），不是事後編造。
- 全部落在 PostgreSQL 內，MVP 不新增基礎設施產品。

### 成本與限制

- 索引時增強的品質決定搜尋上限，需要人工抽查機制。
- 查詢改寫與潤飾引入兩個降級路徑，需明確逾時與 fallback 行為。
- Embedding 模型更換需全量重建索引（語料小，成本可接受）。

## 定案調整 4（2026-08-29 追記）：RRF 融合已被拿掉，改為 UNION 候選擴充

**不改寫上方任何一段決策文字**（AGENTS.md：決策歷史不原地改寫）。本節記錄的是**實作已經與「決策 §2」的一句話分岔，而分岔有量測依據、卻沒有任何文件承接**——直到今天。

**分岔的內容**

| 寫在哪裡 | 逐字 |
| --- | --- |
| 本 ADR 決策 §2 | 「混合檢索：pgvector 向量相似度＋Postgres FTS（BM25）**以 RRF 融合**。」 |
| `AGENTS.md` 技術棧速覽 | 「混合檢索（向量腿承載跨語言召回，**FTS＋RRF 為召回覆蓋**）」 |
| `db/queries/search.sql` | 兩腿是 **`UNION`**，FTS 腿只做**候選擴充**；排序完全由 `c.distance` 決定（`ORDER BY c.distance ASC NULLS LAST`）。**沒有 RRF。** |

**為什麼實作是對的，而文字沒跟上**

依據就在上面的**定案調整 3**：「RRF 只是召回覆蓋手段，不是排序品質來源；零命中的腿不得參與融合。」兩次量測（同質腿與異質腿）都顯示等權 RRF 無增益、異質腿下還會倒退，而把零命中腿的字母序排名餵進融合會讓 Top-1 由 8/10 假性下滑到 6/10。**UNION 候選擴充是那個結論的直接實作形式**——兩腿都貢獻候選，排序只由向量距離決定，零命中的腿因此結構上不可能污染排序。

**但「RRF 不是排序品質來源」不等於「不做 RRF」**，而實作取的是後者。這一步是對的，只是它只被記在一段 SQL 註解裡（該註解引用 `golden-query-set.md §3.7` 與本 ADR 的定案調整 3）。**下一個讀本 ADR 或讀 `AGENTS.md` 速覽表的人，會以為 RRF 還在。**

**本次處置**

1. 本節（實作事實 ＋ 量測依據）。**決策 §2 的原文保留**。
2. `AGENTS.md` 技術棧那一列同批改為「FTS 腿為召回覆蓋（**UNION 候選擴充，不做 RRF**）」。
3. **不新開 ADR**：這不是推翻一個決策，是**同一份 ADR 的定案調整 3 被實作到底**，而定案調整正是本文件既有的、為此設計的機制（1～3 已用過三次）。

**重開訊號（滿足任何一條就要重新評估融合，並且要新的量測而不是這一段）**

- **語料規模跨一個數量級**（今天 45 筆策展 ＋ 使用者匯入）。候選窗（50 ＋ 50）在小語料上等於「兩腿都全給」，UNION 與融合的差別因此被壓平；語料大到候選窗真的在截斷時，這個等價關係消失。
- **FTS 腿對中文有了可用的設定**（`02:DISC-005` ⑤ 要求的那個決定）。今天 FTS 腿寫死 `websearch_to_tsquery('english', …)`，中文查詢只答對 20%——**一條幾乎不貢獻中文候選的腿，本來就沒有東西可以融合**。它變得有用之後，「排序只看向量距離」才第一次成為一個真的取捨。
- **向量腿換模型或換維度**。定案調整 1 的跨語言召回讀數綁在 `text-embedding-3-small` 上。

## 定案調整 5（2026-09-06 追記）：詞彙腿看得見中文之後——bigram 覆蓋腿進公開搜尋

**不改寫上方任何一段決策文字。** 本節記錄：**定案調整 4 列出的第二條重開訊號——「FTS 腿對中文有了可用的設定」——已經滿足**，本 ADR 因此第一次重新評估「排序只看向量距離」這個取捨，而評估的結論不是推翻它，是在它旁邊加一條不參與排序競爭的候選規則。

**發生了什麼**：互動創作工具先於公開搜尋在 `05` R-47 定案時量出——公開 SQL 的英文 tsvector 詞彙腿對繁體中文查詢的召回是 **F1@3 0.02**，對這個目錄的查詢分佈等於沒有這條腿；改用字元 bigram（`simple` config，0058 `search_documents.bigram`）之後，創作工具三組查詢集合計 F1 從 0.588 升到 **0.877**。這正是定案調整 4 描述的那個轉折點：「一條幾乎不貢獻中文候選的腿，本來就沒有東西可以融合」，而現在它有東西可以貢獻了。

**`05` R-48 因此裁定接進 `PublicHybridSearchSkills`，形狀是候選擴充不是排序融合**：bigram 腿以「查詢全部 token AND 查詢」為判準生成一個獨立候選集，**覆蓋查詢全部 token 的列不受既有 0.75 向量距離截斷，且排在所有向量命中之前**；名稱完全命中再置頂於覆蓋腿之上；降級路徑（embedding 不可用）同樣加 bigram OR english。

**數字**（golden set 60 題重放，`search-f1/results-public-rule-2026-09-06.txt`）：golden 48 題 Top-1 44／Top-3 48／recall@5 48、干擾 12／12 拒答——**接上覆蓋腿前後三者完全不變**；名稱 31 題 Top-1 30→31；特定詞 25 題 Top-1 7→23、Top-3 10→25、recall@5 11→25。M1 閘門凍結證據（`gate-test §3.2`）因此不需要分開統計：唯一變動的兩組（名稱、特定詞）是新增召回，不是既有召回的排序改變。

**為什麼「排序權在向量」沒有被推翻**：定案調整 4 的結論是「排序只由向量距離決定，零命中的腿不得參與融合」——覆蓋腿沒有違反這句話的字面，因為**覆蓋是一個集合判準（在不在候選集裡、排不排在向量命中前），不是一個分數**。覆蓋列彼此之間、以及非覆蓋列彼此之間，排序依然完全由向量距離決定；覆蓋腿只移動了「向量距離之外，還有沒有別的東西能讓一列先被看到」這一步,它不曾把 bigram 的任何分數混進 `ORDER BY`。這與定案調整 3／4 反對的「等權 RRF 把兩腿分數平均」是兩件不同的事。

**重開訊號（滿足任一條就要重新評估，並且要新的量測而不是這一段）**：

- **語料規模跨一個數量級**（同定案調整 4）——候選窗與截斷在小語料上壓平了很多差異,語料大到窗口真的截斷時,覆蓋腿「不受截斷」這條規則的實際影響會變大,需要重新量它是不是還只影響名稱與特定詞兩類查詢。
- **向量腿換 embedding 模型或維度**（同定案調整 4）——覆蓋腿的截斷判準沿用既有的 0.75／0.55,換模型後這兩個數字本身可能需要重新定。

## 定案調整 6（2026-09-07 追記）：F1 寫死在 k＝正解數；索引文本靠 v7 例句補齊；創作工具改跑公開規則

**不改寫上方任何一段。** 負責人的目標「F1 ≥ 95%」與「資料端也重要」（[report §15](../plans/mvp/m5/creation-measure/report.md)）：

1. **量法**：F1 的定義固定為「頁面截在 k＝正解數」的逐題 F1、干擾題以空頁為對，三組查詢集（golden 60、名稱 31、特定詞 25）平均。F1@1 對兩份正解的題上限 0.67，不再拿它當目標。
2. **資料**：`enrich-skill/v7` 把任務例句加到 6～8 句並規定分布（格式詞＋人的講法、無格式、處境句、逐操作）。三組合計 F1 0.927→0.955，golden 剩下的 miss 全是近義對的第二名。這是**定案 §1「索引時摘要是必要項」的續集**：例句就是索引文本裡「使用者會怎麼問」的那一半。
3. **規則**：創作工具的目錄搜尋不再用自己的 0.55——在 v7 語料上掃截斷，0.75（＝`MaxCosineDistance`）最高且干擾拒答仍 12／12——改跑公開規則（覆蓋優先、名稱置頂、丟掉沒向量的列）。查重守門另有 `CreationDuplicateDistance`＝0.55，因為它問的是同一份而不是相近。
4. **重開訊號**：增強提示或模型再換要重跑 `search_f1_score.py --docs`；生產目錄重做 v7 增強前，線上數字仍是 v6 的（`04` 丙-180）。

## 定案調整 7（2026-09-07 追記）：目錄＝有 metadata 的文件

**不改寫上方任何一段。** `05` R-52 裁定「先資安確認、再抽 metadata、才入庫」，落地方式是**目錄的述詞多一條**：`PublicSearchSkills`／`BrowseCatalogSkills`／`PublicHybridSearchSkills` 的 fts 與 lex 兩條候選腿、以及創作工具的 `CreationLexicalSearchSkills`，一律加上 `(enrichment_status = 'enriched' OR embedding IS NOT NULL)`（`db/queries/search.sql`）。**目錄從今天起的定義是「有 metadata 的文件」，不是「已建立的版本」。**

**為什麼這是這份 ADR 的事而不只是一條 SQL 述詞**：本 ADR 決策 §1 把索引時增強定為必要項（定案調整 4 第 4 條：「索引時的 LLM 摘要與範例句是必要項，不是 nice-to-have」），而在此之前「必要」只約束了排序品質——一份沒有摘要、沒有例句的文件仍然會被回傳，只是排得比較後面或符合原因比較空洞。**這次調整把「必要」升級為「進場門檻」**：沒有 metadata 的文件不只是排得差，是根本不在候選集裡。

**與 ADR-013 既有的「匯入不因增強失敗而失敗」不衝突**：那句話管的是**版本能不能建立**——`skillpkg.Validate` 通過就建版本，增強失敗只讓那個版本的 `enrichment_status` 停在 `pending`。**這次調整管的是建立之後、版本能不能被別人搜到**：兩者是管線的不同階段，`pending` 的版本現在既建立成功、也對擁有者以外的人不可見，直到每小時的 backfill（`ListPendingEnrichment`）把它補進 `enriched`。

**`partial_index` 的語意因此收斂**：在此之前它涵蓋「完全沒有 metadata」與「有 metadata 但沒有向量」兩種殘缺；前者現在直接不進候選集，不會再以 `partial_index` 的身分被回報——這個旗標今天只剩後一種情形（`02:DISC-002` 已同批加一句補充）。

**生成品也走同一道門**：`admission.Service` 的 `sourceGenerated` 分支不再跳過 `enrichPackage`，`ListPendingEnrichment` 的 backfill 也不再排除 `source_type='generated'` 的列——互動創作候選 materialize 之後同樣會被增強一次（約 US$0.01）。**這不改變 `GEN-007`「生成物不進公開搜尋」的保證**：排除仍然做在 `SearchSkills` 的讀取側（workspace／`is_catalog` 範圍判準），這次的增強只是讓查重（`CreationKnowledgeIDs`）與擁有者自己的工作區搜尋看得到它，不會讓生成物越過目錄的邊界。

**生產目錄的重做走新工具，不是本 ADR 的自動生效**：`cmd/reindex` 新增 `REINDEX_REENRICH=<prompt version>` 環境變數（SQL `ResetCatalogueEnrichmentBefore`，把目錄裡不是這個版本的 `enriched` 列退回 `pending` 再交給既有 backfill 重跑）；現有 45 份策展內容仍是 v6 增強，要負責人在部署環境親自執行（約 US$2，見 `05` R-52、`04` 丙-180）。

## 定案調整 8（2026-09-07 追記）：索引文本來自不受信任內容——策展是唯一結構性緩解，放寬准入前必須重量

**不改寫上方任何一段。** 本 ADR 的檢索設計把索引文本交給 LLM 從不受信任的 `SKILL.md` 推出來：決策 §1「索引時增強」如此設計，定案調整 4 第 4 條把它定為必要項，定案調整 7 再把它升級為進場門檻——沒有 metadata 的文件根本不進候選集。這次量測回答的是這條路的另一面：**索引文本可以被寫它的人操縱**，而排名（覆蓋腿判準、向量距離截斷）完全由索引匹配決定，與畫面上寫什麼精選層級或掃描狀態無關。

**最壞情形**（`search_f1_score.py --poison`，索引文本＝golden 句子本身，`docs/plans/mvp/m5/creation-measure/search-f1/results-f1-poison-2026-09-07.txt`）：**投毒文件擠進 Top-3 的題數**——golden 60 題裡有 **32 題**（紅線是 0；這是污染計數，不是正解命中率）；golden 60 題 F1 由 0.914 掉到 **0.525**；116 題合計由 0.955 掉到 **0.754**。

**公平情形**（三份投毒文件也經 `enrich-skill/v7` 正常增強後才入索引，`results-f1-poison-enriched-2026-09-07.txt`）：投毒擠進 Top-3 的題數 golden **37/60**、name **13/31**、token **9/25**；golden 60 題 F1 由 0.914 掉到 **0.786**；116 題合計由 0.955 掉到 **0.889**；**排除投毒後的乾淨題 F1 仍是 0.914**——投毒不是壓低正解排名，是自己擠進候選。

**兩個試過而分不開的訊號**：① tags 格式詞數（`injection/poison_format_words.py`，詞表印在輸出檔首行，`injection/results-format-words-2026-09-07.txt`）——投毒三份是 **5／4／0**，真實 31 份最高是 `docx` 的 **7**（`data-analyst` **6**、p90 **5**、中位數 1），投毒最高的那一份（5）有三份真實文件比它高（7、6、6）、另有三份與它同分，區間重疊；② 任務例句彼此的語意離散度（`injection/poison_dispersion.py`，`injection/results-dispersion-2026-09-07.txt`）——投毒三份 **0.748／0.730／0.689**，真實 31 份最大 **0.758**、p90 **0.683**，投毒完全落在真實分布內。撤回的路：曾在 `enrich_checks` 加一條「格式詞過多／誇大」的 overreach 自檢規則，數字不成立（會誤傷合法的多格式 Skill），已撤回、沒有進碼庫。**結論是這不是參數還沒調好**——兩種情境都沒過線，程式端也找不到能把投毒與合法內容分開的訊號。

**為什麼這是這份 ADR 的事**：投毒能不能被排上前面，取決於「索引文本從何而來、誰能把文件放進索引」，這正是本 ADR 決策 §1 與定案調整 7 的管轄範圍，不是單純的資安檢查清單項目。定案調整 7 已經把「目錄＝有 metadata 的文件」定為進場門檻；這次量測證明**門檻擋住投毒的方式只有一種**——擋在「誰能把文件放進目錄」這一關，而不是靠索引之後的任何排序或畫面規則。

**因此定案（`05` R-53）**：

1. 目錄維持策展——只有人工審核才能把內容放進 `is_catalog` 工作區，這是 OWASP LLM04（資料與模型投毒）**唯一夠格的結構性緩解**。任何「使用者匯入自動進公開目錄」「第三方 Skill 市集接入」一類**放寬准入**的提案，動工前必須重跑投毒量測；畫面上的揭露（精選層級、掃描狀態）不算緩解——本次量測證明排名由索引匹配決定，與畫面上寫什麼無關。
2. 投毒量測列為**常設紅線**——往後每次改索引文本生成規則（增強提示版本）或檢索規則（截斷值、覆蓋腿、詞彙腿），連同 F1 一起重跑 `search_f1_score.py --poison` 與 `--poison-dir`，兩組數字寫進同一份報告。紅線維持嚴格版不放寬（最壞情形也不得進任何 golden 題的 Top-3）：它的用途是放寬准入前的門檻，今天過不了正是「不要放寬」的證據，而不是紅線定錯。
3. 不採納（現在不做）：對僅 `indexed` 層級的結果加 Top-3 曝光上限或延遲策展信號。理由：它防的是「投毒已經進了目錄之後」的擴散，而今天要進目錄必須先經過人；第 1 條已經規定任何放寬前先重量，所以現在做是在猜形狀。**重啟條件**：出現放寬准入的提案、且重量後紅線未過——屆時再設計並回填 `03`。

**不推翻任何既有決策**：定案調整 7「目錄＝有 metadata 的文件」原文不動；這一節加的是它上面一層的前提——**誰能把文件放進目錄**，metadata 門檻管的是「文件有沒有資格被索引」，這一節管的是「文件有沒有資格被放進去讓 metadata 門檻檢查」，兩層互不取代。
