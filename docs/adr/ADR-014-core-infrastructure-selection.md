# ADR-014：核心基礎設施採以 PostgreSQL 為中心的最小受管組合

> **Superseded by [ADR-018](./ADR-018-containerized-core-infrastructure.md)（2026-08-14，方向改為容器化自架）。** 以下內容保留原樣作為決策歷史，不再是現行決策。

- 狀態：**Superseded**（原：Proposed，定案條件為部署平台確認與成本試算）
- 日期：2026-08-13
- 決策者：產品負責人、架構規劃

## 背景

ADR-003／008／010 定義了資料所有權、非同步邊界與部署單元，但未選擇具體產品。團隊規模小，維運能力是最稀缺資源；同時 NFR-006 已要求所有基礎設施透過標準介面（SQL、S3 API、OIDC、OpenTelemetry）接入，供應商更換成本已被架構控制。

## 選型原則

1. 受管服務優先，不自架可以買到的東西。
2. 產品數量最少：每新增一個資料產品，就多一套備份、監控、升級與失敗模式。
3. 只透過標準介面使用，保留抽換能力。
4. 拆分依 ADR-010 的壓力觸發，不預先建設。

## 評估選項

### 選項 A：全自架開源組合（Postgres＋Kafka＋Elasticsearch＋Vault…）

- 優點：無供應商費用、控制力最大。
- 缺點：維運面遠超團隊能力；每個元件都是全天候責任。

### 選項 B：多產品受管組合（受管 DB＋受管 Kafka＋受管搜尋引擎＋Redis…）

- 優點：各元件最佳化。
- 缺點：MVP 規模用不到各元件的強項，卻要承擔全部的整合、監控與帳單複雜度。

### 選項 C：以 PostgreSQL 為中心的最小組合（建議）

MVP 規模下，PostgreSQL 一個產品可同時承載交易資料、全文檢索、向量檢索、工作佇列與 Trace 分割表。

## 決策

採選項 C：

| 能力 | 選擇 | 說明 |
| --- | --- | --- |
| 關聯式資料 | 受管 PostgreSQL | 領域資料事實來源；同時承載 FTS＋pgvector（ADR-013） |
| 物件儲存 | 受管 S3 相容儲存 | 短效授權以 presigned URL 實作（ADR-003 物件存取） |
| Queue／事件 | Postgres 佇列表 | Outbox 與佇列同庫同交易，事件發佈免二段式；以 `FOR UPDATE SKIP LOCKED` 或成熟函式庫實作 |
| Workflow | 自建狀態機＋佇列重試 | 狀態已由 ADR-004／008 定義；補償複雜或人工介入流程增多時再評估 Durable Workflow Engine |
| Run Trace | Postgres 分割表＋大型 Payload 進物件儲存 | 回應 ADR-003 待決策；按時間分割便於保存期限政策 |
| Secrets | 部署平台 Secrets Manager | 平台自身憑證；使用者憑證（後 MVP，隨 MCP）另以 KMS envelope encryption 設計 |
| 身分 | OIDC 相容的受管或函式庫方案 | 不自建密碼系統；社群登入起步 |
| O11y | OpenTelemetry SDK＋受管後端 | 不自架監控棧；後端供應商可換 |

Queue 的拆分觸發：多服務獨立消費、吞吐超出單庫負荷、或需要重播歷史事件時，遷移至受管 Queue（SQS／Pub/Sub 級別）；因 Consumer 已要求冪等（ADR-008），遷移語意不變。

## 影響

### 正面

- 一個資料產品：備份、交易一致性、監控、升級只有一套。
- Outbox 即佇列，消除了「寫庫成功、發訊失敗」這一整類故障。
- 所有元件走標準介面，符合 NFR-006 的抽換要求。

### 成本與限制

- PostgreSQL 成為單一故障域與未來的主要拆分點，需要容量與連線數監控。
- Postgres 佇列吞吐有上限（每秒千級任務內安全），超出即觸發遷移。
- Trace 高頻寫入需批次插入與分割表維護。

## 驗證方式

- 煙霧負載測試：百級併發 Run 的事件寫入與佇列消費延遲。
- NFR-006 契約測試覆蓋物件儲存與 Queue 介面，確認可用替代品通過。
- 備份還原演練涵蓋資料庫與物件儲存的一致性程序（ADR-010 DR 要求）。
