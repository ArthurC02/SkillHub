# ADR-004：Sandbox 隔離與執行安全

- 狀態：Accepted
- 相關：[資料所有權與核心基礎設施](./ADR-002-data-ownership-and-core-infrastructure.md)、[模型閘道與可觀測性](./ADR-005-model-gateway-and-observability.md)、[Repo 結構、CI 與驗證層](./ADR-013-repository-layout-ci-and-verification-tiers.md)、[開發自動化與依賴治理](./ADR-014-developer-automation-and-dependency-governance.md)、[淨測試模式](./ADR-022-clean-test-mode.md)、[外部系統的 Port 與 Adapter](./ADR-024-ports-and-adapters-for-external-systems.md)

## 背景

Skill Hub 的核心功能是執行從網路取得、內容不受信任的 Skill（指令、Script、依賴、外部 URL、MCP 設定與資產）。這不是邊緣情境，隔離強度的預算必須高於一般 SaaS。普通容器並不自動等同安全 Sandbox，尤其當它與 Web 主機、資料庫或容器管理介面共用高權限資源時；格式驗證通過、靜態掃描通過也都不代表執行安全。Sandbox 輸出、MCP 回應與 Dataset 本身還可能夾帶 Prompt Injection 或惡意內容。

需要的是：一套 Zero Trust 的供應鏈與信任模型、一個明確且可驗收的隔離技術與部署拓撲、以及把「安全基線」變成可自動判定的門檻，而不是一句原則性的宣示。

## 決策

### 決策 1：分層信任模型，不用單一「安全」標章

所有外部內容預設不受信任，依下列七個維度分層呈現證據，不得用單一綜合分數取代：

| 維度 | 可能狀態 |
| --- | --- |
| 來源 | 未知、可追溯、人工確認 |
| License | 未知、已宣告、人工確認 |
| 規格 | 有效、警告、無效 |
| 靜態檢查 | 未檢查、通過、警告、阻擋 |
| 執行 | 未試跑、成功、失敗、部分成功 |
| 相容性 | 未驗證、在指定環境通過、在指定環境失敗 |
| 社群／平台證據 | 無證據、使用紀錄、平台精選 |

系統依信任層級分四個安全區域：公開邊界（Web、API Gateway、登入；核心限制是輸入驗證、速率限制、身分驗證）、控制與資料區（應用、資料庫、搜尋、Secrets；僅受信任服務身分可存取）、不受信任執行區（Sandbox Worker、Egress Proxy；無核心資料庫權限、短效存取、預設拒絕網路）、使用者裝置區（本機工具與資料；本機確認、最小路徑範圍、可撤銷裝置）。

### 決策 2：Skill 匯入供應鏈，匯入與掃描階段不得執行套件內 Script

```text
取得外部內容 → 建立 Source Record → Quarantine → 計算內容雜湊
→ 安全解壓與檔案清單 → 解析 SKILL.md → 格式驗證
→ License 與來源分析 → Script／URL／依賴靜態掃描
→ 建立不可變 Skill Version → 建立搜尋投影 → 依證據標示精選或已索引
```

License 辨識規則與其對打包的阻擋效果屬[打包、授權溯源與散布](./ADR-007-packaging-license-provenance-and-redistribution.md)範圍，本 ADR 只定義它在匯入流程中的位置。

### 決策 3：靜態掃描的阻擋等級與執行前重新掃描

每個掃描發現有明確的 Severity：`error` 阻擋、`warning`／`info` 只揭露不阻擋，逐 finding code 指定，不是逐次人工判斷。掃描結果彙總為單一 `Blocked` 旗標。

**執行前必須以套件當下位元組重新掃描一次，`error` 級存在或掃描本身失敗都拒絕執行（fail-closed）**——不得只信任匯入時的舊掃描結果，因為版本或內容可能已變動。

### 決策 4：Provider 架構與最低安全基線

Sandbox 由一個獨立部署在專屬執行區域的 Provider（`SelfHostedProvider`）提供，疊加以下最低基線；後續決策（gVisor、拓撲、Egress）是在這個基線之上加強，不是取代。基線是對任何 Provider Adapter 的要求，不是對某一種技術的要求：換成 MicroVM 或受管沙箱服務時，同一份基線照樣要成立。

**計算隔離**：每次 Run 獨立環境與暫存工作區；非 root、非特權身分；不允許 privileged mode 與 Host PID／IPC／Network namespace；不掛載 Docker 或容器管理 Socket；基礎檔案系統唯讀，只開放明確暫存與輸出路徑；套用系統呼叫／capabilities 最小權限；限制 CPU、記憶體、磁碟、程序數、檔案描述符與最大執行時間；不支援 GPU、特權程序、巢狀容器或長時間背景服務。

**網路隔離**：預設拒絕所有非必要出站；允許的外部服務經受控 Egress；阻擋 Loopback、Link-local、Metadata Service、RFC1918／內部網路及控制平面位址；記錄目的地、協定、決策與資料量，不記錄內容；不接受網際網路主動入站。

**資料與憑證**：Skill、Dataset 與設定以單次 Run 的短效授權取得；Sandbox 不取得平台長效憑證或資料庫權限；Secrets 只在必要時間與程序可見，不落盤、不進 Log；Artifact 上傳限定目的地、大小與有效期；Run 結束（含失敗與逾時）必須清理暫存空間，清理端點可重複呼叫；Run 終止後記錄 `cleanup_status`，不以最終回應成功代替清理確認。物件短效授權採預簽 URL，**沒有撤銷手段**——簽出去即有效到 TTL 為止，這是明示的殘餘風險而非可監控的門檻，窗口上界即簽發時的 TTL（該 Run 硬牆鐘＋5 分鐘）。

**執行映像**：只允許預先建置、版本化與掃描的 Runtime Image；不允許使用者指定任意基礎 Image；映像更新不得改變歷史 Run 記錄中的 `runtime_version`。具體供應鏈治理見決策 13。

### 決策 5：gVisor 為隔離技術基線，執行節點是獨立、不進 Kubernetes 的純 VM 池

以 gVisor（`runsc`）作為使用者態核心攔截層，疊加在決策 4 的基線之上。選擇理由：一般雲端 VM 即可執行，不需裸機或巢狀虛擬化；沿用容器映像與工具鏈；比加固容器（runc＋seccomp）多一層核心攻擊面隔離，比 MicroVM 的維運與部署平台限制輕。

節點編排採**每台 VM 一個主機服務**：每台節點跑 Docker Engine（`daemon.json` 註冊 `runsc` runtime、`icc: false`、`iptables: true`，Run 容器接在預設 bridge），節點上唯一的服務是 `sandboxd`，由 systemd 以非 root 使用者（附 docker 群組）執行並套 systemd 的沙箱化選項；容器只有 Run 的 gVisor 容器與 `sandboxd` 的常駐 P-02 探針。`sandboxd` 不放進容器：它要操作 dockerd，放進容器就得把 `docker.sock` 以可寫 bind mount 掛進去——那正是節點准入 C-01b 擋下的形狀，而且換不到任何隔離，握有 `docker.sock` 就等於握有主機 root。`sandboxd` 的執行檔由 CI 建成映像、以 commit SHA 發佈，節點從釘 digest 的映像取出。不引入 Kubernetes 或任何叢集排程器——調度決策已經在控制平面（依可用 slot 與 egress 模式選節點），第二個排程器只會與它衝突；也不引入 Nomad 等替代叢集技術。

gVisor、Docker Engine 與 systemd 是自建 Provider 內部的 Adapter。`sandboxd` 的執行邏輯只依賴自己的驅動 Port（啟動、等待、停止、移除、讀取 Trace 與 Artifact、探測出口），容器執行期是這個 Port 的一個實作：換成 MicroVM 是新增一個驅動，換成受管沙箱服務是在控制平面新增一個 Provider Adapter。能力宣告由驅動依它實際做到的事回報（例如每個 Run 是否有專屬工作區、資源上限是否被強制），`sandboxd` 不替驅動統一宣稱；控制平面依隔離強度與這些值選節點，不看產品名。

節點以 IaC 建置（cloud-init＋Egress 允許清單），無狀態、不接受手動修改，改動即重建：建置腳本在已建置過的節點上拒絕重跑。節點上的 repo 是**部分 checkout**，只取該角色 `checkout-paths` 列出的部署檔；完整 repo 帶著測試 fixture 裡的資料庫連線字串，會讓節點准入 P-05 失敗，也把節點用不到的程式碼放上一台跑不受信任內容的機器。`sandboxd` 啟動前先確認 nftables 規則已載入、bridge 流量經過 netfilter、`runsc` 已註冊，任一不成立就不啟動。節點入站只開 `sandboxd` 服務埠且來源限控制平面 IP，其餘全部 DROP；SSH 走供應商 console，不作為部署流程的一部分。

**節點以 7 天為週期滾動重建**，另有事件觸發的立即重建：gVisor 安全基準版本變更、逃逸疑慮、該節點清理連續失敗。重建週期不與映像重掃週期同步——兩者換的內容（OS／gVisor 對比 Runtime 映像內容）與變更節奏不同。

> 重評條件：Sandbox 節點數 > 4（與[資料所有權與核心基礎設施](./ADR-002-data-ownership-and-core-infrastructure.md)的對應擴張觸發條件同一門檻、同一理由：手動加減節點成本已超過學習成本），或需要按 Workspace／地區分池而靜態節點清單表達不了時，必須重開編排評估；候選順序是 Nomad 優先於 k3s——因為排除叢集的理由是「不與應用共用編排層」，獨立叢集只是成本問題。

### 決策 6：節點單租戶的單位是「執行平面」，同節點可併存多個 Run，但有強制條件

節點只承載不受信任執行平面的工作負載，不與控制平面、資料平面或任何應用工作負載混排——這是「單租戶」的定義，單位是**平面**，不是 Run，也不是 Workspace。同一節點上多個 Run 併存被接受（per-Run 一台專用 VM 在既有容量與時間模型下不可行；per-Workspace 分池在只有個人工作區時買不到額外隔離卻要多一套池管理），代價由下列強制條件壓住：

| # | 強制條件 |
| --- | --- |
| 1 | 每個 Run 一個獨立 gVisor sandbox，`/work`／`/out` 為該容器私有 tmpfs，不共用任何可寫層、Volume 或快取 |
| 2 | 同節點的 sandbox 之間網路不可達：`--icc=false` 加每 Run 一個獨立網路命名空間，東西向一律 DROP |
| 3 | sandbox 不得連到 `sandboxd` 自身服務埠、節點 bridge gateway 位址或節點 loopback |
| 4 | 節點 7 天滾動重建（決策 5） |
| 5 | 逃逸疑慮成立時的動作是全池緊急停用，不是隔離單一節點 |
| 6 | 沙箱層允許清單的目的地不得是控制平面節點的位址——模型閘道須有沙箱面專屬位址，不得沿用它在控制平面節點上的位址，否則節點單租戶與平面隔離會被一條防火牆規則繞過 |

**明示的殘餘風險**：一次成功的 gVisor 逃逸可觸及同節點其他 Run 執行中的資料。此風險在 MVP 規模下被接受，緩解手段是 7 天重建與一鍵全池停用；一旦威脅模型或多租戶規模升級，對應動作是為高安全等級需求新增 MicroVM 或受管沙箱服務的 Provider，而不是改變同節點多 Run 的政策。

### 決策 7：Egress 以 nftables default-deny 強制、沙箱沒有 DNS，允許清單分兩層

不部署 L7 Proxy（Squid／Envoy）。強制點在主機側（`forward` 鏈或 Run 的 netns 內，不是容器內的 `output` 鏈——容器內規則能被逃逸後改掉），預設 `drop` 並記錄，只 `accept` 到允許清單渲染出的釘選位址。**沙箱沒有 DNS**：沙箱層唯一的目的地以釘選 IP 表達，平台交給 Run 的模型閘道位址就是 IP 字面值，forward 鏈丟棄所有往 53 埠的流量；Run 容器接在 Docker 預設 bridge，因為使用者自訂網路帶有 dockerd 代為向外查詢的內建 DNS，那條查詢路徑不保證經過 forward 鏈。沒有解析，DNS Rebinding 與 tunneling 就沒有落腳處。渲染器仍產生一份固定解析器設定（只回答允許清單的靜態記錄、其餘 NXDOMAIN），留給允許清單出現非 IP 目的地的那天，節點目前不啟用。IPv6（`ip6`）鏈同樣維持預設 drop 且不得渲染 accept 規則，防止以 AAAA 解析繞過只涵蓋 IPv4 的允許清單；這張表不分介面，節點因此在建置時關閉 IPv6，否則節點自己的 IPv6 連線（套件更新、拉映像）也會被它切斷。

允許清單按信任等級分兩層：

| 層 | 主體 | 信任等級 | 允許目的地與強制形式 |
| --- | --- | --- | --- |
| 沙箱層（`tier: sandbox`） | Run 的 gVisor 容器 | 完全不受信任 | 目的地固定為**模型閘道一項**，以釘選 `IP:port` 表達，`pinned_ip` 必填；新增任何第二個目的地即觸發重新評估是否改用 L7 Proxy |
| 節點層（`tier: node`） | `sandboxd`、`dockerd` | 平台服務 | 物件儲存端點、Trace ingestion 端點、容器映像 registry；以 FQDN 比對（目的地由第三方持有，IP 會輪替），不得填 `pinned_ip` |

允許清單存放於單一設定檔（`infra/egress/allowlist.yaml`），是節點渲染規則的唯一來源，人工修改節點視為設定漂移，下次重建即抹除。每筆條目含 `tier`、`name`、`fqdn`、`pinned_ip`、`port`、`protocol`、`justification`、`owner`、`review_by`。變更流程：獨立 PR 只改這個檔、需核准、同一 PR 必須一併更新威脅模型文件、合併後由節點重建套用（不熱改執行中節點）。每筆 `review_by` 不得超過 90 天，逾期即告警並凍結（不得再新增目的地，但不自動移除既有項目，避免自動移除模型閘道讓平台停擺）。

以自動化強制而非依賴人記得：沙箱層條目數必須恰為一且指向模型閘道，任一 tier 出現模型供應商網域即失敗（新增供應商一律在模型閘道內加，不在允許清單加）；未部署前 `pinned_ip` 保持未設值，此狀態下渲染不出任何 `accept` 規則，即沙箱什麼都到不了，方向是 fail-closed 而非留待補完。

`sandboxd` 在接受一次 Run 時，逐項比對平台送來的 egress 允許清單與節點實際渲染的清單，不相符即以既有的能力不符錯誤拒絕，避免接上一張到不了目的地的網路而讓 Run 空等到逾時。

記錄目的地 IP:port、協定、方向、決策（accept／drop）、位元組數、時間與 Run 的關聯鍵；不記錄內容、Header、URL 或任何 payload；保存 90 天。記錄的格式由平台定義在 [`contracts/events/egress-record.schema.json`](../../contracts/events/egress-record.schema.json)，分兩種：出口記錄（來源位址、目的地、協定、兩個方向的封包與位元組數、放行或阻擋與擋下它的規則、時間）與 Run 位址記錄（`run_id`、Attempt、位址，以 `assigned`／`released` 兩筆標出起訖）。查詢以「同一個位址、落在那個 Run 的存活時間內」把兩者接起來；runbook、告警與測試只讀這個格式。

產生與搬運記錄的工具都是 Adapter，輸出在寫進 journal 前就已經是上面的格式，換掉它們不改格式與查法。現行的 Adapter：被放行的連線在結束時由 conntrack 事件取得兩個方向的封包與位元組數（節點開啟 `nf_conntrack_acct`，沒開 `sandboxd` 不啟動，記錄程序停了 `sandboxd` 跟著停）；被擋的嘗試來自 forward 鏈的 `log prefix`；這兩者的原始文字都由節點上的 `sandboxd egress-record` 逐行轉成記錄，Run 位址記錄則由 `sandboxd` 在取得與交還位址時各寫一筆。節點每七天換新，本機不能當保存處，所以記錄經 `systemd-journal-upload` 推到控制平面的 `systemd-journal-remote`；控制平面每日刪掉最後寫入超過 90 天的檔，存量逼近 4 GB 上限（到上限會先丟最舊的、未滿 90 天的記錄）時告警。推送走私有網路上的明文 HTTP，與派送 Run 的 9000 埠同一個上限：私有網路上的其他主機能偽造或讀到記錄，所以 19532 只對沙箱節點開。

不受信任執行環境若被用於挖礦、掃描或濫用流量，底層雲端供應商的處置可能偏向直接停機而非事先通知；除本節的 default-deny Egress 外，另需事前與供應商溝通用途，並建立濫用偵測與自動封停 Run 的流程。

### 決策 8：MCP 與外部網路的防護原則

連線前先發現並顯示 MCP 工具、權限與目的地；遠端位址經 SSRF 與 DNS Rebinding 防護，阻擋內部位址、Metadata Service、Loopback 與未允許網段；MCP 憑證存於 Secrets Store，執行時短效注入；記錄工具名稱、參數摘要、目的地與結果狀態，敏感值先遮罩；MCP 回應本身仍視為不受信任輸入。此章節在遠端 MCP 能力對外開放時生效。

### 決策 9：Prompt Injection 邊界與可信輸出分層

Skill、Dataset、網頁、MCP 回應與 Artifact 都標記來源與信任層級；評估模型不取得控制平面工具或高權限 Secrets；內容中出現的指令不能改變平台政策、允許工具或資料存取範圍；結構化工具呼叫一律由 Policy Enforcement 再驗證，不只依模型判斷；使用者可見報告區分來源事實、系統規則判斷與模型推論三個層次。

### 決策 10：Artifact 與下載的重新驗證

Sandbox 產生的 Artifact 進入 Quarantine，檢查檔案大小、類型、壓縮炸彈、惡意內容與 Secrets；瀏覽器顯示不可信 HTML／SVG 等內容時使用安全隔離或下載模式；打包時依 License、來源與 Secrets 政策重新驗證一次，不沿用匯入時的舊結論。

### 決策 11：稽核事件範圍

至少記錄：Skill 匯入、來源變更、掃描與下架；權限確認與拒絕；Secret 建立、使用、撤銷與刪除的 metadata；Run 建立、Provider 選擇、取消、逾時與清理；Artifact 下載及使用者資料刪除。稽核不得保存 Secret 明文或不必要的 Dataset 內容。

### 決策 12：執行映像的供應鏈治理

Runtime Image 發佈至 GHCR，SBOM 與掃描結果以 OCI referrer（`cosign attach`／`oras attach`）隨 image digest 保存，成為節點入池前可查詢的機器可讀來源；digest 是唯一該被引用的識別，不是任何檔案裡的版本字串。

| 項目 | 值 |
| --- | --- |
| 掃描結果有效期 | 30 天，到期前 7 天告警；到期即該 digest 不得被新 Run 引用（已在跑的 Run 不中斷） |
| 漏洞等級門檻 | Critical／High 且上游**有**修復版本：阻擋發佈，無豁免路徑。且上游**無**修復版本：逐項具名列入豁免清單（CVE、原因、緩解層、複審日），複審日＝該 CVE 首次被豁免日期＋90 天，逾期即該次掃描結論視為過期（等同阻擋）。Medium 以下只記錄不擋 |
| 豁免批准 | 由產品負責人核准，形式是豁免清單的變更 commit，須載明 CVE 與理由 |

### 決策 13：Agent SDK 版本精確釘選，行為靠實測驗證不靠推理

Runtime Image 基底以 digest 釘選；Agent SDK 以精確版本釘選並透過 lockfile 安裝，映像建置路徑不得出現語意化版本範圍。「升級」定義為任何會改變映像 digest 的變更（SDK、基底映像、映像內任何套件）。

任何升級 PR 合併前，必須在新 digest 上實際跑過並附輸出證據，缺一不得合併：

1. **Skill 載入條件**：掛已知 Skill 的 Run 能發現到該專案 skill，並產生對應的載入事件。
2. **閘道相容**：模型呼叫全數經模型閘道，撤銷金鑰後呼叫必須被拒絕。
3. **計費欄位**：確認用量欄位語意（含快取相關 token 計數）與閘道側 spend 對帳一致。
4. **用量事件發出條件**：確認用量事件是否仍只在正常結束路徑發出（崩潰／被殺／中止時是否發不出）。

**不得以 SDK changelog 或「這個選項的語意應該沒變」代替實測**——SDK 的行為可能靜默改變且不拋錯，Run 依然回報成功。每次升級的證據（新舊版本與 digest、四項測項結果、是否推翻既有文件敘述）落檔在映像旁的升級記錄檔案，並在推翻既有敘述時同步修正對應的程式碼註解與說明文件。

### 決策 14：節點與供應鏈的定值門檻（可自動判定，做不到即 fail-closed）

| 項目 | 值 | 違反時 |
| --- | --- | --- |
| 節點重建週期 | 7 天滾動 ＋ 事件觸發立即重建 | 超期告警並排入重建佇列；>14 天仍未重建由值班手動 drain |
| gVisor 安全基準版本 | 上游最新版或前一版，且發佈日不早於 90 天前；每月例行更新隨節點重建進行 | 未達基準的節點不得加入池，已在池者 drain；全池未達基準時新 Run 停留排隊，不得降級放行 |
| gVisor 逃逸類 CVE 應變 | 每日 cron 比對上游 releases／advisories 後開出 issue 起 24 小時內完成全池換版，做不到即依停用流程停用該 Provider；起算點刻意訂為 issue 開出時刻而非上游 advisory 公開時刻，因為前者才是可稽核的時戳，代價是最壞情況比公開時刻晚 24 小時起算 | 逃逸類 CVE 未在時限內處理視為必須停用 |
| gVisor 高風險 CVE 應變 | 7 天內處理 | 同上邏輯，時限較寬 |
| 遺留資源掃描頻率 | 每 5 分鐘一輪；平台不認得的 sandbox 有 5 分鐘派工在途寬限，已辨識且已終態者立即清除 | 掃描停擺超過兩輪視為無人知道洩漏了多少，最高嚴重度告警並暫停受影響節點池的新 Run |
| 遺留資源告警 | 同一筆資源連續兩輪掃描仍存在 | 告警 |
| 遺留資源暫停（佔用執行槽的資源） | 單節點遺留佔其宣告執行槽數 50%（下限 1 筆）即該節點 drain；全池遺留佔總執行槽數 25%（下限 2 筆）即暫停整個節點池派送 | 停止接受新 Run，直到遺留筆數降回門檻以下並連續兩輪維持才恢復；drain 期間暫停該節點的例行滾動重建 |
| 遺留資源暫停（不佔執行槽的憑證／網路規則） | 連續三輪撤銷失敗 | 最高嚴重度告警，不自動暫停新 Run 派送（暫停無法讓已外洩的憑證消失，需要人介入） |

以上比例門檻以「執行槽」為單位（而非絕對數量），使同一套規則在節點數增減時仍然成立；下限存在是為了避免在極小節點池下把單一容量事件放大成全平台事故。

### 決策 15：SEC-009／SBX-010 逃逸與安全驗收程序

驗收拆成兩個套件：

- **Suite 1**（可在一般 Linux CI runner 上執行，不需要巢狀虛擬化——gVisor 預設平台以 seccomp 攔截系統呼叫，只有指定 KVM 平台時才需要）：公開容器逃逸 PoC 集與通用逃逸嘗試、syscall 煙霧級 fuzz、資源耗盡測試、Runtime 相容性重跑、映像設定的宣告式稽核。
- **Suite 2**（只能在即將加入池、與生產同一份 IaC 建置的真實節點上執行，且在加入池之前跑）：節點設定的宣告式稽核、網路外洩與東西向隔離、憑證範圍、清理失敗與遺留資源門檻（含人工注入假遺留資源以驗證告警與暫停路徑）、Provider 契約測試、對核心資料庫與內部服務的常駐連線嘗試探針。

前置條件（缺一即整體判 fail）：受測 Runtime Image 已發佈並附 SBOM 與掃描證據；節點的 gVisor 基準版本已填實際值；沙箱層允許清單的釘選位址已指向非控制平面節點的模型閘道位址。

**通過判準**：全部測項須全數通過、零項為未知；任一項失敗或未知，`SelfHostedProvider` 不得開放外部使用者提交 Skill 執行；不得以「其餘項目風險低」為由部分放行——若某項在可預見期間內結構性做不到，正確動作是修改基線並記錄新的決策，不是在驗收表上放水。常駐連線嘗試探針一旦偵測到成功連線，須立即終止該 Run 並以最高嚴重度告警。

執行時機：每次節點加入池前跑 Suite 2；`sandbox` 與 `images` 相關程式碼變更時 CI 跑 Suite 1（Runtime 相容性測項除外，僅在 Runtime Image 或 gVisor 版本變更時才需要，因為它需要實際模型呼叫成本）；首次全套執行（Suite 1＋2）需要產品負責人見證簽署，作為「可以開放外部使用者」的授權；每次節點依 7 天週期重建時，自動重跑宣告式稽核部分。證據保存至少一年（長於一般 Trace 保存期，因為這是上線授權的證據）。

### 決策 16：對外開放與逃逸驗收未完全通過並行，是被接受的風險

在決策 15 的驗收尚未全部通過前，允許 Sandbox 對外部使用者開放試跑，這是一個被明示接受的風險，不是已解決的問題：在逃逸邊界尚未完整驗證的節點上，會執行外部使用者提交的不受信任程式碼。此接受附帶下列前提，任一項不成立即不適用：

- 開放對象維持具名邀請制，不對公眾開放註冊；
- 參與者已知悉並同意執行環境尚未完成完整逃逸驗收；
- 停止派送的開關與免費用量強制點維持有效；
- Sandbox 既有的 default-deny 網路、非 root、唯讀根檔案系統與資源限制（決策 4）不受影響。

在此風險下的強制條件：

1. 在第一位外部使用者送出 Run 之前，Suite 1 必須已在該即將服務外部使用者的節點上執行過一次且結果存檔——它不需要巢狀虛擬化，成本是一天級而非部署專案級。
2. 剩餘未完成的驗收項目不設絕對日期，改以事件為錨：必須在第一位外部使用者的第一個 Run 之前完成，受測節點必須在此之前已經存在。
3. 執行期間，只要 Suite 1 的逃逸嘗試或 Suite 2 的網路外洩測項任一項在該節點上失敗，即刻觸發停止派送，先停止、後由人複核逃逸疑慮是否成立——判斷需要時間，派送不應在判斷期間持續。

## 影響

### 正面

- 使用者能理解「格式有效」「已掃描」與「已試跑」三件事的差異，供應鏈、MCP、Sandbox 與評估共享一致的信任模型。
- 在一般雲端 VM 即可達到強隔離，不限縮部署平台選擇；沿用容器工具鏈，映像建置、掃描與 SBOM 流程不必另起爐灶。
- 安全基線與驗收門檻可自動判定（宣告式探針、CI 斷言），不依賴人記得或人工複查逐條落實。
- 東西向阻擋與允許清單是同一組規則，不是兩套機制；沒有引入 L7 Proxy 或叢集排程器等目前用不上的元件。
- 升級到 MicroVM 或受管沙箱服務都在 Provider 邊界內，核心不必變動。

### 成本與限制

- 平台自行承擔 Sandbox 逃逸、資源濫用與網路外洩風險，需要專門的安全測試、修補、映像供應鏈與告警能力。
- 同節點多 Run 併存的橫向風險是被接受、不是被消除的；緩解手段（7 天重建、一鍵全池停用）本身不是隔離。
- 允許清單以釘選 `IP:port` 表達，適合平台自有且 IP 由自己控制的目的地；一旦沙箱層需要指向第三方目的地，需要重新評估是否引入 L7 Proxy。
- Egress 記錄只有 L3/L4 粒度（沒有 URL 或 SNI），允許清單只有一項時等同零損失，清單一旦成長就不是。
- 物件短效授權的預簽 URL 沒有撤銷手段，窗口上界即簽發 TTL，是明示且無法監控的殘餘風險。
- 掃描會有誤報與漏報，需要保留人工評審與申訴流程；無法承諾任何外部 Skill 絕對安全。
- 逃逸與安全驗收成本高（真實節點、真實模型呼叫），因此拆成便宜可常跑的部分與昂貴只在必要時跑的部分；在驗收完全通過前對外開放，是一個被記錄在案、隨時可被撤回的風險接受，不是預設狀態。

## 待決策

- Artifact 掃描與高風險檔案（HTML／SVG 等）在瀏覽器端的顯示策略尚未定案。
- 執行中 Egress 阻擋事件累計到多少次即終止 Run，尚未定值，需要實際部署後的誤報率資料。
- 值班輪替在團隊擴編、或開放外部使用者提交 Skill 執行之前不重開；責任歸屬與通知路徑已隨安全事件回應的允收準則定案，重開的觸發條件寫在那裡。
- 節點池是否採預先起好 Sandbox 的預熱策略以縮短冷啟時間，尚未決定。
- `sandboxd` 自身的緊急修補是否允許不重建節點就滾動更新，尚未拍板（傾向一律走節點重建以維持節點無狀態）。
- 是否為 Agent SDK 升級開一條有預算的排程化 CI 驗證路徑，減少對人工觸發升級驗證的依賴，尚未決定。
- 若上游提供可程式化查詢「目前生效的 Skill 來源」的能力，能否用它把 Skill 載入驗證從真實 Run 降級為較便宜的煙霧測試，尚未評估。
