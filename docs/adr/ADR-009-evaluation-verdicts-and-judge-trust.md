# ADR-009：評估判定與 Judge 信任邊界

- 狀態：Accepted
- 相關：[ADR-002](./ADR-002-data-ownership-and-core-infrastructure.md)（不可變快照、Trace 分割與清理政策）、[ADR-003](./ADR-003-run-orchestration-and-async-workflows.md)（Run 狀態機與終態不可變）、[ADR-005](./ADR-005-model-gateway-and-observability.md)（模型呼叫走的閘道、成本歸因、O11y／Trace／Evaluation 的邊界劃分）、[ADR-018](./ADR-018-aggregates-and-domain-events.md)（Evaluation aggregate）、[ADR-020](./ADR-020-design-system-trust-signals-and-screen-words.md)（信任訊號詞彙與缺席／不確定的呈現方式）

## 背景

Run 執行完成不代表任務被完成——沙箱回報「成功」只代表這一輪 agent 沒有拋錯，與輸出是否達成驗收條件無關。平台需要一個獨立的機制去判斷任務是否達成，且這個判斷要能在 rubric 或 Judge 版本升級後重新產生，而不能破壞既有 Run 的不可變性。判斷的執行者是 LLM Judge，而它讀取的內容——agent 輸出、tool 結果、artifact 文字——全部是不受信任內容，且有動機說服 Judge 給出高分。

本主題要回答三件事：Evaluation 的判定與 Run 的執行狀態是什麼關係；一份判定與它的證據要如何長期保存、如何在尺變動後重新產生而不遺失歷史；以及 Judge 的信任邊界要用什麼可驗證的機制維持，而不是「相信模型」。

## 決策

### 決策 1：Run 終態與 Evaluation 判定分離，互不回寫

`runs.status` 回答「這次執行發生了什麼」；`evaluations.overall` 回答「任務達成了嗎」。兩者是兩張表的兩個獨立欄位：Evaluation 的判定不回寫 `runs.status`，也不回寫 `runs.failure_class`。Run 狀態機既有的 `evaluating → succeeded` 路徑不變，評估是這條路徑上的一個步驟，不是第二個狀態機。

落地要求：

- 評估寫入 `evaluations`，不 UPDATE `runs` 的任何欄位。
- 沒有評估的 Run，UI 顯示「未評估」，不是通過。
- 評估本身沒有跑完（例如模型閘道故障）與「未評估」分開顯示：前者的文案是「評估未完成」。
- Run 終態使用執行語意（「執行完成」／「執行失敗」）；任務判定另起一列，顯示四態：符合／部分符合／未符合／無法判斷。使用者看到的第一行是任務判定而不是 Run 終態，所有「通過」或「未通過」結論都能展開查看依據。

理由：

- `runs.failure_class` 的值域區分「平台的問題、可重試」與「Skill 的問題、不重試」，是重試決策的依據。若「輸出不符驗收條件」也算進 failed，會讓一個不該重試、也不是故障的結果被塞進重試分類器——重試只會用同一個 Skill 版本跑出同一個不符合的輸出。
- 已終態的 Run 有不可變 trigger 擋住修改；而決策 2 的重評是 append-only、會不斷對同一個 Run 產生新判定。若終態由評估決定，Run 終態就得隨 rubric 升版變動，直接撞上這條不可變限制。
- 執行事實與任務判斷是兩個問題：把判斷寫回執行事實，會讓「判斷來源」這個必要欄位失去落點，也會讓沒有評估的歷史 Run 因終態被判斷污染而失去意義。

### 決策 2：重評是 append-only，當前判定恰好一份

rubric 或 Judge prompt 升版後，可以對同一個 Run 重新評估。`evaluations` 以 partial unique index `(run_id) WHERE superseded_at IS NULL` 取代「一個 Run 只能有一份評估」的限制；新評估寫入時，在同一交易內把前一份標上 `superseded_at`，歷史判定全部留著、不覆寫。`evaluations` 在兩種終態（判定完成、判定失敗）都套用不可變 trigger，但保留三個可變欄位：`feedback_helpful`／`feedback_comment`（使用者可以多次表態）與 `superseded_at`（由下一份評估標記）。每一份判定都記下產生它的完整條件：`judge_prompt_version`、`rubric_version`、`judge_model`、`evidence_complete`。

理由：一份「上週說通過、今天說未通過」卻查不到上週那份判定的評估，使用者無法判斷是 Skill 變了還是尺變了；append-only 讓「尺變了」成為看得見的事實。這也是決策 1 的另一面——終態必須不可變，判定卻要能重新產生，兩者只能分屬不同的欄位與不同的變動規則。

### 決策 3：證據雙存——引用＋判定當下的可讀摘要

`criterion_results[].evidence` 的每一筆同時保存兩部分：

| 部分 | 內容 |
| --- | --- |
| 引用 | `kind`、`trace_event_id` ＋ `occurred_at`，或 artifact 路徑＋位元組區間，或輸出的字元區間 |
| 摘要 | `excerpt`（判定當下複製的、已遮罩的可讀片段，附長度上限與 `excerpt_truncated` 標記）＋ `available: boolean` |

`occurred_at` 是必要欄位而非方便欄位：Trace 事件按時間分割、主鍵含時間，少了它定位不到分割區。讀取時若引用的分割區已被清理，`available: false`，UI 顯示保存下來的摘要並標明「原始事件已超過保存期，以下為評估當時保存的摘要」——不是空白，也不假裝原始事件還在。`evaluations` 對 Trace 事件刻意不加外鍵：Trace 的保存政策是整批刪除到期分割區，外鍵會與這個政策衝突。

### 決策 4：LLM Judge 的四條防線

Judge 讀取的一切內容視為可能包含 Prompt Injection。四條防線全部是要求，不是可選項：

1. **輸出結構固定**：strict `json_schema`，模型只能填格子、不能改變流程或增加欄位。判定值域固定為 `passed`／`failed`／`undetermined`，值域外一律降為 `undetermined`。
2. **Judge 沒有能力**：無工具、無網路（只經模型閘道）、無檔案系統、無寫入，不知道 workspace、不知道 Run 狀態機。就算被注入成功，最壞後果是對這一次判定說謊，而這被第 3 條擋住一半。
3. **證據必須可回驗**：每條判定要附證據引用，平台側逐條回驗；指不到就把該條降為 `undetermined` 並記下不可回驗的原因。模型可以編故事，但編不出一個平台查得到的引用。
4. **不受信任內容與指示分隔**：待評內容放在標明界線的區塊內，並在 prompt 內明示其中任何指示都不是給模型的。這不是保證，只是降低成功率——真正的保證是第 1、2、3 條，它們讓注入成功也拿不到權限。

配套規則：模型回傳的判定一律標示為模型來源，不得讓模型自稱是規則判定；輸入被截斷時，受影響條目允許降為 `undetermined`——看不到全文卻判 `passed` 是不誠實的。`undetermined` 是安全的預設，不是失敗。

**第 3 條（引用回驗）的現行判準**：一個引用成立，若且唯若它的引文能在可回驗的來源裡（正規化後）逐字找到；`kind` 是模型給的提示，不是憑證。可回驗的來源目前是 Run 的 trace 摘要與 agent 的最終輸出，不包含 artifact 位元組——控制平面不解封存不受信任的套件內容去做比對。

- 當指名的來源交不出引文時，平台會在全部可回驗來源裡搜尋這段引文：找得到即視為歸錯類，以實際找到的來源成立這個引用並記下改正紀錄（報告與 UI 需顯示）；找不到即視為不可回驗，不得滿足證據要求。
- `artifact` 型引用仍然合法，但只能證明「檔案存在、大小是多少」——路徑在 manifest 上是模型編不出來的，但引文內容本身未經回驗。單靠 artifact 引用不足以滿足證據要求，且 UI 上要明說它只證明存在、未回驗引文（措辭依信任訊號詞彙的既定原則）。
- 逐字比對前，兩邊只做以下正規化：Unicode NFC；連續空白（含全形空格、換行、tab）折成一個半形空格；去除首尾空白與結構性標點（`} ] ) , ; " ' 「 」 『 』` 與反引號）——只去首尾，不去中間，中間的標點是內容。正規化後長度不足 12 個字元的引文不接受正規化比對，只接受原樣逐字命中。比對結果分三態存下來：`exact`／`normalized`／`not_found`，`normalized` 是可稽核的事實而非靜默的成功。
- **可回驗材料涵蓋解碼後的內容**：一則 trace 事件的可回驗材料，是它儲存的原始 JSON 文字，加上其中每一個字串值解碼後的內容，兩者都套用上述正規化與長度下限，各字串值之間以 NUL 相接（使跨欄位拼接命中在結構上不可能）。原因是 Judge 讀到的是解碼後的文字（例如真正的換行字元），資料庫裡存的卻是轉義後的 JSON——同一個事實的兩種呈現若只拿一種去比對，會把一則正確的引用因編碼差異誤判為找不到。payload 無法解析為 JSON 時，回驗退回只比對原始文字——解碼器放棄不該讓一則引用變成不可回驗。超過門檻搬到物件儲存、資料列只留 key 的大型 trace payload 不在回驗範圍內：回驗只比對留在資料列裡的內容，不把物件內容取回來比對，理由與 artifact 位元組不進控制平面同一條。
- 一條準則裡只要有一則引用回驗失敗（`not_found`），整條準則降級，即使同一條準則已附有其他回驗通過的引用——一則不可回驗的引用足以使整條準則不可信，不因其他佐證抵銷。

### 決策 5：Judge 使用獨立於試跑預設的中階模型

Judge 使用中階模型，不是試跑預設的輕量模型：試跑預設回答的是「沙箱工作負載跑 Skill 時用什麼」，與平台自己做判定要用什麼是兩個問題；Judge 品質直接決定評估結果的可信度，判定不準的話證據再完整也沒有用；與試跑刻意使用不同模型以降低自我偏袒——用同一個模型評自己的產出，偏誤方向與產出方向一致。

Judge 是平台工作負載：走平台側金鑰，不使用 Run 的短效 Virtual Key，但呼叫必須帶 `run_id`／`evaluation_id` metadata 以歸因成本。模型閘道故障即評估失敗，不猜、不降級為「大概通過」。

**取樣未必被釘住**：判定的可歸因性以 `judge_model`／`judge_prompt_version`／`rubric_version`／`evidence_complete` 這幾個欄位為準，不額外新增取樣（temperature／seed）欄位——一筆判定實際用的取樣是模型與呼叫當下閘道設定共同決定的，而閘道設定本身在版本控制之下，會漂移的是設定不是判定。目前 Judge 使用的模型層不保證取樣被釘住在零（部分供應商拒絕非預設值），因此「上週過、這週不過」除了模型／prompt／rubric 版本差異外，也可能是取樣差異——這是已知且尚未消除的殘留限制。

家族層級的共同偏誤無法排除：Judge 與試跑目前是同一供應商的同一模型家族，跨家族比對不在必要範圍內。

### 決策 6：Judge 陪審團可選開啟，逐條多數決

取樣殘留限制的緩解是陪審團，不是釘住取樣：開啟時同一份材料由三個獨立呼叫各判一次，每個成員是閘道上的一個角色、各用不同 seed；換其中一個角色的模型只改閘道設定一行，讓成員的錯誤不再同型。預設關閉，因為開啟會讓每次判定的模型費用成為三倍——要不要花這筆錢是營運決定。開關是營運後台「平台設定」的一筆資料庫設定，改動要寫理由並與稽核同一交易；每次評估開始時讀它，所以改了下一次評估就生效，不必重啟；讀不到設定的那次評估以錯誤結束，不默默退回單一 Judge。

- **先回驗、再投票**：每個成員的判定先各自走完決策 4 的引用回驗，投票的是回驗後的結果——一個成員宣稱通過但引用不可回驗，那一票就是 `undetermined`。
- **逐條嚴格多數**：每條準則取過半數的結果，並沿用投出該結果的第一個成員的理由與證據；沒有過半就記 `undetermined`、理由寫出票數、不附任何一個成員的證據，並以一則警告點名意見分歧的準則。整體結果由投票後的逐條結果重算。
- **缺一不可**：任一成員呼叫失敗，整次評估失敗，與單一 Judge 的閘道故障同一條規則——兩票不是陪審團。
- 判定的 `judge_model` 記下所有成員實際回報的模型；用量相加，任一成員未回報費用時整次費用記為未知，不以部分加總冒充全額。

### 決策 7：Judge 的分數要先過人工校準才拿來做決定

一組 Judge 設定（模型、提示版本、rubric 版本）在被用來判斷「某個版本是否變好」之前，要先對一份由人逐條盲標的樣本量一致率：人判符合的條目 Judge 也判通過的比例，以及人判不符合的條目 Judge 也判不通過的比例，兩者都要達到 0.85；樣本兩邊都要有足夠的條目，人標「判斷不了」的不計入分母。沒有過校準的設定，它給的分數只當參考，不作任何門檻或比較的依據。Judge 設定任一項改變就重新校準；校準樣本、人工標註與結果與判定一樣只增不改。

能用程式判的條件不交給 Judge：數字、日期、字數、句數、有沒有呼叫某個工具、有沒有提出問題，都由程式比對；Judge 只判程式判不了的部分。驗收條件因此可以帶一個檢查方式——最終回答有沒有提到指定的值（數字與日期認常見寫法）、Run 有沒有以提問結束、有沒有在不提問的情況下答完——帶檢查的條件由平台依 Run 自己的紀錄判，結果標為規則判定、不送 Judge；同一次評估裡其餘條件照常送 Judge，整體結果由兩邊的逐條結果一起重算；全部條件都帶檢查時不呼叫模型。規則判定與 Judge 一樣守證據完整的底線：Trace 有缺口時，規則判出的通過降為 `undetermined`，判出的不通過照記。判定的對象是整段對話的結果：以提問結束、成功的 Run 不單獨評估，等使用者回答後由接續的 Run 評估；「有沒有提問」看的是整條接續鏈裡每一輪的提問，不只最後一個 Run。

一條驗收條件的檢查是一棵樹，不是單一檢查。葉子是判定者：上面三種程式檢查，加上把這條條件交給 Judge 的 `judge`；內部節點是組合：串聯（依序執行，前一步沒通過就停，後面的不執行）、並聯全部通過、並聯任一通過、條件（第一個子節點是條件，通過走第二個、沒通過走第三個，沒有第三個就算通過）與 Fan-Out（對每個值各執行一次子節點，子節點的值以 `{item}` 代入，至少指定數量通過才算通過，未指定就要全部）。組合採三值邏輯：結果一確定就定案，還有分支沒判也不等；無法判斷的分支讓結果無法判斷，除非其餘分支已足以決定。評估分兩段：先不呼叫 Judge 把每棵樹算一遍，已經定案的條件不送 Judge，只有還卡在 `judge` 葉子上的條件才送，Judge 回來後再算第二遍；所以前面的程式檢查沒過，後面的 Judge 就不會被呼叫，花費也不會發生。結果用到 Judge 的判定就標為模型來源，否則標為規則判定；超過一個節點的樹逐節點記下每一步的結果與理由，沒被執行的節點不記。條件分支只看子節點的判定結果，不讀任意欄位、不執行使用者提供的程式。一棵樹最多 50 個節點、8 層；檢查方式由平台的登錄表定義，新增一種葉子或組合只加一個定義，不改既有的判定與驗證程式，平台也把登錄表列給編輯器使用。Test Lab 不認得檢查方式，驗證由評估端注入：沒有接上驗證的 Test Lab 拒絕所有帶檢查的條件，不會默默收下。

判定節點還有一種 prompt 評分器：一段評分指示，告訴 Judge 這條條件怎樣才算符合。Admin 定義的評分器全平台共用；使用者定義的存在自己的 Workspace，只有那個 Workspace 看得到、用得到——多租戶的邊界與其他 Workspace 資料相同。評分器以版本保存，版本只增不改，每一版都要寫明改了什麼，並與稽核事件同一交易寫入；檢查樹的葉子指名一個版本 id，存檔時驗證這個版本是平台的或同一個 Workspace 的，評估時再驗一次，看不到就判 `undetermined`、不呼叫模型。之後的新版本不會改變既有檢查用的尺。評分器的輸出仍是 `passed`／`failed`／`undetermined` 加引用，與 Judge 同一條回驗與降級規則；指示只能定義這一條條件怎樣算符合，不能改作答格式、證據規則或其他條件。評分器與 Judge 一樣先校準才採信（決策 7）：沒校準過的評分器結果只當參考。Judge 只被呼叫一次：第一段在還沒定案的樹裡收集「在某種判定結果下仍可能走到」的模型葉子——串聯在規則判出不通過的那一步之後就不再收、條件在判定未定時兩個分支都收——一次送出，每片葉子各自得到一個判定；`each` 底下的葉子依值各算一片，指示裡的 `{item}` 代入該值。

檢查樹在測試題的驗收條件裡設計：同一棵樹同時畫成流程圖與一份可用鍵盤操作的大綱，選取任一節點後在旁邊的表單改值、加子節點或刪除；節點的種類、值與子節點數量的上下限都從 `GET /evaluation/check-kinds` 讀，表單在送出前就指出哪個節點還不完整，平台存檔時仍再驗一次。流程圖用 **React Flow**（`@xyflow/react`，MIT，連同傳遞依賴共 19 個套件，皆為 MIT 或 ISC，無安裝腳本），只在設計驗收條件時以獨立 chunk 載入；版面由樹的形狀直接算出，不另裝排版引擎。Rete.js（外掛體系與編輯器框架，超出唯讀檢視的需要）、JointJS（進階功能需商業授權）、GoJS（商業授權）、react-diagrams（維護停滯）與 Mermaid（只能輸出圖，不能點選節點）不採用。流程圖只負責呈現與選取，不能拖拉或連線——樹的結構只由表單改，所以畫面上看到的永遠是平台會驗證的那個形狀。評分器在 `/lab/graders`（Workspace 專用）與 `/admin/graders`（平台通用）管理。

### 決策 8：能力評估集從失敗中沉澱，作為所有新 Skill 的共同尺

平台維護一份 Skill 能力評估集，用來驗證新生成的 Skill 能做到什麼、哪裡還能精進。評估集從真實失敗長出來：開發與量測中每發現一種失敗，就在讀完逐場紀錄、確認錯的是 Skill 而不是考題或評分之後，寫成一個任務；任務是使用者真的會送的請求，附參考解答證明它可解，並標明正確的補資訊方式（計算、讀 Skill 自帶的知識、搜尋、追問、照常理假設）。同一種行為要同時有「該發生」與「不該發生」的任務，避免只往一個方向最佳化。

評估集分兩層：能力層收目前還做不好的任務，分數低是正常的、用來看還有多少空間；穩定通過的任務升進回歸層，回歸層要維持接近全數通過，掉分就是退步。需要追問的任務用一個模擬使用者依任務藏著的事實回答，評的是整段多輪對話的結果。每個任務跑多次，報告每次都成功的比例，不只報至少一次成功的比例。兩個版本的比較在同一組任務上逐題配對，附信賴區間，門檻在比較之前寫定。

平台以評估批次執行這件事：一個批次把選定的 Test Case 對同一個 Skill Version 各跑指定次數，每個 Test Case 的權限摘要要先確認過；Run 照一般的准入與計費，在工作區的執行名額空出時一個接一個啟動；建立 Run 與把它記到批次的那一次試跑在同一筆交易裡，那次試跑已經被另一個推進者記上時整筆 Run 回滾，所以中途當掉或兩個推進者同時領到同一次試跑，都不會留下沒記到批次的 Run，也不會為同一次試跑扣兩次費用。等待就能解決的拒絕（名額已滿、派送暫停、掃描尚未就緒）讓批次等，其餘拒絕停止批次並記下原因。每次試跑以它整段對話結尾的評估為準；只有符合、部分符合、不符合算進分母，還在跑、等回答、無法判斷、沒評到的照列但不計分。報告列出每題至少一次通過與每次都通過，整體通過率附 95% Wilson 區間；試跑期間 Test Case 被改過、各次看到的題目不同的題，報告會標出來。兩個批次的比較以同一個 Test Case 為一對：每對的差是兩邊在該題的通過率相減，結果是平均差與依成對標準誤算出的 95% 區間；只在一邊有判定的題目列為未配對、不計入。

評估集是活的：任務寫錯了就修那個任務並升版本，舊版本的分數只和舊版本比；考題被調過的部分不再當作沒看過的考題。

## 影響

### 正面

- 重試分類器只處理它該處理的事，`failure_class` 的值域不必為了評估而擴張。
- 重評與 Run 終態不可變性可以同時成立：一個是 append-only 的判斷歷史，一個是不可變的執行事實。
- 「執行成功但任務沒完成」是一個說得出口的狀態，不必靠使用者自己讀 Trace 才發現落差。
- 評估報告的壽命與 Trace 保存期限解耦，且讀得出自己讀到的是摘要還是原始事件。
- Judge 被注入的最壞後果有界：拿不到權限、改不了流程、編不出一個查得到的引用；判定的可信度有一條可驗證的下界，不必靠相信模型。
- 引用回驗能分辨「歸錯類」與「編造」、能容忍儲存編碼差異，減少把正確判定誤判為不可信的情況。

### 成本與限制

- 對外部消費者而言，「Run 成功」不再是一個可以單獨判斷結果的欄位，必須一併讀 evaluation；這是誠實的代價，不是缺陷。
- 已終態卻沒有評估的歷史 Run 永久停在「未評估」，除非另行決定補評，那是產品決策，不在本主題範圍內。
- 儲存隨重評次數線性成長：每份判定多存一份摘要，重評又多存一份完整判定。
- 引用回驗會把一部分本來判得出來的條目降成 `undetermined`，這是刻意的權衡：寧可誠實地說不知道。
- Judge 使用的模型層比試跑預設貴，控制成本的手段是輸入截斷政策，不是換一個更便宜的模型。
- 陪審團開啟時判定費用與延遲的上限都隨成員數放大（成員並行，延遲取最慢的一個）；三個成員目前指向同一個模型，緩解的只有取樣差異，不含模型層級的共同偏誤。
- 四條防線降低而非消除 Prompt Injection 的成功率，這一點只寫在契約文字裡，不寫成保證。
- 一則不可回驗的引用會拖垮整條準則，即使該準則同時附有其他已通過回驗的引用。
- 檢查樹的流程圖多一個 runtime 依賴（React Flow 與它的 19 個傳遞依賴），只在設計驗收條件的 chunk 裡；升級時要重查授權。

## 待決策

- Judge 跨模型家族的 A／B 比對，不在目前必要範圍內。
- 正規化命中的 12 字元門檻是推導值，需要以更多真實 Run 校準，方向只能往上調整。
- 可回驗來源是否納入 Test Case 的輸入快照：目前不在回驗範圍內，需先確認不會讓「引用輸入」變成一種繞過。
- 重評的觸發權（誰可以要求重評、是否開放使用者手動觸發）：目前僅有平台側批次重評。
- 一則不可回驗的引用是否足以拖垮整條準則：現行規則是「任一引用回驗失敗即降級」，維持這條規則的依據是「編碼落差已排除」這個前提；下一輪量測若在編碼落差排除後仍量到同型失敗，需要重新檢視是否改為「至少一則通過即保留」。
- `agent_output` 與 artifact 型引用是否存在與 trace 事件同型的編碼落差：目前看不到——`agent_output` 存的就是解碼後的文字，不是 JSON——但尚未排除。
- 引用改正紀錄（`reattributed_from`）要不要回饋給 Judge 的提示：模型若反覆把 trace 標成 artifact，那是提示的缺陷而非判定的缺陷，但把統計餵回提示會讓判定與提示互相糾纏，需先量測再決定。
