# ADR-018：核心基礎設施改採容器化自架（取代 ADR-014 的最小受管組合）

- 狀態：**Accepted**（2026-08-14 定案）
- 日期：2026-08-14
- 決策者：產品負責人、架構規劃
- 取代：[ADR-014](./ADR-014-core-infrastructure-selection.md)（核心基礎設施最小受管組合）

## 背景

[ADR-014](./ADR-014-core-infrastructure-selection.md) 以「受管服務優先，不自架可以買到的東西」為第一選型原則，選定受管 PostgreSQL ＋ 受管 S3 相容儲存的最小組合。該 ADR 的定案條件是「部署平台確認與成本試算」，兩者都在 M0 完成——但過程中出現一個 ADR-014 未預期的輸入：

**負責人於 2026-08-13 指示平台元件走雲原生容器化**（Postgres 等以容器自架），2026-08-14 批准 M0 全部產出並指示開工。這個方向與 ADR-014 的選型原則 1 直接衝突（衝突面僅限 PostgreSQL 一列，其餘各列不受影響）。依 AGENTS.md 的文件維護規則，推翻既有決策應新增 ADR 並將舊文件標為 `Superseded`，而非原地改寫 ADR-014，故有本 ADR。

[cost-estimation.md](../plans/mvp/m0/cost-estimation.md) v2 的立場需要先說清楚：**它不重新辯論容器化方向，只回答「怎麼做最划算」與「哪裡該例外」。** 本 ADR 沿用同一立場——方向是負責人的決策，本文件負責把它變成有邊界、有例外、有退出條件的架構決策。

ADR-014 的其餘結論（PostgreSQL 為中心承載交易／FTS＋pgvector／River 佇列／Trace 分割表、Outbox 即佇列、只透過標準介面使用以保留抽換能力、依 ADR-010 的壓力觸發拆分）**在本 ADR 中全部延續**，改變的是這些能力**跑在哪裡、由誰維運**。

## 評估選項

### 選項 A：最小受管組合（＝ ADR-014 原取向）

受管 PostgreSQL（Neon 或 DO Managed）＋ 受管物件儲存，應用以 VM 部署。

- 優點：維運工時最低（每月 2.6–3.6 h）；備份、failover、版本升級是供應商責任；PostgreSQL 主版本升級的工時接近 $0。
- 缺點：與負責人指示的雲原生容器化方向不符；**跨供應商延遲風險**（Hetzner 節點 ＋ Neon 資料庫是成本最低的受管組合，但兩者不同供應商，v1 成本試算把此列為「最需要先驗證的一項」）；受供應商計費模型變動影響（Hetzner 2026-06-15 調價、Neon 改價）。
- 成本：封測 $466／早期成長 $1,314（D. Hetzner+Neon）。

### 選項 B：E1 單節點容器化（建議）

docker compose 或 k3s 單機，控制平面全容器化；PostgreSQL 以容器跑在自有節點上。

- 優點：**消除跨供應商延遲風險**（Postgres 與應用同節點／同內網——這是容器化最實在的一個收益）；資料主權；不受供應商計費模型變動影響；**節點合併**（封測情境由 3 台獨立 VM 併為 1 台）；符合雲原生方向且不預先建設編排層。
- 缺點：Postgres 單實例無自動 failover，節點或容器故障＝全平台停機至人工還原；備份還原、版本升級、磁碟水位監控全是自有責任（每月 +5～10 h）。
- 成本：封測 **$283**／早期成長 **$967**（E1 Hetzner）。

### 選項 C：E2 受管 Kubernetes

DOKS（控制平面免費）或自管 K8s，CNPG 管理 PostgreSQL primary + standby。

- 優點：CNPG 自動 failover（**這是 E2 唯一能買到而 E1 買不到的東西**）；宣告式編排、滾動更新、設定漂移可控。
- 缺點：**在 MVP 規模不省錢**——E2 DOKS（$2,212）比受管的 C. DO（$1,909）貴 $303，E2 Hetzner（$1,001＋）比 E1 Hetzner（$967）貴；多一層 K8s 版本升級稅（每季 1.3–5.3 h）；Hetzner 無受管 Kubernetes，走 E2 須自管控制平面。
- 成本：封測 $518／早期成長 $2,212（E2 DOKS）。

### 三個選項共同的事實（[cost-estimation.md](../plans/mvp/m0/cost-estimation.md) §4.3）

1. **供應商差異 > 架構差異。** 受管的 D（Hetzner+Neon，$1,314）比容器化的 E1 DO（$1,848）便宜 29%——節點單價才是主導變數，不是容器化與否。
2. **容器化省的錢集中在非 Sandbox 部分。** 非 Sandbox 成本省 68%（$347），但 Sandbox 池佔早期成長情境的 83%，總帳單只省 26%。
3. **以任何合理的工程師時薪計，容器化 PostgreSQL 在 MVP 規模不靠省錢回本**（損益平衡費率僅 $18–69/h）。它的正當理由是非金錢的：消除跨供應商延遲風險、不受供應商計費變動影響、資料主權、架構方向一致性。

## 決策

**採選項 B：E1 容器化，跑在 Hetzner Cloud 節點上（docker compose 或 k3s 單機），並保留三項明確的容器化例外。**

### 1. 容器化的元件

| 元件 | 說明 |
| --- | --- |
| **PostgreSQL + pgvector + FTS + River 佇列 + Trace 分割表** | 容器化，跑在自有資料節點。ADR-014「一個資料產品承載全部」的核心結論不變 |
| **LiteLLM Proxy** | 本來就是 OSS 自架（MIT），無變化（ADR-017） |
| **Go API／River Worker／Python LLM 服務** | 自有程式碼；容器化的實質收益是節點合併 |

**PostgreSQL 備份採 pgBackRest 或 WAL-G，持續 WAL 歸檔至物件儲存。**「還原演練」（不是備份設定，是還原）是 E1 單實例架構可被接受的前提，須排入開工前收尾工作——未演練過的備份等於沒有備份（ADR-010 DR 要求）。

### 2. 節點供應商：Hetzner Cloud（主推），DigitalOcean（風險退路）

即使經 2026-06-15 調價（CCX 線 +113～173%），Hetzner 在兩個情境仍最低成本：封測 $283 vs DO $502、早期成長 $967 vs DO $1,848。

> ⚠️ **v1 那個「3.8 倍 vCPU 價差」的論證已被複核推翻**，實際是 1.49 倍（對 AWS）／1.70 倍（對 DO General Purpose）。Hetzner 仍最便宜，但這是一個需要與風險權衡的普通成本優勢，不是「便宜到不需要思考」。

**選 Hetzner 必須付出的代價**：其濫用政策對「執行不受信任程式碼」的處置偏向直接停機而非協商。對策見 [ADR-015](./ADR-015-sandbox-isolation-technology.md) 定案紀錄（default-deny Egress Proxy ＋ 事前與供應商溝通用途 ＋ 濫用偵測與自動封停）。**若負責人不接受此風險，DO 是完整退路**（單一供應商、DOKS 控制平面免費、每秒計費對短命節點有利），代價是早期成長情境每月多 $881。

### 3. 容器化的三項例外（實證，不是原則性豁免）

| 例外 | 決定 | 理由 |
| --- | --- | --- |
| **物件儲存** | 用供應商的 S3 相容受管服務（Hetzner Object Storage $8／DO Spaces $27） | **自架反而貴 10–30 倍**：早期成長情境需約 2.6 TB block storage ≈ $266/月，尚未含節點與營運工時。S3 類服務賣的是攤提後容量，block storage 賣的是保留容量。跑在節點內含 NVMe 則無跨節點耐久性，與 ADR-015「節點定期重建」直接衝突 |
| **Langfuse** | 維持 Cloud（$29–57/月） | 自架 v3 需 ClickHouse + Redis + S3 三個新資料產品，違反 ADR-014 選型原則 2（產品數量最少）——**該原則在本 ADR 中延續有效** |
| **Sandbox 執行節點** | 獨立 VM 池 ＋ gVisor，**不進 Kubernetes** | [ADR-015](./ADR-015-sandbox-isolation-technology.md) 明訂執行平面為獨立 VM 池、不與應用工作負載混排。放進 K8s 會讓 ADR-001 的平面隔離退化為命名空間隔離 |

> **MinIO 的授權與產品風險（即使不採用也記錄於此）**：MinIO 為 **AGPL-3.0**，其第 13 條網路 copyleft 條款在「物件儲存以網路服務形式被存取」的情境下，傳染範圍需法務判斷——即使只在內部網路使用，這是需要明確結論而非默認安全的問題。加上 2025 年後開發重心移往商業版 AIStor、社群版管理功能大幅精簡，把資料耐久性押在正在縮減社群投入的專案上風險不對稱。
> **若未來確需自架物件儲存，首選 [SeaweedFS](https://github.com/seaweedfs/seaweedfs)（Apache-2.0）**——三個候選中唯一授權乾淨者，S3 gateway 成熟、對大量小物件效率佳。Garage（AGPL-3.0）授權類別與 MinIO 相同。**採用受管服務可完全繞開此問題，且成本最低。**

### 4. E1 → E2 的切換觸發條件

**不預先建設編排層**——ADR-010 的「依壓力拆分，不預先建設」原則同樣適用。以下任一成立即評估切換，全部未成立就留在 E1：

1. **PostgreSQL 單實例的計畫外停機已影響 Run 完成率**——這是 E2 唯一能買到而 E1 買不到的東西（CNPG 自動 failover），也是最可能的觸發項。
2. **控制平面節點數 > 4**，手動編排的部署、滾動更新與設定漂移成本超過 K8s 的學習與升級成本。
3. **ADR-010 服務拆分觸發表已觸發任一列**（Run Orchestrator、Ingestion Worker、Catalog & Search、Evaluation Worker 需獨立擴展或獨立部署）。
4. **團隊具備至少 1 名可負責 K8s 版本升級的成員**——這是**必要條件不是加分項**。前三項成立但此項不成立時，正確動作是先做 PostgreSQL 備援（E1 ＋ 手動 standby），不是上 K8s。

切換時應**重新試算而非沿用本文件數字**：走 E2 時 DOKS（控制平面 $0）相對 Hetzner 自管的優勢會顯現，但節點價差仍達 $881/月。

## 影響

### 正面

- **跨供應商延遲風險消除**：PostgreSQL 與應用同節點／同內網，v1 成本試算列為「最需要先驗證的一項」的風險不再存在。
- **不受供應商計費模型變動影響**：Hetzner 六月調價、Neon 改價都不會傷到自架的 PostgreSQL。
- 平台成本較最佳受管對照組低 **$183（封測）／$347（早期成長）**；在模型費重估為 $0.05/Run 後，這筆錢佔早期成長總帳單由 6% 升為 **20%**，不再是可忽略的零頭。
- ADR-014 的核心結論（一個資料產品、Outbox 即佇列、標準介面抽換）全部延續，**應用程式碼不因本 ADR 改變**——NFR-006 的介面契約沒有動。
- Sandbox 隔離邊界（ADR-015）與模型出口邊界（ADR-017）不受影響。

### 成本與限制

| 項目 | 說明 |
| --- | --- |
| **PostgreSQL 單實例無自動 failover** | 節點或容器故障＝**全平台停機至人工還原**。MVP 可接受（Run 為非同步、無金流、封測使用者數少），**但必須明示，不可默認為「和受管一樣」** |
| 維運工時 | 每月 **8–13 h**（受管對照組 2.6–3.6 h），增量 **+5～10 h/月**：備份還原演練 2–4 h、小版本升級與重啟窗口 1–2 h、節點 OS 修補與重建 2–3 h、監控告警維護 2–3 h |
| **不靠省錢回本** | 損益平衡時薪僅 $18–69/h。**若推動容器化的理由是省錢，這份數字不支持**；理由若是架構自主與風險控制，數字不反對 |
| PostgreSQL 主版本升級 | 人工執行、需停機窗口（受管方案此項為 $0 工時） |
| 磁碟水位耗盡 | 無供應商告警，需自建監控；Trace 分割表 `DROP PARTITION`（PDM-006 90 天）是主要控制手段 |
| **Hetzner 濫用政策** | 與容器化無關，但隨供應商選擇而來；見上方第 2 節與 ADR-015 |
| 容器化不觸及最大單項 | **Sandbox 池佔平台成本 83%**，容器化省的是控制平面與資料層。唯一真正的成本槓桿是縮短單 Run 佔用時間（敏感度最高，翻倍即池 +60%）與控制 Run 量（PDM-010） |

## 驗證方式

- **PostgreSQL 備份還原演練**（不是備份設定，是還原）——E1 單實例可被接受的前提，開工前收尾必做。
- ADR-014 既有的驗證方式全部延續：煙霧負載測試（百級併發 Run 的事件寫入與佇列消費延遲）、NFR-006 契約測試涵蓋物件儲存與 Queue 介面、備份還原涵蓋資料庫與物件儲存的一致性程序。
- 節點故障演練：驗證「單節點故障 → 人工還原」的實際 RTO，並與 NFR／DR 目標對照；若 RTO 不可接受，即為 E1 → E2 觸發條件 1 的提前訊號。

## 待決策

- **編排層取 docker compose 或 k3s 單機**（兩者皆在 E1 範圍內；k3s 較接近 E2 的遷移路徑，compose 較簡單）。
- **是否採 Hetzner**——上方為主推，但濫用政策風險的接受與否是產品負責人決定；不接受則走 DO 退路。
- **Hetzner Cloud Volume 單價**與 **DO Block Storage 單價**尚未逐項查證（影響 E2 的 CNPG PVC 成本試算）。
- O11y 受管後端選擇與免費額度評估（自 ADR-014 承接，未回答）。
- LiteLLM 與主 PostgreSQL 共用實例或獨立小實例（自 ADR-017 承接，未回答）。
- E1 的部署與設定管理方式（IaC 工具、機密注入路徑）——Sandbox 節點的 IaC 要求見 ADR-015，控制平面節點的對應作法尚未決定。
