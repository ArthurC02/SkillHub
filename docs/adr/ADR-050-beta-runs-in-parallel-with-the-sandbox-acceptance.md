# ADR-050：封測與 Sandbox 驗收並行——一個被明示接受的風險，不是一個被解決的問題

- 狀態：Accepted
- 日期：2026-08-23
- 裁定者：產品／平台負責人
- 修訂：[ADR-015](./ADR-015-sandbox-isolation-technology.md) 定案紀錄的「語意界線」一句（**只縮小那一句的適用範圍，ADR-015 其餘全部不變、不 Superseded**）
- 相關：`02:SEC-009`、`03:SBX-010`、[ADR-022](./ADR-022-sandbox-deployment-topology-and-security-thresholds.md) 第三部分、`04` 甲-1～甲-4、乙-14

## 背景

ADR-015 的定案紀錄寫著一句硬的：

> ⚠️ **定案的語意界線**：本 ADR 轉 Accepted 表示「採用 gVisor 這個方向、後續實作應遵循」，**不表示隔離強度已被驗證**。上方最後兩列是**上線前的硬性關卡**——SEC-009／SBX-010 未通過不得開放外部使用者提交 Skill 執行。

`04` 乙-14 把它變成一個要拍板的問題：**甲類四項（SEC-009、SBX-010、SBX-005／007 的生產網路面、SBX-002 的閘門 A 探針）是不是封測 D 日的阻擋項？** 該列當時的建議裁定是「是，四項全部到期」。

M0～M3 期間這句話不構成衝突，因為那段時間**沒有任何外部使用者**。封測第一次讓外部人員在真實部署上建立 Run，前提就此成立。

## 決策

**甲類四項不是封測 D 日的阻擋項，封測與甲類驗收並行。**

這**推翻**了上引那句的字面。ADR-015 的其他一切——gVisor 為基線、獨立 VM 池、ADR-005 基線疊加、IaC 與定期重建、default-deny egress——**一項都沒有動**。

## 這是什麼性質的決定

**它接受一個風險，不是解決一個問題。** 說清楚接受的是什麼：

在甲類通過之前，封測參與者提交的**不受信任程式碼**會在一台**逃逸邊界尚未被驗證**的節點上執行。ADR-022 第三部分的 45 項覆蓋核對此時是 0 項 `pass`；`infra/nodes/gvisor-baseline.txt` 仍是 `unset`；P-02 常駐探針（Sandbox → 核心資料庫）不存在；生產級 egress 強制、允許清單與 DNS 固定解析（N-01～N-07）不存在。

**這些不是「還沒量到」，是「還沒有」。** 本 ADR 不把它們寫成別的樣子。

## 這個裁定沒有授權的事

以下不是本 ADR 新增的條件，是**已經由別處決定、而且仍然成立**的事實。列在這裡，是因為「並行」很容易被讀成「這些也一起放寬」：

| 仍然成立 | 出處 |
| --- | --- |
| 封測是**具名邀請制**，12 人（三層各 4 ＋3 候補），不是對公眾開放 | `03:BETA-001`、[m4/pdm-009-beta-proposal.md](../plans/mvp/m4/pdm-009-beta-proposal.md) |
| 參與者須簽署同意書並知悉資料保存政策 | 乙-16、[consent-and-data-policy.md](../plans/mvp/gate-test/consent-and-data-policy.md)（待法務） |
| 停止派送的開關存在且可一鍵觸發，其中兩條 P1 判準已自動 | `03:SEC-012`、[p1-dispatch-halt.md](../runbooks/p1-dispatch-halt.md) |
| 免費額度強制點存在（PDM-010） | ADR-028 |
| 沙箱 default-deny 網路、非 root、唯讀 rootfs、資源限制 | ADR-005、SBX-007 |

**「封測對公眾開放」不在本裁定範圍內。** 本 ADR 只談 12 位具名受邀者；把封測擴大成公開註冊是另一個決定，而那個決定會讓上表第一列失效——上表第一列正是本裁定敢下的一部分理由。

## 一件會讓這個裁定便宜很多的事實

ADR-022 第三部分把 10 個測項分成兩個 Suite，而**兩者的成本差一個量級**：

- **Suite 1**（T1、T2、T3、T4、T8 的映像半、T7 的一部分）只需要 **Linux ＋ Docker ＋ runsc**，`ubuntu-latest` 即可。ADR-022 §0 推翻了「逃逸測試需要巢狀虛擬化」這個前提（`systrap` 用 seccomp ＋ SIGSYS，只有 `--platform=kvm` 才需要 `/dev/kvm`），而 CI 已於 `15a9dd7` 接上。T1 的通用嘗試另有可直接執行的腳本（`tools/sec009/t1-escape-attempts.sh`，含負對照）。
- **Suite 2**（T5 網路、T6 憑證、T7 節點半、T9 契約、T10 常駐探針）只能在**即將加入池的那台節點**上跑——換一台機器就換了受測物。

**所以「甲類全部到期」與「什麼都不做」之間不是只有兩個選項。** 在第一位外部使用者按下試跑之前，Suite 1 在那台節點上跑一次是**一天的事，不是一個部署專案**。

**本 ADR 不把它定為條件**——那是負責人的取捨，不是這份文件可以代簽的。它只把「這個選項存在而且很便宜」寫下來，因為裁定當下沒有人算過這筆帳。

## 影響

- `04` 甲-1～甲-4 **維持未結**，但不再是封測 D 日的阻擋項；`RELEASE-006` 與封測 D 日的相依關係要依此重排。
- `02:SEC-009` 的允收準則**一個字都不變**：45 項全數 `pass`、0 項 `unknown` 仍然是它的門檻。改變的只是「這個門檻在什麼時點之前必須達成」。
- ADR-015 定案紀錄的那一句**不刪除**，回填指向本 ADR 的引用（決策歷史不原地改寫）。
- 對外措辭要對齊：封測招募與同意書若有任何一句宣稱隔離強度已驗證，那句話現在是不實陳述。**同意書的資料處理段落必須據實說明程式碼在尚未完成逃逸驗收的環境中執行**——這件事併入乙-16 的法務清單，是本 ADR 產生的新工作。

## 待決策

1. **第一位外部使用者的 Run 之前，是否要求 Suite 1 在該節點上跑過一次？** 上一節說明它為什麼便宜。目前沒有答案，而**沒有答案等於「否」**——這正是本 ADR 要把它寫下來的原因。
2. **甲類完成的目標日期。** 「並行」不等於「無限期」，而目前沒有任何文件寫著一個日期。
3. 封測期間若 T1／T5 的任一項在節點上失敗，是否即刻觸發 `SEC-012` 停止派送？（判準上屬 P1 的「逃逸疑慮」，但那是人的判斷，見 runbook §2.3。）
