## 背景

ADR-020 的待決策第 2 條逐字問的是：「封閉測試（`BETA-001`）是否需要邀請碼／白名單閘門疊在 OAuth 之上」。M4 的封測第一次讓非團隊成員在真實部署上建立 Run，這個問題到期。

它連帶一個更難的問題：**免費額度的強制點在哪一層。** PDM-010 提案了一組數字（首月 20 次、其後每月 30 次、每日 5 次、並行 2），但沒有說誰來執行。而本專案在這一題上**已經答錯過一次**——`04` 乙-2 記錄的 `TokenBudget`：`300_000`／`60_000` 被寫進 `policy_snapshot`、**顯示在執行前權限摘要上並要求使用者確認**，而平台與沙箱都不強制。那個狀態被判定為「兩者中最壞的一種」，因為它直接踩 `NFR-001`「UI 不得誤導」。最後的處置（`SBX-013`）是找出**唯一看得到那個數字的地方**並在那裡強制。

配額有同一個陷阱，形狀不同：閘道上有三個看起來像煞車的機制，沒有一個是配額。

## 決策 1：准入採「允許清單疊在 OAuth 之上」，不做邀請碼

登入仍走 GitHub OAuth（ADR-020 不變）。`user_identities.provider_user_id` 命中部署設定的允許清單，才開放私有功能。

| | 在清單內 | 不在清單內（含未登入） |
| --- | --- | --- |
| 搜尋、Skill 詳情 | ✅ | ✅ |
| Fork、建立 Run、下載 | ✅ | ❌ |

- **與 `DISC-010` 天然一致**：「未受邀者看得到目錄」本來就是既有行為（公開搜尋不要求登入），不是為封測新開的路徑。
- **實作是一個 middleware ＋一份部署設定，比照 `SEC-011` 的 `OPERATOR_USER_IDS` 既有前例**，該項刻意不做 DB 角色表的三條理由（角色表要連帶做授予端點、該端點自己的授權、以及授予的稽核，三者存在的唯一目的是讓同一個帳號提拔自己）在此**完全適用**。名單異動＝改設定並重啟。
- **沿用 `SEC-011` 的稽核形式**：每次啟動寫一筆 roster audit event，內容是**當下生效的清單與筆數**。它答的是「誰現在在名單上」，**不答「誰在何時被加入」**——後者的事實在部署設定的變更歷史裡。**寫不成該筆事件時 fail-closed：該次啟動不承認任何受邀者。**
- **不做邀請碼**：碼要產生、保管、兌換、撤銷、過期，還要一個兌換頁，而它自己是一組新的機密材料。它想解決的問題（防止不請自來的人用掉配額）在允許清單下已經被解決。
- **未在清單內看到的是說明 ＋「回報你的使用情境」入口，不是 404。** 這與 `SEC-011` 的 operator 端點回 404 不衝突，兩者的判準不同：operator 端點的存在本身是要隱藏的，而封測名單的存在不是機密——目錄剛剛才把內容列給這個人看，對他佯稱功能不存在只會被同一個 API 打臉（同 `02:SEC-011` 對 `/files` 回 403 而非 404 的既有理由）。
- **三個入口共用同一支回饋端點與同一個表單**：未受邀、額度耗盡、阻斷回報，由 `kind` 分流（PDM-010 §8.1 已把「額度耗盡」設計成需求訊號蒐集管道，此處只是讓另外兩個入口共用它）。

## 決策 2：配額的強制點是平台自己的計數器，落在 `internal/run` 的 `Create`

### 2.1 閘道上的三個機制，逐項寫明它們管什麼、為什麼不是配額

| 機制 | 它真正管的 | 為什麼**不是**每帳號每月的配額 |
| --- | --- | --- |
| Virtual Key 的 `max_budget` | **單次 Run 的金額上限** | **每 Run 一把新鑰匙**（alias `skillhub-attempt-<id>`，Run 終止即撤銷，`SBX-008`）。它不跨 Run 累加——三十次各 $0.30 的 Run 全部合法通過 |
| `tpm_limit` | **速率** | 速率不是總量。限得住一分鐘內的爆量，限不住一個月跑三百次 |
| Workspace 並行上限 ＝ 2 | **同時幾個**（`gateb.go`，交易內 advisory lock ＋非終態計數） | 同時只能跑兩個，不代表一個月不能跑三百個 |
| 軟／硬牆鐘 | **單次時長** | 同上 |
| harness 的 token 累計（`SBX-013`） | **單次 Run 的 token** | 同上，且它在沙箱**之內**——它看得到的只有這一次 Run |

**五個都是必要的，沒有一個回答「這個帳號這個月還能跑幾次」。** PDM-005 §5.2a 對 token 上限已經下過同型的結論（「`max_budget` 與 `tpm_limit` 都不是 token 上限的代理，三者職責不同、須併用」）；配額是同一句話的第三次套用。

### 2.2 強制點與計數方式

- **強制點：`internal/run` 的 `Create`，＝閘門 B 現在住的地方**，與並行上限**同一處、同一個交易、同一個 advisory lock**。理由不是方便：那裡是**唯一一個「Run 即將被建立」且還沒有花掉任何一分錢的位置**。超出即 **422 且不建 Run**，與閘門 B 既有四項阻擋同一形式。
- **計數用既有的 Run 列做時間窗計數，不新增「餘額」欄位。** 餘額是可以漂移的快取；並行上限用的是「非終態計數」而不是一個 counter 欄位，配額沿用同一個做法。
- **退還因此是一個查詢述詞，不是一次會漏掉的寫入**：計數查詢排除 PDM-010 指定的那些平台側 `failure_class`。寫入式的退還一定會有漏掉的路徑（崩潰、重啟、清理失敗），述詞式的不會。
- **計數起點是進入 `preparing` 的 Run**（PDM-010）：資源真正被佔用之後才計。`provisioning` 階段失敗本來就還沒計數，所以「自動退還」實際只對 `preparing` 之後的平台側失敗生效。

### 2.3 顯示與強制的順序是硬的

**乙-2 的教訓逐字帶到這裡：顯示一個平台不會執行的上限，是所有選項裡最壞的一個。** 因此：

1. 先做強制點與具名測試；
2. 再做 `GET /me/quota` 與權限摘要上的剩餘次數與重置時間。

**配額欄位刻意不進 `summary_hash`**（同 `estimated_cost` 的既有裁定，`TEST-011`）：`summary_hash` 涵蓋的是「這個 Run 能碰什麼」，配額是狀態不是權限，它變動不該作廢使用者手上的確認。

## 決策 3：三層併用，本 ADR 不取代閘道的任何一層

| 層 | 管什麼 | 失去它會發生什麼 |
| --- | --- | --- |
| 平台計數器（本 ADR） | 這個帳號這個窗口能跑幾次 | 成本上限失效，`01` §12「Sandbox 成本不可持續」無對策 |
| Virtual Key `max_budget` | 這一次最多花多少 | 單一失控迴圈可在一次 Run 內燒掉整個窗口的預算 |
| `tpm_limit` | 速率 | 併發爆量打穿閘道 |

三層各自擋一種失控形態，缺一種就有一種擋不住。**本 ADR 只補最外面那一層，不動閘道側任何既有設定。**

## 決策 4：值由 PDM-010 給，本 ADR 定的是強制點與語意

- 本 ADR **不定任何數字**。PDM-010 §8.1 的提案（首月 20／其後每月 30／每日 5／並行 2／計數起點 `preparing`／退還與不退還的分類）自己標了一個必須擇一的地方：**首月是 `min(20,30)=20` 還是 20+30=50**，提案原文寫著「請負責人明確擇一，不要留給實作推斷」。
- **未擇一之前，配額不得上線顯示**——顯示一個實作自行推斷出來的數字，是乙-2 的另一種形態。強制點可以先做（它不需要知道最終值），顯示不行。
- 封測人數與成功門檻屬 PDM-009，提案見 [`m4/pdm-009-beta-proposal.md`](../plans/mvp/m4/pdm-009-beta-proposal.md)，**同樣待追認**；允許清單的長度由它決定。

## 影響

### 正面

- ADR-020 的待決策 2 結案，且答案是既有機制的一次重用而不是一個新子系統：一個 middleware、一份部署設定、一筆啟動時的 audit event。
- 「配額會不會被執行」不再取決於實作者有沒有讀到 PDM-010——強制點與並行上限住在同一個函式、同一個交易裡，改動其中一個會直接看到另一個。
- 封測的成本上限第一次有一個真的會作用的機制（`01` §12 風險表「Sandbox 成本不可持續」的對策落點）。
- 未受邀者的畫面成為需求訊號的第三個入口，而不是一堵沉默的牆。

### 成本與限制

- **允許清單在部署設定裡，所以名單異動要重啟。** 單人團隊、封測一批人的規模下這是正確的取捨；擴編或名單需要頻繁異動時，升級路徑是「這裡改讀資料表」，路由與 handler 不動（同 `SEC-011` 的既有升級路徑）。
- **roster audit event 只答「誰現在在名單上」**，不答「誰在何時被加入」。這是刻意的最小形式，限制寫在這裡以免日後被讀成完整的授予稽核。
- **時間窗計數每次建立 Run 都要掃一次該 Workspace 的 Run 列**。封測量級下可忽略；量級上來時的升級路徑是加索引或改為物化計數，**但物化計數會把「餘額」變回一個可漂移的快取**，屆時必須連同退還語意一起重新設計，不能只加一個欄位。
- **配額擋的是次數，不是花費。** 一個把 token 用滿的 Run 與一個三秒就結束的 Run 各計一次。要控花費得靠 `max_budget` 那一層——這是三層併用的直接後果，不是缺陷。

## 待決策

- ~~**PDM-010 的首月語意擇一**（`min(20,30)=20` 或 20+30=50）；未定前不得顯示配額。~~ → **已於 2026-08-22 由 [`04` 乙-15](../plans/04-backlog-and-handoffs.md) 裁定：取 `min(20,30)=20`，不疊加。** 決定性的理由是本 ADR 自己的立場的延伸——疊加會引入第二個時鐘（跨月滾存？月底過期？），而配額是設計系統 §2.2 的東西，顯示與強制必須指得到同一行。落點是 `product/entitlements/quota.go` 的 `quotaFirstWindowRuns`（顯示面本來就讀 `Usage()` 算出的 `windowLimit`，首月印的一直是 20 而不是 30，所以這次沒有任何顯示要改）。**四個數字本身仍待負責人簽字**，那是 PDM-010 的追認，不是這一條。
