# ADR-010：產品分析與稽核邊界

- 狀態：Accepted
- 相關：[ADR-002 資料所有權與核心基礎設施](./ADR-002-data-ownership-and-core-infrastructure.md)、[ADR-004 Sandbox 隔離與執行安全](./ADR-004-sandbox-isolation-and-execution-security.md)、[ADR-005 模型閘道與可觀測性](./ADR-005-model-gateway-and-observability.md)、[ADR-007 打包、授權溯源與散布](./ADR-007-packaging-license-provenance-and-redistribution.md)、[ADR-021 營運後台](./ADR-021-operator-backoffice.md)

## 背景

鐵律要求 Secrets 不得出現在分析事件中，但「分析事件」需要一個可檢查的定義：schema、儲存位置、保存期限、讀取者。

平台既有的四類資料各自答不出漏斗問題（使用者從輸入意圖到查看詳情、試跑、給回饋、下載，逐段走了多遠）：平台 O11y 指標是聚合計數，沒有使用者維度；Audit Event 只記 actor／動作／資源 ID／時間戳、不含內容，且搜尋本身不是一個稽核動作；Run Trace 只涵蓋一次 Run 之內，答不出漏斗前兩段（此時還沒有 Run）；LLM 閘道的觀測資料只看得到模型呼叫。

在開始收集使用者行為事件之前，必須先定義這一類資料的形狀與邊界——一旦開始收集，保存、遮罩與揭露的義務同時成立，回頭緊縮一個已在收集的資料類別，代價是已經收集的那一批。

## 決策

### 決策 1：產品分析事件是獨立的第五類資料，且不是任何領域問題的事實來源

平台的可觀測性資料分三類（平台 O11y／Run Trace／Evaluation，見 [ADR-005](./ADR-005-model-gateway-and-observability.md)），本 ADR 定義第五類：

| 類別 | 回答 | 事實來源 |
| --- | --- | --- |
| 平台 O11y | 服務健不健康 | 是 |
| Run Trace | 一次 Run 內發生什麼 | 是 |
| Evaluation | 任務達成了嗎 | 是 |
| Audit Event | 誰做了什麼 | 是 |
| 產品分析事件 | 有多少人走到漏斗的哪一段 | 否 |

漏斗報表引用的 Run、評估、建議與下載事實一律取自領域表，不取自分析事件。四個分析事件不各自對應一段漏斗；第七段由領域表回答，造訪開始與下載意圖另有用途：

| 漏斗段 | 怎麼回答 |
| --- | --- |
| 輸入意圖後查看至少一個詳情 | 新事件 `search_performed`、`skill_detail_viewed` |
| 查看詳情後 Fork 或啟動試跑 | `runs` 列 |
| 建立 Run 後成功完成 | `runs` 表 |
| 完成 Run 後認為結果有幫助 | `evaluations.feedback_helpful` |
| 改善建議被採用 | `evaluation_suggestions.decision` |
| 完成試跑後打包下載 | `download_records` |
| 首次使用後再次回來試跑或重新驗證 | `runs`／`evaluations`；同一查詢窗口內，同一 Workspace 在至少兩個不同 UTC 日建立 Run 或評估 |
| （封測阻斷問題分析的預備資料） | `session_started`；不參與七段漏斗，目前沒有自動讀取報表 |
| （區分「按了下載」與「下載成功」） | 新事件 `download_started`（成功那一半仍取 `download_records`，此項在七段之外） |

新增第五個事件之前，必須先說明既有領域表為何答不出來。

`session_started` 保留作為封測阻斷問題分析的造訪起點資料，不把它改成留存分母。寫入端在瀏覽器回傳有效長度的 `sh_analytics` cookie 後，依 `sh_analytics_visit` 的 UTC 日期判斷是否記錄；冷啟請求尚未確認 cookie 時不記錄，並行請求仍可能重複，因此事件筆數不等於訪客人數。此事件不帶 Workspace 關聯，沒有專屬屬性，也不表示使用者已搜尋、試跑或成功完成任何任務。

這是已收集但尚未接上自動消費端的預備資料，不宣稱已能完成 `BETA-004` 的阻斷歸因。`feedback_reports` 沒有分析 session 識別，不能把回報與事件自動串起來，也不得以時刻相近或相同 Workspace 猜測串接。是否把 session 識別加入回報仍是另一項隱私決策；本決策不授權新增欄位、擴大追蹤或反查登入憑證。封測準備與範圍複審須重新檢查這項預備用途，不能用本次保留理由推導永久收集的必要性。

第七段維持 `tools/analytics/funnel.sql` 的 Workspace 口徑：分母是在窗口內建立 Run 或評估的 Workspace，分子是其中跨至少兩個 UTC 日有此活動的 Workspace。它不是帳戶終生首次使用 cohort，也不是再次開啟目錄的比例；窗口外的回訪不計，只能當下界。沒有 `session_started` 不影響這一段計算，有它也不能證明回來試跑。

### 決策 2：事件形狀只記型態、不記內容——白名單而非黑名單

固定欄位為 `event_id`、`event_name`、`occurred_at`、`session_id`、`workspace_id`（登入後才有，未登入為 `NULL`），加上該事件名稱在 schema 中宣告的屬性。

- schema 未宣告的屬性一律丟棄，不是記下來再遮罩：黑名單漏一項是洩漏，白名單漏一項只是少一個維度。
- 一律不記自由文字內容。`search_performed` 記查詢的長度、語言、是否有結果、結果數、是否套用篩選，不記查詢原文——查詢原文可能含個資，需要質性資料的管道另有明示同意。
- `skill_detail_viewed` 記 `skill_id` 與到達來源（搜尋第幾名／直接連結）。
- 「Secrets 不得出現在分析事件中」由結構保證：只有白名單屬性、沒有一個屬性承載自由文字，不靠遮罩器再跑一次。Run Trace 因承載執行內容而需要遮罩（[ADR-005](./ADR-005-model-gateway-and-observability.md)），分析事件在結構上沒有可遮罩的東西。

### 決策 3：與 Audit Event 的邊界——不合併、不互相代替

| | Audit Event | 產品分析事件 |
| --- | --- | --- |
| 回答 | 誰做了什麼（可稽核，可能成為證據） | 有多少人走到哪一段（彙總） |
| 主體 | 具名 actor（取自 session） | `session_id`；登入後才有 Workspace 關聯 |
| 涵蓋範圍 | 重要操作：匯入、權限確認、Secret metadata、Run 生命週期、Artifact 下載、使用者資料刪除（見 [ADR-004](./ADR-004-sandbox-isolation-and-execution-security.md)） | 漏斗四事件 |
| 保存 | 遠長於分析事件（涵蓋跨年度安全事件回溯） | 365 天，只含白名單屬性 |
| 可變性 | 不可刪改 | 可整批刪除、可重建彙總 |
| 帳號刪除 | 去識別化 actor 保留 | 去識別化（移除 Workspace 與帳號關聯），彙總保留 |

拿 audit 當分析來源會同時做壞兩件事：要嘛往 audit 裡塞內容（破壞它不含內容的隱私設計），要嘛答不出漏斗前兩段（那兩段沒有任何 audit 動作）。反過來拿分析事件當稽核也不行——它可以被整批刪除、可以重建，一份可以被合法整批刪除的紀錄，不能拿來回答「誰在何時做了什麼」。同一個使用者動作可以同時產生兩者（例如下載：audit 記誰下載了哪個 artifact，分析記有一個 session 走到了下載段），這不是重複，兩者的保存期限、可見性與刪除行為都不同，合併會讓兩邊都被較嚴的那一個綁住。

### 決策 4：與 Run Trace 的邊界

| | Run Trace | 產品分析事件 |
| --- | --- | --- |
| 範圍 | 一次 Run 之內 | Run 之外，含還沒有 Run 的那兩段 |
| 使用者可見 | 是 | 否 |
| 內容 | 承載執行內容，因此必須遮罩 | 結構上不承載內容，沒有可遮罩的東西 |
| 關聯 | `run_id`／`attempt_id`／`seq` | `session_id` |

漏斗前兩段根本沒有 Run，Trace 在結構上就答不了它們，這是類別錯誤而不是尚未實作。下載不產生 Trace 事件（打包不是 Run）：下載的紀錄走 audit 與 `download_records`，走到漏斗的那一份走分析事件，三者各自獨立。

`session_id` 不得重用登入 session token 或其雜湊——那是憑證材料。分析用的 session 識別是另一個隨機值，不可反查回 session 列；未登入時它是唯一的關聯手段，登入後才附上 `workspace_id`。

### 決策 5：保存、匿名化與揭露

- 保存期限 365 天。長度介於 Run Trace（月級）與 Audit Event（跨年回溯）之間：短於 Audit 是因為分析事件不是稽核事實、不需要跨年回溯；長度足以覆蓋跨月的回訪觀察窗，也是送法務與寫進同意書的數字。
- 新資料類別在保存期限未定值前不得開始收集；一旦開始收集才回頭緊縮期限，代價是已收集的那一批。
- 未登入的互動一樣量測（漏斗第一段發生在登入之前），該類事件只有 `session_id`、沒有 `workspace_id`。
- 帳號刪除採去識別化保留：移除 Workspace 與帳號關聯，事件本身保留，供跨季度的漏斗比較使用；封測期間蒐集的質性回饋同此處理。
- 使用者揭露是必要條件不是加分項：資料保存政策必須列出這一類資料的存在、內容範圍（含「不記查詢原文」這句）與保存期限。分析事件是唯一一類使用者沒有主動提交任何東西就會產生的資料，揭露的義務因此比其他類別更重。

### 決策 6：存在 Postgres，不新增資料產品、不接外部分析 SaaS

- 存 Postgres，按月分割，`DROP PARTITION` 清理，保存期限直接決定分割策略。
- 不新增資料產品（[ADR-002](./ADR-002-data-ownership-and-core-infrastructure.md) 的最少產品原則）：現有量級距離需要專用分析儲存的門檻還有數量級的差距。
- 不接外部分析 SaaS：它會帶進資料出境與第三方 cookie 兩個新的合規面，而漏斗量測只是一組 SQL，不是一個平台。
- 讀取面是後台查詢，不做即時儀表板：這一類資料要回答的是一份報告，不是一個一直開著的畫面。打開時查一次、不輪詢的圖（營運後台的趨勢頁）不算即時儀表板，它回答的仍是一份報告。

## 影響

### 正面

- 鐵律裡的「分析事件」從一個沒有指涉對象的詞，變成一個有 schema、有儲存、有期限、有讀取者的資料類別，可以被檢查。
- 「新增一個分析管線」被縮小成四個事件，因為決策 1 強制先問既有領域表答不答得出來。
- Audit Event 的隱私設計（不含內容、長保存期）被保護下來，不會為了做漏斗而被迫塞內容。

### 成本與限制

- 不記查詢原文的代價是真的：「使用者輸入了什麼卻找不到東西」這個訊號，在分析事件裡只剩長度與語言，須由樣本量遠小的質性管道補足，這是刻意的取捨。
- `session_id` 讓「同一個人」只能追到 session 粒度，跨裝置或清掉瀏覽器狀態的同一個人會被算成兩個；登入後可由 `workspace_id` 合併，登入前不行，漏斗第一段因此系統性略微高估分母，報表須寫明這一點、不得讀作精確值。
- 多一張按月分割的表要維護（分割建立、清理、備份體積）。
- 不做即時儀表板在營運上可能不方便：要看數字得跑查詢，但一直開著的畫面會產生盯著它的成本，而漏斗數字在事後才有意義。

## 待決策

- 公開 Beta 之後的量級是否需要專用儲存或外部工具：訊號是查詢時間或分割表體積，屆時另立 ADR；本 ADR 的事件形狀（白名單屬性、無自由文字）刻意與儲存實作無關，換儲存不必重新設計事件。
- A／B 實驗框架：漏斗量測與實驗分流是兩件事，後者需要分流、樣本量計算與結果判定三套東西，目前不在範圍內。
- 分析事件的讀取權限：目前讀取者即部署者本人；出現非工程角色需要看報表時，是否沿用 [ADR-006](./ADR-006-identity-workspace-admission-and-allowances.md) 的 operator 角色或另立角色，屆時另議。
