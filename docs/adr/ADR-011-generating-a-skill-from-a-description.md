# ADR-011：從描述生成 Skill

- 狀態：Accepted
- 相關：[ADR-001](./ADR-001-system-context-planes-and-deployment-path.md)（能力提供者分工）、[ADR-004](./ADR-004-sandbox-isolation-and-execution-security.md)（驗證與信任邊界）、[ADR-005](./ADR-005-model-gateway-and-observability.md)（模型閘道）、[ADR-006](./ADR-006-identity-workspace-admission-and-allowances.md)（配額機制）、[ADR-007](./ADR-007-packaging-license-provenance-and-redistribution.md)（`redistribution`、License 溯源）、[ADR-008](./ADR-008-intent-search.md)（目錄三態）、[ADR-009](./ADR-009-evaluation-verdicts-and-judge-trust.md)（引文回驗）、[ADR-012](./ADR-012-interactive-creation.md)（多輪、有結構化解析保存的互動創作）

## 背景

搜尋找不到夠接近的 Skill，或使用者根本不了解 Skill 規格時，產品需要一條「不必先學會寫 Skill」的路：讓模型直接把任務描述（或一張流程圖、或幾個既有 Skill）變成一份可安裝的 Skill 版本。這條路必須回答三件事：生成物在信任與散布意義上算什麼、驗證與品質的界線在哪、失敗與花費怎麼收斂成一個使用者看得懂的結果。

這條路刻意與「改善既有版本」（引文必須逐字對上既有 Run 證據，見 ADR-009）分開：生成沒有既有版本、沒有 Run、沒有引文可以回驗，把兩者接同一套語意只會讓其中一套防線在另一邊整條落空。

## 決策

### 決策 1：生成物只存在於建立它的工作區，不進公開目錄、不進搜尋索引

目錄的三態階梯（見 ADR-008）量的是「經過多少人工檢視」，生成物在這把尺上沒有一格符合：沒人審查過、不是從平台外匯入、也不是從平台外找到的。不進目錄就不必新增第四態、不必決定收錄政策——這與生成不屬於初期公開發佈範圍一致。

使用者對自己生成的 Skill 能做的事，與對自己匯入的 Skill 完全相同：看得到、試跑得了、改得動、下載得了；別人看不到，連生成者自己搜尋時也看不到。

**目錄開放的前提是三件事同時成立，缺一不可**：有人負責審查生成物；目錄收錄檢核表對機器產出的每一項都有答案（尤其是「License 明確」「來源可追溯」「作者可辨識」三項，機器產出在字面上都答不出來）；能篩掉「這個 Skill 本來就做不到的任務」這一類通過驗證但沒有意義的產出。三者不成立之前，這條路徑不存在。

### 決策 2：三種輸入模式，一條輸出路徑；輸出永遠是新 Skill 的第一個版本

生成請求可以帶任務描述（文字）、一張流程圖、或幾個既有 Skill 作為參考，三者中至少要有任務描述或流程圖之一；參考清單本身不構成一次完整請求，因為模型仍然需要一個任務才知道要做什麼。三種模式共用同一個生成端點與同一條後續路徑：Go 端呼叫模型、打包、走與匯入完全相同的驗證，寫下版本一、`redistribution = generated`。

生成的輸出**永遠不延續任何既有版本的版本鏈**——參考 Skill 進的是模型讀的材料，不是請求的起點版本，這與「改善」是兩種語意、兩個端點，不因為多了參考輸入而合併。呼叫→打包→驗證→失敗重試的迴圈寫在 Go 一個平鋪的迴圈裡，不引入多輪代理框架；需要多輪對話與跨輪保存結構化解析的互動創作是另一條路徑（見 ADR-012），不在這條路徑的範圍內。

### 決策 3：參考既有 Skill 有可讀性限制

被參考的 Skill 必須是呼叫者讀得到的（自己的工作區，或依既有 Fork 範圍規則可讀的目錄項目），且不是已下架、不在存取限制之下、`redistribution` 不是被封鎖的值——任一命中就整批拒絕生成請求，並在同一個回應裡指出是哪一項與原因。一個平台已經判定不可信、不可散布、或已撤下的 Skill，沒有理由被當成「值得參考的既有實務」餵給模型。

### 決策 4：輸入的留存範圍——只留數位指紋，不落地存流程圖位元組

流程圖只接受點陣圖（不含 SVG，因為 SVG 可以夾帶腳本與外部引用，等於在生成路徑上多開一個未經驗證的解析面），有解碼後位元組上限；平台不儲存圖片本身，只記它的雜湊、媒體類型與位元組數，供之後在詳情頁的「這次生成用到的輸入」區塊顯示。理由是流程圖對生成結果沒有事後複現的價值——生成物的來源紀錄仍然是任務描述、提示詞版本與模型識別，這些已經足夠說明「同樣的輸入問同一個模型應該得到同一份東西」；保存任意使用者上傳圖片會立刻背上一整套物件儲存的保存期限、存取控制與刪除規則。參考 Skill 的清單同樣以名稱顯示在生成物的來源區塊，每個名稱連到該 Skill 的詳情頁——那一頁本來就做可讀性判定，連結不會多洩漏任何東西。

日後若需要保存原圖以支援複現診斷，那是一個需要重新裁定保存期限、存取控制與儲存成本歸屬的新決定，不在本決策的範圍內自動成立。

### 決策 5：建版門檻是既有的套件驗證加一條生成專屬的空內容檢查，生成的 Script 不享任何寬待

生成物寫版本前必須通過與匯入完全相同的驗證（見 ADR-004）：一條檢查不過，整組生成結果拒絕，不建版本。這是一道語法門，不是品質門——多數檢查是結構性的（`SKILL.md` 存在、frontmatter 合法、規格外欄位、命名格式、路徑逃逸），但其中一條是內容檢查：對每個檔案的內容比對憑證樣式，命中即阻擋，回饋只給檔案路徑不揭露比對到的值。除此之外，生成路徑在這道語法門之外再加一關：若模型交出的 `SKILL.md` 本文完全空白，直接拒絕為格式不正確，不讓它憑合法的 frontmatter 矇混過關——這一關只存在於生成路徑，因為只有模型產出才會出現「鍵名合法、內容全空」這種形狀。不另立額外的品質規則，因為建立當下沒有能力判斷「這個 Skill 有沒有用」——那是試跑存在的理由。生成的 Script 走與匯入的 Script 完全相同的靜態掃描、`SKILL.md` 內嵌程式碼揭露與沙箱執行；畫面上不得因為「這是平台生的」而少一個警告，因為生成模型不是可信來源，它只是一個沒有上游的來源。

生成物在建立當下沒有經過任何人可以看見的檢視，也沒有任何試跑證據——這件事必須在畫面上明確說出來，不是驗證通過就等於品質保證。

### 決策 6：阻擋級失敗的重試規則

驗證失敗時，平台不修改模型交出的位元組——重試永遠是同一個 prompt、同一個模型，不加修正提示，因為多數阻擋是隨機的排版類手滑而不是系統性的能力缺陷。規則：

- 阻擋級發現 ⇒ 重試恰好一次；第二次仍被擋 ⇒ 失敗，把發現逐字交給使用者，不重寫成安慰話。
- 憑證樣式那一類發現是例外，**不套用重試**：那類內容多半是寫作習慣而不是手滑，同一個 prompt 重試大概率原樣重現，等於花錢買同一個答案。同一次生成若同時出現這一類與其他類，以不重試為準。
- 上限就是一次，不做「重試到成功」的無界迴圈。
- 一次重試能顯著提高通過率，但不會趨近於零；介面不得對外承諾生成的成功率。

### 決策 7：輸出長度上限與額度按「一次生成」計

模型輸出上限需要蓋住推理與內文的總和，不能只看內文長度，否則會把一次把預算花在推理上的呼叫錯判成「輸出太長」。呼叫因為超過上限被截斷時是一個與決策 6 不同的失敗類別，不重試，直接告知使用者這次任務的產出超過一次生成能處理的範圍。額度扣的是「一次生成」這個使用者動作，不是背後的呼叫次數——決策 6 的重試是平台自己選擇的結果，不該讓使用者為它多付一次；因此重試失敗與截斷都不扣額度，失敗的成本落在平台身上而不是使用者身上。

### 決策 8：`redistribution` 新增 `generated`，License 欄位由生成器留白

生成物的位元組是平台的模型應使用者要求產生、只落在他自己的工作區、只有他讀得到——交還給他不構成平台多加一個散布環節，所以下載沒有被額外鎖住。但它不與「使用者自己提供的內容可以下載」共用同一個值：兩者對「能不能發佈到公開目錄」這個問題的答案不會一樣，前者要問「這份別人寫的東西你有沒有權利散布」，後者要問「模型寫的東西的權利歸屬是什麼」；共用一個值只會讓其中一邊將來被錯誤地一起放行。這個值也刻意不寫成「允許」，任何未來的發佈路徑都必須停下來重新判定。

生成器不得在 frontmatter 寫入 License 宣告——生成物在授權意義上沒有上游可以溯源（即使輸入包含了讀過的參考 Skill，那些也只是模型的閱讀材料，不構成授權上游），模型自己編出來的宣告不能佔用「已經有人宣告過」這個狀態。License 狀態預設未知，由使用者事後自行宣告；未知不擋下載，但擋住每一條發佈路徑，這正是需要的效果。

### 決策 9：生成物可以作為 Fork 的來源

Fork 需要原始 Skill、原始版本、來源與 License 關係，生成物四項都有：原始 Skill 是它自己，來源是那筆生成紀錄，License 是「未知直到使用者宣告」。`redistribution` 的值逐字被 Fork 繼承。刻意允許而不是阻擋，因為阻擋反而需要新增規則、錯誤碼與說明，而這些都沒有實際需要服務的對象。

### 決策 10：生成消耗獨立的配額，預設使用較便宜的模型

生成的花費與 Run 的花費分開累計（機制與門檻數字見 ADR-006），不共用同一個池——共用會讓一次生成安靜地吃掉試跑的餘額，而試跑是搜尋漏斗量測的核心動作，不該被一條額外路徑侵蝕。生成的預設模型以環境變數注入，切回更貴的模型只是改一個設定值，不改程式。選擇較便宜模型的理由不是省錢優先，而是它在唯一量過的維度上更好：多數驗證失敗集中在 frontmatter 鍵名這類字元級瑕疵，輸出愈短，出錯的暴露面愈小；同一次重試規則對它同樣適用。

較便宜的模型的已知限制是它傾向只產出單一檔案，不主動附帶腳本——這是否代表較差的產出尚未驗證，不得被解讀成「便宜的模型產出品質更差」或「更好」的證據，它只證明了通過驗證的機率更高。

### 決策 11：入口只接在「找不到」與工作區列表，不在首頁放對等按鈕

生成的入口只出現在搜尋「沒有夠接近的結果」的分支，以及使用者自己的工作區 Skill 列表。首頁不放一個與搜尋對等的生成按鈕：先搜尋、搜不到再生成，這個順序本身是刻意的產品意見，把它做成二選一會讓使用者在還沒有任何判斷依據時就要在「免費且熟悉」與「要花錢且沒有證據」之間選。

生成能力何時對外可見，與這條路徑何時可以動工是兩個分開的決定：能力可以先在程式裡落地，實際曝光另外由一個獨立的開關控制，預設關閉。這樣可以先把可驗證的機制（契約、驗證、額度）準備好，而不必等到曝光時機成熟才開始寫程式。

## 影響

### 正面

- 不了解 Skill 規格的使用者第一次有一條走得完的路，不必先學會寫 Skill 才能開始。
- 生成物與匯入物在版本、驗證、試跑、評估、打包上共用同一套機制，新增的只有生成這一步本身。
- 三種輸入模式共用同一條驗證與儲存路徑，不必為生成物維護第二套規則。

### 成本與限制

- 生成物在建立當下沒有任何人工檢視或試跑證據，驗證只把最基本的格式錯誤與明顯的憑證外洩擋下來，擋不住「這個任務本來就做不到」這一類看起來合格但沒有意義的產出——這是這條路徑最大的新風險，緩解只有「不進目錄」與「不給 Script 寬待」兩層，畫面上必須把這件事說清楚。
- 較便宜的預設模型不主動寫腳本，帶腳本的產出是否對使用者更有用尚未驗證；重試後仍有一定比例的殘餘失敗，UI 不得承諾成功率。
- 參考既有 Skill 與流程圖各自帶入一種新的不可信輸入：別人寫的文字要進模型的提示詞、任意上傳的圖片要先解碼——兩者都要落在既有的不可信資料處理與大小上限之內。
- 流程圖只留數位指紋，換來的代價是事後無法回答「當時傳的到底是哪張圖」；重新保留原圖需要一個新的、明確處理保存期限與存取控制的決定，不會因為出現個案就自動打開。
- 目錄開放的三個前提今天都不成立，這條發佈路徑實際上不存在，也不是因為沒人想過。

## 待決策

- 帶腳本的生成物與純指示型的生成物，哪一種對使用者更有用，需要試跑與人的評估才能回答。
- 一次重試後仍然失敗的少數案例，第三次重試是否值得，目前沒有資料支持任何一個答案。
