# ADR-028：平台 Agent

- 狀態：Accepted

## 背景

平台要由多個無人值守的 Agent 協助管理：解讀每天的維運事實、預測封存時機、初判失敗、提出清理與調整。它們和使用者在 Skill 裡跑的 Agent 是兩件事——那些 Agent 執行不受信任的內容，關在沙箱裡；平台 Agent 的程式是平台自己的，危險來自它讀到的資料與它被允許做的事。

現況有三個缺口。所有身分都假設是人：使用者、Session、operator 名冊都以 user 為單位，稽核紀錄的行為者欄位只能指向一個 user 或留空。模型呼叫已經有一個合適的形狀——互動創作由 Python 決定下一步、Go 保存狀態並執行工具（[ADR-012](./ADR-012-interactive-creation.md)）——但它是為創作寫死的，沒有可以讓第二個 Agent 重用的迴圈。最後，一個會被提示注入或單純判斷錯誤的 Agent，後果必須有界：它能讀什麼、能做什麼、能花多少錢，都要在它之外被強制。

## 決策

### 決策 1：Agent 是登記過的機器身分

每個平台 Agent 在資料庫裡有一筆登記：名稱、用途、負責的營運者、啟停狀態、模型角色、每日花費上限、允許的工具與允許提出的動作。Agent 不是 user：不能登入、沒有 Session、不在 operator 名冊上，也不持有任何點數帳戶。

稽核紀錄的行為者分成三種：人、Agent、系統。Agent 觸發的每一筆稽核都指向它的登記。停用有兩層：單一 Agent 的啟停，以及全域的 Agent 煞車；兩者都在下一步之前生效，不等目前的執行結束。

### 決策 2：Agent 只決策，Go 執行

Agent 的迴圈由 Go 驅動。執行的狀態、步數、預算、逾時與取消都在 Go 擁有的 Postgres 裡；每一步，Go 把目前的狀態與可用工具的定義交給 Python 能力服務，取回「下一步」——一個工具意圖，或最終的結構化結果。Python 不持有狀態、不碰資料庫、不執行工具、不決定授權。這與互動創作是同一個形狀；創作日後遷入同一個通用迴圈，不另養第二套。

平台 Agent 不在沙箱裡執行。沙箱是為不受信任的 Skill 設計的，裡面工具全開，安全完全靠隔離；平台 Agent 需要的是窄工具與動作核准，把它放進沙箱只會讓它要拿控制平面的事實時繞路。

### 決策 3：工具是型別化的唯讀事實

工具由 Go 提供、逐個登記，每個工具有固定的輸入與輸出型別，由擁有那項事實的 Bounded Context 經組合根注入；沒有 shell、沒有任意 SQL、沒有讀檔。每一次工具呼叫都寫進 Agent 的執行紀錄。工具回傳中由使用者產生的文字（Skill 名稱、描述、回報內容）一律以資料圍欄包起來，讓模型分得出那是資料不是指令。

### 決策 4：動作分三級，破壞性動作每次都要人核准

Agent 不直接改變系統，只提出提案。動作在 Go 的動作登錄表裡逐個登記，各自屬於一級：

| 等級 | 意思 | 誰放行 |
| --- | --- | --- |
| 唯讀 | 產出報告、告警 | 自動 |
| 可逆 | 效果可完整撤回的調整 | 可預先授權給特定 Agent；未授權時同破壞性 |
| 破壞性 | 刪除、封存、改變別人看得到的東西 | 每次都要營運者在後台核准 |

提案帶預覽（會發生什麼、影響多少筆）、理由與逾期時間。核准後由既有的實作執行——`maintenance` 子命令或領域服務——不為 Agent 另寫一份。提案是 Go 擁有的狀態機：提出之後被核准、駁回或逾期，核准後執行成功或失敗；每一次轉移都寫稽核。營運者核准一個提案，是以營運者自己的身分放行，受營運後台既有的權力邊界限制；Agent 不能提出營運者本來就不能做的動作。

第一批動作是「立刻補跑」各個維運工作：日報看到某個工作逾期，就提出補跑它的提案，預覽是那個工作的擁有者以與工作本身相同的條件算出的筆數，工作會逐筆再檢查的寫成「最多」，一次只處理一批的寫出批量。預覽每一項都是零筆的提案不記錄、不送到營運者面前——沒有東西會改變就不需要核准；逾期本身仍以待辦留在收件匣，因為該修的是排程，不是手動補跑。核准後不由 Worker 執行，而由既有的 `maintenance` 程序每五分鐘領取已核准的提案、以清除用的資料庫角色跑同一個子命令，結果回寫提案——刪除資料的權限仍只在那個程序。同一個動作同時只有一個進行中的提案；24 小時內沒有核准即逾期作廢，由 Worker 定期標記。可逆動作的預先授權尚未裁定之前，一律比照破壞性等人核准。

### 決策 5：隱私邊界與營運後台相同

Agent 不讀私人資料：Trace、Prompt、Test Case、Dataset、Run 明細與產出都不在任何工具的回傳裡。Agent 讀的是不指向帳號的彙總與維運事實。擴大這條邊界需要另立決策，並先回答揭露與同意。

### 決策 6：每次執行一把限額金鑰，花費記帳但不扣使用者點數

每次 Agent 執行簽一把閘道 Virtual Key，限額、限時、限該 Agent 的模型角色，執行結束即撤銷。花費寫進成本事件：沒有使用者、參照指向那次 Agent 執行，不產生任何扣點分錄。每日上限在 Go 簽發金鑰前先檢查，閘道的總額是第二道而不是唯一一道。模型以閘道的角色別名指定，換模型只改閘道設定。

### 決策 7：排程在 Worker，每次執行有上限

Agent 的執行由 Worker 的週期工作觸發，佇列消費者仍只有 Go Worker。每次執行有步數、token 與時間上限，到達即以「未完成」結束並記錄原因，不重試到成功。執行紀錄的保存依資料保存的處置規則宣告。

### 決策 8：新的 Bounded Context `operations`

Agent 登記、執行紀錄、提案與動作登錄表屬於一個新的 Supporting context `operations`。它不讀別人的表：工具背後的事實與動作背後的實作，都是由各擁有者提供、在組合根注入的介面。

### 決策 9：每個 Agent 有固定考題

每個 Agent 附一組固定的事實快照與期望：給定這份輸入，輸出的提案不得越權、引用的事實必須存在於輸入、等級必須正確。預設以測試替身跑在 CI；真模型的量測按需執行，費用與結果一起記錄。

### 決策 10：Agent 回報的事是可追蹤的待辦，不是讀完就沒了的信

Agent 的結果裡需要人注意的每一項，由 Go 在完成執行的同一個交易裡記成一筆待辦，附它引用的事實當時的值。同一件事以引用的事實辨識：之後的回報只要與一筆待辦共用任一個引用，就併進那一筆、累計次數，不另開；進行中的待辦優先、其次是最近出現的。回報不再提到的進行中待辦標成「已自行恢復」；已解決或已自行恢復的事再被回報就重新打開；營運者忽略的事再被回報仍維持忽略，只累計次數。狀態只有待處理、處理中、已解決、已忽略、已自行恢復五種，營運者可走的轉移由 Go 決定，每一次轉移都寫進待辦自己的經過與稽核，Agent 造成的轉移記在 Agent 名下、營運者的記在營運者名下。之後的提案進同一個收件匣。

## 影響

### 正面

- 第二個、第十個 Agent 都接在同一個基座上：身分、工具、動作、預算、稽核與停用各只有一套。
- Agent 被注入或判斷錯誤時，最壞的後果有界：讀不到私人資料、做不了未登記的動作、破壞性動作過不了人、花不超過自己的上限。
- 稽核第一次分得出「人做的」與「Agent 做的」。

### 成本與限制

- 稽核紀錄的行為者欄位要改模型，既有的讀取查詢與營運者動作清單要一起跟上。
- 破壞性動作的放行速度受限於營運者的反應時間；這是刻意的。
- 創作遷入通用迴圈之前，會有兩個形狀相同的迴圈並存。

## 待決策

- 核准通知目前只在後台出現；要不要推送到外部管道，等第一批提案的實際頻率出來再決定。
- 可逆動作預先授權的範圍：哪些 Agent、哪些動作可以在無人值守的時段直接執行。
- 創作遷入通用迴圈的時機。
