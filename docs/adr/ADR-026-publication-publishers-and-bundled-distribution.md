# ADR-026：發佈、發佈者與組合散布

- 狀態：Accepted
- 相關：[ADR-006 身分、Workspace、准入與額度](./ADR-006-identity-workspace-admission-and-allowances.md)、[ADR-007 打包、授權溯源與散布](./ADR-007-packaging-license-provenance-and-redistribution.md)、[ADR-008 意圖搜尋](./ADR-008-intent-search.md)、[ADR-017 Query 與寫入所有權](./ADR-017-query-and-write-ownership.md)、[ADR-018 Aggregate 與領域事件](./ADR-018-aggregates-and-domain-events.md)、[ADR-021 營運後台](./ADR-021-operator-backoffice.md)

## 背景

散布是產品三個核心之一，但它今天只有一半：**平台有下架，沒有上架。**

治理那一側的動詞齊備——限制、可散布判定、策展層級、下架都有營運者端點，違規內容拿得下來。作者那一側一個動詞都沒有：決定一個 Skill 是否公開的是 Workspace 上的一個布林旗標，而整份 SQL 只有讀它的查詢，沒有任何路由或介面能把它打開。「公開目錄」因此是平台自己持有的一個 Workspace，內容由維運手動放進去。作者能做的只有把可攜套件下載下來，用平台以外的方式傳給別人。

同時，散布的單位只有一個 Skill Version。**匯入認得 Agent Plugin，但那是入口形狀**：一個 Plugin 進來之後被攤平成 N 個各自獨立的 Skill，之後沒有任何地方看得出它們是一套，也沒有辦法把它們交還成一份。取得別人的 Skill 只有 Fork 一條路，而 Fork 與打包都要求封測准入。

跨過 MVP 之後這三件事同時變成阻塞，而且互相咬住：**沒有發佈動作，任何交付形狀都沒有出口**；**沒有命名空間，目錄一長大就在通用名稱上撞車**；**沒有組合，使用者永遠只能一個一個給、對方一個一個裝。**

命名與身分不自己發明。成熟市集在這件事上已經收斂成同一組做法：識別字是「命名空間前綴 ＋ 本體名稱」而不是把作者塞進名稱裡；命名空間綁在帳號或組織上、自助註冊、驗證是事後的加值而非發佈門檻；改名不原地覆寫，而是保留舊識別字並轉址或標示棄用；真正不可變的引用只能靠內容位址，可變的標籤都可能被事後改指向。宿主端還貢獻了一條現成的答案：一個 Plugin 的元件在使用者環境裡是掛在以 Plugin 為名的命名空間之下（`deploy-tools:reviewer`），所以**安裝端的同名衝突不是平台要解的問題**。

## 決策

### 1. 發佈是一個作者發起、可撤回、可稽核的動作，對象是一個不可變版本

發佈的主體是 **Publication**：一筆記錄「某個發佈者把某個不可變版本對外揭露」的事實。狀態是 `draft → published → delisted`，每次轉移留稽核紀錄。可發佈的版本只有兩種：一個 Skill Version，或一個 Bundle Version。

**既有的治理動詞掛在這個狀態機上，不另造一套**：限制、可散布判定、策展層級與下架作用於 Publication，不作用於 Workspace。平台自己持有的目錄 Workspace 從此是一個發佈者，不是一個機制。

### 2. 曝光與發佈分離

**發佈立刻產生一個可分享的公開位址；進入搜尋與目錄需要曝光資格。** 兩件事不共用一個開關：分享不該被審核卡住，而目錄品質要守得住。曝光資格的判準由內容審核決定，不由發佈者宣稱。

未取得曝光資格的 Publication 仍然可讀、可下載、可被連結——它只是不出現在搜尋與目錄裡。畫面必須說出它是哪一種狀態，不得讓作者以為自己已經上架。

### 3. 發佈者是命名空間的擁有者：全站唯一、自助註冊、事後驗證

一個帳號一個發佈者，對應一個帳號一個 Workspace。註冊不預審；**驗證徽章與能不能發佈是兩件事**，前者是加值，後者不設門檻。

**名稱規則沿用 Agent Skill 規格對 `name` 的規則**（小寫英數與 `-`、首尾為英數、不得連續 `-`），不另造一套——Skill 的 manifest 名稱已經被規格綁死成那個形狀，兩套規則會在匯出時打架。另有保留字清單擋冒充平台與上游供應商的名字，**並擋近似拼寫**（以 `.` 或其他符號取代連字號去模仿保留名同樣拒絕）。

### 4. 對外識別字是 `publisher/name`，名稱在發佈者內唯一

跨發佈者可以同名，引用一律帶發佈者。理由是通用名稱不能先到先得地燒掉：`code-review` 這種名字若全站唯一，第一個註冊的人就拿走了所有人的字。Skill 與 Bundle 共用同一個命名空間，所以一個發佈者底下不會有同名的 Skill 與 Bundle。

**這個識別字是目錄身分，不是安裝身分。** Skill 套件裡的 manifest `name` 仍然照公規，安裝之後由宿主決定它叫什麼。

### 5. 改名不原地覆寫

發佈者名稱與發佈物名稱都不支援原地改名。改名的形狀是：新識別字發佈、舊識別字保留為 tombstone 並轉址到新的。**舊識別字永不被其他人取得**。理由是我們的核心價值是可追溯，而轉址比燒毀名字保留更多相容性；冒名風險已由發佈者前綴擋掉大半。

### 6. Bundle 是一份釘住成員版本的發佈物，不是罩在 Skill 上的實體

一個 Bundle Version 是一份清單：**釘住的 Skill Version ＋ 一個 semver 版本字串 ＋ 一份說明**。它不改變任何 Skill 的身分、不建立跨 Skill 的聚合、不擁有成員。更新一個 Bundle ＝ 建立新的 Bundle Version；成員升版也是。

消費端因此看得到「這一版把哪個成員從哪一版升到哪一版」，這是有版本的組合與一次性壓縮檔的唯一差別，也是它值得存在的理由。

### 7. Bundle 的匯出形狀是 Agent Plugin

匯出時 `plugin.json` 的 `name` 是 Bundle 的名稱，每個成員放在 `skills/<manifest name>/`。**這推翻「平台不產出 Plugin」**：不產出的理由當時是「把 N 個 Skill 組回一個 Plugin 是一個發佈功能，不是匯入的對稱操作」，而本 ADR 就是那個發佈功能。

匯出的 Plugin **只含 Agent Skill**：`mcp.json` 與宿主專屬元件永遠不在裡面，因為平台從不匯入它們，也不替使用者決定要執行什麼。畫面要說出這件事，否則從別處帶著 MCP server 的 Plugin 進來又出去的人會以為東西還在。

**安裝端的同名衝突由宿主的命名空間承擔**——宿主以 Plugin 名前綴它的元件。平台不為此另造機制，也不改寫成員的 manifest 名稱。

### 8. 信任取最壞

一個 Bundle 的授權、靜態掃描判定、可散布資格與執行環境相容性，**一律取成員中最差的那一個**。任一成員不可散布，整個 Bundle 不可發佈，訊息要指名是哪一個成員與哪一條理由。

這不是保守的預設，是唯一誠實的聚合方式：一份組合能提供的保證不可能高於它最弱的成員，而使用者是整份安裝的。

### 9. 發佈物以內容雜湊釘住，版本字串只是語意標籤

Bundle 要求 semver，但**釘住成員靠內容雜湊，不靠版本字串**。版本字串的用途是讓消費端判斷「該不該升」，它不是完整性機制；可變的標籤都可能被事後改指向，這也是不可變版本規則已經在守的東西。

### 10. 揭露要具體，不接受泛泛免責

下載或安裝之前一次揭露：這個發佈物掃到什麼、授權事實與可再散布的範圍、在哪一層相容性上被驗過、它含有與不含有什麼。**「平台不保證內容」這種句子在這裡是退步**——沒有掃描與授權事實的平台只能那樣寫，我們有。

### 11. 策展層級說的是誰發佈這個目錄，不是每個東西做了什麼

策展層級是目錄品質的訊號，不是對單一發佈物行為的保證。畫面用語不得讓它讀起來像後者。

### 12. 匯入的處置不變

Agent Plugin 仍然是匯入形狀：不建立 Plugin 實體、不建立跨 Skill 的版本聚合，Plugin 層的事實由每個 Skill Version 的來源欄位承載。本 ADR 新增的是**作者這一側**的組合與發佈，兩者不對稱是刻意的——匯入來的是別人的容器，發佈出去的是作者自己組的清單。

## 影響

- **兩份已簽的東西要改寫**：規格裡「平台不產出 Plugin」那一條允收準則，以及打包 ADR 決策 9 最後一條「我們產出的仍然只有標準 Agent Skill 套件」。改寫的簽名請求在[待裁定清單](../plans/05-pending-rulings.md)。
- **MVP 的範圍界線要重新界定**：「完整公開發佈與創作者 Marketplace」原本明文排除在 MVP 外，而本 ADR 是它的一部分。
- **搜尋索引要有文件型別**：一個 Bundle 在目錄裡是一列，它的成員仍可被單獨搜到但要標出歸屬。否則一個五個成員的 Bundle 會在結果裡佔五列，而它們是同一個東西。
- **資料模型新增三個主體**：發佈者、Publication、Bundle（含它的版本與成員）。它們屬於哪個 Bounded Context、哪張表由誰擁有，依既有的登記程序決定，本 ADR 不在此定值。
- **封測准入這道牆要重新判斷**：今天 Fork 與打包都要求受邀，而發佈與取得是產品化的主路徑。
- **命名空間一旦開放就無法回頭**：tombstone 規則意味著每一個被註冊的名字都永久佔用。這是開放自助註冊的代價，先到先得的字越早開放越便宜、越晚開放越貴。
- **可攜套件的形狀不變**：單一 Skill 的套件、`INSTALL.md` 的欄位與三層相容性一個字不動。Bundle 匯出是**另一種**交付形狀，不是取代。

## 待決策

- 平台內分享的最小形態是公開連結、定向分享，或維持平台外傳遞（見[待裁定清單](../plans/05-pending-rulings.md)）。
- 發佈與取得是否對未受封測邀請的人開放。
- 驗證徽章的授予標準與它綁定哪些欄位；現階段刻意不做。
- 一個 Bundle 能不能含**其他發佈者**的 Skill Version。它牽動可再散布的授權判定，比自己的成員複雜一層。
- 發佈者是否可以多於一個帳號（組織形態），以及那時 Workspace 與發佈者的對應關係。
- 舊識別字轉址的保存期限，以及 tombstone 是否出現在搜尋結果。
