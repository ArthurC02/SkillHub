# ADR-024：外部系統的 Port 與 Adapter

- 狀態：Accepted
- 相關：[ADR-001 系統情境、平面與部署路徑](./ADR-001-system-context-planes-and-deployment-path.md)、[ADR-003 Run 編排與非同步工作流程](./ADR-003-run-orchestration-and-async-workflows.md)、[ADR-004 Sandbox 隔離與執行安全](./ADR-004-sandbox-isolation-and-execution-security.md)、[ADR-016 Platform Bounded Context 與 Context Map](./ADR-016-platform-bounded-contexts-and-context-map.md)、[ADR-017 Query 與寫入所有權](./ADR-017-query-and-write-ownership.md)、[ADR-022 淨測試模式](./ADR-022-clean-test-mode.md)

## 背景

Skill Hub 依賴的外部系統都會被換掉：沙箱的隔離技術與容器執行期、雲端與節點建置、防火牆與連線追蹤、日誌傳送、映像 registry、模型閘道、物件儲存，關聯式資料庫也是外部系統。換的理由各不相同（成本、安全等級、供應商停止服務、規模），發生的時間也排不進計畫。

外部系統的名字、錯誤訊息、輸出格式或能力描述一旦進了領域程式碼，換掉它就不再是換一個零件，而是改寫業務規則，連帶讓測試與 runbook 失效。「不綁定供應商」原本只寫在 Run 編排裡，其他外部系統沒有同一條規則，於是出現產品名被寫成領域常數、連線記錄的查法綁在某個工具的文字輸出上這類洩漏。

## 決策

### 決策 1：領域擁有 Port，外部系統只以 Adapter 接入

- Port 是需要某項能力的一方，用自己的語言定義的介面。方法、輸入輸出與錯誤分類都用領域詞彙，例如「沒有空位」「已不存在」「拒絕」「暫時不可用」，不用供應商的狀態碼或例外名稱。
- Adapter 實作 Port，負責把外部系統的概念翻譯成 Port 的語言。外部系統的 SDK、型別、錯誤字串與設定鍵只出現在 Adapter 裡。
- 依賴方向單向：Adapter 依賴領域，領域不依賴 Adapter。用哪個 Adapter 由組合根依部署設定決定，領域程式碼裡沒有「如果是某個供應商」的分支。
- Port 只開在外部系統的邊界。系統內部模組之間照 Bounded Context 與 Query 所有權的規則協作，不為了「可替換」替內部程式加介面。
- 資料庫同樣適用：業務規則在程式碼裡，SQL 負責存取與機制（補零、只寫一次、並行保護這類守衛），不擁有業務概念。

### 決策 2：跨行程契約是 Adapter 的線路格式，不是 Port 本身

行程內的 Port 是程式介面；OpenAPI 或事件 schema 描述的是某個 Adapter 與遠端服務之間怎麼說話。自建沙箱的 HTTP 契約因此是「自建 Provider」這個 Adapter 的格式。接一個不說這份契約的託管沙箱服務，是在控制平面再寫一個實作同一個 Port 的 Adapter，不需要先架一個轉譯服務去模仿我們的契約。跨行程契約仍然 OpenAPI-first，仍由 codegen 檢查漂移。

### 決策 3：能力與政策用領域的值表達，不用產品名

外部系統宣告能力時，領域比對的是值，不是名字。隔離以強度表達：強（使用者態核心或硬體虛擬化，例如 gVisor、MicroVM）、弱（與主機共用核心的容器）、無（直接以主機行程執行）；部署政策寫的是可接受的最低強度。出口是否被強制、資源上限是否真的被強制、記錄是否可用，同樣是值。新技術只要誠實宣告出相同的值就能被接受，不必借用舊產品的名字，也不必修改比對邏輯。

### 決策 4：外部系統產出的資料，先正規化成平台的格式

會被查詢、保存、稽核或由測試讀取的資料（出口連線記錄、Trace、Run 結果），格式由平台定義並放在 `contracts/`。Adapter 把工具的原始輸出轉成這個格式才寫出；runbook 的查法、告警規則與測試只讀平台格式。換掉產生資料的工具，這些讀者都不用改。

### 決策 5：每個 Port 附一組所有 Adapter 共用的契約測試

每個 Port 附一組契約測試與一個 Fake Adapter。任何 Adapter 接入前都要通過同一組測試，所以「換掉某個外部系統」的驗收是新 Adapter 通過契約測試，不是直接在正式環境試。必須靠真實外部系統才驗得出來的性質（隔離逃逸、真實雲端網路）另列為部署期驗收，不混進契約測試。

### 決策 6：節點與部署層也是 Adapter

節點建置腳本、防火牆規則與服務管理單元，是「部署目標」的 Adapter。它們的輸入是平台自己的來源（允許清單、release 設定），由平台的渲染器轉成目標系統的格式。換雲端、換防火牆或換服務管理器，是新增一個渲染目標與建置腳本；來源檔與它的檢查不變。

## 影響

### 正面

- 換外部系統的影響範圍限定在 Adapter、組合根與部署腳本；業務規則、歷史資料、runbook 查法與測試都不變。
- 同一個 Port 可以同時接多個 Adapter（例如兩種沙箱並存），由能力與政策挑選。
- Fake Adapter 讓業務規則不必起真實外部系統就能測試。

### 成本與限制

- 每個外部邊界多一層翻譯；翻譯錯了只有契約測試抓得到，契約測試本身也要維護。
- Port 以領域語言定義，實際上是各外部系統能力的交集；某個系統特有的能力需要另外設計受控的擴充點，不能直接穿過 Port。
- 正規化會丟掉原始輸出裡平台沒定義的欄位；需要時要擴充平台格式，而不是回頭去讀原始輸出。
- 只有一個 Adapter 的 Port 看起來像多餘的抽象；它存在的理由是外部系統會換，這個理由不適用於系統內部的程式。

## 待決策

- 模型閘道以標準協定（OpenAI 相容 API）當替換點；協定之上是否還要一層行程內 Port，等第一次實際替換時評估——今天只接過一個閘道。
  **物件儲存這半已經有答案**：第一次實際替換是淨測試模式，而它換掉的是協定的另一端（行程內起一個講 S3 的本機服務），客戶端一行沒改。協定就是替換點，不需要再加一層。
- **身分提供者的替換點已界定，仍未決的是第二個供應商**。領域擁有 `IdentityProvider` 介面（`AuthURL`／`Exchange`／`Identify`，只講領域語言、不帶供應商狀態碼），GitHub OAuth 是它今天唯一的 Adapter。**仍未決的是啟用第二個供應商的訊號與時點**，見[身分、Workspace、准入與額度](./README.md#身分workspace准入與額度)。
