# ADR-006：身分、Workspace、准入與額度

- 狀態：Accepted
- 相關：[ADR-001：系統情境、平面與部署路徑](./ADR-001-system-context-planes-and-deployment-path.md)、[ADR-003：Run 編排與非同步工作流程](./ADR-003-run-orchestration-and-async-workflows.md)、[ADR-004：Sandbox 隔離與執行安全](./ADR-004-sandbox-isolation-and-execution-security.md)、[ADR-005：模型閘道與可觀測性](./ADR-005-model-gateway-and-observability.md)、[ADR-010：產品分析與稽核邊界](./ADR-010-product-analytics-and-audit-boundaries.md)、[ADR-011：從描述生成 Skill](./ADR-011-generating-a-skill-from-a-description.md)、[ADR-016：Platform Bounded Context 與 Context Map](./ADR-016-platform-bounded-contexts-and-context-map.md)

## 背景

平台需要一個不引入額外基礎設施元件、且能立即支撐 Workspace 租戶邊界的身分機制；MVP 場景是個人創作者，但資料模型不能因為「先做個人版」而在未來加入團隊時要求大規模遷移。

Run 與生成都會產生模型與 Sandbox 成本，即使尚未正式收費也必須可計量、可限制。封閉測試第一次讓非團隊成員在真實部署上建立 Run，因此「誰能進來」與「誰能花多少」必須有明確、可稽核的強制點，而不是仰賴閘道側看似像煞車、實際管的是別的事的機制。

## 決策

### 決策 1：唯一登入方式是 GitHub OAuth，身分與帳號分離

- MVP 唯一登入方式為 **GitHub OAuth（Authorization Code flow）**。
- 身分與帳號分離：`user_identities (provider, provider_user_id) → user_id`；新增第二個 Provider 只是新增一列，不動 `users` 表。
- 首次登入自動建立 User 與個人 Workspace，兩者同一交易完成。
- Email 取自 GitHub 已驗證的 primary email，僅作顯示與通知用；帳號比對鍵是 `provider_user_id`，不是 Email（Email 可變、可重複註冊）。

理由：目標使用者（Agent Skill 個人創作者）的 GitHub 帳號覆蓋率接近全員，身分供應商本身就是內容供應鏈的所在地；自建 Email／密碼要自行承擔雜湊、重設信、防爆破與外洩監控，且需要新增寄信服務；外部身分 SaaS 則與自架基礎設施的方向相悖，MVP 只需要登入，採購整套 IdP 是過度配置。

### 決策 2：Session 是伺服器端狀態，存在 Postgres，不用 JWT

- **伺服器端 Session，存 Postgres `sessions` 表**；撤銷（登出、封鎖、帳號刪除）必須立即生效，JWT 的撤銷清單本質上就是一張 Session 表，不如直接用表。
- Token 為 256-bit 隨機值，DB 只存 SHA-256 雜湊；DB 外洩不等於 Session 劫持。
- Cookie：`HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`。
- 有效期：固定 30 天絕對過期，不做滑動續期。
- CSRF 防護：`SameSite=Lax` ＋ 狀態變更端點僅收 JSON body（非表單 content-type）；OAuth `state` 以一次性 Cookie 驗證。
- 過期 Session 由既有的非同步清理路徑批次刪除，清理本身冪等。

### 決策 3：授權一律由 Session 在伺服器端推導，Auth 不獨立成服務

- 身分驗證只證明「你是誰」，授權必須另外檢查 Workspace 與資源的關係；請求的 `user_id` 與個人 `workspace_id` 一律由 Session 在伺服器端解析，不信任用戶端宣稱的值。
- 公開讀取（搜尋、Skill 詳情）不要求 Session；私有路徑一律經過 Session middleware。
- 身分解析是每個私有請求的熱路徑，留在控制平面單體內，不拆成獨立服務：拆出後密鑰仍在同一信任區、熱路徑多一個網路跳點、且會把身分資料所有權切開。套件邊界即未來若要拆分時的既有接縫。
- 離線環境的登入路徑由 Provider 抽換承載，不由服務拆分承載：伺服器以特定環境變數啟動時開啟一個開發用登入端點（`dev` Provider），不出外網即可登入；正式環境不設此變數，路由不存在。
- 多身分供應商的擴充路徑：新增直連目錄服務等同新增一個 provider 值與一個憑證驗證入口，同套件、同資料模型；對接客戶端身分系統（SAML/OIDC、SCIM、群組同步）等企業聯邦需求出現時，另外評估既有身分伺服器方案，不自行從零打造。

### 決策 4：服務身分（非人類主體）不走使用者 Session

- 控制平面內部呼叫能力提供者：僅限私網，附靜態 Bearer Token（環境變數注入），對方驗證；單機部署下這已是信任邊界的全部，跨機部署時再升級為雙向 TLS 或服務網格。
- 模型出口使用每 Run 短效的模型閘道 Virtual Key；Sandbox 的物件存取使用短效物件授權；兩者均不使用使用者 Session。

### 決策 5：Workspace 是唯一的租戶邊界

- 每位使用者建立一個個人 Workspace；所有使用者擁有的 Skill、Test Case、Run、Secret Reference、Artifact 與 Usage 都以 Workspace 作為租戶邊界。
- Membership 與 Role UI 可以簡化，但領域模型保留 Owner、Member 與未來自訂角色的擴充能力。
- 公開 Skill 可以由平台或公開 Workspace 擁有；使用者 Fork 後的新 Skill 屬於個人 Workspace，並保留來源譜系。
- 授權原則：Repository／Query 預設要求 Workspace Scope；背景工作、Provider Callback 與 Artifact 下載使用受限的服務身分與資源層級的授權；不信任用戶端傳入的 `workspace_id`，一律由伺服器依 Membership 與資源歸屬驗證；公開讀取與私有修改走不同的權限路徑。
- Workspace ID 由伺服器端生成，並在跨服務契約中明訂為租戶標籤，執行平面無法用它取得任何額外權限；事件攜帶的 `workspace_id` 由寫入端從 Run 反查得出，不信任外部傳入的值；Session middleware 是唯一的權限範圍來源。
- 資料隔離現況為共享資料庫、共享 Schema 的邏輯隔離，但所有租戶資料必須有 Workspace Scope，且需要自動化的跨 Workspace 存取測試；物件金鑰、搜尋文件、Trace 與快取同樣攜帶租戶邊界；管理員的支援性存取具備稽核與有限時效。未來若需要獨立資料庫、區域或加密金鑰，由 Workspace Policy 選擇不同的部署／儲存設定檔。

### 決策 6：封測准入是允許清單疊加在 OAuth 之上，不做邀請碼

登入仍走 GitHub OAuth；`provider_user_id` 命中部署設定的允許清單，才開放私有功能。

| | 在清單內 | 不在清單內（含未登入） |
| --- | --- | --- |
| 搜尋、Skill 詳情 | 可 | 可 |
| Fork、建立 Run、下載 | 可 | 不可 |

- 與公開搜尋不要求登入的既有行為天然一致：未受邀者本來就看得到目錄。
- 實作是一個 middleware ＋ 一份部署設定（比照 operator 允許清單的既有前例）：不做 DB 角色表，因為角色表需要連帶做授予端點、該端點自己的授權，以及授予稽核，三者存在的唯一目的會是讓同一個帳號提拔自己。名單異動即改設定並重啟；名單需要頻繁異動時的升級路徑是改讀資料表，路由與 handler 不動。
- 每次啟動寫一筆名冊稽核事件，內容是**當下生效的清單與筆數**——回答「誰現在在名單上」，不回答「誰在何時被加入」（後者的事實在部署設定的變更歷史裡）；寫不成該筆事件時 fail-closed：該次啟動不承認任何受邀者。
- 不做邀請碼：碼需要產生、保管、兌換、撤銷、過期與一個兌換頁，本身還是一組新的機密材料；它要解決的問題（防止不請自來的人耗用配額）在允許清單下已經解決。
- 未在清單內看到的是說明加「回報使用情境」入口，不是 404；目錄已經把內容列出來給這個人看過，佯稱功能不存在只會被同一個 API 打臉。
- 「未受邀」「額度耗盡」「阻斷回報」三個入口共用同一支回饋端點與同一個表單，以種類分流。

### 決策 7：額度的強制點是平台自己的計數器，不是模型閘道

模型閘道上有數個看起來像煞車的機制，各自管的是別的事，沒有一個回答「這個帳號這個時間窗還能跑幾次」：

| 機制 | 它真正管的 | 為什麼不是每帳號每時間窗的配額 |
| --- | --- | --- |
| 閘道 Virtual Key 的金額上限 | 單次 Run 的金額上限 | 每 Run 一把新鑰匙，Run 終止即撤銷，不跨 Run 累加 |
| 閘道的 TPM 限制 | 速率 | 速率不是總量，限得住一分鐘內的爆量，限不住長期的累計次數 |
| Workspace 並行上限 | 同時能跑幾個 | 同時上限不代表一段時間內的總次數上限 |
| 軟／硬牆鐘 | 單次執行時長 | 同上 |
| Sandbox harness 的 token 累計 | 單次 Run 的 token 總量 | 只看得到這一次 Run |

五者都必要，但缺一不可地都不是配額；配額因此是**第三層**，各層各自擋一種失控形態，本決策不取代閘道側任何既有設定：

- **強制點：`internal/run` 的 `Create`**，與並行上限同一處、同一個交易、同一個 advisory lock——那是唯一一個「Run 即將被建立、還沒有花掉任何一分錢」的位置。超出額度即拒絕且不建立 Run。
- **計數用既有 Run 列做時間窗計數，不新增「餘額」欄位**：餘額是可能漂移的快取，並行上限用的是非終態計數而不是計數器欄位，配額沿用同一做法。
- **退還是一個查詢述詞，不是一次寫入**：計數查詢排除特定的平台側失敗分類；寫入式退還必然有崩潰、重啟或清理失敗等會漏掉的路徑，述詞式的不會。
- **計數起點是 Run 進入「準備中」狀態**：資源真正被佔用之後才計，更早階段的失敗本來就不計數。
- **顯示必須排在強制之後**：先做強制點與具名測試，再做剩餘次數與重置時間的顯示端點；顯示一個平台不會執行的上限，比完全不顯示更糟。額度欄位不進入權限確認的雜湊摘要——配額是狀態不是權限，它的變動不該作廢使用者手上的確認。
- 配額擋的是次數，不是花費；控制花費靠閘道金額上限那一層，這是三層併用的直接後果。
- 具體額度值是產品決策，本 ADR 只定強制點與語意；未經產品決策核准的數字不得顯示於任何畫面。

### 決策 7a：Policy 涵蓋的不只是次數配額

除了決策 7 的次數配額，Workspace Policy 至少還涵蓋：

- Dataset、Artifact 與 Trace 的大小限制。
- 允許的 Provider、Runtime、模型與網路政策；自備 API Key 與平台代付模型適用不同政策。
- 高風險 Skill 或 MCP 的阻擋與人工確認。
- Policy Decision 保存規則版本與判定結果，確保歷史 Run 可解釋。

### 決策 7b：Usage Record 以追加事實保存

每次 Run 至少計量：Provider／Sandbox 執行時間、CPU／Memory、模型 Token 與費用、網路流量與 MCP 呼叫次數、Dataset／Trace／Artifact 儲存量、評估與重跑的額外成本。

Usage Record 只追加、不因價格表更新而改寫；帳單由 Usage 與當時有效的價格／方案另外算出，不回頭改寫已記錄的事實。

### 決策 8：Run 額度與生成額度是兩個獨立開關，語意相同但不共用

- Run 額度由一個部署層級的開關控制：**未設定＝以既定數值強制，`off`＝不強制且不顯示**。這個不對稱是刻意的——未設定的保存期限代表「不蒐集」是安全的，但未設定的額度代表「唯一的成本上限是關閉的」，並不安全；關閉額度因此必須是一個明確寫下的動作。
- 顯示跟著強制走：開關關閉時，剩餘次數查詢端點不掛載、執行前的權限摘要不帶額度區塊；同意書、說明文案等對外敘述同樣不得宣稱有額度存在——關閉的是強制，使用者不因此該被告知一個實際不會發生的擋下行為。
- 關閉額度只影響**次數**，不影響**單次 Run 的成本上限**：閘道的單次金額上限、TPM 限制與 Sandbox 的 token 總量上限（決策 7 表格中的機制）不受影響、持續強制。
- 生成額度使用**第二個獨立開關**，不與 Run 額度共用同一個開關：兩者語意逐字相同（未設定＝強制、關閉＝不強制且不顯示），但管的是不同動作——共用一個開關或一個計數池，會讓一次生成安靜地吃掉試跑的餘額，而試跑正是 MVP 漏斗要量測的行為。
- 生成額度的計數方式是計算已生成的 Skill 來源列數，而不是維護一個可扣減的餘額欄位——沒有餘額可扣，就沒有東西會扣錯；生成路徑其餘規則（重試、截斷、目錄可見性、Fork 來源資格）見 [ADR-011：從描述生成 Skill](./ADR-011-generating-a-skill-from-a-description.md)。
- 生成額度的強制點在呼叫模型之前完成，早於寫入生成結果的交易——模型呼叫夾在中間，讓一個資料庫連線跨著它等待的代價，遠大於它能擋掉的溢出；並行溢出以每 Workspace 一個進行中生成名額限制。
- 兩個開關目前都設定為關閉：一次生成的實測成本比一次試跑的閘道實付中位數低一個量級，而生成額度的四個數值（每日、每時間窗、首個時間窗、時間窗長度）與 Run 額度的四個數值都已完成產品面核准，兩者關閉純粹是部署階段的暫時選擇，不是數值或機制未定；恢復強制時沿用同一組已核准的數值，不需要重新推導。

## 影響

### 正面

- 零新增基礎設施元件、零密碼保管責任；登入路徑與 Skill 的內容供應鏈重合。
- 撤銷即時：登出、封鎖、帳號刪除都只是刪除一列 Session。
- 個人 Workspace 的資料模型不阻礙未來團隊與企業租戶功能；用量、成本與限制從第一天就可觀察。
- Provider Routing 可依 Workspace Policy 演進。
- 「配額會不會被強制」不再取決於實作者是否讀過額度數值的文件——強制點與並行上限住在同一個函式、同一個交易裡，改動其中一個會直接看到另一個。
- 封測准入重用既有的允許清單機制，只增加一個 middleware、一份部署設定與一筆啟動時的稽核事件，而不是一個新子系統；未受邀者的畫面同時是需求訊號的入口。

### 成本與限制

- 單一身分供應商依賴：GitHub 帳號被停用等同無法登入本站；本地開發與端對端測試需要處理這個外部依賴或使用開發用登入端點。
- 需要維護 GitHub OAuth App 的憑證；Client Secret 比照模型閘道機密同等級管理。
- 所有查詢與背景工作都需要處理租戶 Context；共享 Schema 的邏輯隔離需要嚴格測試與開發規範持續守住。
- 允許清單存放在部署設定裡，名單異動需要重啟；規模擴大或名單需要頻繁異動時，才值得換成資料表存放。
- 時間窗配額計數每次建立 Run 都需要掃描該 Workspace 的 Run 列；量級上升後的升級路徑是加索引或改為物化計數，但物化計數會讓「餘額」重新變成可能漂移的快取，屆時退還語意需要一併重新設計。
- 生成額度的並行限制只擋到「同一個瀏覽器分頁裡的一個按鈕」規模的入口；入口形態改變時需要另外補上跨進程的並行鎖。

## 待決策

- 第二身分供應商的啟用訊號與時點。
- Local Runner 的配對憑證是否重用本 ADR 的 Session 機制，見 [ADR-001：系統情境、平面與部署路徑](./ADR-001-system-context-planes-and-deployment-path.md)。
- 企業資料隔離設定檔（獨立資料庫、區域或加密金鑰）的觸發條件。
- 封測結束後允許清單的退場方式：清空、保留為早期使用者名單，或改為開放註冊。
- 公開釋出時 Run 額度與生成額度是否轉為強制，以及是否需要新的數值。
