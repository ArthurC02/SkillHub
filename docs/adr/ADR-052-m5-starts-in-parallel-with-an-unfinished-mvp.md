# ADR-052：M5 與未完成的 MVP 並行——三個啟動條件全部暫時放行

- 狀態：Accepted
- 日期：2026-08-23
- 修訂：[ADR-046](./ADR-046-generating-a-skill-from-a-task-description.md) 決策 1（改變 M5 的啟動時點；「M5 是 MVP 之外的獨立里程碑」不變）、`01` §10 的 M5 啟動條件三項
- 同形先例：[ADR-050](./ADR-050-beta-runs-in-parallel-with-the-sandbox-acceptance.md)（封測與 Sandbox 驗收並行）——**一個被明示接受的風險，不是一個被解決的問題**
- 相關：`04` 乙-10、[m5/README.md](../plans/mvp/m5/README.md)、[m4/release-checklist.md](../plans/mvp/m4/release-checklist.md) H-8

## 背景

ADR-046 決策 1 把生成路徑列 M5 而不是插進 MVP，理由逐字是：

> 理由是時序不是意願：M1 的驗證閘門 D 日仍未宣告……**封測漏斗的第一段量的正是「輸入意圖後查看至少一個 Skill 詳情的比例」**——那個數字要在「沒有第二條出路」的條件下量，才知道搜尋本身夠不夠好。此時把生成插進 MVP，等於在自己要買的資訊上先加一個變數。

`01` §10 因此給了 M5 三個啟動條件：①MVP 封測結束 ②漏斗第一段有讀數 ③`GEN-009` 基線。

**2026-08-23 稍早，PDM 先放行了第 ② 項；同日再放行其餘兩項。** 目的一致：讓 M5 開始得了。

## 決策：三項全部暫時放行，**M5 即刻可開工**

`01` §10 的 M5 啟動條件三項自即日起不阻擋 M5 開工。三項各自的狀態一件都沒改變——**被移除的是「阻擋」這個效力，不是那些事實**：

| 原條件 | 事實現況（**未改變**） |
| --- | --- |
| ① MVP 封測結束 | **未開始。** `RELEASE-009` 未勾，H-8 未執行 |
| ② 漏斗第一段有讀數 | **未量。** D 日未宣告、9 場未跑、G1～G4 沒有任何一個數 |
| ③ `GEN-009` 基線 | **①②與 (甲)(乙) 已完成，③④未完成**——③要 Sandbox ＋ 評估管線，④要人 |

## 這是什麼性質的決定

**與 ADR-050 同型：一個被明示接受的風險。** ADR-046 決策 1 指出的那個問題**沒有被解決**，只是被接受了：

> 封測漏斗第一段要在「沒有第二條出路」的條件下量。

**這件事今天仍然為真。** 本 ADR 不主張它不重要，只主張 M5 的開工不再等它。

## 這個裁定沒有授權的事

**開工不等於曝光。** 這是本 ADR 唯一的硬邊界：

- **M5 的生成入口不得對封測使用者出現**，直到漏斗第一段有讀數為止。
- 理由不是保守，是**這個放行的目的會被曝光反噬**：`01` §11.2 第一段量的是「輸入意圖後查看至少一個 Skill 詳情的比例」。封測使用者一旦看得到「沒有夠接近的 Skill → 生成一個」，那個比例量到的就不再是搜尋好不好，而是兩條路的分流。**那個數字買不回來**——它只有一次機會，而封測只有 12 個人。
- 落地形式：`GEN-008` 的 UI 在封測環境以旗標關閉。**旗標的預設是關**，開啟需要漏斗讀數存在，這與 `01` §7.3 的既有立場一致（生成不在 MVP）。

**其餘不在授權範圍內的**（與 2026-08-23 稍早那次放行相同，逐項重述而不是引用，因為合併讀是這類文件最常見的失效方式）：

- **M1 閘門本身仍未通過。** D 日仍要宣告，`gate-test/` 的材料一個字都沒被放行，前期驗證 2 一次都沒問過。
- **`RELEASE-001`～`010` 一項都沒動**，H-8 仍是負責人動作。**M5 開工與 MVP 發佈是兩件事**，本 ADR 只動前者。
- **`01` §7.3 不變**：MVP 首發仍不含從零生成 Skill。M5 是 MVP 之外的里程碑，並行不會把它移進去。

## 這個放行的終止條件

- **② 與 ③ 隨其事實成立而自然失效**：D 日宣告並產出讀數之後，②回到原本的形式；`GEN-009` ③④ 完成之後，③亦然。
- **① 隨封測結束而失效。**
- **曝光旗標的解除只綁 ②**，與 ①③ 無關。

**三項全部回到原狀時，本 ADR 只剩歷史意義。** 在那之前，它是一份必須被一起讀的但書。

## 影響

### 正面

- M5 開始得了。規格、工作項與量測 harness 都已就緒（`02` §4.9、`03` §19、`m5/`），此前唯一缺的就是准許。
- 兩個里程碑並行的成本在單人團隊裡是真實的，但 M5 的前 4 個工作項（契約、`apps/llm` 端點、Go 流程、配額）**與 MVP 封測的剩餘工作沒有檔案重疊**——後者剩下的幾乎全是部署期與人的動作（`release-checklist` §2、§3）。

### 成本與限制

- **`01` §10 的里程碑表同時有兩個未完結的里程碑。** 這正是 2026-08-23 稍早選「開 M5」而非「插進 MVP」時被列為代價的那一項，現在它成立了。
- **漏斗第一段的讀數風險沒有消失，只是被移到曝光旗標後面。** 旗標若被誤開，那個數字就沒了，而**沒有任何機制會告訴我們它被誤開過**——這是本 ADR 最脆弱的一點，它靠一個預設值和一條紀律，不靠強制。
- **`GEN-009` ③④ 現在是與實作並行的量測，不是前置。** 這表示 `GEN-011` 之前的實作是在「不知道生成物好不好用」的狀態下進行的。ADR-051 決策 2 記的那個未知（帶腳本 vs 純指示哪一種有用）因此會更晚才有答案。

## 待決策

- **曝光旗標要不要有稽核事件。** 上面自承「沒有任何機制會告訴我們它被誤開過」。一個 `feature_flag_changed` 的稽核事件是便宜的解法（`CORE-008` 的既有管道），但它需要一個決定：旗標屬於誰、誰能改。留給 M5 實作時回答。<br>**✅ 2026-08-23 已回答：有，而且它已經在跑。** `audit.ActionFeatureFlags`（`feature_flags.roster`），**每次 API 啟動寫一次**，形狀沿用既有的兩份 roster（operator 與 beta）——記的是這個部署自己的設定，不是一次授權。<br>**兩件與原構想不同的事**：①**不是 `feature_flag_changed`**，因為旗標是環境變數不是一張可以被改的表，「誰在什麼時候改的」屬於部署設定自己的變更歷史，寫在這裡會讓它看起來像一份它不是的授權稽核；②**everything off 的時候也寫**，因為「這個部署沒有曝光過任何東西，從這個時間起」正是事後有人會需要的那句話，而**一列不存在的紀錄說不出它**——它跟「這個 build 還沒有這個旗標」長得一模一樣。<br>**它不是 fail-closed**：寫不進去只記 `slog.Error`，不擋服務——這一列是既有決定的紀錄，不是強制它的東西，為自己的記帳把平台停掉是不對的取捨。
