# ADR-070：LLM 可觀測性不外接第三方服務——縮限 ADR-017 的觀測那一半

- 狀態：**Accepted**（2026-09-10 負責人裁定「簽署所有待辦清單」，本份為 [`05` R-24](../plans/05-pending-rulings.md) 取 (b) 的落地）
- 日期：2026-09-10
- 相關：[ADR-017](./ADR-017-model-gateway-and-llm-observability.md)（本份只縮限它的**觀測**半邊，閘道半邊完全不動）、[ADR-068](./ADR-068-credit-is-the-only-unit-of-account.md)（`cost_events` 是平台支出的事實來源）、[ADR-026](./ADR-026-evaluation-reassessment-evidence-lifetime-and-judge-trust-boundary.md)（Judge 品質）、`03` O11Y-001～004、`04` 丙、`05` R-24

## 背景

ADR-017 的狀態是 `Accepted`，決策段逐字寫著「Python 服務以 Langfuse SDK 埋點，LiteLLM 閘道以原生回呼補齊；一律附 `run_id` 關聯」，並規劃了 Prompt Management。

**這一半一行都沒有實作**，而且從來沒有出現在任何一份工作清單上。2026-08-29 的稽核逐項查證：

- `apps/llm/pyproject.toml` 的依賴是 `fastapi`／`uvicorn`／`litellm`／`openai`，**沒有 langfuse**；`apps/llm/src` 全樹沒有任何 langfuse import。
- `infra/compose/litellm-config.yaml` 的 `litellm_settings` 只有 `drop_params: true`，**沒有 `success_callback`**；`docker-compose.yml` 全檔沒有任何 `LANGFUSE_*`。
- 四份活文件（`01`／`03`／`04`／`05`）對「Langfuse」的命中數各是 0；`03` 的 `O11Y-001`～`004` 全部是 Prometheus 與產品分析事件，**沒有一項承接 LLM 可觀測性**。
- 技術棧速覽（[agent-instructions.md](../development/agent-instructions.md)）仍把「LLM 觀測 ｜ Langfuse Cloud」列為定案。

也就是說：**一份 `Accepted` 的 ADR、一列技術棧、零個工作項、零個殘項。** 這正是 `AGENTS.md` 開頭那句「一個事實好幾份定義」的完整形狀——下一個要查「我們的模型呼叫有沒有被記下來」的人（人或 Agent）會落在 ADR-017 上，然後照它去接一個不存在的東西，或以為已經接好了。

**這不是安全問題。** ADR-017 的邊界守則 2 已經把 Langfuse 排除在事實來源之外，而逐檔確認過**沒有任何一行程式把它當真相讀**——這一點是乾淨的。要修的是文件與實際的落差，不是一個漏洞。

## 決策

### 1. 不引入外部 LLM 觀測服務

不做 Langfuse SDK 埋點，不做 LiteLLM 的 `success_callback` 回呼，不做 Prompt Management。**ADR-017 的閘道半邊一個字都不改**：LiteLLM 仍是唯一出口、每 Run 短效 Virtual Key、供應商金鑰只存在閘道（鐵律 8、11）。

**否決「只做回呼那一半」的理由，是本專案自己的一條紅線而不是成本**：回呼要兩個環境變數，其中一個是 Langfuse 的金鑰。鐵律 11 的形狀是**供應商金鑰只存在閘道**；為了一個封測期間沒有人會去看的儀表板，在閘道之外多開一個金鑰存放點，是把一條紅線換成一個方便。同日 [`05` R-72](../plans/05-pending-rulings.md) 以完全相同的判斷否決了「把閘道金鑰複製進 CI secret 以排程跑付費 E2E」——**兩項互為對照，判準一致**。

### 2. 模型呼叫的事實來源，就是系統裡已經有的那三樣

| 要回答的問題 | 由誰回答 | 為什麼夠 |
| --- | --- | --- |
| 這次呼叫花了多少、打的是哪個模型 | **`cost_events`**（ADR-068 決策 3） | 它是平台支出的唯一帳，每一筆都在，而且它是**產品功能**不是觀測附加物——所以它不會因為沒有人看就腐爛 |
| 這個 Run／會話裡發生了什麼、順序如何 | **Trace 分割表**（ADR-004、TRACE-001） | 已有 `run_id` 關聯，已有保存期限與遮罩規則 |
| 這次改動有沒有讓品質退步 | **`tools/eval-regression`** | ADR-017 原本把 golden query set 與 Judge 品質回歸指給 Langfuse Datasets/Evals，**而它們今天實際上就是靠這支腳本跑的**。本決策只是讓文件與它對上 |

### 3. 放棄了什麼，明寫

外部服務會給、而上面三樣不給的，是**互動式的探索介面**：把同一個提示的多次呼叫並排比較、在網頁上標註、把一組樣本存成 Dataset 反覆重放。這三件事今天靠人工讀報告完成，**而 2026-08-29 稽核抓到的「沒有任何一次模型呼叫釘住 temperature 或 seed」正是這類工具最省事的用途**（該項已由 [`05` R-31](../plans/05-pending-rulings.md) 於 2026-08-30 另行裁定並落地，不依賴本決策）。

**接受這個放棄的條件是規模**：12 人封測、45 個精選 Skill 的資料量，撐不起一個 Dataset/Evals 工作流要求的樣本數。若哪天樣本量真的到了那個級距，重開這個決定的正確方式是新增一份 ADR 取代本份，**而不是回頭把 ADR-017 當作它還成立**。

### 4. `03` 不新增承接工作項

本決策的內容是「不做」。一個承接「不做」的工作項，就是本 repo 反覆抓到的那種永遠不會被勾的空格子（`05` §0.3 記過同型三次）。**承接本決策的是這份 ADR 自己**，以及技術棧那一列的更正。

## 後果

- 正面：技術棧表第一次與實際一致；下一個查「模型呼叫有沒有被記下來」的人會落在 `cost_events` 與 Trace 上，而那兩個是真的存在的東西。
- 正面：閘道之外不多一份金鑰，鐵律 11 的形狀維持完整。
- 成本：模型品質的跨版本比較仍然是「跑一次腳本、人讀一份報告」，沒有互動式介面。**這是一個已知的、被記下來的缺口**，不是一個被遺忘的缺口——兩者的差別正是本份 ADR 存在的全部理由。
- ADR-017 **不原地改寫**（文件規則）；[ADR 索引](./README.md)在它那一列標註觀測半邊已由本份縮限。

## 待決策

- **樣本量到什麼程度才值得重開**：本份沒有訂一個數字，因為今天沒有任何依據可以訂。重開的觸發訊號寫成質性的：**當「同一個提示的多次呼叫要並排比較」成為每週都會做的動作時**，這個決定應該重看。
