# ADR-023：帳號清除與 Credit

- 狀態：Accepted
- 相關：[新 ADR-003｜Run 編排與非同步工作流程](./ADR-003-run-orchestration-and-async-workflows.md)、[新 ADR-004｜Sandbox 隔離與執行安全](./ADR-004-sandbox-isolation-and-execution-security.md)、[新 ADR-005｜模型閘道與可觀測性](./ADR-005-model-gateway-and-observability.md)、[新 ADR-006｜身分、Workspace、准入與額度](./ADR-006-identity-workspace-admission-and-allowances.md)、[新 ADR-010｜產品分析與稽核邊界](./ADR-010-product-analytics-and-audit-boundaries.md)、[新 ADR-012｜互動創作](./ADR-012-interactive-creation.md)、[新 ADR-016｜Platform Bounded Context 與 Context Map](./ADR-016-platform-bounded-contexts-and-context-map.md)、[新 ADR-017｜Query 與寫入所有權](./ADR-017-query-and-write-ownership.md)

## 背景

帳號清除（`03:CORE-007`、`02:NFR-002`）必須是不可逆的終點：清除之後不能再冒出屬於這個帳號的私人資料列。但 Session 驗證只能擋住新請求，擋不住已經通過驗證、正在寫資料，或仍持有短效上傳授權的既有工作；會建立私人資料根列的路徑分散在多個 Bounded Context（Run、Skill 匯入、其他資料 producer），任何一條在清除盤點之後才落地都會讓「已刪除」又長回資料。

平台同時需要一個內部計價單位，回答兩個使用者看不到答案的問題：一次動作大概花多少、帳號還能花多少。既有的次數配額（`RUN_QUOTA`／`GENERATE_QUOTA`，新 ADR-006）量的是次數不是金額；模型閘道的 `max_budget`／`tpm_limit`（新 ADR-005）管的是單次呼叫上限與速率，都不回答「這個帳號的餘額還夠不夠」。互動創作（新 ADR-012）已經有逐步的實測成本，但那些數字只存在於會話內部，不會轉成任何使用者資產或負債。量到的真實成本是後面幾條決策（面額、加成、門檻）的直接依據：

| 項目 | 中位 | 最大 |
| --- | ---: | ---: |
| 一場互動創作會話（不含試跑與評審） | $0.023–0.030 | $0.041–0.050 |
| 評審每場 | ≈$0.019 | — |
| 單次生成對照 | $0.0045 | — |
| 目錄搜尋一次 embedding | $0.00001 | — |
| 會話上限 `max_cost_usd`（新 ADR-012 已定） | — | $1.00 |

這個計價單位一旦存在，自己的清除語意也必須裁定：它是不是一般使用者資料、要不要跟著帳號清除掉。

## 決策

### 決策 1：帳號清除以 Workspace 寫入 fence 序列化，逐一 Bounded Context 補上物件盤點

所有會建立 Workspace 私人資料根列的交易，先以 `workspace-objects:<workspace_id>` 取得 shared advisory lock，取鎖後重查該 Workspace owner 尚未進入 purge；跨越 Object Store I/O 的路徑（Dataset、Skill 套件上傳）改持 session-scoped shared lock。資料庫 trigger 是共同強制點。

帳號清除先取得該帳號名下全部 Workspace 的 session-scoped exclusive lock；只有在 Run context 證明所有 Run 已終態且完成 sandbox cleanup 之後，才寫入清除起點、盤點物件並執行清除——尚未安靜時是延後,不是失敗,仍保留可重試的 lease。清除起點寫入之前仍可取消；之後既有 Session 失效,OAuth／DEV login 不得把原身分誤認為新帳號,而「已進入清除等待」的帳號在被主動查詢時只算已認領工作,不提前宣告不可逆階段已開始。

Run Artifact 的清除清單除了既有的 manifest 列,也由每個 Run Attempt 推導其固定 archive key——sandbox 可能已經上傳,但 manifest 的 best-effort 寫入可能還沒成功。為了讓清除知道一個 Attempt 是否曾經核發過下載授權,Attempt 建立時明寫「未核發」,把已核發的授權交付給 Provider 前改成「已核發」；只有「未核發」狀態可以被自動判定為安全並關閉,狀態不明的既有列一律視為「未知」,不得用經過的時間或核發上限反推它安全。

Skill package 在寫入 Object Store 前先寫 durable 的收集意圖,Uploader 與 collector 對同一個 content-addressed key 共用另一把 advisory lock,並在鎖內重查是否仍有 Version 引用；成功 Version 的意圖可安全丟棄,失敗或中斷留下的 bytes 可被重試清除。

固定鎖序是「Workspace 清除 fence → package／domain 鎖 → 資料列寫入」；清除流程只取得 Workspace exclusive fence,不反向取得 producer 的 domain 鎖。

Object Store 不具交易性——package 收集意圖與 Run Attempt 授權狀態都是「先記可重試工作、再寫 bytes／發授權」的同一種紀律,collector 與清除流程永遠先重查引用或狀態,再刪除。

### 決策 2：新寫入不變量上線前必須先排空可能違反它的舊版程序

決策 1 的保護橫跨資料庫與 Object Store,不能把「migration 已執行」當成「所有程序都已遵守新協定」。當某個保護（例如 Run Attempt 的核發狀態欄位）是新加入、舊版程序不會遵守時,上線前必須先停止所有可能違反該不變量的舊版 Maintenance、Worker 與可能產生物件的舊版 API 程序,新舊版本不得滾動混部,直到排空完成才可重新啟用該保護的強制路徑。

排空之後,等待期須涵蓋已核發授權的最長存活期,再加上額外寬限與時鐘飄移,而不是任意選一個看起來夠久的數字；在目前的授權存活期配置下,這個等待期是 15 分鐘（授權存活上限）＋5 分鐘（寬限）＋1 分鐘（時鐘飄移）＝21 分鐘。等待期滿之後,依限定條件把舊版留下的「未知」狀態列一次性修復為可判定狀態；在完成排空與修復之前,清除流程對這些列 fail-closed 是正確結果——即使 migration 曾經替舊列補寫一個有限期限,也不能只憑期限推定舊版程序沒有在稍後才核發授權。新的寫入不變量只保護新寫入之後才產生的物件;重新啟用帳號清除之前,還必須先完成一次舊版程序可能留下的 Object Store 孤兒物件盤點與對帳,證明沒有未配對的物件殘留。

### 決策 3：Credit 是唯一計價單位，只在系統內有效，不可兌現

平台面對使用者的每一個成本呈現,只有一種單位——不顯示美元,不顯示 token 數當作額度,不做第二種積分或等級。Credit 是系統內部的貨幣;美元只用於平台自己記帳與模型閘道計價,兩者的角色分開:**貨幣＝Credit（使用者看得到,出現在餘額、扣點、三道閘、封測報酬）；Money＝美元（平台自己看,出現在成本事件、閘道的 `max_budget`／花費）。** 使用者可達的回應不得出現任何 `*_usd` 或以 `usd` 結尾的欄位。

反過來,Credit 不是貨幣的影子:它不能被兌換回現金、不能轉給另一個帳號、不能跨系統使用,不對接任何第三方支付或積分系統。這是設計約束,不是免責聲明——任何未來提案若要讓 Credit 可以兌現或跨系統流通,必須先推翻本決策、新增 ADR,而不是在既有欄位上加一個旗標。

換算 Credit↔美元的匯率（面額與加成,決策 4）是平台自己公告的常數,不是平台不擁有的外部匯率;這與「一個外幣兌換率不是平台自己的事實」是兩回事,不構成不換算的理由。

### 決策 4：面額與加成

面額為 **1 credit = US$0.001**。「平台真實支出」換算「使用者扣除額」的一步套用加成,預設 **1.3**,存成 basis points（`13000`）,理由是整數運算不失真,且與模型閘道既有美分計價同一慣例。每一筆分錄記下寫入當時生效的加成值,日後調整加成不改寫既有分錄——一筆已發生的扣款不因明天的定價政策改變而回頭變成另一個數字。

決策 10 的保守開始門檻常數與滾動窗長度維持現值:保守門檻 **70 credits**,滾動窗 **7 天**。

### 決策 5：兩本帳，各自的事實不合成一張表

**成本事件表**記平台的真實支出。每一次付費的模型／embedding 呼叫都記一筆,不分這筆呼叫最終有沒有人買單,種類至少涵蓋:創作步驟、目錄搜尋 embedding、索引增強、評審、建議、單次生成、Run,以及搜尋結果「為什麼符合」的說明生成。欄位至少含用途種類、模型識別、提示詞版本、輸入／輸出 token 數、微美元整數金額（避免浮點誤差）、Workspace id（可為 null,匿名搜尋沒有 Workspace）、使用者 id（同理可為 null）、來源參照（依種類決定是會話 id、Run id 還是 Skill version id）、冪等鍵。**不存查詢字**——這是分析事件「不留查詢內容」規則（新 ADR-010）對成本事件的同一條套用:一次搜尋花了多少錢是平台的事實,使用者搜了什麼字不是這張表要回答的問題。

**扣點分錄表**記使用者餘額的異動,只記四種動作:扣點、授予（operator 動作）、充值（MVP 期間與授予同一機制）、調整（人工更正）。每一筆扣點分錄指向它來自哪一筆成本事件（一對一或一對多）,沒有對應成本事件的扣點分錄不成立。分錄一經寫入不可修改,更正一律用新的調整分錄,不得原地改寫。

兩本帳的分工判準:成本事件回答「平台花了多少」,扣點分錄回答「使用者被記了多少」——兩者金額在有加成時不相等,合成一張表會讓加成這個中間步驟消失,之後想調整加成而不動歷史事實就做不到。

帳號的鍵是**使用者**,不是 Workspace——MVP 期間一位使用者剛好只有一個個人 Workspace,那是巧合的基數對應,不代表兩個 id 可以互換或省略轉換。`run`、`trial` 等呼叫端傳的是 Workspace id 時,轉成使用者 id 是組裝根明確要做的一步。

跨 Context 存取 Credit 一律經組裝根注入的換算與扣點函式,呼叫端不直接 import Credit 所屬套件（新 ADR-016 的 Customer–Supplier 型式）——顯示換算與實際扣點共用同一份函式,理由是三個畫面各自換算就是三個會分岔的匯率。

### 決策 6：餘額是分錄的和；物化欄位只是讀取捷徑

一個帳號的 Credit 餘額,定義上是它名下全部扣點分錄的和。為了不讓每次讀取都掃全表,帳號上放一個物化欄位,在寫入分錄的同一個交易內同步更新。這與配額計數器故意相反:配額的計數對象本身會變動,物化欄位漂移只可能是「有分錄沒有同交易更新它」,是可以被交易保證消滅的錯誤。**讀取用物化欄位（畫面顯示、三道閘的判斷都讀它）,對帳與稽核用分錄的和;兩者不同步時,以分錄的和為準。**

### 決策 7：扣點接在既有結算之後、同一交易，按動作類型各自的冪等鍵；讀不到花費時的處理依動作類型而不同

互動創作每一步結算後,在與會話狀態前進同一個資料庫交易內,寫入一筆成本事件與一筆對應的扣點分錄。**冪等鍵是（會話 id、revision）**,沿用會話既有的樂觀鎖版本欄位——同一個 revision 的結算重跑（例如 Worker 重試同一個 Job）必須是同一筆分錄,不得重複扣款。單次生成與評審／建議沒有 revision 的概念,各自的冪等鍵是該次呼叫的既有唯一識別（生成請求 id、評估／建議的 attempt id）。

**用量未知時,依動作類型決定要不要按預留額扣:**

- **互動創作的一步**:讀不到閘道回報的實際成本時,以這一步的預留額（呼叫端傳入的單次呼叫成本上限）計算扣點,並在分錄標記為估計值。絕不因為讀不到成本而扣 0——讀不到成本最可能的原因是呼叫已經花了錢而回報管道斷了,把它當成免費正是這條規則要堵的漏洞。
- **一次 Run**:保留額是模型閘道本身的每 Run 支出上限（換算 Credit 後,目前為 $0.50 × 1.3 ＝ 650 credits）,因為這是平台自己設的硬上界,不需要用統計估。**讀不到花費時只記一筆估計值為 0 元的成本事件,不扣點**——與創作步驟刻意不同,因為讀不到自家閘道的回答是平台的問題,不該讓使用者被扣一整個上界。結算發生在 Run 清理流程,且必須在撤銷該次呼叫的短效授權**之前**完成,撤銷之後就問不到那把授權花了多少。
- **目錄搜尋（含 embedding 與「為什麼符合」的說明生成)**:成本事件照記,**不產生扣點分錄**——搜尋只餵統計,不收使用者的 Credit。

**成本事件與扣點分錄各自的交易不得再向連線池要第二條連線**——結算與開始前檢查都必須沿用呼叫端已經持有的交易,否則在單連線環境下會互相等待造成死鎖。

### 決策 8：換算一律無條件進位；使用者輸入的換算方向朝保守側捨入

任何「美元轉 Credit」「Credit 轉整數扣除額」的換算,一律無條件進位,不做四捨五入或無條件捨去——捨去或四捨五入在大量小額呼叫上會系統性地讓平台實際支出高於記錄下來的扣除額,進位的系統性誤差方向相反,且每筆金額本身是微美元等級,累積誤差可忽略。這條規則適用每一處換算:成本事件轉扣點、統計門檻的百分位數轉 Credit。

在使用者可以自行輸入預算的畫面（例如互動創作的預算滑桿）,換算方向依保守原則各自決定:花費與占用換成點數顯示給使用者看時進位（不少報）;使用者輸入的點數換回預算美元時捨去（承諾的預算價值不超過他輸入的點數）；顯示上限取「價值不超過單場硬上限的最大點數」（捨去）,顯示下限取單次呼叫成本上限換算後的進位值。領域與資料庫仍以美元為單位運作,換算只發生在對外的回應與請求邊界,不回寫。

### 決策 9：三道閘各自獨立、疊加生效

| 閘 | 檢查時機 | 判準 | 後果 |
| --- | --- | --- | --- |
| ① 開始前 | 建立新會話／新一次生成之前 | 餘額 < 決策 10 推導出的門檻 | 拒絕開始,不消耗任何成本 |
| ② 每步扣款前 | 決策 7 的每步結算,在呼叫模型之前用該步的預留額試算 | 餘額 − 本步預估 < 負債下限 | 停止該會話,不再進行下一步；已發生的成本仍照決策 7 結算 |
| ③ 單場上限 | 既有機制 | 單場成本硬上限與加碼請求（新 ADR-012 已定,出貨值 $1.00） | 中止並要求使用者主動加碼預算 |

三者疊加生效,任一道擋下就停,不取最寬鬆的一道。閘 ①、② 與既有的次數配額（新 ADR-006）是平行機制,不是替代關係——次數配額問「還能跑幾次」,Credit 閘問「餘額還夠不夠」,兩者可以同時生效或同時關閉,互不依賴。

閘 ①、② 讀的都是「一場」層級的統計與摘要,不是「一步」層級——用一步的統計會比決策 10 要擋的「明顯不夠跑完典型一場」寬鬆得多；顯示餘額是否足夠開始的畫面與閘 ① 必須讀同一個層級的定義,避免畫面說可以開始、送出卻被擋下。

閘 ② 的負債下限是一個可設定值（目前 **−50 credits**）,對應「欠一場」的量級,讓使用者在餘額見底時仍能完成手上這一場,而不是跑到一半被腰斬,同時把負債鎖在「最多再欠一場」的量級。**這個下限是軟的**:閘 ② 判斷時只用該步的預留額試算,並不真的把預留額鎖住,所以同一個帳號同時有多件事在跑時,每一件都對著同一個餘額試算、都會通過,再各自花掉自己的預留額。實際跌破下限的超出量因此有界:**不超過同時在跑的預留額總和減去其中最大的一筆**,跌破之後下一件事的試算一定不過,超出不會累積。要改成硬下限,需要在開始時真的鎖住預留額、結算時退回,兩條結算路徑都要改;而在現有的並行上限下,超出量有界,採用軟下限已足夠。

### 決策 10：門檻由統計推導，不是寫死的常數；統計本身有新鮮度要求

閘 ① 的門檻不是設定檔裡的固定數字,而是**最近一個滾動窗（決策 4：7 天）的第 95 百分位數 × 加成,無條件進位**——用 p95 而非中位數或最大值,是因為它要擋的是「明顯不夠跑完典型一場」,不是擋掉一切比中位數貴的使用,也不是等到真的一毛不剩才擋。**樣本數不足（少於 20）時退回決策 4 的保守常數,並在畫面上明確標示這是估計值而非依實測推導的門檻。** 統計本身也有保存期限:若最近一列統計超過 48 小時未更新（例如排程停擺）,視同沒有統計,同樣退回保守常數。

統計的滾動窗與每日重算都**只採計實付的成本**,標記為估計值的成本事件、以及任何一步曾是估計值的會話摘要,都不計入樣本——用估計值推導門檻會系統性地把分位數往不準確的方向拉。滾動窗內完全沒有樣本時,百分位數與最大值的空值以零處理,同樣落回樣本不足的保守路徑,不能讓整個每日重算因為一個空窗而中止。

單次生成的開始前檢查發生在既有的次數配額檢查之後、呼叫模型閘道之前;被擋下時的失敗原因記為 Credit 而非配額,讓使用者與稽核都看得出擋在哪一道。

### 決策 11：統計兩種輸入時機，各自獨立、互不取代

**事件驅動**:一場互動創作會話進入終態（保存或取消——放棄的失敗會話可能透過加碼請求回到等待輸入,不是真正的終點,不觸發)時,把該場全部成本事件收斂成一列摘要（會話 id、總花費、步驟數、是否曾有任何一步是估計值、最後一步時間),寫入統計的輸入來源。這一步掛在會話狀態推進的同一個交易的 savepoint 裡,寫失敗不連帶讓保存或取消失敗。摘要只從成本事件彙總得出,不另存金額,是帳的衍生物,不是第三本帳。

**固定時間**:既有的排程佇列（新 ADR-003）新增一個每日執行的工作,重算滾動窗的百分位數與最大值、樣本數,寫入最新一列統計;同一次執行也負責把「最後一步早於逾時」而未被事件驅動捕捉到的會話（逾時、或前述不算終態的失敗)補上或更新摘要,採用可重複執行的合併寫入,取消之後才結算的步驟會在隔天被補進總額。

兩種時機各自寫各自的資料,事件驅動確保每一場結束都立刻貢獻一個樣本點,固定時間確保即使某天沒有任何會話結束,統計仍會依既有樣本重新計算（例如樣本數剛好跨過門檻)。

### 決策 12：MVP 不接金流，充值即 operator 授予

MVP 期間不存在任何真實付款路徑:充值等於 operator 在既有管理入口下手動寫入一筆授予分錄,套用既有的「operator 動作必填理由、寫 audit event、不可自助授予」規則——每一筆授予或調整分錄都是一個具名理由的 operator 動作。封測受測者的報酬即是這個機制的第一個使用者:一筆帶理由的授予分錄,不是金額轉帳。

授予分錄不接受負值;人工更正若需要扣減,一律記成調整分錄。對不存在的 Workspace 授予回傳「找不到」而非伺服器錯誤。授予的請求在 MVP 期間刻意不做冪等——重送會授予兩次。

### 決策 13：帳號清除不觸碰任何 Credit 紀錄，且不設保存期限

Credit 帳戶、扣點分錄、成本事件與會話摘要在帳號清除後原樣保留,永久不清——帳號清除流程不包含刪除 Credit 紀錄這一步,也不存在任何依時間視窗刪除這些表的排程或路徑。這些表適用不可變表的紀律,任何新增的刪除查詢都會被查詢所有權檢查擋下（新 ADR-017）。

使用者那一列在清除後不刪、只標記刪除時間,所以 Credit 紀錄裡的使用者與 Workspace 參照在清除後仍然有效。決策 5 已經要求成本事件不存查詢原文,這些紀錄只有金額、token 數、模型名稱與時間,不含使用者輸入的文字,清除之後留存這些紀錄不構成額外的隱私風險。

## 影響

### 正面

- 帳號清除可以是真正的終點:清除起點寫入之後,分散在多個 Bounded Context 的私人資料 producer 都會在同一把 Workspace fence 之下被擋下或延後,不會有資料在清除盤點之後才長出來。
- 使用者第一次能在動作之前看到大概要花多少 Credit、還剩多少;平台第一次有機制在餘額見底前主動擋下開新會話,而不是無上限地累積負債。
- 成本事件與扣點分錄分開,加成或未來引入真實金流時,歷史分錄不必回頭改寫;負債下限雖是軟的,但超出量有界且量級可預期。

### 成本與限制

- 清除流程新增的資料庫 trigger 是刻意的共用最後防線,各 Bounded Context 仍擁有自己的查詢與清除語意,沒有新增跨 Context 直接查表的例外。
- 新協定上線時,若不確實排空舊版程序,清除或扣點會出現與新舊版本假設不一致的競態;完成排空與修復之前,清除寧可延後也不冒進。
- 三道閘任一道的門檻設得太保守,會讓使用者在餘額仍充足時被擋下;決策 10 的統計推導與樣本不足時的保守常數緩解了這個問題,但不能消除,面額與加成調整仍會直接改變體感。
- Credit 紀錄永久保留是一個明確選擇,不是預設遺漏——它排除了未來以「保存期限到期」為由清理這些表的路徑。

## 待決策

- **Credit 過期政策**:授予或充值的分錄是否應該連帶一個有效期限,逾期未用的 Credit 如何處理,尚未定義。在裁定之前,預設行為是 Credit 不過期。
