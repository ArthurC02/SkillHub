# ADR-039：前端設計系統與 UI/UX 評估準則 — 把既有的隱性決策成文化，不引入第三方設計系統

- 狀態：Accepted
- 日期：2026-08-22
- 決策者：產品負責人、架構規劃
- 相關：[ADR-016](./ADR-016-language-and-framework-selection.md)（前端選型）、[ADR-036](./ADR-036-real-browser-verification-tier.md)（真實瀏覽器驗證層＝本 ADR 多數規則的實際把關者）、[ADR-025](./ADR-025-run-terminal-state-and-evaluation-verdict-separation.md)（執行狀態與評估判定分離）、[ADR-038](./ADR-038-platform-product-domain-language-and-value-stream-navigation.md)（價值流詞彙）、[`01` §2.1／§3／§5](../plans/01-goals-and-plan.md)、[`02:NFR-001`／`NFR-007`／`DISC-004`](../plans/02-specifications-and-acceptance-criteria.md)、[`04` 乙-2](../plans/04-backlog-and-handoffs.md)
- 操作手冊（活文件）：[docs/design/system.md](../design/system.md)

## 背景

過去幾批 UI 工作全部是**反應式修缺陷**：截圖 → 看到壞的 → 修。

成效是真的。第一批兩頁找到 6 個缺陷；ADR-036 的瀏覽器層落地後，第一次真正的用途只是「拍十五張截圖然後看」，再抓到 6 個（`h3` 沒有任何規則、`RunTrace` 的標題全是平的、相容性徽章橫跨 1075px、Test Case 建立表單三個欄位三種版面、Test Case 列是全 app 唯一沒有卡片的清單、第二個 list reset 少了 `margin: 0`）；把那條溢出斷言從一頁擴大到 `router.tsx` 宣告的每一條路由，又自己抓到 4 頁在 375px 破版。

**但每一個判斷都是臨場品味，沒有可對照的標準。** 最直接的證據是同一個 `h1`：第一次被判定為「品味問題，不動」，第二批又被改掉（56px 的 landing hero 被套在每一條路由上，所以「資料保存政策」跟搜尋頁那句一行邀請語一樣大）。**同一個東西兩個相反的判定，因為沒有準則。**

缺的不是更多修補，是一把尺。

### 要先講清楚問題有多大

本 ADR 立案時曾對外表述「12 種字級不是尺度是累積」。**那句話講得太重，在此更正。**

`index.css` 確實宣告 12 個 `font-size` 值，但其中 5 個是 `@media (max-width: 1024px)` 的響應式對應值（36←56、30←40、20←24、18←20、16←18），不是獨立的階。拆掉之後**桌面實際只有 9 階，而且每一階都有明確工作**。真正該合併的只有一組：`.badge` 的 13px 與 `.note` 的 14px 差 1px，沒有人分得出來。

間距同理：11 個值裡 **7 個在 4px 網格上**（而且承載絕大多數的使用次數，12px 用 19 次、8px 用 17 次），偏離的是 2／5／6／10 四個，其中 5px／10px 還是從 `min-height: 32px` 與 20px line-height 反推出來的。

**這個 repo 的文化是誠實對帳。** 把一個溫和的問題寫成災難，會讓整份文件失去可信度——那正是本 ADR 想建立的東西。真實情況是：**系統大致成形，但它只存在於 CSS 註解與幾個人的記憶裡，沒有一處可以被引用來裁決爭議。**

### 產品把三件事變成義務，不是偏好

- **可判斷**。願景是「可信任基礎平台」（`01` §3），四個問題的第二個是「難以判斷是否可信」（`01` §1）。使用者的核心動作是決定要不要信任並執行別人的程式碼，所以每個畫面必須讓證據、**以及證據的缺席**都看得見。
- **快到第一個判斷**。MVP 承諾是 10 分鐘走完找到 → 驗證 → 下載（`01` §3），代表沒有任何畫面可以讓讀者為了拿到頭條而費力。
- **一個介面服務三種成熟度**。`01` §2.1 明文要求「非技術使用者可理解的任務語言」＋「可展開的進階技術資訊」，且同節說使用者「可能處於不同成熟度階段，而非固定角色」。**漸進式揭露因此是產品需求，不是風格偏好**（也是 `01` §5 產品原則第 7 條）。

## 評估選項

### 選項 A：引入第三方設計系統（Radix／shadcn 之類）

- 優點：元件行為（焦點管理、`aria-*`、鍵盤互動、彈出層）由上游維護；新畫面起步快；有現成的 token 慣例。
- 缺點（否決理由，三條都具體）：
  1. **`apps/web` 目前是純 CSS、零 UI 依賴。** 775 行 `index.css`，沒有 CSS-in-JS、沒有 utility framework、沒有元件庫。引入一套會把前端的依賴面與建置面從零抬到一個新的量級，而 ADR-016 選 SPA 的理由裡沒有一條需要它。
  2. **這個 app 的元件語彙承載的是產品特有的信任語意，不是通用元件。** `badge`／`criterion`／`notice`／`RiskIndicator`／`LicenseBadge`／`CompatibilityStatus` 回答的是「這個判定是誰下的」「這件事未知還是未通過」「平台自己降級了這個判定」。通用元件庫沒有這些概念，套上去之後每一個都要 unstyled + 自訂，等於付了依賴的代價卻沒拿到它的好處。
  3. **換一套會把已經寫在 `index.css` 註解裡的推理全部丟掉重來。** 那些註解不是裝飾：`--danger` 為什麼從 `#d33` 改成 `#b91c1c`（4.11:1 / 3.55:1 → 5.82:1 / 5.86:1）、`--link` 為什麼不能直接用 `--accent`（4.39:1 低於 AA）、停用態為什麼用 `border-style: dashed` 而不是 `opacity: .5`、`.filter-bar` 的 track 為什麼是 320px（1126px 要落三軌不是四軌）。這些是 QA-009 與 NFR-007 的實際推導過程，而且 [`contrast.test.ts`](../../apps/web/src/contrast.test.ts) 直接讀 `index.css` 的 token 來反覆驗證它們。換掉底層等於同時作廢那個測試與它守的東西。

### 選項 B：把既有隱性決策成文化＋補缺口（採用）

- 優點：零新依賴；規則的來源就是現有程式碼與規格，可以逐條標出處而不是憑空發明；補的三個缺口（表面規則、字級尺度的一處合併、間距偏離清單）都是小改；產出一張逐頁可用的 checklist，直接對治「同一個東西兩個相反判定」。
- 缺點：文件會漂——`index.css` 改了而文件沒改，就變成第二份不可信的來源。以「事實來源是 `index.css`，文件只記數字出現在哪條規則」與活文件慣例壓制；字級與間距的機器守門仍未建（見待決策 1）。

### 選項 C：維持現狀，不建系統

- 優點：零成本，繼續靠截圖與人眼，而且它確實抓到過東西。
- 缺點（否決理由）：**背景那段的 `h1` 前後矛盾就是它的產物。** 沒有準則時，同一個判斷可以在兩批之間反轉，而且沒有任何機制會指出反轉發生了。反應式修缺陷抓得到「壞掉的」，抓不到「不一致的」——後者要有尺才量得出來。

## 決策

**採選項 B。** 建立一份四層的設計系統文件，四層由上往下是：**義務 → 原則 → 系統 → 強制對照表**，並在原則之後放一張逐頁 checklist。細節與現值在 [docs/design/system.md](../design/system.md)（活文件）；本節只記決策本身。

### 1. 三個 UX 義務不可談判

可判斷、快到第一個判斷、一個介面服務三種成熟度。三者各自有 `01` 的出處，違反是產品缺陷而非品味爭議。

### 2. 八條原則，全部標出處

| # | 原則 | 出處 |
| --- | --- | --- |
| 1 | 未知不是空白 | `02:DISC-004`「缺少資料的欄位顯示未知，不得自行推定為通過」；`Compare.tsx` 檔頭與 `signature` 的 `undefined` 設計 |
| 2 | 顯示與強制成對 | `04` 乙-2「現狀（顯示但不強制）是兩者中最壞的一種」→ `02:NFR-001` UI 不得誤導 |
| 3 | 狀態先給文字，顏色是第二訊號 | `02:NFR-007` 第 3 條 |
| 4 | 停用要說原因 | `index.css` `.filter-bar` 註解：「a disabled control with no stated cause reads as a bug, and the cause is the honest part of the feature」 |
| 5 | 執行狀態與任務判定是兩軸 | ADR-025；`RunEvaluation.tsx` 的 `RUN_STATUS_LABEL`（「Never a pass/fail of the task」） |
| 6 | 平面答案優先，識別符折疊 | `01` §2.1 與 §5 原則 7；`SkillDetail.tsx` 的三個 `<details>` |
| 7 | 禁止用 `opacity` 弱化文字 | `index.css` QA-009 註解與 `contrast.test.ts` 檔頭；舊值把 `--text` 壓到 2.18:1~3.71:1，全數低於 AA |
| 8 | 毀滅性動作兩段式，第二段說會毀掉什麼 | `ConfirmDelete.tsx` 檔頭（`02:WS-002` 第 3 條、`02:SEC-006`）；`WorkspaceSkills.tsx` 的 scope 文案 |

**八條全部找得到出處，本 ADR 沒有新增任何一條原則。** 這是選項 B 成立的證據：系統早就存在，缺的只是一個可以被引用的地方。

第 7 條要特別記一句它的機制理由：`opacity` 是**任何色彩 token 都攔不住**的破壞方式，因為乘數落在合成之後。`contrast.test.ts` 量的是靜態 hex，結構上量不到它（該檔自己寫明），所以次要文字**只用字級降階**——這不是偏好，是唯一能被現有測試守住的做法。

### 3. 系統：三處變更，其餘照現況成文

- **字級**：桌面 9 階收成 **8 階**，唯一變更是 `.badge` 的 13px 併入 meta 的 14px。**micro（12px）只給等寬字**——mono 在同字級下視覺偏大，12px mono 約等於 14px sans。
- **間距**：4px 網格 `4 / 8 / 12 / 16 / 20 / 24 / 32`；偏離的四個值（2／5／6／10）**照 `db/query-owners.yaml` 的 `allow:` 慣例處理**——具名、有理由、**只能縮短不能增加**。那個檔案對自己的容忍清單寫的是「是**存量漂移**，不是擴充點」，而它現在是零條；設計系統的偏離清單用同樣的語意。
- **表面（新增規則，這是先前真正缺的一條）**：卡片＝清單裡**一則可以被獨立判斷的東西**；notice＝**平台對這一頁講的話**；裸區塊＝敘述文字。

  這條規則正好解釋了上一批「Test Case 列不是卡片」為什麼是缺陷，而不只是不好看：一則 Test Case 完全是可以被獨立採信或拒絕的東西，卻只是一疊段落，而同一個 app 裡其他四族（搜尋結果、驗收條件與建議、打包目標、下載紀錄）都有卡片。commit `90ade82` 的原文是「the only list in the app whose items were not the card every other list uses」。修法是套用既有的 `.search-result`，不是發明第五種樣式——這也是設計系統該有的行為。
- **狀態語彙**：badge（永遠帶文字）＝一個事實的標籤；`--danger` 邊框＋文字＝這件事不通過／會擋住你；`--accent-border`＝未知／未驗證；虛線邊框＝這個東西不是完整有效的（平台降級了判定，或控制項不能用）。顏色與線型永遠是第二或第三訊號。

### 4. 強制對照表，含誠實的空格

每條規則要寫明由什麼把關，**沒有把關者的必須直說沒有**。目前的分界大致是：ADR-036 的瀏覽器層守合成像素、375px 溢出（全部 18 條路由）、焦點環、Tab 順序；`contrast.test.ts` 守 token 層對比；`a11y.test.tsx` 守標題不跳級與 88 條 axe 規則。

**沒有人把關的有四類**，其中一類有前科：

- **「標題該降級而沒降」**——axe 的 `heading-order` 只罰跳級，不罰「該往下一級卻沒往下」。`RunTrace` 八個該是 `h3` 的 `h2` 就是這樣在 138 個 jsdom 測試下活了下來。
- 字級／間距在尺度上（待建，見待決策 1）。
- 卡片規則、未知不是空白、停用說原因（只能靠人看截圖）。

**這一格的存在本身就是價值**：知道哪些規則沒有機器在守，才知道 checklist 的哪幾條非人工不可。

### 5. 詞彙沿用 ADR-038

畫面上的分區名稱、導覽用語與價值流詞彙以 [ADR-038](./ADR-038-platform-product-domain-language-and-value-stream-navigation.md) 的產品領域語言為準。本 ADR 只管視覺與呈現規則，**不另立一套產品名詞**——兩套名詞是 §2 原則 2 的同型錯誤（介面講的話與平台的事實對不上）。

## 影響

### 正面

- 「同一個東西兩個相反判定」有了裁決依據：爭議先查 §4 的系統表，不在表裡才是新決策。
- UI 批的產出可被複查：checklist 九條逐頁走，過或不過寫得出來。
- 新畫面不必重新發明表面與狀態語彙，直接沿用既有 class（Test Case 卡片的修法即範例）。
- 沒有新增依賴、沒有新增建置步驟、沒有作廢任何既有測試。

### 成本與限制

- **文件會漂**，而且它漂的時候沒有任何測試會 FAIL。這是選項 B 相對選項 A 的真實代價（第三方系統的 token 至少會被打包工具檢查）。以「事實來源是 `index.css`」與活文件慣例壓制，但這只是紀律不是機制。
- **checklist 九條裡有七條是手動的**，成本落在每一批 UI 工作的人身上。要不要把它做成固定關卡，見待決策 3。
- 偏離清單一旦有人往下加行，這套尺就退化成描述現況的文件。`db/query-owners.yaml` 的 `allow:` 靠 CI 守住零條；本檔的偏離清單**沒有等價機制**。

## 待決策

1. **字級／間距的漂移守門要不要建。** 形狀大致清楚：讀 `index.css`，抽出所有 `font-size` 與 `padding`／`margin`／`gap` 的 px 值，比對 §4.1／§4.2 的尺度加上具名偏離清單，不在清單上就 FAIL——與 `contrast.test.ts` 同一個做法（讀真的那個檔案、不留第二份副本）與 `db/query-owners.yaml` 同一個棘輪語意。取捨在於誤報：`border-radius`、`letter-spacing`、`min-height`、grid track 寬度都不是間距，要嘛精確挑選屬性、要嘛容忍雜訊。**在建之前，checklist 第 9 條維持手動。**
2. **「標題該降級而沒降」有沒有辦法機器檢查。** 這是本文件唯一一個「已知沒有守門、且已經出過事」的規則。可能的方向：從 `<section>`／landmark 的巢狀結構推出期望層級再比對，或對每一頁的標題樹做快照測試（結構變了就要有人確認）。兩者都可能比它守的東西還吵，需要先評估。
3. **要不要把評估準則做成每批 UI 工作的固定關卡。** 選項：(a) 純文件，靠自律；(b) 在 `03` 開一個工作項，每批 UI 交付時逐條回答並寫進 commit message；(c) 併進既有的截圖流程——`e2e/shots.spec.ts` 已經對 18 條路由落檔，checklist 可以就著那組截圖走。(c) 成本最低，但它只涵蓋人工那幾條。
4. **要不要有 `--danger` 版的 notice。** 目前阻斷性訊息（`Packaging.tsx` 的「不能打包」）與非阻斷的降級說明共用同一個外觀，靠文字分辨（NFR-007 允許）。這是 §4.3 那張表講不清楚的一格。
5. **偏離清單的兩個「待收」值（2px 與 6px）怎麼收。** 6px 出現在六條規則上，實質是一條沒登記的「緊密清單間距」——登記成尺度的一階，或收成 4px／8px，二選一；繼續兩邊都不是，是這份文件最容易先爛掉的地方。
