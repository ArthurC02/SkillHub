# ADR-008：意圖搜尋

- 狀態：Accepted
- 相關：[ADR-011](./ADR-011-generating-a-skill-from-a-description.md)（生成流程的參考 Skill 搜尋沿用本 ADR 的檢索規則，門檻另定）、[ADR-012](./ADR-012-interactive-creation.md)（互動創作的查重搜尋沿用本 ADR 的檢索規則，門檻另定）、[ADR-017](./ADR-017-query-and-write-ownership.md)（Skill Search Document 的存活判準與投影規則）

## 背景

使用者以任務描述搜尋 Skill，需要在每個候選旁顯示符合原因。任務語言與 `SKILL.md` 的技術詞彙往往不重疊，純關鍵字比對召回率差；已索引內容搜尋 p95 需低於 2 秒，排除每次查詢都讓 LLM 閱讀候選內容的作法；語料規模小（策展內容以精選為主），不需要獨立搜尋引擎。搜尋索引是可從 Skill Version 事實來源重建的投影，不是事實來源本身。MVP 不接入外部市集或目錄站的即時搜尋結果，第三層來源由使用者自行提交 URL 匯入產生，屬於匯入管線的範圍。

## 決策

### 決策 1：混合檢索——向量腿承載召回，詞彙腿只做候選擴充，排序只看向量距離

檢索分兩腿以 `UNION` 合併候選，不做 RRF 或任何加權融合：

- **向量腿**：pgvector 相似度，距離門檻 0.75；承載跨語言召回（任務描述常與英文 `SKILL.md` 語料零詞彙交集）。
- **詞彙腿**：Postgres FTS（`websearch_to_tsquery`）加字元 bigram（`simple` config）比對，只用來擴充候選，不參與排序。其中**覆蓋查詢全部 token 的列**（bigram 完整覆蓋）不受向量距離門檻限制，且排在所有向量命中之前；名稱完全命中再置頂於覆蓋腿之上。

排序在覆蓋列彼此之間、以及非覆蓋列彼此之間，一律只看向量距離；覆蓋腿只決定「有沒有東西先被看到」，不曾把任何詞彙分數混進排序分數。零命中的腿因為是集合判準（在不在候選集裡），結構上不可能污染排序——這正是否決 RRF 的理由：等權融合對零命中腿一樣給分，量測顯示它對排序無增益甚至倒退。

查詢時先做一次輕量 LLM 查詢改寫（意圖→任務關鍵詞＋結構化過濾條件），改寫失敗或逾時一律降級為原句，且**降級後的原句仍要進向量腿**——只落到 FTS 腿是真正的失效路徑，會讓延遲風險（p95 < 2 秒）沒有意義地換成品質風險。Embedding 服務本身不可用是另一條獨立的降級路徑：向量腿打不通時，詞彙腿加開 `english` 設定與既有 bigram 一起比對，不等同查詢改寫失敗的降級。

規則過濾與排序調整（來源層級、驗證狀態、相容性）在候選集之上疊加，不影響上述排序基礎。

### 決策 2：索引時 LLM 增強是進場門檻，不是排序調整項

每個 Skill Version 建立時，LLM 讀取 `SKILL.md` 與套件結構，產出任務導向摘要、6～8 句涵蓋不同講法（格式詞＋日常講法、無格式、情境句、逐操作）的任務例句、輸入／輸出／工具／依賴標籤，連同 Embedding 一併寫入 Skill Search Document。產出標示為模型產出，錯誤可由人工修正並觸發重建。增強失敗不影響版本建立（`skillpkg.Validate` 通過即建版本），但**沒有 metadata（`enrichment_status = 'enriched'` 或已有 Embedding）的文件完全不進任何搜尋候選集**——公開搜尋、瀏覽、混合搜尋與創作工具的查重搜尋一律加上這條門檻。未增強的版本由每小時排程回填；只有增強完成後才對擁有者以外的人可見。

生成物（互動創作／單次生成的產出）同樣要經過索引時增強，理由是查重與擁有者自己的工作區搜尋需要看到它；這不改變生成物不進公開搜尋的邊界——排除仍在讀取側依 workspace／catalog 範圍判斷。

索引重建流程（`cmd/reindex`）可從 Skill Version 事實來源完整重生 Search Document；生產目錄要重做既有內容的增強（例如換了增強提示版本）另走專門的重新增強旗標，不因提示版本更新而自動生效。

### 決策 3：符合原因分兩級生成

預設由命中欄位以模板生成，零額外延遲；Top-N 結果可選 LLM 潤飾，逾時或失敗降級為模板版本，不阻塞回應。決策 2 的任務例句是模板能否產出內容的前提——沒有詞彙交集的命中（跨語言查詢的常態）沒有例句可用時，模板完全產不出符合原因。

### 決策 4：策展是唯一的結構性反投毒防線，且是常設紅線

索引文本由 LLM 從不受信任的 `SKILL.md` 推出，排名完全由索引匹配決定，與畫面上顯示的精選層級或掃描狀態無關——量測顯示投毒文件（索引文本直接抄目標查詢的答案）在未經正常增強時可擠進三成以上查詢的候選前段，即使經過正常增強流程也仍能擠進候選；同時找不到任何可用訊號（標籤格式詞數量、任務例句語意離散度）能把投毒內容與合法內容的分布分開。

因此：

- 目錄維持人工策展——只有人工審核能把內容放進 `is_catalog` 工作區，這是防止索引投毒**唯一夠格**的結構性緩解；任何放寬准入的提案（使用者匯入自動進公開目錄、接入第三方市集）動工前必須重跑投毒量測。
- 投毒量測是**常設紅線**：往後每次改索引文本生成規則（增強提示版本）或檢索規則（門檻值、覆蓋腿、詞彙腿）都要重新測，紅線是「最壞情形下投毒文件不得進任何查詢的 Top-3」；連同檢索品質（以固定 query set 量 F1／recall，正解數處截斷、干擾題以空頁為對）一起重跑，兩份數字寫在同一份報告。
- 不對僅 `indexed` 層級的結果加 Top-3 曝光上限或延遲策展信號——這道防線防的是投毒已經進了目錄之後的擴散，而進目錄前已有人工策展把關，第一點已規定任何放寬准入前先重跑投毒量測；只有出現放寬准入的提案、且重量後紅線未過，才需要重新設計這道防線。

### 決策 5：基礎設施維持 PostgreSQL，不引入獨立搜尋引擎

初期使用 PostgreSQL（pgvector＋FTS）承載全部檢索，不引入 Elasticsearch／Typesense 等專用引擎。Embedding 模型為 `text-embedding-3-small`（1536 維），查詢改寫與符合原因潤飾採用同一檔位裡延遲與成本最低的模型，索引時增強因產出直接成為主要檢索欄位而採用品質優先的模型；三者都經模型閘道呼叫，不直連供應商。拆分獨立搜尋引擎的觸發條件是語料規模或查詢演進速度顯著成長；因索引是可重建投影，屆時遷移不涉及事實來源改動。

## 影響

### 正面

- LLM 成本與 Skill 數量成正比，不隨查詢量增加，未登入搜尋可負擔。
- 符合原因有真實依據（命中欄位／例句），不是模型即時編造。
- 全部落在既有 PostgreSQL 內，不新增基礎設施產品；索引可完整重建，不是另一份事實。
- 覆蓋腿把「跨語言查詢答不出來」這類失效模式收斂成一個可重跑的量測腳本。

### 成本與限制

- 索引時增強的品質決定搜尋上限，且是安全邊界的一部分（決策 4），需要人工抽查與常設投毒重測，不能只靠自動化指標。
- 查詢改寫與符合原因潤飾各自是一個降級路徑，需要明確逾時與 fallback 行為；忘記把降級後的原句送進向量腿會讓延遲風險換成隱性的品質風險。
- 詞彙腿（FTS＋bigram）與門檻值（0.75）綁在目前的語料規模與 Embedding 模型上；語料規模跨數量級、或向量腿換模型／換維度時，覆蓋腿與門檻的實際影響需要重新量測，不能沿用既有數字。
- 策展保持人工，代表搜尋品質的成長速度受限於人工審核吞吐量；這是決策 4 的直接代價，不是可以繞開的實作細節。
