# ADR-029：產品分析事件與 audit／Trace 的邊界

- 狀態：Accepted
- 日期：2026-08-17
- 決策者：產品負責人、架構規劃
- 相關：[ADR-009](./ADR-009-observability-trace-and-evaluation-boundaries.md)（平台 O11y／Run Trace／Evaluation 三分，本 ADR 是其第五類且明確從屬）、[ADR-007](./ADR-007-trust-security-and-supply-chain.md)（稽核事件清單）、[ADR-017](./ADR-017-model-gateway-and-llm-observability.md)（Langfuse 作為第四軌的從屬處置，本 ADR 沿用同一種寫法）、[ADR-018](./ADR-018-containerized-core-infrastructure.md)（最少產品原則）、[ADR-003](./ADR-003-data-ownership-and-storage.md)（資料生命週期與刪除可追溯性）
- 設計來源：[docs/plans/mvp/m4/beta-design.md](../plans/mvp/m4/beta-design.md) §4，[docs/plans/mvp/m4/README.md](../plans/mvp/m4/README.md) §7 差-4
- 承接需求：`02:O11Y-004`（本 ADR 同批新增）、`03` BETA-002／004

## 背景

**鐵律 11 明文寫著「Secrets 不得出現在套件、Log、Trace 明文或分析事件」，而全 repo 沒有任何一份文件定義「分析事件」是什麼。** 它沒有 schema、沒有儲存位置、沒有保存期限、沒有讀取者。一條禁令套在一個沒有定義的東西上，實務上等於沒有禁令。

M4 的封測讓這件事到期：`03` BETA-002 要量 `01` §11.2 的核心漏斗，而**平台目前沒有任何產生使用者行為事件的機制**。既有的四類資料，逐項都答不出來：

| 既有的東西 | 它答什麼 | 為什麼不能當漏斗 |
| --- | --- | --- |
| `O11Y-001`～`003` 的 Prometheus 指標 | 平台健康（搜尋延遲、Run 排隊、成功率、清理失敗） | 是**聚合計數**，沒有使用者維度，答不出「同一個人有沒有從詳情走到試跑」 |
| `CORE-008` 的 audit event | 合規紀錄：誰、做了什麼、對哪個資源、何時 | PDM-006 提案給它 400 天、**只存 actor／動作／資源 ID／時間戳、不含內容**。拿它當分析來源，要嘛往裡面塞內容（破壞它的隱私設計），要嘛答不出「使用者輸入了意圖卻沒點任何結果」——搜尋根本不是一個 audit 動作 |
| Run Trace | 一次 Run 內發生什麼 | 漏斗的前兩段（搜尋 → 詳情）根本還沒有 Run |
| Langfuse | LLM 工程調優，**明文非事實來源**（ADR-017） | 同上，且只看得到模型呼叫 |

**在寫第一行事件產生程式碼之前需要這條線**，因為一旦開始收集，保存期限、遮罩與使用者揭露的義務就同時成立，而回頭改一個已經在收集的資料類別，代價是已收的那批。

## 決策 1：分析事件是第五類資料，明確從屬，不是事實來源

ADR-009 劃了三類（平台 O11y／Run Trace／Evaluation），ADR-017 加了第四軌（Langfuse，明確從屬），本 ADR 加第五類並沿用同一種寫法。

| 類別 | 回答 | 事實來源 |
| --- | --- | --- |
| 平台 O11y | 服務健不健康 | 是（維運領域） |
| Run Trace | 一次 Run 內發生什麼 | 是（使用者可見的執行事實） |
| Evaluation | 任務達成了嗎 | 是（判定領域） |
| Audit Event | 誰做了什麼 | 是（合規領域） |
| **產品分析事件（本 ADR）** | **有多少人走到漏斗的哪一段** | **否** |

**分析事件不是任何領域問題的事實來源。** 漏斗報表引用的 Run、評估、建議與下載事實一律取自領域表。這條與 ADR-017 對 Langfuse 的既有立場、與鐵律 5 對 `run_lifecycle` 的既有立場是同一條規則的第三次套用。

**七段漏斗只有四個事件是真的要新做的**，其餘五段既有領域表就答得出來：

| `01` §11.2 的漏斗段 | 怎麼回答 |
| --- | --- |
| 輸入意圖後查看至少一個詳情 | **新事件** `search_performed`、`skill_detail_viewed` |
| 查看詳情後 Fork 或啟動試跑 | `runs` 列（Fork 另可由 audit 推） |
| 建立 Run 後成功完成 | `runs` 表 |
| 完成 Run 後認為結果有幫助 | `evaluations.feedback_helpful`（`EVAL-006`） |
| 改善建議被採用 | `evaluation_suggestions.decision` |
| 完成試跑後打包下載 | `download_records`（`WS-004`，M4） |
| 首次使用後再回來 | **新事件** `session_started` |
| （區分「按了下載」與「下載成功」） | **新事件** `download_started`（成功那一半仍取 `download_records`） |

這一點很重要：它把「新增一個分析管線」縮小成**四個事件 ＋ 一組跨表查詢**。任何要求新增第五個事件的理由，都必須先說明為什麼既有領域表答不出來。

## 決策 2：形狀只記型態，不記內容——白名單而非黑名單

事件的固定欄位：`event_id`、`event_name`、`occurred_at`、`session_id`、`workspace_id`（登入後才有，未登入為 NULL），加上**該事件名稱在 schema 中宣告的屬性**。

- **schema 未宣告的屬性一律丟棄，不是記下來再遮罩。** 理由與打包的內容規則同型（ADR-027 相關設計）：黑名單漏一項就是洩漏，白名單漏一項只是少一個維度。
- **一律不記自由文字內容。** `search_performed` 記查詢的**長度、語言、是否有結果、結果數、是否套用篩選**，**不記查詢原文**——查詢原文可能含個資（`gate-test/recruit.md` §5.2 第 6 項已為閘門的逐字稿點名同一個風險）。要看原文得走 `BETA-003` 的質性管道，那條路徑有使用者的明示同意。
- `skill_detail_viewed` 記 `skill_id`（平台自己的公開識別）與到達來源（搜尋第幾名／直接連結）。
- **鐵律 11 的「分析事件」自本 ADR 起取得定義**：即本 ADR 定義的這一類事件。而「Secrets 不得出現在其中」由**結構**保證（只有白名單屬性、且沒有一個屬性承載自由文字），不是靠遮罩器再跑一次——`TRACE-005` 的遮罩器存在的前提是 Trace 必須承載內容，分析事件沒有那個前提。

## 決策 3：與 audit event 的邊界——兩者不合併，也不互相代替

| | Audit Event（`CORE-008`／ADR-007） | 產品分析事件（本 ADR） |
| --- | --- | --- |
| 回答 | **誰**做了什麼（可稽核，可能成為證據） | **有多少人**走到哪一段（彙總） |
| 主體 | 具名 actor（取自 session） | `session_id`；登入後才有 Workspace 關聯 |
| 涵蓋範圍 | ADR-007 列舉的重要操作（匯入、權限確認、Secret metadata、Run 生命週期、**Artifact 下載與使用者資料刪除**） | 漏斗四事件 |
| 保存 | **400 天**（PDM-006 提案），不含內容 | **180 天**（本 ADR 提案值，見決策 5），只含白名單屬性 |
| 可變性 | **不可刪改** | 可整批刪除、可重建彙總 |
| 帳號刪除 | 去識別化 actor 保留 | 去識別化（移除 Workspace 與帳號關聯），彙總保留 |

- **拿 audit 當分析來源會同時做壞兩件事**：要嘛往 audit 裡塞內容（破壞它「不含內容」的隱私設計），要嘛答不出漏斗前兩段（那兩段沒有任何 audit 動作）。
- **反過來拿分析事件當稽核也不行**：它可以被整批刪除、可以重建，這正是它與 audit 最本質的差別。一份可以被合法整批刪除的紀錄，不能拿來回答「誰在何時做了什麼」。
- **同一個使用者動作可以同時產生兩者**（例如下載：audit 記「誰下載了哪個 artifact」、分析記「有一個 session 走到了下載段」）。這**不是重複**，兩者的保存期限、可見性與刪除行為都不同；合併會讓兩邊都被較嚴的那一個綁住（packaging-design §7.2 對「下載紀錄 vs audit event」已下過同型的結論）。

## 決策 4：與 Run Trace 的邊界

| | Run Trace | 產品分析事件 |
| --- | --- | --- |
| 範圍 | **一次 Run 之內** | **Run 之外**，含還沒有 Run 的那兩段 |
| 使用者可見 | 是（一般／進階模式） | 否 |
| 內容 | 承載執行內容，**因此必須遮罩**（`0019` 的 `CHECK (masked)`） | 結構上不承載內容，因此沒有可遮罩的東西 |
| 關聯 | `run_id`／`attempt_id`／`seq` | `session_id` |

- **漏斗前兩段根本沒有 Run**，所以 Trace 在結構上就答不了它們——這不是「還沒實作」，是類別錯誤。
- **下載不產生 trace 事件**：打包不是 Run（contract-deltas §5 的既有裁定）。下載的紀錄走 audit 與 `download_records`，走到漏斗的那一份走分析事件，三者各自獨立。
- **`session_id` 不得重用 ADR-020 的 session token 或其雜湊**：那是憑證材料。分析用的 session 識別是另一個隨機值，**不可反查回 session 列**；未登入時它是唯一的關聯手段，登入後才附上 `workspace_id`。

## 決策 5：保存、匿名化與揭露

- **保存期限提案 180 天**，隨 PDM-006 一併追認。推導：漏斗第七段「首次使用後再回來」需要一個跨月的觀察窗，90 天（Trace）不夠；400 天（audit）沒有必要，那個長度是為了跨年的安全事件回溯而存在。180 天覆蓋一次封測加一次範圍複審週期。
- **未定值前不得開始收集。** 這不是新規則，是 `NFR-002`「保存期限仍為待決策事項，確定後須轉換為可測試的時間要求」的直接套用——差別在於既有資料類別是先存在後補值，而分析事件還沒開始，所以可以照順序做。
- **未登入的互動一樣量測**（漏斗第一段發生在登入之前），該類事件只有 `session_id`、沒有 `workspace_id`。
- **帳號刪除 → 去識別化保留**：移除 Workspace 與帳號關聯，事件本身保留。與 PDM-006 §6.1 對 Run metadata 與 Evaluation 結果的既有處理同型（「北極星指標與漏斗需要跨季度比較；去識別化後隱私風險低」）。**封測的質性回饋同此處理**（beta-design §6.2 已點名這個新問題）。
- **使用者揭露是必要條件不是加分項**：資料保存政策必須列出這一類資料的存在、內容範圍（含「不記查詢原文」這句）與保存期限。`NFR-002` 第 1 條要求「使用者在上傳前可查看資料保存政策」，分析事件是唯一一類**使用者沒有主動提交任何東西就會產生**的資料，因此揭露的義務比其他類別更重而不是更輕。

## 決策 6：存在 Postgres，不新增資料產品、不接外部分析 SaaS

- **Postgres，按月分割，`DROP PARTITION` 清理**——形式比照 `trace_events` 的既有做法（`0004` 已有前例），保存期限直接決定分割策略。
- **不新增資料產品**：同 ADR-018 的最少產品原則。封測量級（十餘人、一段兩週的測試期）距離需要專用分析儲存的門檻還有好幾個數量級。
- **不接外部分析 SaaS**：它會帶進資料出境與第三方 cookie 兩個新的合規面，而我們要回答的只有七段漏斗——那是一組 SQL，不是一個平台。
- 讀取面是後台查詢，**不做即時儀表板**：`BETA-002` 要的是一份報告，不是一個一直開著的畫面。

## 影響

### 正面

- 鐵律 11 的「分析事件」從一個沒有指涉對象的詞，變成一個有 schema、有儲存、有期限、有讀取者的資料類別；那條禁令因此第一次可以被檢查。
- `BETA-002` 有了承接者（`02:O11Y-004` ＋ `03` O11Y-004），不再是一條沒有任何工作項對應的允收準則。
- 「新增一個分析管線」被縮小成四個事件——因為決策 1 強制先問「既有領域表答不答得出來」。
- audit 的隱私設計（不含內容、400 天）被保護下來，不會為了做漏斗而被迫塞內容。

### 成本與限制

- **不記查詢原文的代價是真的**：「使用者輸入了什麼卻找不到東西」這個最有價值的訊號，在分析事件裡只剩長度與語言。它由 `BETA-003` 的質性管道補，而那條管道的樣本量遠小於分析事件。**這是刻意的取捨，不是疏漏。**
- **`session_id` 讓「同一個人」只能追到 session 粒度**，跨裝置或清掉瀏覽器狀態的同一個人會被算成兩個。登入後可由 `workspace_id` 合併，登入前不行——漏斗第一段因此系統性地略微高估分母。**報表必須寫明這一點**，不得把它讀成精確值（同 `gate-test/README.md` §2.5「所有百分比應讀作量級」的既有紀律）。
- **多一張按月分割的表要維護**（分割建立、清理、備份體積）。與 `trace_events` 共用同一套既有做法，但仍然是第二張。
- **決策 6 的「不做即時儀表板」在封測期間可能不方便**：要看數字得跑查詢。這是刻意的——一個一直開著的畫面會產生「盯著它」的成本，而封測要看的東西在事後才有意義。

## 待決策

- **保存期限 180 天的追認**（隨 PDM-006）：本 ADR 提案值，未追認前不得開始收集。
- **公開 Beta 之後的量級**是否需要專用儲存或外部工具：訊號是查詢時間或分割表體積，屆時另立 ADR；本 ADR 的事件形狀（白名單屬性、無自由文字）刻意與儲存實作無關，換儲存不必重新設計事件。
- **A／B 實驗框架**：MVP 不做。漏斗量測與實驗分流是兩件事，後者需要分流、樣本量計算與結果判定三套東西，`01` §7.3 的範圍內沒有它。
- **分析事件的讀取權限**：MVP 只有一個人，讀取即部署者。擴編或出現非工程角色需要看報表時，需要一個與 `SEC-011` operator 分開的角色（operator 明文不得讀取 Workspace 私有資料，而彙總報表不是私有資料，兩者不應合併），屆時另議。
