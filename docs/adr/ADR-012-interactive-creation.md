# ADR-012：互動創作

- 狀態：Accepted
- 相關：[ADR-001](./ADR-001-system-context-planes-and-deployment-path.md)（系統情境與能力提供者邊界）、[ADR-003](./ADR-003-run-orchestration-and-async-workflows.md)（Job／Outbox／冪等，試跑沿用既有 Run）、[ADR-004](./ADR-004-sandbox-isolation-and-execution-security.md)（試跑的沙箱執行）、[ADR-005](./ADR-005-model-gateway-and-observability.md)（LiteLLM 閘道、Trace 遮罩）、[ADR-006](./ADR-006-identity-workspace-admission-and-allowances.md)（既有單次生成額度、Workspace 私人資料的清除 fence）、[ADR-008](./ADR-008-intent-search.md)（目錄檢索）、[ADR-009](./ADR-009-evaluation-verdicts-and-judge-trust.md)（評估回饋的信任邊界）、[ADR-011](./ADR-011-generating-a-skill-from-a-description.md)（單次生成路徑，本 ADR 是它的多輪延伸）、[ADR-023](./ADR-023-account-purge-and-credit.md)（會話成本上限、帳號清除）

## 背景

既有的生成路徑是一次任務描述換一個版本：沒有多輪澄清、沒有草稿修訂、沒有跨輪讀圖確認，也沒有可恢復的會話。互動創作要補上這段旅程，但受兩條既有邊界夾住：狀態機的唯一事實來源只能是 Go／Postgres（不能引入第二套 Run 狀態或 Python 側的跨 Job 持久化），而模型的輸出在被 Go 接受之前只是提案，不是這場對話已經發生的內容。等待畫面要說出後端真的知道的事，不能靠前端用快照亂猜，也不能把一份平台可能不採用的草稿即時畫出來。

## 決策

### 決策 1：固定 Workflow 加有界 ReAct，圖在 Python 端逐 Job 重建

`apps/llm` 以 LangGraph 編排一條固定 workflow：需求整理與澄清、流程圖或參考的理解確認、目錄查找與比較、確認參考、確認 brief 與驗收條件、草稿、Go 端驗證、經授權的沙箱試跑、依回饋修訂、使用者明確確認保存。資料已充分時可以跳過中間步驟，不強制每次都走滿全部輪次。圖只在單一 Job 內存在、每個 Job 由 Go 交來的快照重新建構，不使用 LangGraph 原生的跨程序 durable interrupt 或 checkpointer——這樣狀態機的持久化邊界只有一個。

### 決策 2：Go／Postgres 是創作會話的唯一事實來源

會話狀態以版本化快照保存：已確認需求、對話與必要摘要、原始輸入的引用、參考版本、草稿 revision 與雜湊、待處理的動作或確認、工具結果、用量、job attempt、供 Test Case 使用的 `sample_input`、附件中繼資料；狀態變化另以 append-only 事件記錄。Go 以同交易 outbox、expected-revision 的 CAS 與冪等鍵管理重啟、取消、逾時與重送；重複或遲到的結果不得重做副作用，也不得重建版本。理由是快照與事件都已經是既有 Run 狀態機（ADR-003）的同一種持久化紀律，多開一條路徑等於多一個事實來源。對話、草稿與參考皆屬私有會話資料，受 [ADR-006](./ADR-006-identity-workspace-admission-and-allowances.md) 帳號刪除與共享的清除 fence 管理；公開只能涵蓋使用者明確選定、預覽確認且通過治理的套件內容，原始對話、原圖、輸入資料與參考全文不會自動外流，私有會話維持私有。

### 決策 3：Python 只回結構化提案，不擁有任何持久化或授權決策

Python 不執行不受信任的 Skill 或 Script、不直連核心資料庫、不消費佇列、不擁有 AuthZ 或成本政策，也不做 Go 領域狀態的轉移；圖內下一步仍由 LangGraph 在單一 Job 內決定，但工具意圖一律交回 Go 執行（檢索、讀取、驗證、試跑），結果再交回 Python。所有模型呼叫走 LiteLLM 閘道。這是既有能力提供者邊界（ADR-001、ADR-005）在互動場景下的具體套用，不是新規則。

### 決策 4：保存確認綁定使用者所見的草稿版本

最後的保存確認綁定使用者看到的草稿 revision 與雜湊，確認之後模型不能再換內容。試跑前必須先取得使用者對成本、工具、資料與候選版本的明確確認，才建立私有不可變候選並走既有 Run；試跑成功不自動完成會話，最後確認選的是同一個已 materialize 的候選，不再重新生成或建版。使用者也可以在未試跑、但 Go 套件驗證通過的情況下確認保存，畫面必須明示這份草稿未經試跑驗證。同一個候選重複確認不重建版本；正式 Version 與 Run 歷史一律不可覆寫，草稿本身可以修訂。

### 決策 5：流程圖只保存理解與指紋，不保存原始位元組

流程圖跨輪保存的是已確認的結構化理解與指紋，不是原圖位元組；要重新讀圖必須重新上傳，畫面不得宣稱能回放原圖。流程圖是與文字、參考並列但走法不同的入口，且是其中的實驗性功能——平台資源優先給白話與參考兩個入口：流程圖先呈現「圖上看到什麼」的結構化理解讓使用者確認，不確定之處必須先問人，才進入起草——不確定處是起草的閘門，不是起草之後的修訂項。快照另外保存每一輪附件的中繼資料（訊息位置、媒體類型、位元組數、雜湊），只為了讓一個看得到自己歷史的對話不會弄丟自己的回合；縮圖只由送出它的那個瀏覽器在本機還原，換一台裝置或別人看同一個會話時，那一輪顯示的是「附了什麼、為什麼看不到」，不是空白也不是假裝有圖。**這是一個刻意可逆的立場，不是永久決定**：日後若要保留原圖位元組供顯示或事後複現，需要另立決策一併回答保存期限、存取控制與儲存成本三件事，現在的紀錄不足以支援。

### 決策 6：參考既有 Skill 固定版本、每次使用重驗權限

參考鎖定在使用者選定的那個版本，每次使用都重新驗證讀取權限；權限失效時等待使用者換選，不可靜默跳過。資料不足以生出可用 Skill 時，系統可以說明限制或替代方案，不得捏造工具能力。確認參考的畫面要讓使用者看到判斷依據，不只是描述與相容性：精選層級、掃描狀態與警告一併顯示，確認本身仍由使用者決定。

### 決策 7：目錄查找用混合檢索，先查重再決定要不要生成

創作工具的目錄檢索改跑與公開搜尋相同的規則——覆蓋優先、名稱置頂、丟掉沒有向量的候選（詳見 [ADR-008](./ADR-008-intent-search.md)）——不再用自己的分數門檻；搜尋意圖最多帶三個改寫，連續兩輪空手即撤回搜尋、回報「找不到」；意圖不清先問人不亂猜。查重問的是「是不是同一份」而非一般排序，另固定用 0.55 的距離門檻，時機固定在兩個——會話的第一則訊息、以及 materialize 之前——命中時停在確認參考或確認重複的畫面，讓使用者在既有 Skill 之間做選擇。若草稿與被列出的重複同名，Go 只要求模型改名（不動內容、不重新確認 brief），改名後的新草稿不重跑查重。

### 決策 8：命中既有 Skill 可以直接採用，繞過整條創作管線

使用者在查重時選擇採用既有 Skill，會話直接進入保存狀態：不澄清、不出草稿、不做 Go 驗證、不試跑、不 materialize，Go 直接把選中的 Skill 以既有的 Fork 路徑複製進呼叫者的工作區，會話快照標記為「已採用」，候選即該份 Fork。這不是「保存確認綁定使用者所見草稿」規則的例外，因為採用路徑本來就沒有草稿可綁定——它繞過的是整條管線，不是保存那一步。採用不消耗模型呼叫預算（只有一次目錄查詢的 embedding 成本），也不計入既有的單次生成額度，因為它的來源類型不是生成。

### 決策 9：修訂用三次獨立的模型呼叫，重寫的內容覆蓋決定的內容

一次修訂步驟固定拆成三次模型呼叫：診斷（逐條標出哪個未通過的驗收條件要修在內容、條件或樣本）、以純文字重寫草稿內容、最終決定（給使用者的建議與訊息）。第三次呼叫回傳的內容一律被第二次的重寫結果覆蓋——這是對付較小模型「一邊描述修改了、一邊交回逐位元相同的草稿」這個已知失效模式的結構性解法，不是靠提示語氣去說服模型。若診斷判定要修的是驗收條件或輸入樣本而不是內容本身，流程退回確認 brief 那一步，由使用者重新確認。產品金鑰維持較小的模型等級：量測顯示旗艦模型無論用於草稿或試跑都沒有明顯提升可驗收比例（旗艦寫 0/14、旗艦跑 2/10），模型等級因此不是這段旅程的槓桿，三次呼叫的拆分正是為了因應這個既定選擇下較小模型的失效模式。

### 決策 10：工具呼叫只是意圖，網路存取先問人、失敗不重試

模型每輪可以請求呼叫工具（例如抓取一個網址）以補足資訊，或在試跑之後定向追問使用者；工具意圖一律只由 Go 執行，不下放給 Python 或 API 行程。以抓取網頁為例：模型只能提出網址，Go 先檢查、再問使用者，取得同意後由 Worker（既有的佇列消費者）在呼叫模型之前完成抓取，觀察結果以結構化資料交回。連網前一定要問人；被目標網站或部署環境擋下只回報一次、不自動重試。試跑沒有通過時，先由 Go 列出問題交使用者回答，模型才依回答修訂，不讓模型憑空重猜。

### 決策 11：使用者訊息可以附在流程圖或選擇參考之後，但一次只能挑一種素材

上傳流程圖或選擇參考時，使用者可以在同一次動作附上一句話，走與一般訊息完全相同的規則（長度上限、訊息則數上限、遮罩）；這不新增動作種類，也不改變任何一個既有的確認關卡——流程圖仍走兩段確認，選擇參考仍停在確認參考等待使用者。流程圖與選擇參考不能在同一次動作裡合併送出，介面在送出前擋下並提示使用者分開處理。

### 決策 12：對話與工具觀察一律先遮罩、評估回饋先去除連結，草稿逐字抄襲要擋

使用者訊息與抓回的網頁內容在寫入快照前一律先經遮罩處理，才交給模型；參考的既有 Skill 內容與工具觀察在提示中以明確的圍欄標記包起來，讓模型能分辨「這是資料不是指令」。評估給的回饋（判定摘要、每項驗收條件的理由、每個發現的訊息）在交回創作流程前先移除其中的連結——那段文字是模型讀受測 Skill 輸出後寫的，下游沒有理由需要那個網址。草稿在交回時，會比對其內容（名稱、描述、相容性、工具清單與套件內每個檔案）是否出現只存在於評估回饋文字裡、使用者與前一版草稿都沒寫過的標記式字串；命中時不是直接拒絕，而是要求模型用自己的話重寫，重試達上限仍未擺脫則照樣保存並讓使用者知情。

### 決策 13：互動會話的成本與既有額度分開結算

互動會話的模型用量與總預算，和既有的單次生成次數額度、Run 額度分開計算；具體的單場成本上限與加碼機制見 [ADR-023](./ADR-023-account-purge-and-credit.md)。會話一開始就可能已經產生模型費用，失敗或取消也必須如實顯示花費，不得記為零。會話預算一經確認，Go 在預算範圍內逐次核准每一次模型呼叫；超出預算、要求提升權限，或要另開一次試跑，都要重新阻斷、要求使用者明確確認，不能默默放行。

### 決策 14：等待畫面串的是「步驟事件」，不是模型 token，且不需要額外的中繼儲存

創作等待期間不串模型輸出（token），因為模型的輸出在 Go 接受之前不是這場對話已經發生的內容——整份退回與丟棄重問（nudge）是每天都在發生的路徑，串出來的東西可能整份被撤銷；一次修訂步驟又是三次呼叫，其中只有一次的內容會真正被採用，沒有唯一能串的對象。串流承載的是 LangGraph 語意下的「狀態更新」，也就是這一步進到哪個階段（排隊中、已送出模型呼叫、正在讀網頁、正在搜尋目錄、正在驗證草稿、已交回）——這些狀態本來就是 Go 每次狀態轉移都會寫下的 append-only 事實，串流只是把它們推出去，不新增任何狀態，因此與「Run 狀態的唯一事實來源是 Go」的既有邊界相容。

傳輸是一條唯讀的 SSE 端點，事件序號直接用會話列自身的 revision 欄位——快照是累積的，新版本的文件已經包含所有更早版本會說的一切，因此客戶端帶著 `Last-Event-ID` 重連時，伺服器只需要送出當下那份文件，不必另外維護一張事件序號表，也不需要 Redis 之類的中繼儲存。跨行程的新事件通知用資料庫輪詢實現：API 行程每 250 毫秒讀一次會話列的 revision（沿用既有跨程序取消監看的同一個節拍與同一列），不引入 `LISTEN`／`NOTIFY`。每 20 秒送一個 keepalive 註解行維持連線。契約裡端點、參數、`Last-Event-ID`、錯誤回應都寫進 OpenAPI，但 200 回應不宣告 body schema（因為 body 是一串文件而不是單一物件），改由一支測試把伺服器實際送出的 `data:` 內容與同一個資源的一般查詢結果逐位元比對來釘住形狀；反向代理對這條路由關閉 buffering，並有一支測試驗證這件事——因為 buffering 開著時端點仍會回 200、仍會照樣把所有事件送到，只是變得和被取代的輪詢一樣慢，不會有任何錯誤提示這件事發生過。

這個決策的理由不只是等待時間：以既有的模型呼叫紀錄量測，單次呼叫中位數約 4 秒（p95 約 8 秒），一次三次呼叫的修訂步驟中位數約 12 秒；串流步驟事件相較於既有的 1 秒輪詢，中位數省下約 0.5 秒，對單次呼叫中位數約一成二、對 p95 約六趴、對一次修訂步驟約四趴——改善本身並不大。真正的理由是等待期間畫面說的是後端已經確認的事實而不是前端用快照猜的，而且輪詢每次都要整份重抓最新快照（等待越久抓越多次、文件也越大），串流只在版本真的推進時才推一次。

### 決策 15：Token 串流不關死，但要三個前置條件才能重開

不逐字串模型 token 這件事可以重新考慮，但重開之前要先回答三件事：Go 對草稿的既有檢查（逐位元相同、缺流程圖節點、抄襲評估標記、多出未經同意的工具）都需要完整草稿才能判斷，要先有明確裁定說「畫面已經顯示、之後被撤銷的內容該怎麼辦」，不能留給實作者臨場決定；Python 要能在契約層標註三次呼叫裡哪一次的輸出是可以串給使用者看的，不能只寫在程式註解裡；使用者中途取消時，供應商通常仍會照樣計費，成本記錄必須能吃下「串到一半被取消」這種用量狀態，不能一律當成未知用量處理。

## 影響

### 正面

等待畫面呈現的永遠是後端已經確認的事實，不是前端從快照猜測出來的敘述；互動創作不需要引入第二套 Run 狀態機、Python 端跨 Job 持久化或 Redis 之類的中繼基礎設施，續傳與事件序號都直接落在既有的會話列與快照上。查重與採用既有 Skill 的路徑讓「找不到才生成」成為預設，避免同樣的 Skill 被重複生成。針對提示注入的圍欄、遮罩與抄襲比對讓大部分已知的攻擊面有確定性的守門，不完全依賴提示語氣。

### 成本與限制

放棄逐字打字的即時效果；SSE 是這個系統第一條長連線，佔用一個連線與一個 goroutine，天然上界是會話逾時時間，仍需要額度與逾時控管。流程圖原始位元組不落地是刻意可逆的立場，換裝置或換瀏覽器看歷史對話時看不到縮圖。工具意圖裡混入不被允許的執行方式、或模型謊稱驗收條件全數通過這一類風險，目前完全依賴提示層的紀律，Go 端沒有對應的結構性守門。

## 待決策

工具意圖被混入不被允許的執行方式、或模型謊稱驗收全數通過這一類殘留的提示注入風險，應該在哪一層（模型提示、Go 驗證、或兩者）、用多少樣本量測與收斂，目前尚未有定論。
