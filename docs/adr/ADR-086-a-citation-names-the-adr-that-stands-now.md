# ADR-086：引用指向現行的那一份——ADR 只增不改，但舊的編號不能悄悄地繼續被引用

- 狀態：**Accepted**（2026-09-15，負責人提出「ADR 目前已經累積了很多檔案……非常多的文件都直接參考到 ADR，甚至指定某一個 ADR 的編號或是檔案，我覺得這樣子風險非常大，我也不可能放任 ADR 檔案無限增長，請你協助我找到管理的辦法」，看過提案後指示「執行」第一階段）
- 日期：2026-09-15
- 相關：[`docs/AGENTS.md`](../AGENTS.md)〈文件維護規則〉（ADR 是決策歷史：推翻＝新增並把舊的標 `Superseded`）

## 背景

2026-08-13 到 2026-09-15 的 34 天裡累積了 86 份 ADR，平均一天 2.5 份。全 repo 引用 ADR 編號約 5800 次，其中約 4800 次只寫編號、沒有連結，所以 `doc-links` 看不到它們。

份數本身不是風險。風險在於 ADR 同時做兩件事：記錄「當初為什麼這樣決定」，也是「現在的規則寫在哪」的唯一出處。其他文件和程式只能直接寫編號；那一份被取代或被修訂之後，沒有任何東西會告訴引用它的人。當天量到的三種漂移：

| 漂移 | 當天的數字 |
| --- | --- |
| `docs/adr/` 與里程碑紀錄以外，引用整份已被取代的 ADR，卻沒提到取代它的那一份 | 4 行（ADR-024、ADR-058 兩次、ADR-081） |
| 新 ADR 在檔頭寫了 `修訂`／`取代` 某一份，索引上那一份的狀態卻沒寫 | 15 列，包括前一天才寫的 ADR-085 對 ADR-039 |
| 非 markdown 檔（程式、設定、契約、測試）裡的 ADR 編號 | 822 處、130 多個檔（棘輪上限 852，另外 30 處是本檢查自己測試裡的樣本編號）；契約 `contracts/openapi/` 就有 177 處，會跟著產生器進到生成的客戶端、伺服器程式與對外 API 文件 |

## 業界做法

- **寫定後不修改，決策變了就寫新的，把舊的標成 Superseded。** Nygard 的原始文章、[AWS](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)、[Azure Well-Architected](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record) 都這樣寫，與本 repo 既有的規則相同，本文不改它。
- **舊的那份要有指向新版的連結**（[MADR](https://adr.github.io/madr/)），讀者從舊的一路走得到現行的那一份。
- **讀者查閱的單位是整本決策紀錄，不是某一份 ADR**（[Henderson](https://github.com/joelparkerhenderson/architecture-decision-record)、AWS）。
- **不是每個決定都值得一份 ADR**（[Spotify](https://engineering.atspotify.com/2020/04/when-should-i-write-an-architecture-decision-record)）。
- **怎麼控制份數，找不到權威答案。** 主流來源都說只增不刪，沒有一家談封存或合併；[Log4brains](https://github.com/thomvaill/log4brains) 的做法是更好的導覽，而不是更少的檔案。本文待決策 2 的合併與搬移，是依本 repo 的情況設計的，不是業界定論。

## 決策 1：引用被取代的 ADR，同一行要寫出取代它的那一份

- 範圍：`docs/adr/` 與 `docs/plans/mvp/` 以外的所有檔案。那兩處是歷史，照當時寫的留著。
- 「被取代」以索引狀態為準：狀態格以 `Superseded` 開頭。取代它的那一份，就是同一格裡點名的 ADR；狀態寫了 `Superseded` 卻沒點名，本身就是錯。
- 要引用現行的規則，就改指向取代它的那一份；歷史本身就是重點時（「ADR-058 活了一天就被 ADR-060 取代」），就在同一行把兩份都寫出來。

## 決策 2：新 ADR 修訂或取代舊的，舊的那一列索引要寫出新的編號

- 來源是新 ADR 檔頭的 `- 取代：`／`- 修訂：` 那一行：第一個「（」或「；」之前點名的、編號比自己小的 ADR，就是被修訂的那一份。之後的內容是附帶說明，常會提到只是「相容」的 ADR。
- 被修訂的那一份，索引狀態格要寫出新的編號，形狀照既有慣例：`Accepted（決策 N 經 ADR-xxx 修訂）`。**這是維護索引，不是改寫舊的決策**，舊檔一個字都不動。這就是 MADR 說的那條指向新版的連結，差別在於它寫在索引上，而不是舊檔裡。

## 決策 3：程式、設定、契約與測試寫規則本身，不寫 ADR 編號

- **ADR 編號只放在四種地方**：ADR 本身與它的索引、各區域的 `AGENTS.md`（現行規則的入口）、其他 markdown 文件的「依據」，以及 commit message。
- **非 markdown 檔裡的 ADR 編號只准變少。** 上限是 `tools/devctl/adr_citations.go` 的 `adrCitationCeiling`，上線時 852。
  - 超過上限就紅：寫進去的應該是規則本身，或者指向區域的 `AGENTS.md`。
  - 低於上限也紅，要求把上限調到實際數字，不讓它悄悄長回去。
  - 不算在內的：`.jsonl` 量測紀錄（付費量測腳本會自動附加，備註欄是自由文字）、generated 目錄、凍結的語料。
- **markdown 不設棘輪。** 文件拿 ADR 當依據是正常的用法；它們真正的風險是「指向被取代的那一份」，這由決策 1 管，檔名連結指不指得到檔案則由 `doc-links` 管。程式碼註解裡的編號，本來就被 `comment-budget` 零容忍擋下，棘輪數的是字串、測試名稱、lint 說明與契約描述裡的編號。

`automation-check` 的 `adr-citations` 守這三條。

## 影響

### 正面

- **ADR 被取代時，引用它的地方不會安靜地過時。** 活文件裡每一個舊編號旁邊都看得到新編號。
- **索引可以當成決策的現況表。** 每一列的狀態都寫出它被誰修訂過，讀者不必讀完整條鏈，也知道哪一份還單獨成立。
- **新的編號不會再擴散到程式與契約裡。** 既有的 822 處不做一次性大改，隨日常修改逐步清掉。

### 成本與限制

- **決策 1 只抓整份被取代的 ADR。** 部分修訂（例如只改了決策 1）不逐行檢查，只靠決策 2 的索引註記讓讀者看到。
- **決策 2 讀的是散文。** 檔頭沒用 `- 取代：`／`- 修訂：` 格式的修訂（例如寫在 `- 相關：` 裡）看不到；第一個「（」或「；」的切法，是從當天 86 份檔頭歸納出來的。
- **棘輪只數數量，不判斷對錯。** 拿掉一個編號，也要順手把上限調低一格。

## 待決策（負責人裁定前不寫進規則）

1. **寫 ADR 的門檻。** 符合以下任一條才寫 ADR：跨越行程、context 或契約的邊界；事後很難撤回；當時認真比較過替代方案。其餘情況只改規則文件，理由寫進 commit message。這會改變寫文件的習慣。
2. **合併型 ADR 與搬移。**
   - 一條取代鏈太長時（例如前端的 081 → 082 → 085），寫一份新的 ADR，把現行決策完整重寫一次，並取代整條鏈。
   - 完全被取代的 ADR 搬到 `docs/adr/superseded/`。搬移會動到指向那些檔名的連結，要等引用收斂之後再做。
3. **契約裡的 177 個編號**（`public.yaml` 112、`llm-internal.yaml` 39、`sandbox-provider.yaml` 26）。它們會進到生成的程式碼與對外 API 文件。清掉就要重新產生程式碼，而契約與生成目錄屬於高衝突區，由主 Agent 依序處理；清完之後，契約改成零容忍。
4. **各區域的現行決策入口。** `apps/platform`、`apps/llm`、`apps/sandbox` 的 `AGENTS.md` 補上 `apps/web/AGENTS.md` 那種「要做的事 → 現行規則 → 守它的測試」表。決策被取代時，只要改那一列。
