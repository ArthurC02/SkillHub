# Run 費用觀察提案

目前已有創作會話的 known／unsettled／unknown 費用觀察，Run 的完整費用與可信分母仍缺。此提案沿用 Run 擁有生命週期、Credit 擁有費用的已審查邊界，擴充既有同步協作上的批次唯讀事實，不能從估價或「已記帳」推算完整費用。

## 判定與交接

以固定 UTC 時間選取最近 24 小時、左含右不含的全部保留 Run，包含未結束、評估與接續 Run；一個 Run 算一場，不以 attempt、對話鏈或 cost event 代替分母。Run 取得自己的批次與結算標記，Credit 批次回傳費用事實及完整性證據。沒有事件的 Run 仍要分類，不逐 Run 查閘道，不由 Worker 跨 owner 聯表。

只有已結算且完整費用經 owner 證實的 Run 屬 known；明示未知、完整性無法證明、無效金額或已結算卻無事實屬 unknown，其餘待結算者屬 unsettled。金額只從 known 計算，缺 known 時撤下金額，完整的明確零才顯示零。失敗或取消撤下數量、金額及時間；成功空集合才顯示零數量。副本快照不相加，觀察不改帳本、Run、清理或保存政策。

## 仍需決定的證據

歷史 cost event 沒有記錄 spend log 是否在頁數上限被截斷，gateway 來源與 cost_settled_at 不足以證明其完整性。即使修正未來的結算，也不能自動追認舊資料。須由 developer 確認完整性事實的來源、舊記錄辨識與必要遷移，證據不足就保持 unknown，不重扣或補造價格。

兩個 owner 的讀取也不是共同歷史快照；介面需有足以確認同一筆結算事實的證據，或保守分類。這個一致性方式與批次 Port 擴充要先審查，不能用新的 metrics 名稱掩蓋未決事項。

## 測試與反證

七項允收及對應義務全為 planned，沒有執行或通過宣稱。使用固定時鐘驗證 since／until 兩側一微秒；實際 PostgreSQL 與兩個 owner 路徑驗證缺席、已記錄未知、完整零、完整正額、舊不完整與結算中間讀取。驗證每個 Run 只計一次、查詢不隨 Run 數逐筆增加，並比較重讀前後 Run、cost event、Credit、outbox 原樣。失敗與恢復、空批次、解析度、溢位及只含固定 coverage 標籤都有具體預期。

每項保護需有故意移除後會失敗的焦點測試，並精確還原；免費替身與合成批次不替代正式資料量的部署驗收。
