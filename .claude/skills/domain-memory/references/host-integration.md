# Host integration

For a host that dispatches Domain Memory work to its own agents. The Plugin manifest defines no `agents` or `subagents` and gets neither: role files, model settings, concurrency and orchestration stay in the host, which maps the seven capability names to its own agent mechanism without changing the Registry format or the Skills.

A plugin install and a direct Skill read of the Plugin root are different entry points. A host lists the installed Plugin's contents as the Skills under `skills/` and nothing else: the Plugin-root `SKILL.md` router is not a Skill under a plugin install, so an agent working through the installed plugin never sees the router page, its readiness-first instruction, or this file. Each leaf Skill's `description` is sufficient for a host to pick a capability; the Read and Extract Skills open with the readiness step, the other leaf Skills do not restate it. To keep that step from being silently lost, a host must call `readiness` itself before dispatching to a Domain Memory Skill, or route through a direct read of the Plugin-root `SKILL.md` instead of the installed plugin.

The host runs the capabilities [SKILL.md](../SKILL.md) chooses, in separate agents or in one: Read before implementation, after Extract when the Registry has not learned the code yet; Design for a material change; Review before each handoff; Maintain after implementation or source drift; Review a change before a merge. `domain-memory-implementation-hygiene` runs on a code change between Read or Design and the Review handoff, in the implementing context when the host cannot delegate. Delegated work uses the same repository, Registry, evidence rules and Git review boundary: a subagent may prepare a proposal or evidence, and never treats a candidate as reviewed or bypasses the host's write and approval controls.

When delegation is available, pass the implementation handoff from Read or Design to the coding Agent as the task's reviewed context; it may choose other language-native constructs, and returns evidence for the handoff's proof obligations. A host that cannot carry the handoff between agents runs the capabilities in one context and labels the result unverified when the handoff is lost.

A host that carries approvals must also prepare the authority behind them, once per repository and once per machine. `governance-readiness` reports what is still missing, and [Preparing the approval authority](script-api.md#preparing-the-approval-authority) covers both situations and the commands that settle them. Until that is done the Registry holds candidates, which is a legitimate state to work in and not a state to present as reviewed.

The host itself runs the two checks on a code change: `quality-gates --repo-root <repo>` before dispatching it, passing the result to the coding Agent with the handoff, and `counterfactual` on each rule the change added or moved before accepting it, returning the change to its author on a `survived` verdict. An Agent told that a command exists seldom runs it unprompted, and the weaker the model the less often, so a host that leaves them to the coding Agent has the instruction without the check.

A missing Registry in an empty or greenfield repository is a routing state, and an invalid or stale Registry is a blocking handoff state; neither is a reason to skip the lifecycle because a host cannot delegate or a command has no result. For each dispatch the host records the command result, the Registry path used and the Git revision when one exists; a host that cannot record one of these may still run local drafts, and labels the handoff unverified rather than presenting it as reviewed.
