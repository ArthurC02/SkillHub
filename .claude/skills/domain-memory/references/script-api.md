# File-backed Domain Memory API

`scripts/registry_tools.py` is the stable command entry point. It implements the read, query, and controlled update capability that a remote Domain Memory API would provide, using JSON files in the local repository.

| Capability | Command | Machine guarantee |
| --- | --- | --- |
| Map repository sources | `discover-sources --repo-root <repo> [--output <file>]` | Inventories instruction files and candidate decision, requirement, contract, boundary, implementation, and test paths without inferring domain facts. |
| Assess project readiness | `readiness --repo-root <repo> [--registry-root <path>]` | Reports the posture described in [readiness](readiness.md). It is read-only and never promotes a fact or selects a source corpus. With a Registry whose policy names a verifier, `governance_candidates` reports the `configured_verifier` and `configured_trigger` instead of recommending one. |
| Initialize from human choices | `init-domain-memory --repo-root <repo> --output <path> --source <path> --storage-mode <mode> --data-classification <class> --review-mode <mode> --source-authority <identity> [--include <glob>] [--exclude <glob>]` | Requires an explicit destination and source choices. Applies include/exclude and policy resource limits before writing the confirmed map. |
| Verify selected sources | `verify-sources --repo-root <repo> --source-map <path> [--policy <path>]` | Separates the selection moving from its content changing, and, when supplied, rechecks policy limits. A file appearing, disappearing or being renamed under a selected path means the corpus is no longer the one a developer confirmed, so it reports `stale` in `changed_sources`. An edit inside a file that is still there is reported in `content_changed` and leaves the map current: whether a record's evidence survived that edit is a per-citation question `verify-evidence` answers exactly. A snapshot written before listings were recorded can only compare file counts, so a rename inside a directory it selects reaches the citation check instead. The map also keeps the discovery listing it was selected from, `source_groups`, which only tags citations with a source kind and is never evidence; `discovered_but_gone` names its entries that no longer exist, without changing the status. |
| Focus selected sources | `refine-sources --registry-root <root> --repo-root <repo> (--source <path>... \| --add <path>... --remove <path>...)` | Replaces a broad source corpus with focused paths, rebuilds snapshots, and resets selection to agent-asserted until a developer confirms it. `--source` gives the whole selection; `--add` and `--remove` change the current one and leave the rest selected, refusing to remove a path that is not selected. |
| Verify citations | `verify-evidence --registry-root <path> --repo-root <repo> [--path <file>]... [--strict]` | Detects missing, malformed, and changed structured evidence citations, each named by its record's asset and id and carrying the `cited_lines` it records. Before moving a block out of a file, compare the block with each citation's `cited_lines`: a citation inside the block will be found in the new file by `relocate-evidence --from <old file> --to <new file>`, and one outside it stays where it is, at most `shifted`. Statuses: `shifted` with the new `lines` when the excerpt is unchanged but moved within its file, which does not fail; `stale` when the cited lines changed since their digest was recorded; `unhashed` when no digest was ever recorded. `--path`, repeated, checks only the citations of those files and adds `paths`, each requested file with its number of citations and whether it `exists`, so a mistyped path is not read as an uncited file: run it on the files a change edits, before committing, to see whether any citation needs `recite`. `--strict` also fails on a `shifted` citation, so after a re-citation package is applied it shows that none is left. A failing run names the failing counts on stderr. |
| Upgrade legacy citations | `migrate-evidence --registry-root <path> --repo-root <repo>` | Converts only existing, in-repository `path:line` citations into digest-backed structured citations through a journaled update. |
| Verify audit trail | `verify-audit --registry-root <path> [--changes-root <dir>] [--against <git revision>]` | Validates the local append-only hash chain and its small head manifest; it is tamper-evident, not an external immutable log, so dropping the newest events and rewriting the manifest to match goes unseen by the chain alone. `--changes-root` also requires every applied proposal under the directory, including one superseded after it was applied, to have its `apply-approved-updates` event. `--against` compares with the manifest committed at that revision, the anchor a signed commit gives: the log must still hold that many events and end the committed prefix at the committed head, and a revision with no committed manifest anchors nothing and fails. A root without a Registry is `invalid`, not an empty valid chain. |
| Recover an interrupted update | `recover-registry-update --registry-root <path> [--repo-root <repo>] [--force]` | Uses the phase journal and matching audit operation to roll back or complete a transaction, and says whether there was one; `--force` is required only after confirming that a crashed writer left its lock behind. With `--repo-root` it also reconciles a pending apply: the audit log is the commit record, so a proposal it holds an apply for is marked applied, and a proposal it holds none for left the Registry unchanged and its marker is cleared, whatever the proposal's status. Without `--repo-root`, a pending apply that remains is an error. |
| Report Registry health | `probe --repo-root <repo> --registry-root <path> [--policy <path>]` | Says whether a Domain Memory is present, current, and how its sources were established. When the root has no source map but its parent does, it names the likely root instead of reporting nothing. It reports posture, not whether a record is true. |
| Validate the Registry | `validate --registry-root <path> [--repo-root <repo>] [--require-reviewed]` | Checks file shape, asset formats, status values, IDs, and references. `--require-reviewed` additionally refuses a Registry whose records are candidates or whose policy cannot establish a reviewed record at all. |
| Read the whole Registry from another tool | `export --registry-root <path> [--repo-root <repo> --commit <sha>]` | Prints every asset document as one JSON object keyed by asset name, as the working tree holds it or, with `--commit`, as that commit does. Read the Registry through this command, not its files: the files are the plugin's storage, and their layout may change. |
| See which modules change together | `change-coupling --repo-root <repo> [--root <path> ...] [--depth <n>] [--since <date>] [--exclude-subject <regex> ...] [--registry-root <root>] [--min-revisions 5] [--min-shared 5] [--min-degree 30] [--max-changeset 30] [--max-modules <n>]` | Reads the non-merge history and groups each changed file into the module `--depth` directories below the first `--root` that holds it (default `.` and 2), leaving out files directly in a root, files outside every root and modules that no longer exist. For each pair of modules it prints the commits they share and the degree, shared commits as a percentage of their average revisions, keeping a pair when both modules have `--min-revisions`, they share `--min-shared` commits and the degree reaches `--min-degree`. A commit touching more than `--max-changeset` files is skipped and counted, since a sweeping rename or format couples everything; with `--max-modules`, a commit touching more modules than that is skipped and counted in `skipped_sweeping_commits`, which catches a sweep of few files spread wide. A commit whose subject matches an `--exclude-subject` pattern, such as `^(chore|style|test)` (`test(` subjects are often sweeps too), is left out and counted in `excluded_commits`, because a repository-wide sweep couples modules that share no domain. Each pair lists the `subjects` of up to ten of its newest shared commits, so a reader can tell a domain change from a sweep, and with `--registry-root` it names the `contexts` whose `implementation_path` each module lies in, or `null` for code no Context owns, and `explained_by`: `contexts/<id>` when both modules lie in one Context, the interactions, contracts and dependency policies registered between their two Contexts, or nothing, so an empty list is the coupling the Registry does not account for. When a module lies in no Context, `explained_by` is `null`, since the Registry cannot speak for it, and `unmapped` names that module. |
| Score an extracted Registry | `compare-registry --gold-root <path> [--repo-root <repo> --gold-commit <sha>] --candidate-root <path> [--context <gold id> ...]` | Pairs each candidate record with at most one gold record and prints, per asset and overall, the pairs, the gold records missed, the candidate records with no counterpart, and precision, recall and F1. A Context pairs by its `implementation_path`: the same path (`path`), one ending with the other, as when one Registry writes it from the repository root and the other from a module (`path-suffix`), or one inside the other (`nested-path`); otherwise by name. Interactions and dependency policies pair when both of their Contexts pair. Any other record pairs by id or name, ignoring case and punctuation (a term also by a gold synonym, an aggregate by its root), or by naming a paired Context and citing a file the gold record cites; among those, the pair whose cited lines overlap most is taken first, so a record citing the same lines wins over one citing elsewhere in the file. `--context`, repeated, scores only the gold records of those Contexts: the Contexts themselves and the records naming one, for an extraction that covered part of the code; candidate records count only when they name a candidate Context paired with a scoped one, so an extraction of other code does not lower the precision. A Context the gold Registry lacks is refused, and `scope.without_candidate` names each scoped Context no candidate Context paired with, whose records therefore cannot pair. Each `overall_*` score carries its `matched`, `gold` and `candidate` counts, so a ratio over two records reads as such. `overall_attempted` scores only the assets both Registries hold records of, and is `null` when there are none; `overall_independent` scores the same assets with each `copied_evidence` pair left out of both sides, `copied_matches` counts those pairs, and a NOTE says so when they are more than half the matches. A pair other than a Context pair, whose evidence is usually the package documentation either side would cite, is marked `copied_evidence` when one side's cited files and excerpts are all among the other's, as when a harvest dropped a citation, since a blind extraction rarely cites exactly the gold lines. A score is `null` when its denominator is zero. It measures structure, not meaning: a rule worded differently but citing other lines counts as missed. `possible_pairs` lists each missed gold record whose wording shares at least a quarter of its words with an extra candidate in a paired Context, with the `similarity`, for a person to confirm; read it and the missed and extra lists before trusting a number. |
| Report modelling gaps | `coverage --registry-root <path>` | Lists Contexts holding no vocabulary, aggregate, rule, contract, or event, separating an examined absence from an unexamined one, and names every reviewed record that carries no evidence or cites outside the selected sources. |
| Build an evidence citation | `cite --repo-root <repo> --path <file> --start <line> --end <line> [--registry-root <path>] [--show]` | Produces the digest-backed citation object a record's `evidence` requires; pass the object whole, and the Registry keeps only its path, lines and `excerpt_sha256`. `--show` prints the first and last cited lines on stderr, so a range that starts mid-function or points at other code is seen before it is stored. When the cited text also occurs elsewhere in the file, it prints a NOTE on stderr naming where, because such a citation cannot be told apart after the next edit; widen it to lines that occur once. |
| Retrieve a record | `get-record --asset <asset> --id <id>` | Returns the exact stored record or fails. |
| Resolve vocabulary | `resolve-terms --query <text> [--query <text> ...] [--context <id>] [--with-mentions]` | Answers each query in order in one list, each match naming the `query` it answers; the result limit applies per query. Matches a Vocabulary record when its name, id or a synonym appears in the query, or the query appears in one of them or in its definition; a whole sentence is a valid query. Each match carries `match_kind` (`name`, `synonym` or `definition`), listed in that order. Only a `name` match grounds the term; a `synonym` match means the query used a name to avoid, and a `definition` match means no term has that name. When no term matches a query, or always with `--with-mentions`, it lists after the terms the reviewed records whose text holds every word of it, in any order and in another form of the word: any text field, any list of text such as `examples`, and the record's id read word by word, those whose id, name, responsibility, statement, definition or description mentions it first, rules and contracts before other assets, each record once with `match_kind: "mentioned"`, `authoritative: false`, and the `asset`, `id` and every `fields` entry that mentions it: the concept is talked about but has no term yet, which is a gap to record, not proof of who owns it. An empty answer means no reviewed record mentions it either, which still does not prove absence. A NOTE says when the result limit cut a query's matches, and when a matching term hid rules or contracts that mention the query. |
| Confirm the selected sources | `confirm-sources --registry-root <root> --repo-root <repo> --confirmed-by <identity>` | Moves the source map from `agent-asserted` to `developer-confirmed`, recording who and when in the audit chain. Refused without a named developer, and refused once the sources have moved. |
| Retrieve a Context model | `get-context --id <id> [--summary]` | Returns the Context with related vocabulary, aggregates, rules, contracts, and interactions, and `rules_bound_through_collaborations`: rules of other Contexts that cite a file one of this Context's interactions or contracts cites, such as the purge rule of the Context that runs this one's purge step, each with the collaborations it shares a file with. `--summary` gives each record as its id, status and one line, without evidence, for reading before a change. |
| Inspect a boundary | `analyze-boundary --source-context <id> --target-context <id>` | Lists registered direct interactions, contracts and dependency policies. `status` is `known` when an interaction or contract connects them, `policy_only` when only a dependency policy does, which permits the dependency but records no collaboration, and `no_registered_collaboration` otherwise. |
| Find boundaries a change touches | `boundary-impact --registry-root <root> --repo-root <repo> --base <git revision>` | Read-only. Lists the files changed since `base`, tracked or untracked, by the Context whose `implementation_path` holds them, matched as consecutive directory names anywhere in the path. For each pair of Contexts touched together it lists the registered interactions, contracts and dependency policies between them, and it lists the interactions, contracts and dependency policies whose evidence cites a changed file at lines that no longer match; a citation whose lines only moved within the file is not changed evidence. `verdict` is `unregistered-co-change`, `boundary-evidence-changed`, `registered-co-change`, `no-cross-context-change`, or `unknown` when no Context records an `implementation_path`. `outside_every_context` lists the changed files no Context owns, such as a composition root, which the verdict does not cover; `mapped_files` beside `changed_files` says how much of the change the verdict speaks for, and `cited_outside_contexts` names each of those files that a Registry record cites, such as a contract specification or a rule's proving test, with the records citing it. Changing together is a prompt to check, not proof of a dependency. |
| Search an asset | `lookup --asset <asset> --query <text>` | Deterministic file-backed text matching. A record holding the query as written comes first; otherwise the records holding every word of it, in any order and in another form of the word (`concurrent` finds `concurrency`, `licensing` finds `license`); otherwise the records holding the most of its words, with a NOTE saying so. Words such as `after`, `the` or `when` do not count as shared. When nothing holds any word, a NOTE says that this is not proof that no constraint applies, so read `get-context` for the Context being changed. |
| Add or revise a candidate | `upsert-candidate --registry-root <path> --repo-root <repo> --asset <asset> --record-file <file> [--record-file <file> ...]` | Validates a staged complete Registry and applies a recoverable update. Several record files are validated together and written in one update, so records that refer to each other can be added at once, and it says how many it created and how many it updated. A record whose cited excerpts are all among another record's of the asset, or the other way round, is noted as a possible duplicate, by the same test that marks `copied_evidence`. A citation with a path and lines but no digest gets the digests `cite` would give. |
| Harvest a scratch extraction | `harvest-candidates --registry-root <root> --repo-root <repo> --from-root <scratch root> [--context-map <candidate>=<gold> ...] [--keep-duplicates]` | Writes every record of a Registry extracted elsewhere, such as a blind extraction, into this one as candidates, in one update. It pairs the scratch Contexts with this Registry's the way `compare-registry` does, by `implementation_path` or name, and `--context-map` adds or overrides a pairing; a paired Context is not written, and every record naming it is written under the Context it paired with. A record whose id is reviewed here is skipped and listed in `skipped_reviewed`, and one citing exactly the excerpts of a reviewed record is skipped as a copy and listed in `skipped_duplicate` unless `--keep-duplicates`; citations without a digest get one. It prints the renames in `context_map`, every pairing in `context_pairs` with how it paired, `context_id_collisions` for a Context that pairs with the one of the same id here only by that id, not by path, what it `harvested`, `created` and `updated`, the files outside the confirmed sources, and `possible_duplicates`, reviewed or candidate records whose cited excerpts contain or are contained in a harvested record's. |
| Withdraw a candidate | `retract-candidate --registry-root <path> --repo-root <repo> --asset <asset> --id <id> --reason <text>` | Removes a candidate that examination rejected and records the reason in the audit chain. It refuses a reviewed record, which is withdrawn through a superseding proposal instead, and refuses a record the rest of the Registry still references. |
| Put a candidate into a draft proposal | `promote-candidate --package-root <path> --registry-root <path> --asset <asset> --id <id>` | Copies the candidate record, without its review fields, into the draft proposal's `registry_updates` as an upsert; promoting the same record again replaces its entry. The Contexts the record names are added to the proposal's `affected_contexts`. It refuses a record the Registry does not hold, a reviewed record, and a proposal that is no longer a draft. |
| Apply an approved change | `apply-approved-updates --package-root <path> --registry-root <path> --repo-root <repo>` | Requires a valid approved current Change Package and, through a recoverable update, promotes new or candidate records and removes records the proposal names — a reviewed record only when the proposal supersedes the one that reviewed it. Each promoted record has its citations classified against the selected sources, not the `source_kind` the author wrote, and one citing a path outside them is refused: a reviewed fact rests on a corpus a developer confirmed. |
| Start a Change Package | `init-change-package --output <path> [--requirement-id <id>] [--proposal-id <id>] [--proposer <identity>]` | Writes the requirement, proposal, obligation, and evidence templates a material change is reviewed through. Given the identifiers, it writes them into every file that carries them, so they never have to be copied by hand. Without them it prints the flags still blank, which `validate-change-package` will ask for. It refuses a proposal id that a package beside the output already carries, and a package it fails to finish is removed. |
| Package a re-citation | `init-change-package --output <path> --recitation <file> --registry-root <root> --requirement-id <id> --proposal-id <id> --proposer <identity>` | Takes what `recite` or `relocate-evidence` printed and writes a complete routine package: its `registry_updates` and `supersedes`, the affected Contexts the records name, a requirement that every citation is current, and one obligation whose `check` is the full `verify-evidence` command on the cited paths, ready to pass to `record-test-result --command`. Refused when any update changes a record beyond its citations, removes one, or when the file still carries candidates or unmatched citations, because then the change is not a re-citation. Review, approval and attestation run as for any package. |
| Validate a Change Package | `validate-change-package --package-root <path> --registry-root <path> [--repo-root <repo>]` | Requires each registry update to name a known asset, an obligation per acceptance criterion, rule, and contract, a named counterfactual check, and updates that reference existing assets; a Context, Rule or Contract the package itself adds counts as existing. Until the package is applied, it also validates the Registry as the updates would leave it and reports each new error prefixed `once applied:`, and with `--repo-root` it requires every citation in the updated records to be current and every file the ownership and boundary decisions cite as evidence to exist. A valid package with no `registry_updates` says so in a NOTE. An applied or superseded package is history: it is not checked against the Registry it has since been followed by. |
| Re-cite one changed citation | `recite --registry-root <root> --repo-root <repo> --asset <asset> --id <id> --path <path> [--lines <start>[-<end>]] [--replace <path>:<start>-<end>] [--onto <file>]` | Read-only. Cites the given lines and puts the citation in place of the record's one citation of `path`, or of the citation `--replace` names when the record cites a file more than once or the code moved to another file. Without `--lines`, it re-cites the lines `--replace` names, which must be in `path`; that is the case where the code changed but kept its lines. Prints the same shape as `relocate-evidence`: a reviewed record as `registry_updates` with the proposal to supersede, any other record as a candidate. Use it when code changed in place and `relocate-evidence` reports the citation unmatched. `--onto` takes the JSON an earlier `relocate-evidence` or `recite` printed: the record is re-cited from its version there, its entry is replaced, the `supersedes` are merged, the `unmatched` item it resolves is dropped, and the whole file is printed again, so a record with one shifted and one stale citation ends up as one update. When the cited text also occurs elsewhere in the file, it prints a NOTE on stderr naming where, because such a citation cannot be told apart after the next edit; widen it to lines that occur once. |
| Re-cite evidence after a move | `relocate-evidence --registry-root <root> --repo-root <repo> --from <old path> --to <new path>` | Read-only. For every citation under `from`, a file or a directory, finds the cited lines under `to` by their excerpt digest and re-cites them there. A citation whose lines are still in its own file, at the same place or moved within it, is left alone, so splitting a file re-cites only what left it. It prints `registry_updates` for the reviewed records, ready for a Change Package, `supersedes` with the proposals that reviewed them, `candidates` for records not yet reviewed, to pass to `upsert-candidate`, and `unmatched` for each citation whose lines were found zero times or more than once, with `found`, to cite by hand. |
| Preview the next stage | `validate-change-package --package-root <path> --registry-root <path> --as-status <submitted\|verified\|approved\|applied>` | Validates the package as if it had reached that stage and lists everything it still lacks there in one pass. Fields the stage's own command writes, such as `verified_at` or the base revision, are not asked for, and neither are approvals before `approved`, since they can be recorded only once the package is submitted; the success message says so. Run it before each transition instead of discovering the stage's requirements one refusal at a time. |
| Submit for review | `submit-proposal --package-root <path> --registry-root <path> --repo-root <repo>` | Captures the exact Git HEAD and Registry digest before changing a valid draft to `submitted`. |

| Retire a proposal | `supersede-proposal --package-root <path> --reason <text> [--superseded-by <id>]` | Keeps the status the proposal died in, its reason, and its replacement, rather than editing it back to a draft. |
| Redraft a retired proposal | `redraft-proposal --package-root <superseded> --output <path> --proposal-id <id>` | Copies a superseded package into an empty directory as a draft under a new id: every lifecycle field returns to its template value and the superseded fields are dropped, while the requirement, design, and obligations carry over. The draft lists the superseded proposal in `supersedes` and records `redrafted_at`. The command profile only labels the run and never expands into a command, so `--command` is the full invocation, such as `python3 <path>/registry_tools.py verify-audit --registry-root <root>`, not an obligation's shorthand. It records it for that obligation only when it exits 0, with the digest of its full output, replacing any earlier result for the obligation. A failing run, an unknown obligation, or a profile outside a non-empty `approved_command_profiles` writes nothing; an empty list approves any profile. |
| Attest a signed commit | `attest-signed-commit --package-root <path> --registry-root <root> --repo-root <repo> --commit <sha>` | For the `git-signed-commit` verifier: resolves the commit, checks that an authorized signer signed it and that it carries this proposal and revision, then writes `scm_attestation` from the proposal. |
| Audit past attestations | `audit-attestations --repo-root <repo> --changes-root <dir> [--verification-token-env <name>]` | Re-checks every approved or applied package under the directory and reports each as `carried`, `not carried` (the attested commit exists and lacks this proposal, or there is none), or `unconfirmed` (the commit is not in this clone, or the provider cannot be asked). | Verify test attestations | `verify-proposal --package-root <path> --registry-root <root> --repo-root <repo>` | Promotes only a submitted Proposal that every required approval role has approved and that has a passing, digest-backed result for every obligation; approvals can be recorded only while it is submitted, so it names any role still missing. ## Preparing the approval authority

A Registry initialized as `local-draft-only` produces candidates and nothing else; no command promotes a record until the policy names an authority that can be checked from outside the package. Two verifiers cover two situations; `discover-sources` recommends the one that fits the repository.

A repository whose pull requests are reviewed uses `github-pr`: the merged, approved, green pull request is the evidence, and `finalize-proposal` confirms it through the provider API, including that the pull request's head commit carries this Change Package with the same `proposal_id` and `proposal_revision`. This needs a reviewer other than the proposal's author, because a hosting provider does not let an author approve their own pull request.

A repository without that reviewer uses `git-signed-commit`: the maintainer signs the commit that carries the change, and the signature is the evidence. That commit must add this Change Package with the same `proposal_id` and `proposal_revision`, so a signature on an earlier commit cannot stand in for this proposal's review.

| Capability | Command | Machine guarantee |
| --- | --- | --- |
| Report what governance still needs | `governance-readiness --registry-root <path> --repo-root <repo>` | Names the missing pieces: no authorized signer, or no pre-push hook on this machine. A `local-draft-only` Registry reports working memory and needs nothing. |
| Prepare a signing identity | `init-signing-key --repo-root <repo> --principal <identity> [--key-file <path>] [--force] [--sign-every-commit]` | Creates or adopts an ed25519 key, writes the allowed-signers file the verifier reads, points Git at both, and reports the principal and fingerprint to authorize. It prints no private key material. When `DOMAIN_MEMORY_SIGNING_KEY` holds an OpenSSH private key it adopts that instead of generating one, so a container receives the identity as a secret; material it cannot derive a public key from is refused and the partial file removed. |
| Change governance fields | `amend-policy --registry-root <path> --field <field> --value <value> --reason <text> [--verifier <verifier>]`, or several fields at once with `--set <field>=<value>` repeated in place of `--field`/`--value` | Refuses a policy the validator rejects before writing, and appends the old value, new value, and reason of each field to the audit chain. Fields set together are applied as one change: only the final policy is validated, it is written once, and approvals go stale once, so a review mode and its verifier, trigger, and CI requirement move in one command. When `--set review_verifier=<verifier>` is among them, it serves as the verifier for leaving `local-draft-only`. Leaving `local-draft-only` requires `--verifier`, because a review mode and the authority behind it move together. `authorized_signers` takes a comma-separated list, so a lost key can be rotated out. Selected source paths and limits are settled at initialization and are not amendable. |
| Enforce signatures on push | `install-git-hitl-hook --registry-root <path> --repo-root <repo>` | Installs a pre-push hook in the directory Git actually runs, preserving any existing hook beside it and running that first. It checks every pushed commit that touches the Registry. A local hook is bypassable with `--no-verify` and absent on a machine that never installed it, so it is an early warning, not the trust boundary. |
| Check one commit's signature | `verify-git-governance --registry-root <path> --repo-root <repo> --commit <sha>` | Requires a valid signature whose principal or key fingerprint is authorized by the policy, and requires the commit to change Registry files. |
| Check a policy before adopting it | `validate-policy --policy <file>` | Reports every reason a policy would be refused, including a review mode and verifier that contradict each other. |
| Check SCM evidence alone | `verify-scm-attestation --attestation <file> --package-root <path>` | Checks a single attestation against its proposal without finalizing anything. |
| Withdraw local reviewed status | `demote-local-reviews --registry-root <path>` | Returns every reviewed record to candidate and strips its review metadata. Only a `local-draft-only` Registry accepts it: it is how a Registry retracts approvals that turned out not to be externally verifiable. |

Authorize a key by its fingerprint rather than its principal when the address it was created under may change. Both are reported by `init-signing-key` and either satisfies the check.

## Commands outside the lifecycle

No Skill instructs these. They serve setup, migration, and checks that stand on their own.

| Capability | Command | Machine guarantee |
| --- | --- | --- |
| Create an empty Registry skeleton | `init --output <path>` | Copies the asset templates and manifest into a new directory and refuses one that already holds files. It writes no policy and no source map, so the Registry it produces cannot establish a reviewed record at all. `init-domain-memory` is the entry point that records the choices a Registry needs. |
| Move a JSON Registry into concept files | `migrate-registry --registry-root <path>` | Moves a Registry kept as one JSON file per asset into one Markdown concept per record, creating any asset file the old Registry lacked first, and reports what it created. It refuses, changing nothing, when the concept files would not hold every record unchanged. On a Registry already in concept files it only refines records written by an earlier version: a `review` block becomes `verified`, with the proposal it named recorded in the audit log, and a citation loses the hashes and source kind it no longer stores. A Registry with nothing to refine is left as it is. |
| Re-snapshot the selected sources | `refresh-sources --registry-root <path> --repo-root <repo>` | Rebuilds the snapshots of the paths already selected and returns the selection to agent-asserted, so a developer confirms the sources again before they back reviewed records. |
| Scan for secrets | `scan-secrets --repo-root <repo>` | Reports findings, skipped paths, and how much was read. Exit 1 means it found something. Exit 2 means the scan was incomplete, so its silence proves nothing. |
| Check a contract schema file | `validate-contract --schema <file>` | Parses a local JSON schema file and reports `valid`, `invalid`, `missing`, or `unverified`; only `valid` exits 0. A contract it cannot parse locally is `unverified` rather than valid, because the command does not claim a result it did not compute. |

## Checks on the code being written

These need no Registry. They answer two questions an Agent otherwise answers from memory, and gets wrong.

| Capability | Command | Machine guarantee |
| --- | --- | --- |
| Find the repository's own checks | `quality-gates --repo-root <repo>` | Lists the lint, type, architecture, test, hook, and pipeline configuration it finds, each with its path, and counts the test files. A golangci-lint configuration with `depguard` settings is also an architecture gate, and each hook Git runs, read where `core.hooksPath` points, is a hook gate; a sample or a copy kept beside a hook is not. A hook the repository ships elsewhere, such as `.githooks/pre-push` before `core.hooksPath` points there, is a hook gate with `enabled: false`. `standard` is `configured` when a lint, type, or architecture check is configured and `none` otherwise. It reads configuration; it does not read a threshold, run a check, or confirm that a pipeline runs what is configured. |
| Break one protection and restore it | `counterfactual --repo-root <repo> --file <path> --find <text> --replace <text> --test-command <command> [--timeout <seconds>] [--cwd <directory>] [--expect <regex>] [--obligation-id <id>]` | Runs the command on the intact file and refuses when it does not pass. Replaces the one occurrence of the text, runs the command again, and restores the file byte for byte whatever the run did, retrying a restore the system refuses for a few seconds; one that still fails is an error naming the copy to restore from. `killed` exits 0: the tests failed on the broken file. `survived` exits 1: they still passed, so nothing protects that line. Every verdict carries a `reason`; a `survived` one says the change may not break the protection at all (an equivalent mutation) before you write a test for it; `inconclusive` exits 2 and its reason says why: the run did not finish in time, the broken code did not build (an unused variable or import, a syntax error), or, with `--expect`, the failure does not match the pattern. A killed run prints `counterfactual_check`, the object a Change Package's evidence records, naming `--obligation-id` or a placeholder to fill. |

`counterfactual` runs the command the caller passes, in the repository root or `--cwd`, with the caller's permissions, and like `record-test-result` without a shell: it is split by POSIX quoting rules, so a pipeline or several commands go in a script. It refuses text that is absent or occurs more than once, a file outside the repository, and any repository in which an earlier run left a `.counterfactual-original` copy, because that file may still hold a mutation every later proof would run against. Break a protection so the code still builds: in Go, `if ready && false {` keeps `ready` used where `if false {` would not compile. Two guards that cover each other each survive alone; each needs a test only it can satisfy. Read `failure_evidence` before trusting a `killed`: it starts with the output's failure lines, such as `--- FAIL:`, `FAIL:`, `ERROR:` or `panic:`, each with up to three lines indented under it, such as the assertion message, then its last part.

The commands that walk the repository — `discover-sources`, `readiness`, `quality-gates`, and the snapshots behind `confirm-sources`, `refresh-sources` and `verify-sources` — skip what is not the repository's own source. That means every directory named `.git`, `.hg`, `.svn`, `.devctl`, `node_modules`, `.venv`, `vendor`, `dist`, `build` or `generated`, and every path Git ignores. Discovery, `readiness` and `quality-gates` also skip a nested checkout (a directory holding its own `.git`), and snapshots skip symbolic links. `quality-gates` further leaves configuration inside `fixtures`, `__fixtures__` and `testdata` out of its gates and its test count. Only names inside the repository count, so a repository checked out under a directory called `build` is walked normally.

All command output is JSON except success or error messages. Registry-dependent commands require `--registry-root`; `readiness` may omit it when assessing a repository before Domain Memory exists. The scripts do not grant authorization: call a write command only when the current user and repository process authorize it.

For an update, include `registry_updates` in `domain-change-proposal.json`. Each update names an asset and uses `operation: "upsert"` with the complete record, or `operation: "remove"` with the `id` of a record the Registry holds. A removal is refused when no such record exists, so a mistyped id fails loudly instead of doing nothing, and the staged Registry is validated before the update lands, so a record the rest of the Registry still references cannot be removed. Submission records a deterministic digest of all standard Registry files plus the observed Git HEAD when available; verify, finalize and apply require that digest to remain current, or the records the proposal touches to be unchanged since it, as [proposal-lifecycle](proposal-lifecycle.md) describes. `verify-proposal` validates submitted test results as attestations; it does not run an arbitrary command from the package. The apply command validates the Change Package, then rejects an update that would overwrite or remove a reviewed record unless the proposal's `supersedes`, one proposal id or a list of distinct ids, names the exact proposal that reviewed it; a package that replaces records reviewed by several proposals lists them all. Naming that approval is what makes the replacement governed: the replacing proposal still carries its own approvals and SCM evidence, and one that names a different proposal, or none, is refused. This is how a reviewed record follows a domain that changed; a record whose cited line moved is corrected this way, not left stale.
