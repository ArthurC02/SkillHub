# File-backed Domain Memory API

`scripts/registry_tools.py` is the stable command entry point. It implements the read, query, and controlled update capability that a remote Domain Memory API would provide, using JSON files in the local repository.

The commands fall into two groups, which `registry_tools.py --help` lists too. Everyday commands are the seven-step workflow, harvest, review and reading. Advanced commands set up, govern, recover, migrate and measure: rarely run, still needed.

## Everyday commands

| Capability | Command | Machine guarantee |
| --- | --- | --- |
| Assess project readiness | `readiness --repo-root <repo> [--registry-root <path>]` | Reports the posture described in [readiness](readiness.md). It is read-only and never promotes a fact or selects a source corpus. With a Registry whose policy names a verifier, `governance_candidates` reports the `configured_verifier` and `configured_trigger` instead of recommending one. |
| Verify selected sources | `verify-sources --repo-root <repo> --source-map <path> [--policy <path>]` | Separates the selection moving from its content changing, and, when supplied, rechecks policy limits. A file appearing, disappearing or being renamed under a selected path means the corpus is no longer the one a developer confirmed, so it reports `stale` in `changed_sources`. An edit inside a file that is still there is reported in `content_changed` and leaves the map current: whether a record's evidence survived that edit is a per-citation question `verify-evidence` answers exactly. A snapshot without a listing can only compare file counts, so a rename inside a directory it selects reaches the citation check instead. The map also keeps the discovery listing it was selected from, `source_groups`, which only tags citations with a source kind and is never evidence; `discovered_but_gone` names its entries that no longer exist and `discovered_but_unlisted` names the paths discovery would place in a group today that the map does not list. When either is non-empty, stderr carries one `NOTE:` with both counts, and a map that would be `current` reports `discovery_drifted` instead, still with exit 0, because the listing is not evidence and a new file must not fail a gate; `stale` is never replaced, and the hash fields keep their own verdict. When `content_changed` is non-empty the NOTE also says how many selected sources changed inside and that `verify-evidence` checks the citations, because a confirmation covers which paths are sources, not their text. The NOTE of a `discovery_drifted` map points at `refresh-listing`, which needs no confirmation; the NOTE of a `stale` map points at `refresh-sources` then `confirm-sources`. |
| Verify citations | `verify-evidence --registry-root <path> --repo-root <repo> [--path <file>]... [--strict] [--staged]` | Detects missing, malformed, and changed structured evidence citations, each named by its record's asset and id and carrying the `cited_lines` it records. Statuses: `shifted` with the new `lines` when the excerpt is unchanged but moved within its file, which does not fail; `stale` when the cited lines changed since their digest was recorded; `unhashed` when no digest was ever recorded. `--path`, repeated, checks only the citations of those files and adds `paths`, each requested file with its number of citations and whether it `exists`, so a mistyped path is not read as an uncited file. `--strict` also fails on a `shifted` citation. `--staged` reads each cited file as the Git index holds it instead of from the disk, so it checks what the next commit will contain; a file the index does not hold as a regular file at stage 0 is `missing` and `exists` is false, and an index Git cannot read is refused. A failing run names the failing counts on stderr; with `--staged` it first prints one line per failing citation, `<asset>/<id>: <path>:<start>-<end> changed; check that its statement still holds; recite only if it does, otherwise amend it` for a `stale` one and `<asset>/<id>: <path> is not in this commit; relocate-evidence if it moved, otherwise amend or retire the record` for a `missing` one, which is also what a cited file deleted or renamed in the index becomes. When to run it, and what each status asks of you: [Evidence rules](evidence-rules.md). |
| Verify audit trail | `verify-audit --registry-root <path> [--changes-root <dir>] [--against <git revision>]` | Validates the local append-only hash chain and its small head manifest; it is tamper-evident, not an external immutable log, so dropping the newest events and rewriting the manifest to match goes unseen by the chain alone. `--changes-root` also requires every applied proposal under the directory, including one superseded after it was applied, to have its `apply-approved-updates` event. `--against` compares with the manifest committed at that revision, the anchor a signed commit gives: the log must still hold that many events and end the committed prefix at the committed head, and a revision with no committed manifest anchors nothing and fails. A root without a Registry is `invalid`, not an empty valid chain. |
| Report Registry health | `probe --repo-root <repo> --registry-root <path> [--policy <path>]` | Says whether a Domain Memory is present, current, and how its sources were established; a current selection whose files changed inside is reported with their count and `verify-evidence` named, and one whose discovery listing drifted is reported as `verify-sources` reports it, still with exit 0. When the root has no source map but its parent does, it names the likely root instead of reporting nothing. It reports posture, not whether a record is true. It exits 0 when the Domain Memory is `current`, 2 when it is `absent` (no source map at the root, with or without a likely root named), and 1 for any other status: `stale`, `invalid` or `unverified`. |
| Validate the Registry | `validate --registry-root <path> [--repo-root <repo>] [--require-reviewed]` | Checks file shape, asset formats, status values, IDs, and references. `--require-reviewed` additionally refuses a Registry whose records are candidates or whose policy cannot establish a reviewed record at all. A NOTE on stderr names each approved Change Package under the Registry's `changes/` directory that is not applied yet, and says how to retire one that cannot be, and another each superseded package whose `superseded_by` no package there carries. With `--repo-root` it also refuses a reviewed Context whose `implementation_path` lies over no file in the repository, by the same test `boundary-impact` uses to map a file to its Context, so a path left behind by a move is caught before an impact reads as clean; a candidate's is a NOTE, since a candidate may name code to come, and `ship-package` refuses to review it until the code is there. |
| Report modelling gaps | `coverage --registry-root <path> [--changes-root <dir>] [--repo-root <repo>]` | Lists Contexts holding no vocabulary, aggregate, rule, contract, or event, separating an examined absence from an unexamined one, and names every reviewed record that carries no evidence or cites outside the selected sources. `rules_by_context` gives every Context its `reviewed_rules` and `candidate_rules`, fewest reviewed first, so the Contexts a harvest should start from come first; a Context a rule names but the Registry lacks is listed too. With Change Packages, from `--changes-root` or the Registry's `changes/` directory, each row also lists the reviewed rules by proof: `proven` when a package that reviewed it covers it with a test obligation, `unproven` when none does, and `unknown` when a package that reviewed it since is not there to read; without them a NOTE says the proof was not counted. `rule_totals` counts each rule once, however many Contexts it names: `reviewed_rules`, `candidate_rules`, `contexts_without_reviewed_rules`, and, with Change Packages, `proven`, `unproven` and `unknown`. `--repo-root` is accepted so a script can pass the same flags everywhere, and is not used. |
| Build an evidence citation | `cite --repo-root <repo> --path <file> (--lines <start>-<end> | --start <line> --end <line> | --function <name>) [--registry-root <path>] [--show]` | Produces the digest-backed citation object a record's `evidence` requires; `--function` cites the whole body of the one Go `func` or Python `def` of that name in the file, such as the test that proves a rule, and refuses a name defined twice or not at all; pass the object whole, and the Registry keeps only its path, lines and `excerpt_sha256`. `--show` prints the first and last cited lines on stderr, so a range that starts mid-function or points at other code is seen before it is stored. When the cited text also occurs elsewhere in the file, it prints a NOTE on stderr naming where, because such a citation cannot be told apart after the next edit; widen it to lines that occur once. |
| Retrieve a record | `get-record --asset <asset> --id <id> [--changes-root <dir>]` | Returns the exact stored record or fails, naming up to three ids that start with or resemble the one given. A reviewed rule or contract also carries `proven_by`, read from `--changes-root` or, without it, the Registry's own `changes/` directory when there is one: each test obligation whose source or `also_covers` names it, from the most recent Change Package that reviewed it with such an obligation, so a later re-citation, which carries none, does not hide the proof (a NOTE names it), with the obligation's `check` and the `working_directory` its passing run was recorded in (`.` for the repository root). A NOTE says when the record was not reviewed through a package, or when that package is not under the directory, so the proof is unknown rather than absent. |
| Brief a change or a record | `brief --registry-root <root> --repo-root <repo> (--base <git revision> \| --asset <asset> --id <id>) [--markdown]` | Read-only. One document composed from `boundary-impact`, `dependents`, `get-context --summary` and `verify-evidence`. With `--base`: the verdict; each Context touched with its changed files and summarized model; each record of any asset whose cited lines the change touches, evidence and test citations alike, with its dependents, for a collaboration record whether its cited excerpt changed, and for a rule `check` and `cwd`: the test obligation that proves it in the applied Change Package under `<root>/changes`, or null when no package there proves it; `registry_changes`: each record the Registry gained, amended or lost between the base and the working tree (`change` is `added`, `amended` or `removed`), with its status, summary and `through`, the last proposal whose apply reviewed it, or null; the citation verification of the changed files; the cited files outside every Context, each with `cited_as`, the source kind of that path in the source map or null without one; `source_map`: `{"changed": false}` when `<root>/source-map.json` is the same at the base and in the working tree, otherwise `changed`, `confirmed_by`, `confirmation` and the counts `discovered_added` and `discovered_removed`; and `attention`, one line per thing a reviewer must act on. An unknown base is refused as `boundary-impact` refuses it. With `--asset --id`: the record, its Contexts, the records that reach it through relations, the verification of what it cites, and `attention`. `--markdown` renders the same brief for a pull request or a review note; the default is JSON. What `attention` lists: [brief](#brief). |
| Follow a record's relations | `dependents --asset <asset> --id <id>` | Read-only. Walks every relation from the record in both directions and lists each record reached with its `asset`, `status`, one-line `summary`, the `through` field that joined it and its `depth`. A Context is reached but not crossed, so the walk stays within the record's own coupling instead of spilling over everything in the Context. Before changing a record, this is what else the change may touch. |
| Resolve vocabulary | `resolve-terms --query <text> [--query <text> ...] [--context <id>] [--with-mentions]` | Answers each query in order in one list, each match naming the `query` it answers; the result limit applies per query. Matches a Vocabulary record when its name, id or a synonym appears in the query, or the query appears in one of them or in its definition; a whole sentence is a valid query. Each match carries `match_kind` (`name`, `synonym` or `definition`), listed in that order. Only a `name` match grounds the term; a `synonym` match means the query used a name to avoid, and a `definition` match means no term has that name. When no term matches a query, or always with `--with-mentions`, it lists after the terms the reviewed records whose text holds every word of it, in any order and in another form of the word: any text field, any list of text such as `examples`, and the record's id read word by word, those whose id, name, responsibility, statement, definition or description mentions it first, rules and contracts before other assets, each record once with `match_kind: "mentioned"`, `status: "reviewed"`, the `asset`, `id`, the `contexts` it names, a `summary` (the first sentence of its statement, definition, description or responsibility) and every `fields` entry that mentions it: the concept is talked about but has no term yet, which is a gap to record, not proof of who owns it. An empty answer means no reviewed record mentions it either, which still does not prove absence. A NOTE says when the result limit cut a query's matches, and when a matching term hid rules or contracts that mention the query. |
| Retrieve a Context model | `get-context --id <id> [--summary]` | Returns the Context with its vocabulary, aggregates, rules, capabilities and value objects, the contracts, interactions and events it produces or consumes, and `rules_bound_through_collaborations`: rules of other Contexts that cite a file one of this Context's interactions or contracts cites, such as the purge rule of the Context that runs this one's purge step, each with the collaborations it shares a file with. `--summary` gives each record as its id, status and one line, without evidence, for reading before a change. |
| Inspect a boundary | `analyze-boundary --source-context <id> --target-context <id>` | Lists what is registered between the two Contexts in each direction, so a call one way and a permission the other way are never read as one relation. `source_depends_on_target` holds the interactions and contracts the target produces for the source, the events of the target the source consumes, and the dependency policies from the source to the target; `target_depends_on_source` holds the same the other way round. `status` is `known` when an interaction, contract or consumed event connects them in either direction, `policy_only` when only a dependency policy does, which permits the dependency but records no collaboration, and `no_registered_collaboration` otherwise. |
| Find boundaries a change touches | `boundary-impact --registry-root <root> --repo-root <repo> --base <git revision>` | Read-only. Lists the files changed since `base`, tracked or untracked, by the Context whose `implementation_path` holds them, matched as consecutive directory names anywhere in the path. For each pair of Contexts touched together it lists the registered interactions, contracts and dependency policies between them, and it lists the interactions, contracts and dependency policies whose evidence cites a changed file at lines that no longer match; a citation whose lines only moved within the file is not changed evidence. `boundary_evidence_touched` lists those whose cited lines, as cited now, overlap a line the change added or rewrote, or lie in a new untracked file, with each `touched_evidence` as `path:start-end`: the change touches what the record cites even when the citation still matches. `verdict` is `unregistered-co-change`, `boundary-evidence-changed`, `registered-co-change`, `no-cross-context-change`, or `unknown` when no Context records an `implementation_path`. `outside_every_context` lists the changed files no Context owns, such as a composition root, which the verdict does not cover; `mapped_files` beside `changed_files` says how much of the change the verdict speaks for, and `cited_outside_contexts` names each of those files that a Registry record cites, such as a contract specification or a rule's proving test, with the records citing it. Changing together is a prompt to check, not proof of a dependency. |
| Search an asset | `lookup --asset <asset> --query <text>` | Deterministic file-backed text matching. A record holding the query as written comes first; otherwise the records holding every word of it, in any order and in another form of the word (`concurrent` finds `concurrency`, `licensing` finds `license`, `takedown` finds `taken down`, `take-down` and `TakedownAt`); otherwise the records holding the most of its words, with a NOTE saying so. Words such as `after`, `the`, `when`, `who` or `can` do not count as shared, and neither, in this last step, does a word held by more than a quarter of the records and at least three of them, such as `skill` in a Registry about skills: when only such words are shared, nothing is listed and a NOTE says so, since that list would be noise. When nothing holds any word, a NOTE says that this is not proof that no constraint applies, so read `get-context` for the Context being changed. |
| Add or revise a candidate | `upsert-candidate --registry-root <path> --repo-root <repo> --asset <asset> --record-file <file> [--record-file <file> ...]` | Validates a staged complete Registry and applies a recoverable update. Several record files are validated together and written in one update, so records that refer to each other can be added at once, and it says how many it created and how many it updated. A record whose cited excerpts are all among another record's of the asset, or the other way round, is noted as a possible duplicate, by the same test that marks `copied_evidence`. A citation with a path and lines but no digest gets the digests `cite` would give. |
| Prove and package harvested rules | `harvest --registry-root <root> --repo-root <repo> --spec <file> [--changes-root <dir>] [--through draft\|verified]` | One call per harvest from `--spec`, whose format is under [Harvesting](seven-step-workflow.md#harvesting-proven-rules-from-existing-code). It first cites the enforcing lines and the test function, refusing by path a citation outside the confirmed sources, then runs every counterfactual as one suite, and writes nothing unless each citation holds and each counterfactual is `killed` (`stopped_at` is `spec`, `citation` or `counterfactual` and `package` is null). It then writes each rule as a candidate, or marks a reviewed one `amended`, or `reproven` when only the proof is new, and builds the package under `<changes-root>/<name>`. `--through verified` goes on to submit, record each obligation's test result, record the approval and verify, stopping `tested` with the next step named when the spec has no approval. The report lists each rule's verdict, record outcome and test citation, `package`, `written`, `resumed`, `stopped_at`, `errors` and `next`, for a refusal as for a success; it exits 1 when a stage left errors. A directory holding something other than this spec's package is refused before any counterfactual runs (`stopped_at` `package`), and so is this spec's package once it is past `submitted`. A step that fails after the package is written is reported, not thrown: `written` is true, `stopped_at` is `draft`, `submitted` (test results pending), `tested` (every result recorded, approval or verification pending) or `verified`, and `next` names the resume. Running the same spec again over its own `draft` or `submitted` package resumes it with `resumed` true; a submitted package whose rules changed since is refused. What the harvest writes and what a resume skips: [Harvesting](seven-step-workflow.md#harvesting-proven-rules-from-existing-code). |
| Undo a harvest that did not finish | `discard-harvest --package-root <path> --registry-root <root> --repo-root <repo> --reason <text>` | Refuses a package whose proposal is not `draft`, `submitted` or `verified`, and a directory with no package, so a verified harvest that will not be shipped is undone the same way. Retracts, as `retract-candidate` does and with the reason, each record the package's `registry_updates` name that is still a candidate, except one that another package beside it, not superseded, also names; a reviewed record is left alone. Then removes the package directory and appends one `discard-harvest` audit event with the package path, the `retracted` and `kept` records and the reason, and prints it. |
| Withdraw a candidate | `retract-candidate --registry-root <path> --repo-root <repo> --asset <asset> --id <id> --reason <text>` | Removes a candidate that examination rejected and records the reason in the audit chain. It refuses a reviewed record, which is withdrawn through a superseding proposal instead, and refuses a record the rest of the Registry still references. |
| Put a candidate into a draft proposal | `promote-candidate --package-root <path> --registry-root <path> --asset <asset> --id <id> [--amend] [--repo-root <repo> (--cite <path>:<start>-<end> \| --cite-function <path>:<name>) ...]` | Copies the candidate record, without its review fields, into the draft proposal's `registry_updates` as an upsert; promoting the same record again replaces its entry. The Contexts the record names are added to the proposal's `affected_contexts`. It refuses a record the Registry does not hold, a reviewed record, and a proposal that is no longer a draft. With `--amend` a reviewed record is copied the same way and the proposal that last reviewed it, read from the audit log, is added to `supersedes`, so a rule can be re-proven or changed by editing its entry, such as adding the citation of the test that proves it; it refuses a reviewed record no applied package reviewed. `--cite` and `--cite-function`, each repeatable, add citations built as `cite` builds them to the promoted record's evidence, skipping one it already holds, so re-proving a rule needs no hand edit. |
| Start a Change Package | `init-change-package --output <path> [--requirement-id <id>] [--proposal-id <id>] [--proposer <identity>]`, or, to package a re-citation, `init-change-package --output <path> --recitation <file> --registry-root <root> --requirement-id <id> --proposal-id <id> --proposer <identity>` | Writes the requirement, proposal, obligation, and evidence templates a material change is reviewed through. Given the identifiers, it writes them into every file that carries them, so they never have to be copied by hand. Without them it prints the flags still blank, which `validate-change-package` will ask for. It refuses a proposal id that a package beside the output already carries, and a package it fails to finish is removed. With `--recitation` it takes what `recite` or `relocate-evidence` printed and writes a complete routine package: its `registry_updates` and `supersedes`, the affected Contexts the records name, a requirement that every citation is current, and one obligation whose `check` is the full `verify-evidence` command on the cited paths, ready to pass to `record-test-result --command`. Refused when any update changes a record beyond its citations, removes one, or when the file still carries candidates or unmatched citations, because then the change is not a re-citation. Review, approval and attestation run as for any package. |
| Validate a Change Package | `validate-change-package --package-root <path> --registry-root <path> [--repo-root <repo>] [--as-status <submitted\|verified\|approved\|applied>]` | Prints a NOTE when a counterfactual mutates a file the rules its obligation proves do not cite, since that proves the rule only when the mutated line lies on the execution path of a cited line. Requires each registry update to name a known asset, an obligation per acceptance criterion, rule, and contract, a named counterfactual check, and updates that reference existing assets; a Context, Rule or Contract the package itself adds counts as existing. Until the package is applied, it also validates the Registry as the updates would leave it and reports each new error prefixed `once applied:`, and each promoted record that cites a path outside the confirmed sources, and with `--repo-root` it requires every citation in the updated records to be current and every file the ownership and boundary decisions cite as evidence to exist. A valid package with no `registry_updates` says so in a NOTE. An applied or superseded package is history: it is not checked against the Registry it has since been followed by. With `--as-status` it validates the package as if it had reached that stage and lists everything it still lacks there in one pass. Fields the stage's own command writes, such as `verified_at` or the base revision, are not asked for, and neither are approvals before `approved`, since they can be recorded only once the package is submitted; the success message says so. Run it before each transition instead of discovering the stage's requirements one refusal at a time. |
| Re-cite one changed citation | `recite --registry-root <root> --repo-root <repo> --asset <asset> --id <id> --path <path> [--lines <start>[-<end>]] [--replace <path>:<start>-<end>] [--onto <file>]` | Read-only. Cites the given lines and puts the citation in place of the record's one citation of `path`, or of the citation `--replace` names when the record cites a file more than once or the code moved to another file. Without `--lines`, it re-cites the lines `--replace` names, which must be in `path`; that is the case where the code changed but kept its lines. Prints the same shape as `relocate-evidence`: a reviewed record as `registry_updates` with the proposal to supersede, any other record as a candidate. Use it when code changed in place and `relocate-evidence` reports the citation unmatched. `--onto` takes the JSON an earlier `relocate-evidence` or `recite` printed: the record is re-cited from its version there, its entry is replaced, the `supersedes` are merged, the `unmatched` item it resolves is dropped, and the whole file is printed again, so a record with one shifted and one stale citation ends up as one update. When the cited text also occurs elsewhere in the file, it prints a NOTE on stderr naming where, because such a citation cannot be told apart after the next edit; widen it to lines that occur once. |
| Re-cite evidence after a move | `relocate-evidence --registry-root <root> --repo-root <repo> --from <old path> --to <new path>` | Read-only. For every citation under `from`, a file or a directory, finds the cited lines under `to` by their excerpt digest and re-cites them there. A citation whose lines are still in its own file, at the same place or moved within it, is left alone, so splitting a file re-cites only what left it. It prints `registry_updates` for the reviewed records, ready for a Change Package, `supersedes` with the proposals that reviewed them, `candidates` for records not yet reviewed, to pass to `upsert-candidate`, and `unmatched` for each citation whose lines were found zero times or more than once, with `found`, to cite by hand. A Context whose `implementation_path` is `from`, lies under it, or ends `from` the way `boundary-impact` maps a file to it (the Registry holds `billing/orders`, `from` is `src/billing/orders`) is given its new path in the same output, the same trailing parts of `to`, as a registry update or a candidate by its status. `citations_in_place` counts the citations under `from` whose lines stayed in their own file; when nothing needed moving a NOTE says so, and when `to` holds no file a NOTE names the Contexts whose proposed path review would refuse. |
| Submit for review | `submit-proposal --package-root <path> --registry-root <path> --repo-root <repo>` | Captures the exact Git HEAD and Registry digest before changing a valid draft to `submitted`. Refuses an obligation whose check runs `go test` without `-v` or `-json`, which `record-test-result` could not record, and a promoted record citing a path outside the confirmed sources, which `ship-package` would refuse to review, so the refusal comes before approval and the signed commit. |
| List the Change Packages | `list-proposals --changes-root <dir>` | Prints each package under the directory with its `proposal_id`, `status`, `last_changed_at` (the latest lifecycle timestamp, including a redraft and a supersession; `null` for a draft never submitted), number of `registry_updates` and `supersedes`, and a superseded proposal's `superseded_by`, with `superseded_by_unknown` when no package under the directory carries that id, `supersedes_unknown` listing the ids it supersedes that no package carries, such as deleted or mistyped ones, and `duplicate_proposal_id` on packages sharing an id, so a stale draft or an empty one is found without opening each. |
| Retire a proposal | `supersede-proposal --package-root <path> --reason <text> [--superseded-by <id>]` | Keeps the status the proposal died in, its reason, and its replacement, rather than editing it back to a draft. When no package beside it carries the `--superseded-by` id yet, a NOTE says to create it with `redraft-proposal`, and `validate` names the proposal until one does. It and `redraft-proposal` accept `--registry-root` and `--repo-root` so a script can pass the same flags to every lifecycle command, and use neither. |
| Record human approval | `record-approval --package-root <path> --role <role> --reviewer <identity> --scope <scope> [--approved-at <ISO-8601>]` | Rejects self-approval and duplicate approval for the same role and revision. |
| Record a test result | `record-test-result --package-root <path> --registry-root <root> --repo-root <repo> --obligation <id> [--command "<command>"] --command-profile <profile> [--timeout <seconds>] [--cwd <directory>]` | Runs the obligation's `check`, or `--command` when it is that check with other spacing, while the proposal is draft or submitted, from the repository root, or from `--cwd`, a directory inside the repository recorded as the result's `working_directory`, without a shell, split into arguments by POSIX quoting rules on every platform, so `^`, `|` and `$` reach the program unchanged and pipes, `&&` and `VAR=value` prefixes are not available; set environment variables before calling it, and quote a Windows path that holds backslashes. The command profile only labels the run and never expands into a command, so the check is the full invocation, such as `python3 <path>/registry_tools.py verify-audit --registry-root <root>`, not a shorthand. It records it for that obligation only when it exits 0 and a test passed, with the digest of its full output, replacing any earlier result for the obligation. A run that passed no test writes nothing: `go test` without `-v` or `-json`, because it does not say which tests passed, or with every test skipped; output saying `[no tests to run]`; unittest that ran nothing or skipped every test; a pytest summary without `passed`. A failing run, a command other than the check, a proposal past submitted, an unknown obligation, or a profile outside a non-empty `approved_command_profiles` writes nothing; an empty list approves any profile. |
| Attest, finalize and apply a verified package | `ship-package --package-root <path> --registry-root <root> --repo-root <repo> [--commit <sha>] [--verification-token-env <name>]` | The tail of a review after its verification, in one call and in three steps, in order. With `--commit`, the `attest-signed-commit` step, for the `git-signed-commit` verifier, resolves the commit, checks that an authorized signer signed it and that it carries this proposal and revision, then writes `scm_attestation` from the proposal. The `finalize-proposal` step approves only a verified proposal whose required approval roles, externally verifiable SCM evidence, traceability and base revision still validate. The `apply-approved-updates` step, through a recoverable update, promotes new or candidate records and removes records the proposal names, a reviewed record only when the proposal supersedes the one that reviewed it; each promoted record has its citations classified against the selected sources, not the `source_kind` the author wrote, and one citing a path outside them is refused. Without `--commit` it starts at `finalize-proposal`, for the `github-pr` verifier. ## Preparing the approval authority

A Registry initialized as `local-draft-only` produces candidates and nothing else; no command promotes a record until the policy names an authority that can be checked from outside the package. Two verifiers cover two situations; `discover-sources` recommends `github-pr` when it finds that provider's pipeline directory, `.github/workflows`, and `git-signed-commit` with the `git-push` trigger for every other repository, since the pull-request verifier reads one hosting provider's API.

A repository whose pull requests are reviewed uses `github-pr`: the merged, approved, green pull request is the evidence, and `ship-package` confirms it through the provider API, including that the pull request's head commit carries this Change Package with the same `proposal_id` and `proposal_revision`. This needs a reviewer other than the proposal's author, because a hosting provider does not let an author approve their own pull request. For `github-pr`, fill `scm_attestation` in the evidence bundle from [scm-attestation.json](../templates/scm-attestation.json) once the pull request merges.

A repository without that reviewer uses `git-signed-commit`: the maintainer signs the commit that carries the change, and the signature is the evidence. That commit must add this Change Package with the same `proposal_id` and `proposal_revision`, so a signature on an earlier commit cannot stand in for this proposal's review.

Authorize a key by its fingerprint rather than its principal when the address it was created under may change. Both are reported by `init-signing-key` and either satisfies the check.

## Checks on the code being written

`quality-gates` and `counterfactual` need no Registry. They answer two questions an Agent otherwise answers from memory, and gets wrong.

`counterfactual` runs the command the caller passes:

- in the repository root or `--cwd`, with the caller's permissions;
- like `record-test-result`, without a shell: the command is split by POSIX quoting rules, so a pipeline or several commands go in a script.

It refuses:

- text that is absent or occurs more than once;
- a file outside the repository;
- any repository in which an earlier run left a `.counterfactual-original` copy, because that file may still hold a mutation every later proof would run against.

Reading a result:

- Break a protection so the code still builds: in Go, `if ready && false {` keeps `ready` used where `if false {` would not compile. A broken file that does not build, such as an unused variable or import or a syntax error, is `inconclusive`.
- Two guards that cover each other each survive alone; each needs a test only it can satisfy.
- Read `failure_evidence` before trusting a `killed`: it starts with the output's failure lines, such as `--- FAIL:`, `FAIL:`, `ERROR:` or `panic:`, each with up to three lines indented under it, such as the assertion message, then its last part.
- `inconclusive` means the run did not finish in time, the broken code did not build (whatever `--expect` matches), or, with `--expect`, the failure does not match the pattern.
- `killed` means the tests failed on the broken file. `survived` means they still passed, so nothing protects that line; its `reason` says the change may not break the protection at all (an equivalent mutation), which to rule out before you write a test for it.
- A run that judges nothing can kill nothing: `go test` without `-v` or `-json`, a unittest run of 0 tests or every test skipped, and a pytest run in which nothing passed are refused on the intact file and `inconclusive` on the broken one.
- `failing_tests` names the tests that failed on the broken file, read from `go test -v` or `-json`, where a subtest is named by its top-level test, pytest and unittest output, so a broad test command answers which test proves the protection; it is empty for any other runner.
- A restore the system refuses is retried for a few seconds before it is an error.
- Every refusal exits 3 with the same JSON shape, so a script never takes a refusal for `survived` or a usage mistake for `inconclusive`.

Output follows three cases:

- A command that answers a question (`lookup`, `get-context`, `export`, `verify-evidence`, `quality-gates` and the other reads) prints JSON on stdout, except `probe`, which prints one sentence, and `brief --markdown`, which prints Markdown. `validate`, `validate-policy`, `validate-change-package`, `verify-scm-attestation` and `verify-git-governance` print their verdict on stdout, or one `ERROR:` line per problem on stderr.
- A command that writes (`upsert-candidate`, `submit-proposal`, `init-domain-memory` and the other changes) prints what it did as text on stdout, except `harvest`, `harvest-candidates`, `discard-harvest`, `rebase-proposal`, `ship-package`, `migrate-registry`, `migrate-evidence`, `discover-sources` and `init-signing-key`, which print JSON. A refused step of `harvest` or `ship-package` sits in its report's `errors`, and the command exits 1.
- Every other refusal prints `ERROR: <reason>` on stderr and exits 1, so stdout carries only the command's output.

Three things fall outside these cases: a refused `counterfactual` prints JSON and exits 3, because 1 means `survived` and 2 `inconclusive`; a usage mistake, such as an unknown option or an empty query, exits 2 with argparse's message on stderr, and `probe` also exits 2, with its sentence on stdout, when the root holds no source map; and every `NOTE:` goes to stderr. Output is UTF-8 with line feeds on every platform, and a path a report shows, such as a package outside the repository, is a posix path on every platform.

The commands that walk the repository — `discover-sources`, `readiness`, `quality-gates`, and the snapshots behind `confirm-sources`, `refresh-sources` and `verify-sources` — skip what is not the repository's own source. That means every directory named `.git`, `.hg`, `.svn`, `node_modules`, `.venv`, `vendor`, `dist`, `build` or `generated`, and every path Git ignores. Discovery, `readiness` and `quality-gates` also skip a nested checkout (a directory holding its own `.git`), and snapshots skip symbolic links. `quality-gates` further leaves configuration inside `fixtures`, `__fixtures__` and `testdata` out of its gates and its test count. Only names inside the repository count, so a repository checked out under a directory called `build` is walked normally. Every git and ssh-keygen call gives up after 15 seconds, or after the number of seconds in `DOMAIN_MEMORY_GIT_TIMEOUT`; the limit is per call, so a command that runs git several times can wait several times that. The refusal names the variable and, when the command had written nothing, says that running it again is safe. On timeout the whole process tree the call started is stopped, through a job object on Windows and the process group elsewhere. A hook the plugin installs exports `git config domain-memory.git-timeout` as that variable when the environment does not set it, so a slow machine sets the limit once with `git config --global domain-memory.git-timeout 60`.

Registry-dependent commands require `--registry-root`; `readiness` may omit it when assessing a repository before Domain Memory exists. The scripts do not grant authorization: call a write command only when the current user and repository process authorize it.

The shape of an update:

- Include `registry_updates` in `domain-change-proposal.json`. Each update names an asset and uses `operation: "upsert"` with the complete record, or `operation: "remove"` with the `id` of a record the Registry holds.
- `verify-proposal` validates submitted test results as attestations; it does not run an arbitrary command from the package.

Removal:

- A removal is refused when no such record exists, so a mistyped id fails loudly instead of doing nothing.
- The staged Registry is validated before the update lands, so a record the rest of the Registry still references cannot be removed.

The base revision:

- Submission records a deterministic digest of all standard Registry files plus the observed Git HEAD when available, and, when that commit holds a Registry, the digest of the Registry it holds as `committed_digest`, from which a later check rebuilds the base.
- Verify, finalize and apply require that digest to remain current, or the records the proposal touches to be unchanged since it, as [proposal-lifecycle](proposal-lifecycle.md) describes.

Replacing a reviewed record:

- The apply command validates the Change Package, then rejects an update that would overwrite or remove a reviewed record unless the proposal's `supersedes`, one proposal id or a list of distinct ids, names the exact proposal that reviewed it; a package that replaces records reviewed by several proposals lists them all.
- Naming that approval is what makes the replacement governed: the replacing proposal still carries its own approvals and SCM evidence, and one that names a different proposal, or none, is refused.
- This is how a reviewed record follows a domain that changed; a record whose cited line moved is corrected this way, not left stale.

## Notes on single commands

### `brief`

`brief` is the one document to read before reviewing a change or touching a record.

- A Registry absent at the base lists every record as added in `registry_changes`.
- The `confirmation` of `source_map` is its `selection_status` now, or `removed`.
- `attention` holds one line per asset and reviewing proposal of the records the range changed.
- It holds one line when the source map changed, naming who confirmed it or that it is not confirmed.
- It holds one line per cited file outside every Context, except a file whose kind is `tests`, which only proves a rule and is listed without one.

### `install-pre-commit-hook`

- A path mentioned only in prose or in a Change Package does not count as a citation or source path, so the hook stops at its first check for it.
- The hook refuses on `missing` as well as `stale`, so deleting a cited file, or renaming it to a name nothing cites, stops the commit like a weakened line does; the line for a `missing` citation says the path is not in this commit and points at `relocate-evidence`.
- It checks the staged content, so a file staged in part, or restored on disk after staging, is checked as the commit will hold it.
- The hook it chains to is found through Git at run time, so it runs from a linked worktree too; the pre-push hook finds its chained hook the same way.
- Where `core.hooksPath` names a tracked directory, the installed hook is a committed file that changes every clone's commits, so installing it there is a decision for the repository owner, not a local convenience.

### `mcp-serve`

- A result carries `resultType` only when the request declared its version in `_meta`; a session negotiated through `initialize` gets the plain result shape, which strict clients of those revisions require.
- Under 2026-07-28 the `server/discover` and `tools/list` results carry the caching hints that revision requires, `ttlMs` 300000 and `cacheScope` `public`, because the tool list holds no user-specific data.
- It keeps no session: it answers requests sent before `initialize` and accepts a repeated `initialize`.
