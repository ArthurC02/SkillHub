# ADR-013：意圖搜尋採混合檢索與索引時 LLM 增強

- 狀態：**Accepted**（2026-08-14 定案；原定案條件「PDM-011 Spike 結果、PDM-001 首批類別確認」皆已滿足，見文末「定案紀錄」）
- 日期：2026-08-13（提出）／2026-08-14（定案）
- 決策者：產品負責人、架構規劃

## 背景

DISC-001 要求使用者以任務描述搜尋 Skill，並顯示每個候選的符合原因。這是產品風險表的第一條（搜尋結果多但難以選擇），也是整條漏斗的入口。

限制條件：

- 使用者的任務語言與 `SKILL.md` 的技術詞彙往往不重疊，純關鍵字比對召回率差。
- NFR-004 要求已索引內容搜尋 p95 小於 2 秒，排除每次查詢都讓 LLM 閱讀候選內容的作法。
- 初期語料很小（三個類別、每類少量精選 Skill），不需要獨立搜尋引擎的規模。
- 搜尋索引依 ADR-003 是可重建投影，不是事實來源。

## 評估選項

### 選項 A：純全文檢索（BM25 / Postgres FTS）

- 優點：實作最簡單、延遲最低、無模型成本。
- 缺點：任務描述與 Skill 內容詞彙不重疊時召回率差，正是本產品的核心查詢型態；無法生成有意義的符合原因。

### 選項 B：純向量檢索（Embedding）

- 優點：語意相近查詢召回好；語料小，嵌入成本可忽略。
- 缺點：無法精確過濾結構化條件（來源層級、是否含 Script、驗證狀態）；對精確名稱／工具查詢反而不如 BM25；分數無法直接解釋為符合原因。

### 選項 C：查詢時 LLM 即時閱讀候選並排序

- 優點：品質上限最高，符合原因最自然。
- 缺點：每次查詢的延遲與成本最高，違反 NFR-004；未登入搜尋開放時成本不可控。

### 選項 D：混合檢索＋索引時 LLM 增強（建議）

把 LLM 成本移到索引時（每個 Skill Version 一次），查詢時只做輕量處理。

## 決策

採選項 D，分三段：

### 1. 索引時增強（每個 Skill Version 執行一次）

- LLM 讀取 `SKILL.md` 與套件結構，生成：任務導向白話摘要、適用任務範例句、輸入／輸出／工具／依賴標籤。
- 產出寫入 Skill Search Document（ADR-003 的可重建投影），連同 Embedding 一併保存。
- 生成內容標示為模型產出，錯誤可由人工修正並觸發重建。

### 2. 查詢時檢索

- 輕量 LLM 查詢改寫：使用者意圖 → 任務關鍵詞＋結構化過濾條件；改寫失敗或逾時直接用原句降級。
- 混合檢索：pgvector 向量相似度＋Postgres FTS（BM25）以 RRF 融合。
- 規則過濾與排序調整：來源層級、驗證狀態、相容性（DISC-002 的可解釋排序）。

### 3. 符合原因生成

- 預設由命中欄位以模板生成（「此 Skill 宣告支援＿＿，與你的＿＿需求相符」），零額外延遲。
- Top-N 結果可選 LLM 潤飾；逾時或失敗降級為模板版本，不阻塞回應。

### 搜尋基礎設施

初期使用 PostgreSQL（pgvector + FTS）承載，不引入獨立搜尋引擎。拆分觸發條件依 ADR-010：搜尋規模或查詢演進速度成長時再評估 Elasticsearch／Typesense 等專用引擎；因索引是可重建投影，遷移不涉及事實來源。

## 驗證方式

- PDM-011 Spike：每個首批類別建立至少 20 條任務描述的 golden query set，量測 recall@5 與符合原因可理解性；Spike 不通過則回到本 ADR 重新評估選項。
- p95 延遲量測涵蓋查詢改寫降級路徑。
- 索引重建流程可從 Skill Version 事實來源完整重生 Search Document。

## 影響

### 正面

- LLM 成本與 Skill 數量成正比而非查詢量，未登入搜尋可負擔。
- 符合原因有真實依據（命中欄位），不是事後編造。
- 全部落在 PostgreSQL 內，MVP 不新增基礎設施產品。

### 成本與限制

- 索引時增強的品質決定搜尋上限，需要人工抽查機制。
- 查詢改寫與潤飾引入兩個降級路徑，需明確逾時與 fallback 行為。
- Embedding 模型更換需全量重建索引（語料小，成本可接受）。

## 定案紀錄（2026-08-14）

負責人於 2026-08-14 批准 M0 全部產出並指示開工。本 ADR 依 [PDM-011 意圖搜尋品質 Spike 報告](../plans/mvp/m0/pdm-011-spike-report.md)（v1 ＋ v2 真 Embedding 重測）定案：**維持選項 D（混合檢索＋索引時 LLM 增強），狀態由 Proposed 轉 Accepted。**

Spike 沒有推翻選項 D，也沒有任何證據支持選項 A／B／C 更好（選項 C 仍違反 NFR-004）。但實測結果調整了三段式作法內部的權重，以下四項為**定案時併同採納的實證調整**，優先於上方「決策」章節同題敘述（原文保留為決策歷史，不原地改寫）：

| # | 實證調整 | 依據 |
| --- | --- | --- |
| 1 | **向量腿是跨語言召回的承載者。** 繁中原樣查詢對英文 `SKILL.md` 語料，`text-embedding-3-small` 的 Top-3 召回 5/5（100%）、Top-1 4/5（80%）；同組查詢的 BM25 腿 Top-3 僅 20%。四條與正解**詞彙交集為零**的中文查詢全部由向量腿召回，其中三條為 Top-1 | Spike §9.2、§9.3 |
| 2 | **查詢改寫是 Top-1 精準度的增益步驟，不是召回的必要條件；降級目標是向量檢索，不是原句 FTS。** 上方「決策 §2」的「改寫失敗或逾時直接用原句降級」維持有效，但**必須明確：降級後的原句一定要進向量檢索，只走 FTS 是真正的失效路徑**。改寫把 Top-1 由 80% 補到 100%，逾時即砍是可接受的降級，不是品質懸崖——這也降低了 NFR-004 的延遲風險 | Spike §9.4-1（修訂 v1 §6.2-1） |
| 3 | **RRF 只是召回覆蓋手段，不是排序品質來源；零命中的腿不得參與融合。** 同質腿與異質腿兩次量測都顯示等權 RRF 無增益，異質腿下還會倒退。混合檢索的價值在於「某一腿失效時另一腿仍有結果」。加權融合或依查詢語言動態調權列為後續優化，**不是 MVP 首發假設**。量測缺陷佐證：把零命中腿的字母序排名餵進融合會使 Top-1 由 8/10 假性下滑到 6/10 | Spike §9.4-3、§9.5 |
| 4 | **索引時的 LLM 摘要與「適用任務範例句」是必要項，不是 nice-to-have。** (a) 摘要須涵蓋內文能力、不可只複製 frontmatter（frontmatter 過簡的 Skill 會因資訊不足掉名次），其理由改為「跨語言表現較好、規避 Embedding token 上限、降低成本與重算量」，而非上方原寫的「長文件擠掉正解」（該理由在向量腿上不成立）；(b) 無詞彙交集的命中是真實系統的主流情境，模板式符合原因在這些案例**完全產不出內容**，必須靠索引時生成的範例句支撐 | Spike §9.4-2、§9.4-4 |

**定案時已知、但不阻擋定案的未驗證項**（轉為 M1 實作期的驗證工作，不是本 ADR 的定案條件）：

- 索引時摘要生成、查詢改寫、符合原因潤飾三者在 Spike 中仍為模擬，未呼叫真 LLM；查詢改寫以人工英譯代表，是品質**上界**。
- Spike 直接呼叫供應商 API，**未經 LiteLLM 閘道**；產品實作不得比照（AGENTS.md 鐵律 8、ADR-017）。
- p95 延遲（NFR-004 < 2 秒）含改寫呼叫的端到端量測尚未進行，待基礎設施就緒（ADR-018）。
- 語料 12 份、查詢 10 條，統計意義薄弱；完整 golden query set 見下方待決策回填。
