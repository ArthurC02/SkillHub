## 2. 量化判準

### 2.1 四條判準

| 判準 | 計算式 | 門檻 | 實測 | 判定 |
| --- | --- | --- | --- | --- |
| **G1** 題次通過率 | `N_pass / N_eff` | ≥ 70% | ⬜／⬜ = ⬜% | 通過／不通過 |
| **G2** 達標人數 | 個人通過率 ≥ 60% 的人數 ÷ 人數 | ≥ 2/3 | ⬜／9 | 通過／不通過 |
| **G3** 干擾認同率 | `N_g3 / N_dist_eff` | ≥ 75% | ⬜／⬜ = ⬜% | 通過／不通過 |
| **G4** 否決檢查 | 任一類別 < 50%？任一層全員 < 60%？ | 皆否 | ⬜ | 觸發／未觸發 |

**四條全過 ⇒ 閘門通過。** 任一條不過 ⇒ §4。

### 2.2 邊界判讀

- G1 落在 **68%～72%**（±1 題）：**不得只憑數字下結論**。逐筆檢查該區間內每個 `fail_*`，連同 §3 的質性證據判；仍無法收斂則補 3 場（每層 1 人）重算。
- 任一判準的分母不足滿樣本 80%：結論降級為「未確定」。

### 2.3 失敗型態分布（決策樹的主要輸入）

| `outcome` | 題次 | 佔 `N_eff` |
| --- | --- | --- |
| `pass` | ⬜ | ⬜% |
| **`fail_not_found`**（gold 不在 Top-5） | ⬜ | ⬜% |
| **`fail_no_reason`**（找到但理由非 `on_screen`） | ⬜ | ⬜% |
| `fail_timeout` | ⬜ | ⬜% |

**兩個交叉數**（比上表更有指向性）：

| 交叉 | 題次 | 指向 |
| --- | --- | --- |
| **X-A**：`gold_in_top5 = Y` 且 `picked_is_gold = N` | ⬜ | **答案就在畫面上但沒被選中** → 呈現問題 |
| **X-B**：`picked_is_gold = Y` 且 `reason_source` ≠ `on_screen` | ⬜ | **選對了但說不出畫面上的理由** → 呈現或內容問題 |

**改寫次數分布**（`fail_not_found` 的補充訊號）：

| 改寫次數 | 0 | 1 | 2 | 3（判失敗） |
| --- | --- | --- | --- | --- |
| 題次 | ⬜ | ⬜ | ⬜ | ⬜ |
| 其中 `pass` | ⬜ | ⬜ | ⬜ | — |

> 若「改寫 1 次後就 `pass`」佔比很高，代表**第一次打字與索引之間有系統性落差**——這正是查詢改寫（ADR-013 §2，尚未上線）要解決的事，屬搜尋問題但**已有既定解法**。

## 3. 質性主題整理

### 3.1 材料

- 全部 `reason_quote`（上限 45 條）
- 全部 `friction_quote`
- 收尾訪談 4 題 × 9 人 = 36 條
- 主持人／記錄員各自寫的「這場最重要的一件事」× 18 條

### 3.2 整理方法（親和圖，兩輪）

**第一輪（獨立）**：兩人**各自**把每條引述寫成一張便利貼，只抄原話與出處（場次＋卡片），**不寫詮釋**。各自分堆，堆名事後才取。

**第二輪（合併）**：兩人交換分堆結果，把不一致的堆攤開討論。**分歧本身要記錄下來**——同一句話被兩個人放進不同堆，通常代表那句話有歧義，而歧義往往就是介面的問題所在。

### 3.3 主題分類（合併後歸入下列桶；一條引述可入多桶）

| 桶 | 收什麼 | 典型句式 |
| --- | --- | --- |
| **T1 不知道要打什麼** | 面對搜尋框的空白焦慮 | 「我要打什麼？」「這要打關鍵字還是整句？」 |
| **T2 打了但結果不對** | 查詢與結果的落差 | 「這不是我要的」「它好像抓錯重點」 |
| **T3 看不懂結果列在說什麼** | 摘要、術語、簡繁 | 「這什麼意思」「這是簡體字？」 |
| **T4 分不出哪個比較好** | 近義群 | 「這幾個看起來都一樣」「差在哪」 |
| **T5 不敢往下點** | 信任與風險 | 「這安全嗎」「誰做的」「沒人測過？」 |
| **T6 以為系統壞了** | 誤讀空狀態、停用控制項 | 「是不是掛了」「東西很少喔」 |
| **T7 想做但做不到** | 超出 M1 範圍的期待 | 「可以直接試嗎」「可以下載嗎」 |
| **T8 意外的正面反應** | 有效的設計 | 「喔這個有寫理由，不錯」 |

> **T8 一定要收。** 只收負面訊號會讓修正把有效的東西一起改掉。

### 3.4 嚴重度分級

| 級 | 定義 | 處置 |
| --- | --- | --- |
| **S1** | 直接造成 `fail_*`，且出現在 **3 位以上**受測者 | 進 §5 修正項清單，**閘門重測前必修** |
| **S2** | 造成明顯遲滯或錯誤理解，出現在 2 位 | 進修正項清單，可排在重測之後 |
| **S3** | 單人一次性，或屬個人偏好 | 記錄，不列修正項 |
| **S0** | 觸及鐵律或 NFR（例如把 `pii-flag` 讀成合規保證、Secrets 外露疑慮） | **獨立立案**，不與閘門結論綁定，不論通過與否都要處理 |

> **一人一次的抱怨不進修正清單。** 9 人樣本的雜訊很大，S3 的正確處置是「記著，下次測試看還在不在」。

## 4. 不通過 → 修正項決策樹

> 只在 §2 有任一判準不通過時進入本節。
> **根問題只有三類：搜尋、內容、呈現。** 先分類再開修正項——三類的修正落點、成本與驗證方式完全不同，混在一起會做出「三邊都動一點、哪邊都沒修好」的結果。

### 4.0 分類決策（依序判，第一個成立者即為主因）

```
G1 不通過
  │
  ├─ 1. fail_not_found 佔失敗題次 ≥ 50% ?
  │        │
  │        ├─ 是 ─┬─ 受測者說「這裡本來就沒有這種東西」，
  │        │      │   且 picked 是一個合理的非 gold 項 ──────> 【C 內容問題】
  │        │      │
  │        │      └─ 其餘 ─────────────────────────────────> 【A 搜尋問題】
  │        │
  │        └─ 否 ─┬─ 2. X-A（gold 在 Top-5 但沒被選中）≥ 30% 失敗題次
  │               │       ────────────────────────────────> 【P 呈現問題】
  │               │
  │               └─ 3. fail_no_reason / X-B 佔多數 ─┬─ 說不出理由是因為
  │                                                   │   摘要是簡中或全術語
  │                                                   │   ─────────────> 【C 內容問題】
  │                                                   └─ 其餘 ─────────> 【P 呈現問題】
  │
G3 不通過（干擾題）────> 見 §4.4（分【A】門檻分支與【P】文案分支）
G4 觸發（單類別／單層全滅）────> 見 §4.5，切片後回到第 1 步重判
```

**兩類以上同時成立時**：以題次數多者為主因，另一類降為次要修正項。**不要同時大改兩類**——重測後會分不出是哪個修正起了作用。

### 4.1 【A】搜尋問題

**定義**：真人打的字，檢索沒有把正確答案排進 Top-5。

| 訊號 | 強度 |
| --- | --- |
| `fail_not_found` 佔失敗題次 ≥ 50% | 主要 |
| 「改寫 1～2 次後才 `pass`」比例高 | 主要（且指向已知解法） |
| 口語模糊卡通過率遠低於直述卡 | 支持 |
| 反向跨語言（DOC-4／DAT-4）集中失敗 | 支持 |
| 干擾題系統給了結果（`system_refused = N`） | 門檻分支 |
| 查詢原文與 golden set 同義但用詞差很多 | 確證 |

**先做的驗證（動任何程式之前）**：

1. 把所有 `fail_not_found` 的**查詢原文逐字**加進 `tools/goldenset/queries.json` 的一份**臨時副本**，跑 `python evaluate.py --index-mode enriched`。
   - **離線也重現失敗** → 確為檢索問題，往下走。
   - **離線能命中、線上不能** → 不是檢索模型問題，是**線上管線與評測不一致**（`embeddingText()` 漂移、`enrichment_status='pending'` 的文件對排序腿隱形、篩選述詞誤殺）。先查 golden-query-set.md §10.1 的對齊斷言與 import-report.md §5 的已知 bug。
2. 跑 `python tools/goldenset/evaluate.py --selfcheck` 確認語料與門檻未被動過。

**對策**（依成本排序）：

| # | 對策 | 落點 | 何時選它 |
| --- | --- | --- | --- |
| A1 | **查詢改寫上線**（ADR-013 §2，尚未實作） | `services/llm` ＋ Go 呼叫端 | 「改寫 1 次就 `pass`」佔比高。**這是本測試所測降級路徑的既定解法**，成本最高但已在架構決策內 |
| A2 | **補索引時任務範例句**：對失敗集中的 Skill 重跑增強，讓範例句涵蓋受測者實際用的說法 | `ingest/enrich.go` 的 prompt ＋ 重跑 backfill | 少數幾個 Skill 集中失敗。golden set §10.4 證明這條對 D02／D09 有效 |
| A3 | **門檻重推** | `catalog/http.go` `MaxCosineDistance` | 只在干擾題給了結果、或明顯正確的查詢被拒答時。**必須依 golden-query-set.md §4.1／§10.5 的方法重推，不得手調** |
| A4 | **把篩選述詞下推到候選 CTE** | `db/queries/search.sql`（已有 `ponytail:` 註記） | 失敗集中在有套篩選的題次 |
| A5 | 檢查 `enrichment_status = 'pending'` 的文件數 | `cmd/reindex` | 任何 pending 都會對排序腿完全隱形（import-report §5 Bug 2） |

**不可以做的事**：

- 用受測者的查詢原文反推、手工塞進索引文本（過擬合，下一批受測者的說法會不同）
- 把 `MaxCosineDistance` 調鬆來讓失敗題「有結果」——那會直接讓 G3 崩掉
- 引入等權 RRF 當排序器（golden set §3.7／§10.7 兩次量測都是 −15 條的負增益）

### 4.2 【C】內容問題

**定義**：目錄裡沒有合適的東西，或有但描述本身沒法讓人理解。

| 訊號 | 強度 |
| --- | --- |
| 受測者說「這裡沒有我要的」且 `picked` 是合理的非 gold 項 | 主要 |
| `fail_no_reason` 且說不出理由的原因是摘要看不懂 | 主要 |
| T3（看不懂結果列在說什麼）出現 3 人以上 | 主要 |
| `DOC-4`／`DAT-3`／`DAT-4` 三張卡集中失敗 | **CONTENT-005 分支** |
| T4（分不出哪個比較好）集中在 `WRI-3` 的近義群 | 近義群分支 |
| 離線 golden set 重現不出失敗 | 確證（線上目錄與評測語料只有 15 筆重疊） |

**先做的驗證**：

1. **檢查該題的 gold 標註是否本來就錯。** `task-cards.md` §3 的 gold 是人工對應的，且線上目錄與 golden set 語料只有 15 筆重疊。若受測者選的東西其實更合理 → **是標註錯，不是失敗**；修 §3 對照表並重算 G1（此為**唯一允許的事後重算**，且必須在報告中明列改了哪幾題）。
2. **檢查失敗集中的 Skill 是不是那批簡中的**（`data-analyst` 與 YuYY 系列）。若是且 CONTENT-005 宣稱已完成 → 去看實際入庫的摘要文字，很可能改寫沒有進到索引文本。

**對策**：

| # | 對策 | 落點 | 何時選它 |
| --- | --- | --- | --- |
| C1 | **完成／修正 CONTENT-005 白話摘要**，並確認改寫後有重跑增強與 reindex | `tools/content/` ＋ `cmd/reindex` | 簡中三張卡集中失敗，或 T3 高 |
| C2 | **補目錄**：受測者實際要的東西目錄裡沒有 | CONTENT-003 策展 | 「這裡沒有我要的」重複出現在同一類別 |
| C3 | **近義群的差異化描述**：讓 `humanizer`／`ai-written-check`／`cringe-check`／`full-review` 的摘要各自說清楚「什麼時候該用我」 | 增強 prompt ＋ CONTENT-005 | T4 集中在 WRI-3。golden set §10.6 已記錄近義對是增強的代價，**且指出加更多增強文字沒用** |
| C4 | **修正 `task-cards.md` §3 的 gold 標註** | 本目錄 | 驗證 1 成立 |

**不可以做的事**：

- 為了讓某張卡通過而把 acceptable 清單無限放寬（等於取消判準）
- 把「目錄裡沒有」當成搜尋問題去調檢索

### 4.3 【P】呈現問題

**定義**：正確答案就在畫面上，但受測者沒選它，或選了卻說不出為什麼。

| 訊號 | 強度 |
| --- | --- |
| **X-A**（gold 在 Top-5 但沒被選中）≥ 30% 失敗題次 | 主要 |
| **X-B**（選對但理由非 `on_screen`）佔多數 | 主要 |
| `used_match_reason = N` 比例很高 | 支持（符合原因沒被看見） |
| T5（不敢往下點）、T6（以為壞了）出現 3 人以上 | 支持 |
| 訪談 Q3 有人答「以為壞了／東西很少」 | 停用篩選器分支 |
| `distractor_reaction = thinks_broken` 佔多數 | 空狀態文案分支 |

**先做的驗證**：

1. **`used_match_reason` 與 `pass` 交叉**：若「有看符合原因」的題次通過率明顯高於「沒看」的，代表**符合原因是有效的但不夠顯眼**（版面問題）；若兩者差不多，代表**符合原因寫得沒用**（文案問題）。這兩者的修法完全不同。
2. 重看錄影中受測者的滑鼠停留位置，確認七欄（DISC-002）裡哪幾欄真的被讀了。

**對策**：

| # | 對策 | 落點 | 何時選它 |
| --- | --- | --- | --- |
| P1 | **符合原因提升視覺層級**（不是加字，是往上移／加對比） | `apps/web/src/.../Home.tsx` | 驗證 1 顯示「看了就有效」 |
| P2 | **重寫符合原因的文案**（讓它回答「為什麼是你要的」而不是複述摘要） | 增強 prompt 的 match reason 段 ＋ 顯示層 | 驗證 1 顯示「看了也沒用」 |
| P3 | **空狀態文案分離加強**（`no_results`／`degraded`／`partial_index`／`filtered_out` 四者已分離，但文案可能仍被讀成故障） | `Home.tsx` 四個空狀態區塊 | T6 或 `thinks_broken` 高 |
| P4 | **停用篩選器的呈現方式**：目前是停用控制項＋逐項理由（audit §5.3）。若被讀成「壞了」，選項是改文案、收合，或**在有資料之前整列不顯示** | `Home.tsx` `UNAVAILABLE_FILTERS` | 訪談 Q3 有人答「以為壞了」 |
| P5 | **結果列的七欄取捨**：若受測者只讀名稱與摘要，其餘五欄是雜訊 | `ResultFacets` | X-A 高且訪談顯示資訊過載 |
| P6 | **比較功能的入口**（目前要先勾選才出現 CompareBar） | `Home.tsx`／`Compare.tsx` | T4 高但 `used_compare` 低——**想比較卻沒找到比較功能** |

**不可以做的事**：

- 把「不敢點」直接當成需要更多徽章／標章。DISC-008 明文禁止單一「安全」標章
- 為了讓畫面乾淨而**移除**風險提示或「尚未試跑」標記（DISC-002 允收準則要求）

### 4.4 G3 單獨不通過（G1 通過但干擾題不被接受）

這是最容易被輕忽的一種。分兩支：

| 若 | 則 | 對策 |
| --- | --- | --- |
| `system_refused = N`（系統硬給了結果） | **門檻或管線問題** → 【A】 | A3 重推門檻；先查目錄是否成長（golden set §4.4 觸發條件 1） |
| `system_refused = Y` 但受測者說「壞了／東西很少」 | **文案問題** → 【P】 | P3。無結果的文案必須讓人相信這是**判斷**，不是**故障** |

### 4.5 G4 觸發（單一類別或單一層全滅）

先切出該切片的失敗型態分布（§2.3 只看該切片），再回到 §4.0 重判一次。常見對應：

| 切片 | 常見主因 |
| --- | --- |
| `data` 類全滅 | 【C】CONTENT-005（`data-analyst` 與 YuYY 系列都在此類） |
| `documents` 類全滅 | 【A】golden set 中歷來最弱的類別；先查 DOC-2、DOC-3 |
| 學習者層全滅 | 【P】呈現問題——精深者靠既有知識可以繞過的東西，學習者繞不過。**注意此時精深者會出現大量 `prior_knowledge`**，那些題次本來就不該算 `pass` |
| 精深者層全滅 | 【C】內容問題——他們知道自己要什麼，找不到通常是真的沒有 |

**清單紀律**：

- **S1 全數完成前不得重測。** S2 可以排在重測之後。
- **S0 獨立立案**，不與閘門結論綁定。
- 每一項都要寫**驗證方式**。「改好了」不是驗證方式；可接受的是：離線 golden set 重跑該題、具名測試、或重測時該卡的通過率。
- **一次重測只驗一類主因。** 同時改 A 和 P，重測結果無法歸因。

### 5.1 重測規則

| 情況 | 重測範圍 |
| --- | --- |
| 主因是【A】搜尋，且對策動了檢索或索引 | **全套 9 人重測**（檢索改動影響所有卡片），且需先重跑 golden set 確認沒有回歸 |
| 主因是【C】內容，且只動了特定 Skill 的摘要 | **只重測受影響的卡片**，找 ⬜ 位新受測者。G1 以「該卡通過率」單獨判 |
| 主因是【P】呈現，動的是版面或文案 | **全套 9 人重測**（呈現改動影響所有題次） |
| 主因是【C】且 gold 標註本身錯了 | **不必重測**，修正 `task-cards.md` §3 後重算並在報告中明列 |

> **受測者不可重複使用。** 他們已知答案。第二輪需要新的 9 人（或該類別的新受測者），招募成本要事先算進去——這是 `recruit.md` §5.2 第 12 項「重測預算與時程上限」必須先定的原因。
