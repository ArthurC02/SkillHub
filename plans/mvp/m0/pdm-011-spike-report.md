## 1. 目的與範圍

驗證 ADR-013 選項 D（混合檢索＋索引時 LLM 增強）的可行性：使用者以自然語言任務描述查詢，系統能否把正確的 Skill 排到前面，並產生有依據的「符合原因」。

這是時間盒內的可行性探測，不是 ADR-013 要求的完整 golden query set（每類別 20 條）。本 Spike 的價值在於**盡早找出 ADR-013 假設中最脆弱的一環**，而不是給出最終品質數字。

## 2. 方法

| 項目 | 作法 |
| --- | --- |
| 語料 | 12 份真實公開 `SKILL.md`，取自 `github.com/anthropics/skills`（原始檔存於 `spikes/.../samples/`） |
| Lexical | 自寫 BM25（k1=1.5、b=0.75） |
| 向量 | **TF-IDF 餘弦（代用品）**——環境無 `ANTHROPIC_API_KEY` 與 `OPENAI_API_KEY`，真 Embedding 未驗證 |
| 融合 | RRF（k=60） |
| 索引時增強 | 以 frontmatter（`name`＋`description`）加權 3 倍模擬，未呼叫 LLM |
| 查詢改寫 | 以人工英譯 zh 查詢模擬 ADR-013 §2 的 LLM 查詢改寫，未呼叫 LLM |
| 符合原因 | 依 ADR-013 §3 的模板路徑：取命中詞條中 IDF 最高者填入模板 |
| 中文斷詞 | 字元 bigram（不引入斷詞套件） |

環境：Python 3.14.0，純標準函式庫，無 venv、無第三方依賴（`rank-bm25`／`scikit-learn` 皆未使用，自寫約 60 行即足夠且省去 wheel 相容風險）。

**命中判定的重要修正**：只有當正解文件得分大於 0 才算命中。未修正前，全零分數會讓所有文件同分，排序退化為字母序，第一名被誤計為 Top-1 命中——這會把中文查詢的成績虛報一倍。

### 4.4 三個必須誠實記錄的負面發現

**（a）RRF 在本次設定下沒有帶來任何增益。** 三種方法的每一格數字完全相同。原因不是 RRF 無效，而是**兩條腿送進來的是同一種訊號**：TF-IDF 餘弦本質上仍是詞彙比對，與 BM25 高度相關（改寫後查詢的 top-3 集合平均重疊 73%，其中 3/10 完全相同）。RRF 的價值只有在兩條腿真正互補時才會出現，因此**本 Spike 沒有驗證到 RRF 的價值，也沒有否定它**——這一條必須靠真 Embedding 重測。

**（b）長文件會擠掉正解。** Q06「建立讓 LLM 呼叫內部 REST API 的 server」的正解是 `mcp-builder`，但排第一的是 `claude-api`——那份 `SKILL.md` 有 72KB，內文大量提到 MCP，靠篇幅累積分數壓過了主題精準的短文件。BM25 的長度正規化不足以吸收 4 倍以上的篇幅差距。這直接支持 ADR-013「索引時生成任務導向摘要」的必要性：**應該對摘要與標籤檢索，而不是對原始長文檢索**。

**（c）中文查詢對英文語料的純詞彙召回接近零。** 這正是 ADR-013 背景段落預期的問題，本 Spike 給出了量化值：Top-3 20%，且該筆命中還是英文詞夾帶造成的。

## 5. 符合原因生成

無 API key，僅驗證 ADR-013 §3 的**模板路徑**（零額外延遲的預設路徑），LLM 潤飾未驗證。實際輸出範例：

- Q02（掃描檔抽表格、多份合併）→ `pdf` matches on **scanned, merge, pdfs, tables** — declared purpose: Use this skill whenever the user wants to do anything with PDF files...
- Q04（全公司每週進度更新）→ `internal-comms` matches on **company-wide, weekly, progress, status** — declared purpose: A set of resources to help me write all kinds of internal communications...

評估：**模板路徑可行**。命中詞條確實是使用者查詢與 Skill 宣告的真實交集，符合 ADR-013「符合原因有真實依據，不是事後編造」的意圖，也滿足 DISC-001「顯示每個候選與需求相符的原因」的最低要求。

三項限制：

1. 詞條是**改寫後**（英文）查詢的命中詞。若要對繁中使用者顯示，需要把命中詞映射回原始查詢用語，否則會出現「你搜中文、理由列英文詞」的體驗斷裂。
2. 模板只能解釋**詞彙命中**。若正解是靠向量語意召回（無詞彙交集），模板將產不出理由——這是 ADR-013 未處理的缺口。
3. 未驗證 LLM 潤飾與其逾時降級行為。

## 6. 對 ADR-013 的建議

**結論：方向可行，但三段式作法的權重需要調整。建議 ADR-013 可定案，並在定案時補記以下調整。**

### 6.1 支持維持原決策的證據

- 索引時把 LLM 成本前置的整體架構未被推翻；模板式符合原因確實可行且零延遲。
- 純 PostgreSQL 承載（不引入獨立搜尋引擎）在此規模完全沒有壓力，12 份文件的記憶體內檢索為毫秒級。

### 6.2 建議調整（優先順序與 ADR-013 現行敘述不同）

1. **查詢改寫從「輕量前處理」升格為召回的必要條件**，不是可選增益。ADR-013 §2 目前把改寫寫成可降級步驟（「改寫失敗或逾時直接用原句降級」）。本 Spike 顯示：對繁中使用者查詢英文語料，降級路徑的召回率是 20%，等同無結果。**建議明確定義：改寫失敗時的降級目標是向量檢索（跨語言 Embedding），而不是原句 FTS。**
2. **索引時增強的產出應成為主要檢索欄位**，原始 `SKILL.md` 內文降權或僅作次要欄位。發現（b）證明對原文長文檢索會讓篇幅壓倒主題。
3. **符合原因需要涵蓋「無詞彙交集」的情境**。建議在索引時一併生成「適用任務範例句」，讓向量召回的結果可以引用最相近的範例句作為理由，而不是產不出理由。

### 6.3 定案前仍需驗證的項目（本 Spike 未涵蓋）

| 項目 | 為何重要 | 阻塞於 |
| --- | --- | --- |
| ~~真 Embedding 的跨語言召回率~~ | 決定 6.2-1 的降級路徑是否成立 | **已於 v2 驗證，見第 9 節** |
| ~~RRF 的真實增益~~ | 本次兩條腿同質，未驗證到 | **已於 v2 驗證，見第 9 節（結論為負面）** |
| 完整 golden query set（每類別 20 條） | ADR-013 §驗證方式的原始要求 | PDM-001 首批類別確認 |
| p95 延遲（NFR-004 < 2 秒） | 含改寫呼叫後的端到端延遲，改寫已升格為必要步驟，延遲風險提高 | 基礎設施定案 |

**建議的定案方式**：ADR-013 由 Proposed 轉 Accepted，並在 ADR 中補記 6.2 的三項調整與 6.3 的待驗證清單；不建議因本 Spike 退回重選選項 A／B／C——沒有任何證據支持那三個選項會更好，且選項 C 仍違反 NFR-004。

## 7. 限制總覽（哪些因環境沒驗證到）

- **真 Embedding 完全未驗證**：`ANTHROPIC_API_KEY`、`OPENAI_API_KEY` 皆不存在，向量腿以 TF-IDF 代用，而 TF-IDF 是詞彙方法。所有關於「向量召回」與「RRF 融合價值」的結論皆為未證實。
- **真 LLM 完全未呼叫**：索引時增強（以欄位加權模擬）、查詢改寫（以人工英譯模擬）、符合原因潤飾（未做），三者品質與失敗率皆未知。人工英譯是改寫品質的**樂觀上界**，真實 LLM 改寫會低於此數。
- 語料僅 12 份、查詢僅 10 條，統計意義薄弱；單一正解標註使近似正確的名次不計分，絕對數字偏悲觀。
- 未量測延遲，記憶體內 12 份文件的檢索時間對 pgvector＋FTS 的實際規模無參考價值。
- 未驗證 DISC-002 的結構化篩選（來源層級、是否含 Script、驗證狀態）與可解釋排序。

### 9.3 三個關鍵問題的答案

**A. 繁中原樣查詢 → 英文語料，Embedding 的跨語言召回是否顯著優於 BM25 的 20%？**

**是，差距極大。** BM25 Top-1 1/5（20%）、Top-3 1/5（20%）；`text-embedding-3-small`
對 summary 索引 Top-1 **4/5（80%）**、Top-3 **5/5（100%）**，對 fulltext 索引 Top-1 3/5（60%）、
Top-3 5/5（100%）。也就是 Top-3 召回從 20% 拉到 **100%**，且 v1 中「唯一命中靠查詢夾帶英文詞
`Word`」的假性命中不再是唯一來源——Q02～Q05 四條完全無詞彙交集的中文查詢，向量腿全部召回，
其中三條直接是 Top-1。

意涵：ADR-013 的降級路徑「改寫失敗／逾時 → 向量檢索」**成立**，不需重新設計。
`text-embedding-3-small` 在跨語言這一項**過關**。

**B. 換成真 Embedding 後，RRF 相對單腿是否終於有增益？**

**沒有。這是 v2 最重要的負面發現。** 四種設定的 Top-1 對比（RRF vs 兩腿中較好者）：

| 設定 | RRF Top-1 | 最佳單腿 Top-1 | 差 | RRF Top-3 | 最佳單腿 Top-3 | 兩腿 top-3 平均重疊 |
| --- | --- | --- | --- | --- | --- | --- |
| summary／原樣 | 8/10 | 8/10 | +0 | 10/10 | 10/10 | 37% |
| summary／改寫 | 9/10 | 9/10 | +0 | 10/10 | 10/10 | 47% |
| fulltext／原樣 | 7/10 | 8/10 | **−1** | 10/10 | 10/10 | 43% |
| fulltext／改寫 | 9/10 | 10/10 | **−1** | 10/10 | 10/10 | 63% |

v1 把「RRF 零增益」歸因於兩腿同質（top-3 重疊 73%）。**這個解釋在 v2 被推翻**：重疊已降到
37%～63%，兩條腿確實在送不同訊號，RRF 依然沒有增益，兩種設定下還倒退一名。

真正的原因是**兩腿品質不對稱**。中文原樣查詢下 BM25 幾乎全滅（Q02～Q05 對全部 12 份文件
得分皆為 0），等權 RRF 把這條無效腿的排序平均進來，只會稀釋強腿。改寫後 BM25 變強，但此時
Embedding 也同樣強，融合仍無互補空間。Top-3 在所有設定下都是 10/10 平手——在本語料規模，
RRF 連「候選集合聯集擴大召回」的價值都無從展現，因為單腿已經滿分。

**C. 對摘要索引 vs 對全文索引，長文件擠掉正解的問題（Q06 案例）是否改善？**

**Q06 已解決，但不是靠摘要索引，而是靠換成語意向量。** Q06（`mcp-builder`）在 BM25 下仍是第 2 名
（被 72KB 的 `claude-api` 壓過），但 Embedding 在 **summary 與 fulltext 兩種粒度下都給到第 1 名**。
換言之，v1 觀察到的「篇幅壓倒主題」是 BM25 長度正規化不足的問題，向量檢索本身不吃這一套。

摘要 vs 全文的整體差異則是平手：Top-1 皆 8/10、Top-3 皆 10/10。差異在個別查詢與語言子集：

- 摘要索引在**中文原樣查詢**上較好（Top-1 4/5 vs 3/5）：Q02 `pdf` 2→1、Q03 `pptx` 3→2。
- 全文索引在 **Q08 `skill-creator`** 上較好（1 vs 2）：該 Skill 的 frontmatter 描述過於精簡，
  查詢提到的 evals／triggering 只出現在內文。
- 全文索引在**改寫後英文查詢**上是唯一達到 10/10 Top-1 的設定。

重要保留：本 Spike 的 fulltext 已截斷至 20000 字元（模型 8191 token 上限所迫），這本身就抹掉了
`claude-api.md`（72KB）大部分的篇幅優勢，因此**本測試低估了真實的長文稀釋效應**，摘要索引的
優勢應被視為下界而非上界。

### 9.4 對 ADR-013 定案建議的增補與修訂

以下取代／補充 v1 第 6.2 節：

1. **修訂 6.2-1：查詢改寫從「召回的必要條件」下修回「精準度增益」。** v1 的結論建立在「無改寫
   即 20% 召回」之上；有了真 Embedding，中文原樣查詢的 Top-3 召回是 100%、Top-1 是 80%，改寫
   把 Top-1 補到 100%。結論改為：**向量腿才是跨語言召回的承載者，改寫是 Top-1 精準度的增益步驟。**
   ADR-013 §2 原本「改寫失敗或逾時直接用原句降級」的寫法可以保留，但必須明確：降級後的原句
   **必須進向量檢索**，只走 FTS 才是真正的失效路徑。這同時降低了 v1 提出的 NFR-004 延遲風險
   ——改寫既非必要條件，逾時就砍掉是可接受的降級，不是品質懸崖。
2. **修訂 6.2-2（部分）：摘要索引的理由要換一個。** 原理由「長文件擠掉正解」在向量腿上不成立
   （Q06 兩種粒度都 Top-1）。摘要索引仍值得做，但理由改為：(a) 中文跨語言查詢上表現較好；
   (b) 規避 Embedding 模型的 token 上限——12 份樣本裡已有 1 份需要截斷，真實語料只會更嚴重；
   (c) 成本與重算量。同時要注意反例：frontmatter 過於精簡的 Skill（如 `skill-creator`）會因摘要
   資訊不足而掉名次，因此**索引時生成的摘要必須涵蓋內文能力，不能只複製 frontmatter**。
   建議實作為「LLM 生成摘要 + frontmatter」，而非本 Spike 用的裸 frontmatter。
3. **新增：不要把 RRF 當成品質來源，且必須處理空候選集。** 兩次量測（同質腿與異質腿）都顯示
   等權 RRF 沒有增益，異質腿下還會倒退。建議 ADR-013 明確記載：混合檢索的價值在於**召回覆蓋**
   （某一腿失效時另一腿仍有結果），不在於融合帶來的排序增益；且**零命中的腿不得參與融合**
   （見 9.5）。若日後要追求融合增益，需要的是加權融合或依查詢語言／腿的得分動態調權，
   這超出 MVP 範圍，建議列為後續優化而非首發假設。
4. **6.2-3（符合原因需涵蓋無詞彙交集情境）由 v2 強化為必要項。** Q02～Q05 四條中文查詢對正解
   的詞彙交集為零，卻是向量腿的正常命中——在真實系統中這正是主流情境，模板式理由在這些
   案例上**完全產不出內容**。索引時生成「適用任務範例句」不再是 nice-to-have。
5. **PDM-003 的 Embedding 模型選型：`text-embedding-3-small` 過關**，在本語料與查詢集上沒有出現
   需要換更大模型的證據（Top-3 全數 100%）。

**對定案的整體建議不變**：ADR-013 由 Proposed 轉 Accepted，並補記上述修訂。v2 沒有推翻選項 D，
反而移除了 v1 中最大的未知數。

### 9.5 v2 過程中修正的一個量測缺陷

v1 的 RRF 融合了「零命中腿」的排序。當 BM25 對全部文件得分皆為 0（Q02～Q05 的中文原樣查詢就是
如此），排序退化為字母序，等於把純噪音餵進融合——這是量測工具的假象，真實的 FTS 在這種情況下
回傳的是空候選集。修正為「零命中的腿不參與融合」後，summary／原樣設定的 RRF Top-1 由 6/10
回到 8/10。9.2 與 9.3 的所有數字均為修正後的值。

此修正不影響 v1 的任何數字（`results.txt` 逐字元不變），因為 v1 兩條腿在中文查詢下同時零命中，
原本就記為 miss。

### 9.6 v2 仍未涵蓋的項目

- **仍未呼叫真 LLM**：索引時摘要生成、查詢改寫、符合原因潤飾三者依舊是模擬。查詢改寫仍以人工
  英譯代表，是品質上界。9.4-2 建議的「LLM 生成摘要」因此也未被實測——本 Spike 測到的是裸
  frontmatter 摘要，真實摘要應優於此。
- **未經 LiteLLM 閘道**：v2 直接呼叫供應商 API，這對 Spike 可接受，但**不代表產品實作可以這樣做**
  （AGENTS.md 鐵律 8：所有模型呼叫必須走 LiteLLM 閘道）。
- **未與 `voyage-3` 對比**：[PDM-003 提案](pdm-proposals.md)的定案前置要求比較兩個模型的繁中→英文
  recall，本次僅測 `text-embedding-3-small`（環境無 Voyage 憑證）。不過該模型的 Top-3 已達 100%，
  沒有留下可供 `voyage-3` 改進的空間，**建議把此對比從定案前置降為選項**：除非 Top-1 的
  80%（原樣中文）被判定不足，否則不值得再引入一家供應商。
- 語料 12 份、查詢 10 條的統計意義薄弱依舊；ADR-013 要求的每類別 20 條 golden set 仍待 PDM-001 定案。
- 未量測延遲與 pgvector 實際規模行為；未驗證 DISC-002 的結構化篩選。
