# Skill Hub MVP：規格與允收準則

## 1. 文件用途

本文件定義 MVP 的功能需求、非功能需求與允收準則。每項需求使用固定 ID，供設計、開發、測試與工作清單交叉引用。

## 2. 名詞定義

| 名詞 | 定義 |
| --- | --- |
| Skill | 符合 Agent Skills 概念的完整目錄套件，至少包含 `SKILL.md` |
| Skill Version | 特定時間點不可變更的 Skill 內容快照 |
| Fork | 保留來源關係、可由使用者獨立修改的 Skill 副本 |
| Test Case | User Prompt、測試資料、環境設定與驗收條件的集合 |
| Run | 使用特定 Skill Version 與 Test Case 進行的一次執行 |
| Trace | Run 期間的 Skill 啟用、資源讀取、工具、MCP、Log、錯誤與成本事件 |
| Evaluation | 依規格、執行結果、驗收條件與使用者判斷產生的評估 |
| Artifact | Run 產生並可供查看或下載的檔案 |
| Sandbox Provider | 建立、執行、監控、取消及銷毀隔離環境的可抽換實作 |
| Local Runner | 在使用者電腦執行本機工具或存取私有資料的 Provider |

## 3. 品質與信任狀態

平台不得使用單一「安全」或「完全相容」標章概括所有狀態。至少分開記錄：

- 來源狀態：未知、可追溯、已人工確認。
- License 狀態：未知、已宣告、已人工確認。
- 規格狀態：有效、警告、無效。
- 靜態檢查狀態：通過、警告、阻擋、未檢查。
- 執行狀態：未試跑、成功、失敗、部分成功。
- 相容狀態：未驗證、在指定 Agent／Runtime 通過、在指定環境失敗。

## 4. 功能規格與允收準則

### 4.1 Skill Explorer

#### DISC-001：自然語言意圖搜尋

系統應允許使用者以任務描述搜尋 Skill，不要求輸入 Skill 名稱。

允收準則：

- Given 使用者位於首頁，When 輸入有效任務描述並送出，Then 顯示候選 Skill 或清楚的無結果狀態。
- 結果應保留原始查詢，並顯示每個候選與需求相符的原因。
- 空白或無法理解的查詢不得建立搜尋，並應提示使用者補充任務、輸入或預期輸出。
- 使用者可在未登入狀態完成搜尋與查看公開 Skill。

#### DISC-002：搜尋結果與篩選

允收準則：

- 每個結果至少顯示名稱、白話摘要、來源層級、Agent 相容狀態、依賴、風險提示與最近驗證時間。
- 使用者可依類別、來源層級、Agent、是否包含 Script、是否需要 MCP 與驗證狀態篩選。（**2026-08-15 修訂**：原文保留，六個維度改為分階段允收，見下方「篩選維度的允收階段」表。修訂依據：[m1/m1-work-items-audit.md §5.2／§5.3](m1/m1-work-items-audit.md)——其中 Agent 相容與 MCP 兩維度在 M1 內結構性不可能收斂。）
- 排序不得只使用 Star；排序依據需可被簡要說明。
- 沒有驗證證據的 Skill 必須明確標記「尚未試跑」。
- 尚未進入允收階段的篩選維度不得隱藏，也不得默默忽略：UI 以停用控制項＋逐維度理由呈現，API 對該參數回 400 並附理由。（默默忽略會讓帶該參數的分享連結把整個目錄呈現為篩選後的子集。2026-08-15 隨上一條同批新增。）

**篩選維度的允收階段**（2026-08-15 依 [m1/m1-work-items-audit.md §5.3](m1/m1-work-items-audit.md) 新增；此表只切分允收時程，不改變上方任何一條準則的內容）：

| 篩選維度 | 允收階段 | 啟用條件 |
| --- | --- | --- |
| 是否包含 Script | **M1** | — |
| 驗證狀態 | **M1** | — |
| 類別 | **依 CONTENT-003 策展資料啟用** | 類別目前只存在於策展判斷，無任何欄位保存；需 CONTENT-003 先決定類別是否成為平台欄位，以及使用者自行匯入的 Skill 如何取得類別 |
| 來源層級 | **依 CONTENT-003 策展資料啟用** | 需 CONTENT-003 的人工精選審查產出至少兩種 tier 值；全目錄同值時篩選無法區分 |
| Agent 相容 | **M2（依 Sandbox 實測）** | capability／runtime 兩軸在 M2 Sandbox 試跑前一律 `unverified`；提前提供篩選等於暗示有人做過判定 |
| 是否需要 MCP | **後 MVP（隨 MCP 啟動）** | 靜態掃描與 manifest 皆未捕捉任何 MCP 訊號，訊號來源尚未定義；遠端 MCP 已移出 MVP 首發（見 `TEST-003`） |

#### DISC-003：Skill 詳情與來源追蹤

允收準則：

- 一般模式顯示功能、限制、輸入、輸出、依賴、權限、來源、License 與相容性摘要。
- 進階模式可查看 `SKILL.md` 與套件檔案樹；Script 必須有明確標示。
- 外部 Skill 至少保存來源 URL、來源版本或 Commit、擷取時間及內容雜湊。
- 無法確認 License 時，顯示「授權未知」，不得暗示可自由修改或再發佈。
- 任何 Skill Hub 修改後的版本都能追溯到原始來源及 Fork 關係。

#### DISC-004：Skill 比較

允收準則：

- 使用者可選擇至少兩個候選 Skill 進行靜態比較。
- 比較內容至少包含能力、輸入輸出、依賴、權限、相容性、來源、License 與驗證證據。
- 缺少資料的欄位顯示未知，不得自行推定為通過。

### 4.2 匯入、驗證與個人工作區

#### SKILL-001：Skill 匯入

允收準則：

- 系統可從支援的 URL 或上傳套件建立匯入工作。
- 匯入前後均不得直接執行套件內 Script。
- 匯入結果顯示成功、警告或失敗，並列出原因。
- 重複內容可透過內容雜湊識別，且不覆蓋既有版本。

#### SKILL-002：規格與靜態驗證

允收準則：

- 驗證至少涵蓋 `SKILL.md`、YAML frontmatter、必要欄位、名稱規則及檔案引用。
- 系統能分開呈現阻擋錯誤與可接受警告。
- 系統識別 Script、可執行檔、外部 URL、可能的 Secrets 與宣告依賴。
- 規格通過不得自動標示為執行安全或效果有效。

#### SKILL-003：SKILL.md 內嵌程式碼揭露

背景：靜態檢查若只看副檔名，整份實作寫在 `SKILL.md` fenced code block 裡的 Skill 會被呈現為「不含腳本」。首批匯入實測有 5 個套件以此形式挾帶約 180 行 Python，而檔案掃描回報零腳本（`m1/import-report.md` §4 Top-2）。

允收準則：

- 靜態檢查涵蓋 `SKILL.md` 內的 fenced code block，並依語言標記判斷該內容是否為可執行程式碼。
- 揭露內容至少包含：內嵌總行數、程式碼區塊數、語言別，以及最長單一區塊的行數。
- 揭露訊息明確聲明該程式碼在匯入與掃描期間不會被執行，且不會出現在套件檔案清單上。
- 純敘述性標記（如 `json`、`yaml`、`text`、`markdown`、`diff`）不得計為程式碼。
- 篇幅明顯屬於用法示例的區塊不觸發揭露；門檻值可調整，調整不改變上述揭露欄位。

#### SKILL-004：License 多層溯源

背景與決策依據：[ADR-021](../../adr/ADR-021-skill-license-provenance.md)。精選來源多為 monorepo 子目錄，授權事實散落於 manifest、套件內 LICENSE 檔與 repo 根 LICENSE 三個層級；首批匯入有 37／45 個套件在 frontmatter 未宣告授權（`m1/import-report.md` §4 Top-1）。

允收準則：

- 系統記錄授權運算式時，一併記錄其來源層級（license source），兩者同時存在或同時不存在。
- 來源層級依 ADR-021 的優先序解析：`manifest` > `package-license-file` > `repo-license-file`；較高層級存在時即停止搜尋，不因其內容無法辨識而回退至較低層級。
- 套件根授權檔名的比對不區分大小寫。
- 由打包器搬入的 repo 層授權檔以固定檔名承載，且附帶記錄其來源路徑、repo URL 與 commit 的 provenance 檔；授權全文本身逐位元組原樣保留，不得加註或改寫。
- 使用套件內 LICENSE 檔或 repo 層授權檔解析出的授權，必須產生對應的資訊層級揭露；repo 層的揭露須說明該授權涵蓋 repository，不必然涵蓋本套件內容。
- 以上任一層級解析出的授權，其 License 狀態一律為「已宣告」；任何自動層級都不得將 Skill 標示為「已人工確認」。
- manifest 宣告的授權字串正規化為 SPDX 識別碼；無法對應或有歧義者原樣保留，不得推定。
- 授權未知時 `license_expression` 為 NULL，不得以 `NOASSERTION` 等字串填入運算式欄位。
- Fork 建立新版本時一併複製授權運算式與其來源層級（見 WS-001）。

#### SKILL-005：外部 URL 聚合揭露

背景：`SKILL.md` 與套件檔案內的外部 URL 若逐筆揭露，單一套件即產生 321 筆（多為 OOXML schema namespace），使真正重要的揭露被淹沒（`m1/import-report.md` §4 Top-3）。

允收準則：

- 外部 URL 揭露以主機（host）聚合，每個主機一筆訊息，而非每個 URL 一筆。
- 每筆訊息至少顯示該主機的 URL 總數、數個代表性 URL，以及未列出的相異 URL 數量。
- 聚合不得造成事實遺失：所有原始 URL 與其出處檔案路徑均保留於該筆揭露的明細中。
- 揭露順序穩定：相同套件重複掃描產生相同順序的結果。

#### WS-001：Fork 與版本

允收準則：

- 登入使用者可將 Skill Fork 到個人工作區。
- Fork 保留原始 Skill、原始版本、來源與 License 關係。
- 每次確認保存建立新版本；既有版本不可被原地覆寫。
- 使用者可查看任兩版本的內容差異。

#### WS-002：個人工作區

允收準則：

- 使用者可查看自己的 Fork、版本、Test Case、Run 歷史與下載紀錄。
- 使用者只能存取自己的私有內容。
- 使用者可刪除自己的 Skill、Test Case、Run 輸入及 Artifact；系統應說明刪除範圍。

### 4.3 Test Case 與試跑設定

#### TEST-001：User Prompt 與驗收條件

允收準則：

- 每個 Run 必須包含非空白 User Prompt。
- 使用者可純手動建立驗收條件；系統依 Prompt 與 Skill 自動建議驗收條件為可選強化。
- 使用者可新增、編輯、刪除及確認驗收條件。
- 系統必須保存實際執行時使用的 Prompt 與驗收條件快照。

#### TEST-002：Dataset 上傳

允收準則：

- 使用者可在建立 Test Case 時上傳支援格式的檔案。
- 上傳前顯示大小限制、保存政策及資料使用範圍。
- 檔案只授權給指定 Run／Test Case，不能被其他使用者或 Run 自動存取。
- 使用者可在執行前移除檔案，並可在執行後主動刪除。
- 檔案超過限制或格式不支援時，顯示可理解且不洩漏系統資訊的錯誤。

#### TEST-003：遠端 MCP Server（後 MVP）

本項移出 MVP 首發，依需求訊號啟動；以下允收準則於實作時生效。

允收準則：

- 使用者可設定受支援協定的遠端 MCP 位址及必要憑證。
- 系統連線後先顯示可用工具與要求權限，再允許使用者啟用。
- 憑證不得寫入 Skill Package、Trace 明文或一般應用 Log。
- 系統必須限制或阻擋不允許的內部網路與高風險目的地。
- 連線失敗時，Run 報告需區分 MCP 設定錯誤與 Skill 行為錯誤。

#### TEST-004：本機工具絕對路徑（後 MVP）

本項隨 Local Runner 移出 MVP 首發；MVP 內唯一適用規則：Cloud Sandbox 與 UI 不得宣稱可存取本機絕對路徑。其餘準則於實作時生效。

允收準則：

- Cloud Sandbox 不得宣稱可直接存取使用者電腦上的絕對路徑。
- 使用者選擇本機路徑時，系統要求已連線且相容的 Local Runner。
- Local Runner 在執行前顯示工具路徑、參數、工作目錄與預計存取範圍，並要求確認。
- 使用者可隨時取消執行，Local Runner 必須停止相關工作並回報狀態。
- 未經使用者確認，Local Runner 不得將本機工具或非指定檔案上傳至雲端。

#### TEST-005：執行前權限摘要

允收準則：

- 開始 Run 前顯示 Dataset、Script、工具、MCP、網路、Secrets、Provider 與資源限制摘要。
- 權限有變更時必須重新確認，不得沿用不相符的舊確認。
- 使用者拒絕權限時不得啟動 Run。

### 4.4 Run Orchestrator 與 Sandbox

#### RUN-001：Provider-neutral Run

允收準則：

- Run 定義不包含必須由特定 Provider 才能理解的核心欄位。
- 平台使用自己的 `run_id`，並另存 Provider 的臨時執行 ID。
- Provider 必須宣告 Runtime、網路、資源、地區及其他能力，系統只派送相容任務。
- 更換 Provider 不影響 Skill、Test Case、Trace 或 Evaluation 的核心資料格式。

#### RUN-002：標準 Run 狀態

Run 至少支援：

```text
queued → provisioning → preparing → running → evaluating
→ succeeded | failed | cancelled | timed_out
→ cleaning_up
```

允收準則：

- 每次狀態變更皆記錄時間與原因。
- 使用者可看到目前狀態與最近更新。
- Run 結束後必須進入清理流程，即使執行失敗或取消。
- 重複清理不造成錯誤或破壞其他 Run。

#### RUN-003：SelfHostedProvider

允收準則：

- 每個 Run 使用獨立隔離環境與暫存空間。
- Sandbox 不與 Web/API 或資料庫共用可被工作負載直接存取的主機權限。
- 工作負載以非特權、非 root 身分執行；不得掛載容器管理 Socket。
- 預設封鎖非必要對外網路，只開放使用者確認且政策允許的目的地。
- 套用 CPU、記憶體、磁碟、程序數與執行時間限制。
- Run 結束後清除暫存環境，平台只保存政策允許的 Trace 與 Artifact。

#### RUN-004：取消、逾時與失敗處理

允收準則：

- 使用者可取消 queued、provisioning、preparing、running 或 evaluating 狀態的 Run；取消 evaluating 保留已產生的執行結果與 Trace。
- 超過設定時間的 Run 自動標記 timed_out 並停止工作負載。
- Provider 或 Agent 暫時失敗時，系統需記錄是否可重試；不得無限制自動重試。
- Run 失敗不得阻止使用者查看已產生的安全 Trace 與診斷摘要。

### 4.5 Trace、評估與改善

#### TRACE-001：標準化執行 Trace

允收準則：

- Trace 至少包含時間、事件類型、來源、狀態與關聯 Run。
- 支援記錄 Skill 啟用、資源載入、Tool Call、MCP Call、Script Log、Agent 輸出、錯誤、延遲及成本事件。
- Secrets、Token、密碼與受保護欄位在保存及顯示前完成遮罩。
- 一般模式提供人類可理解的進度；進階模式可查看經安全處理的原始事件。
- Trace 事件順序可被重建，並能識別缺失或延遲事件。

#### EVAL-001：結果評估

允收準則：

- 評估分開呈現規格、啟用、執行、任務效果、相容性與成本問題。
- 每個驗收條件回傳通過、未通過或無法判斷，並附證據或原因。
- 整體結果使用「符合、部分符合、未符合、無法判斷」，不得只提供無法解釋的分數。
- 使用者可對結果提供有幫助／無幫助及文字回饋。
- LLM Judge 的判斷必須標示為模型評估，不得冒充確定事實。

#### EVAL-002：改善建議

允收準則：

- 每項建議至少包含問題、證據、建議修改位置、修改內容與預期影響。
- 系統區分 Skill 內容問題、Runtime 問題、MCP／工具問題與測試資料問題。
- 使用者可逐項接受或拒絕建議，且套用前可查看差異。
- 套用建議建立新 Skill Version，不覆蓋已執行版本。

#### EVAL-003：重新試跑與比較

允收準則：

- 使用者可使用同一 Test Case 對新 Skill Version 重新執行。
- 比較畫面至少顯示驗收結果、最終輸出、錯誤、延遲、成本及 Skill 版本差異。
- 比較結果不得因後續版本修改而改變歷史 Run 資料。

### 4.6 打包與下載

#### PACK-001：標準 Agent Skill 套件

允收準則：

- 下載內容保留正確的 Skill 目錄結構與 `SKILL.md`。
- 打包前再次執行規格驗證；若有阻擋錯誤則不得標示為有效套件。
- 套件保留必要 License、作者、原始來源及衍生關係資訊。
- Secrets、測試憑證、內部路徑及不應散布的 Run 資料不得被打入套件。
- 使用者可選擇是否包含可散布的 Test Case 與範例資料。

#### PACK-002：安裝說明

允收準則：

- 下載頁顯示目標 Agent、支援狀態、安裝位置、依賴與環境變數需求。
- 尚未驗證的 Agent 必須顯示未驗證，不得保證可正常運行。
- 提供至少一個安裝後驗證 Prompt 或檢查步驟。

#### CONTENT-001：三層收錄政策與白名單

平台內容分為精選、已索引、外部結果三層（01 第 8 節）。收錄來源採白名單制，不做大規模全網抓取。

允收準則：

- 每個平台內 Skill 必須屬於三層之一，且層級與第 3 節的品質信任狀態**分開記錄**：層級不是安全標章，也不取代來源、License、靜態檢查與執行狀態。
- 標記為精選的前提是 PDM-002 九項精選檢查**全部為 pass**；任一項為 `fail` 或 `pending` 一律不得標記精選（`pending` 的處置見 `CONTENT-003`）。
- 已索引層只要求：License 狀態可判定、來源可追溯（`SKILL-001` 的雜湊與來源欄位）、無阻擋級靜態檢查結果；不要求九項全過。
- 外部結果層由使用者自行提交 URL 或上傳套件匯入產生（`SKILL-001`）；MVP 不接入市集／目錄站作為內容來源。
- 進入索引的來源必須在白名單內。awesome 清單只作發現管道，任何條目須回溯原始 repo 並走完 PDM-002 的四步回溯准入流程才可加入白名單；清單本身的 License 不繼承給被列的 Skill。
- 任一項檢查不過即記錄否決原因，且不重複評估同一候選。
- 白名單異動（新增、否決、下架）記錄提名人、日期與涵蓋類別，異動流程由 `CONTENT-009` 承接。
- 首批數量目標為每類別精選 4–6、已索引 8–12（含精選）；未達下限不得宣告該類別收錄完成。
- 精選標記的使用者可見措辭為「已人工檢視來源與 License」，不得使用「安全」「官方推薦」等背書語（NFR-001）。

#### CONTENT-002：來源可信度、License 與衍生關係的呈現規則

允收準則：

- 呈現授權時必須同時呈現**授權運算式與來源層級**，不得只顯示運算式；層級語意與優先序依 ADR-021（見 `SKILL-004`）。
- 任何自動解析層級解出的授權，License 狀態一律為「已宣告」。「已人工確認」只能由人工複核給予，且須留下判定理由。
- 「已人工確認」不等於可再散布：source-available 授權可通過人工確認，但依 ADR-012 仍封鎖 Download Artifact。
- 由 repo 層授權檔解析的授權，其揭露須說明該授權涵蓋 repository、不必然涵蓋本套件內容。
- 授權未知時顯示「授權未知」，不得暗示可自由修改或再發佈（`DISC-003`）。
- 來源狀態與 License 狀態分開呈現，不得合併為單一標章（第 3 節）。
- 「宣稱寬鬆授權、實為他人 source-available 衍生物」這類個案只能走人工複核處理；不得有任何自動層級將其放行為可散布。
- Skill Hub 修改後的版本可追溯至原始來源、原始版本與 Fork 關係（`DISC-003`、`WS-001`）。

#### CONTENT-003：首批 Skill 候選清單

允收準則：

- 清單逐筆記錄：來源 repo URL、pin 的 commit SHA、`SKILL.md` 路徑、License 與其來源層級、依賴、是否需外網、Script 規模、所屬類別與層級。
- 三個類別各自達成 `CONTENT-001` 的數量目標，且達標判定以逐筆清單為準，不以估算數字為準。
- 每個精選候選逐項填九項精選檢查的判定值（`pass`／`fail`／`pending`）；`pending` 必須標明承接的工作項目。
- 勾選完成的條件：九項中的 **⑤（無疑似 Secret）與 ⑦（白話摘要）全數 `pass`**，即 `CONTENT-005`／`CONTENT-006` 完成。**⑧（平台基準試跑）不是勾選前提**——勾選當下須在清單中把 ⑧ 明確記為「待 M2 基準試跑，見 `CONTENT-007`／`008`」，不得記為 `pass`。
- License 判定一律以實查 `LICENSE`／`LICENSE.txt` 檔案內容為準，不採信 README 或 repo metadata 的宣稱。
- 尚未完成的法務判定（例如 source-available 條款是否允許平台保存內容快照）阻擋相關項目計入達標數；受影響的類別須標明塌陷風險與跌破下限的數量。
- 淘汰或否決的候選記錄原因與判定依據，供 `CONTENT-001` 的不重複評估規則使用。
- 來源多樣性可被檢查：清單須能列出獨立來源 repo 數，避免單一 repo 承載整個類別。

#### CONTENT-004：首批 Skill 的來源與 License 檢查

允收準則：

- 逐 repo 實地存取並查驗授權檔內容，記錄查核日期與查核方法；所有 URL、commit SHA、License 判定皆以該日觀測為準。
- 每筆保存來源 URL、版本或 commit、擷取時間與內容雜湊（`SKILL-001`、`DISC-003`）。
- monorepo 來源**逐目錄判定授權**，不得以 repo 根 License 一概而論；目錄自帶授權檔時以該檔為準。
- source-available 內容的統一政策：可索引、可在平台內試跑，但**一律不產出任何 Download Artifact**，UI 顯示「可在平台試跑，不提供下載」。放寬此政策需負責人與法務明確確認。
- 無法確認授權者，License 狀態維持「未知」，且不得進入打包流程。
- 作者可辨識（GitHub 帳號或組織）已逐筆記錄，供 `CONTENT-009` 的下架與變更通知使用。

#### CONTENT-005：一般使用者可理解的白話摘要

允收準則：

- 摘要與任務範例句由生產路徑（索引時增強）產生並保存為模型產出標示；不得在文件或後台就地手寫。
- 產出欄位限 ADR-013 的白名單（白話摘要、任務範例句、輸入／輸出／工具／依賴標籤、限制）；**不得包含信任、風險、安全、品質的判斷**。
- 一般模式顯示所需的「限制」欄位須有值（`DISC-003`）；缺值者不得判定為通過。

  > **2026-08-16 修訂（負責人授權紀錄：2026-08-16 決定不進行人工審核）。** 審核方式改為**自動化審校**：以**獨立 Judge 模型**（`gpt-5.6-terra`，PDM-003 Judge 層，與生成模型 `gpt-5.6-sol` 分離）加機械檢查逐筆判定，判準與閾值先驗寫死於審校 Script 並附設計理由。「審核人不得是產生者」由**模型分離**滿足；抽審規定由**全 45 筆全量審校**取代（強度高於原準則，故不另設抽樣比例）。審校對象為**線上目錄的該版文字**（下方非決定性上限），工具為 [`tools/content/review_summaries.py`](../../tools/content/review_summaries.py)，KPI 定義、閾值推導與逐筆判定見 [`m1/content-review-report.md`](m1/content-review-report.md)。負責人核可該報告即為核可審核結果；原文保留於刪除線供回溯。

允收準則：

- 每筆完成規格驗證與靜態掃描，結果分為阻擋、警告與資訊三類分開呈現（`SKILL-002`）。
- 匯入與掃描階段**不執行套件內任何 Script**；掃描為純靜態判定。
- 掃描涵蓋 `SKILL.md` 內嵌可執行程式碼（`SKILL-003`）、外部 URL（`SKILL-005`）、疑似 Secret 與宣告依賴。

- 指向套件外檔案的跨 Skill 引用須決定呈現方式，不得靜默忽略。
- 規格與掃描通過不得標示為執行安全或效果有效（NFR-001、`SKILL-002`）。

- `writing` 類的每個精選附一份可編輯 rubric，供 LLM Judge 逐項回傳證據引文（PDM-003）。

本項依賴 M2 的 Test Case 與 Sandbox，里程碑為 M2。

- 基準試跑在隔離 Sandbox 內執行，不在匯入或掃描階段執行。

## 5. 非功能需求

### NFR-001：安全

- 未受信任內容不得在主要 Web/API 程序內執行。
- 所有 Dataset、Secrets、工具與 MCP 權限採最小權限原則。
- Sandbox 預設禁止不必要的檔案、程序與網路存取。
- 重要操作保留稽核事件，包括匯入、執行、權限確認、下載與刪除。
- 未登入搜尋、外部即時搜尋與匯入端點必須具備速率限制與濫用防護。
- 靜態掃描通過不等於安全保證，UI 必須避免此類誤導。

### NFR-002：隱私與資料生命週期

- 使用者在上傳前可查看資料保存政策。
- 使用者可主動刪除 Run 輸入與 Artifact。
- 刪除工作需具有可追蹤狀態，且不再出現在一般存取介面。
- Secrets 不得出現在套件、一般 Log、分析事件或未遮罩 Trace。
- 保存期限仍為待決策事項，確定後須轉換為可測試的時間要求。

### NFR-003：可靠性與可恢復性

- Run Orchestrator 可辨識 Provider 不可用、執行失敗、評估失敗與清理失敗。
- 每個終止狀態都有可理解的使用者訊息與內部診斷碼。
- 清理工作可安全重試，並能發現超過期限仍存在的 Sandbox。
- 服務重新啟動後，Run 狀態可從持久資料與 Provider 狀態恢復或安全終止。

### NFR-004：效能目標

以下為 MVP 規劃目標，需在確認基礎設施後校準：

- 已索引內容的搜尋回應目標：第 95 百分位小於 2 秒，不含外部即時搜尋。
- 建立 Run 後應在 3 秒內回應已排入佇列或明確失敗。
- 一般 Trace 事件在產生後目標 3 秒內出現在執行畫面。
- Sandbox 建立時間、完整 Run 時間及下載打包時間需被量測並可觀察。

### NFR-005：可觀察性

- 平台 O11y 與使用者可見 Run Trace 分開管理。
- 平台至少量測搜尋延遲、Run 排隊時間、建立時間、成功率、逾時率、清理失敗率與 Provider 可用性。
- 每個服務事件可透過 `run_id`、`user_id` 與 Provider 關聯，但不得把敏感資料寫入 Log。

### NFR-006：可抽換性

- Provider 特定程式碼限制在 Adapter／Provider 邊界。
- 核心領域資料不使用 Provider 專屬路徑、狀態或 Artifact URL 作為永久識別。
- 至少以契約測試驗證 SelfHostedProvider（及未來 LocalRunnerProvider）的共同生命週期行為。

### NFR-007：可用性與可理解性

- 主要流程可在一般模式完成，不要求使用者閱讀 YAML、Log 或 `SKILL.md`。
- 所有錯誤提供下一步行動，不只顯示技術錯誤碼。
- 風險、相容與評估狀態必須同時提供文字，不只依賴顏色。
- 主要操作可使用鍵盤完成，表單具有標籤與清楚的驗證訊息。

## 6. 安全需求（SEC）

本節於 **2026-08-15 新增**，關閉威脅模型的開放問題 **Q19**（`02` 沒有 SEC-* 需求 ID 與允收準則，`03` 第 16 節的十個工作項因此無正式判準）。位置依 Q19 的建議置於非功能需求之後。以下準則**取自 [m0/threat-model-and-sandbox-baseline.md](m0/threat-model-and-sandbox-baseline.md)（v2）已落地的 32 條威脅與 45 項基線檢查**，不新增安全要求；該文件未定的門檻值一律標為未涵蓋，不在此處代為定值。

標註「後 MVP」者不在 MVP 首發範圍，其允收準則於對應功能啟動時生效。

### SEC-001：威脅模型

允收準則：

- 交付物涵蓋資產清單、信任等級、信任邊界圖，以及按資產分節的 STRIDE 威脅逐條記錄；每條至少含情境、影響、現有緩解、殘餘風險與後續工作。
- 現況覆蓋 **32 條威脅**，其中 8 條標註「後 MVP」（遠端 MCP 4 條、Local Runner 4 條），MVP 首發期間生效 24 條。後 MVP 威脅仍須完整記錄，但其緩解工作不排入 M0–M4。
- 每條威脅的後續工作對應到既有工作項目 ID，或明確標為「新增工作（需求負責人排入）」；無承接者不得留白。
- 緩解措施只引用既有 ADR；任何需要新決策的緩解一律記入開放問題，威脅模型本身不建立新架構決策。
- 威脅優先序依「嚴重度 × 殘餘風險」排序，且每個里程碑結束複審一次。
- 維護觸發條件明確：新增資產、新增 Provider、開放新的 egress 目的地、啟動 Local Runner 或遠端 MCP 時必須更新；引用的 ADR 被 `Superseded` 時同步改引用新 ADR。
- **勾選前提**：Q15（匯入 SSRF 在 MVP 期間的歸屬）與 Q16（後 MVP 威脅不排入 M0–M4 是否為認可決定）已有負責人答覆。

### SEC-002：Sandbox 最低安全基線與阻擋條件

允收準則：

- 基線以逐項可判定的檢查清單表達，每項具備 ID、檢查內容、驗證時機、等級（阻擋／告警）、依據 ADR 與所屬閘門；現況為 **45 項（阻擋 42、告警 3）**，分計算隔離、節點與拓撲、網路隔離、資料與憑證、執行映像、清理與遺留資源六區。
- 「阻擋」的語意是**不通過即不得通過其所屬閘門**，不一律等於「不得啟動 Run」；四個閘門為 A 節點准入、B Run 啟動前、C 執行中、D 終止與持續治理，45 項全部歸屬其中至少一個。
- 檢查本身無法執行時（例如政策服務不可用）視同未通過（fail-closed），不得因檢查機制故障而放行。
- gVisor 是額外一層，不替代任何一項檢查。
- 節點池中無合格節點時，新 Run 停留在 `queued` 並顯示「執行環境暫時不可用」；不得降級排到一般應用節點。
- 除基線檢查外，閘門 B 另阻擋：使用者未確認或未重新確認執行前權限摘要（`TEST-005`）、Skill Version 靜態掃描結果為阻擋級（依 `SEC-003` 政策）、超出 Workspace 並行或額度上限、請求能力超出 Provider 宣告能力（`RUN-001`）。
- 每一項檢查都被第 5.6 節的測試類型覆蓋；**M1 結束前不要求全數通過，M2 的 SelfHostedProvider 驗收必須全數通過**。

### SEC-003：Skill 匯入與執行前靜態掃描政策

允收準則：

- 政策明確定義每類掃描發現對應的等級（阻擋／警告／資訊），且該對應可逐項判定；此政策未定案前，閘門 B 的「靜態掃描結果為阻擋」條件不可判定。
- 阻擋級結果使該 Skill Version 不得進入 Run 啟動（閘門 B）。
- 匯入與掃描階段不執行套件內任何 Script。
- 掃描涵蓋 `SKILL.md` 內嵌可執行程式碼（`SKILL-003`）、外部 URL（`SKILL-005`）、疑似 Secret 與宣告依賴（`SKILL-002`）。
- 掃描通過不得呈現為安全保證，UI 須避免此類誤導（NFR-001）。
- **未涵蓋（待決策）**：匯入抓取器的 SSRF 與 DNS Rebinding 防護、內部位址封鎖與來源 allowlist 在 MVP 期間**無工作項目擁有**（`SEC-004` 標為後 MVP，但 URL 匯入是首發功能）。負責人須擇一：擴寫本需求納入匯入抓取器防護，或新增 MVP 內的專責需求與後 MVP 的 `SEC-004` 共用同一組封鎖規則。

### SEC-004：遠端 MCP 的 SSRF、內部網路與資料外洩防護（後 MVP）

本項隨遠端 MCP 移出 MVP 首發；以下允收準則於實作時生效。

允收準則：

- 阻擋 loopback、link-local（含 Metadata Service）、RFC1918 與內部網段、控制平面位址；DNS 由受控解析器固定解析以防 DNS Rebinding。
- MCP 憑證不得寫入 Skill Package、Trace 明文或一般應用 Log（`TEST-003`、鐵律 11）。
- MCP 回應視為完全不受信任內容，與 Skill 套件、模型輸出同級；不得因其來自使用者設定的位址而提升信任。
- 連線失敗時，Run 報告須區分 MCP 設定錯誤與 Skill 行為錯誤（`TEST-003`）。

### SEC-005：Secrets 儲存、短效注入、遮罩與撤銷

允收準則：

- 模型憑證為每個 Run 專屬的短效 Virtual Key，帶預算上限與 TTL；供應商金鑰只存在於模型閘道，任何工作負載不得直連供應商。
- Skill、Dataset 與設定以單次 Run 的短效授權取得，授權範圍限本 Run 資源；Sandbox 不得取得任何平台長效憑證或資料庫權限。
- Secrets 不寫入映像層、不寫入持久磁碟、不出現在啟動參數的持久記錄中。
- Run 終止（含成功、失敗、取消、逾時）後，Virtual Key 與所有短效授權被撤銷。
- Secrets、Token、密碼與受保護欄位在保存及顯示前完成遮罩（`TRACE-001`、NFR-002）。
- **未涵蓋（待決策）**：Virtual Key 注入 Sandbox 的機制（環境變數或設定檔）尚未定案，兩者對 Script 的可讀性差異顯著；遮罩失敗後的補救流程（撤銷、清除已存事件、通知）目前只有偵測指標、無回應程序，建議併入 `SEC-010`。

### SEC-006：Dataset、Trace 與 Artifact 的保存及刪除政策

允收準則：

- 使用者可主動刪除 Run 輸入與 Artifact；刪除工作具可追蹤狀態，完成後不再出現在一般存取介面（NFR-002）。
- Run 終止後暫存空間被銷毀，且清理狀態被記錄，不以最終回應成功取代清理確認。
- Artifact 上傳授權限定目的地、大小與有效期。
- **未涵蓋（待決策）**：Run、Dataset、Trace 與 Artifact 的保存期限尚未定值（NFR-002 自陳此缺口），未定值前相關威脅無法轉成可測試要求；LLM 觀測平台的保存期限、遮罩範圍與 Prompt 出境的使用者揭露義務亦未定案。

### SEC-007：來源、License 與下架處理政策

允收準則：

- 來源、License 與衍生關係的呈現規則依 `CONTENT-002`；首批內容的實查與判定依 `CONTENT-004`。
- 上游內容刪除或改寫的偵測、失效與下架流程依 `CONTENT-009`，並與 `INGEST-010` 共用同一流程。
- 下架不刪改既有 Skill Version 與歷史 Run；既有 Run 仍可追溯其使用的版本。
- 授權未知或不可散布者不得進入打包流程（`CONTENT-004`、`PACK-001`）。
- **未涵蓋（待決策）**：上游重抓的頻率與失效判準尚未定值（同 `CONTENT-009`）。

### SEC-008：使用者與 Run 之間的資料隔離驗證

允收準則：

- 所有使用者資料查詢預設要求 Workspace Scope，且 Scope 取自 session，不信任呼叫端傳入的識別；非擁有者的存取一律不揭露資源存在。
- 隔離以具名整合測試驗證，至少涵蓋私有內容列表、刪除、Fork、版本差異與公開搜尋五條路徑，並在 CI 以實際資料庫執行。
- 憑證範圍測試通過：跨 Run 使用短效授權、TTL 過期後使用皆須失敗。
- Sandbox 對核心資料庫的連線嘗試以常駐探針實際驗證被阻擋（非僅設定檢查）；偵測到即立即終止該 Run 並以最高嚴重度告警，視為架構回歸訊號。
- **未涵蓋（待決策）**：是否採用資料庫層的租戶隔離作為第二層防護尚未決定；目前隔離完全依賴應用層正確性。採用需新增 ADR。

### SEC-009：Sandbox 逃逸、資源濫用與權限提升測試

允收準則：

- 測試覆蓋基線 45 項的全部：逃逸測試（計算隔離與節點專用性）、資源耗盡測試（CPU／記憶體／磁碟／PID／FD／逾時）、Runtime 相容性測試、網路外洩測試（DNS tunneling、內網掃描、Metadata Service）、憑證範圍測試、清理失敗測試、設定與供應鏈稽核、Provider 契約測試。
- 設定與供應鏈項目以**宣告式稽核**（節點准入探針、映像發佈流水線斷言）驗證，不以滲透測試代替。
- 每次擴充 Runtime 時重跑 Runtime 相容性測試。
- **M1 結束前不要求全數通過；M2 的 SelfHostedProvider 驗收必須全數通過。** 隔離技術 ADR 由 `Proposed` 轉 `Accepted` 的條件包含逃逸測試通過與 Runtime 相容性驗證通過。
- **可執行的驗收程序見 [ADR-022](../../adr/ADR-022-sandbox-deployment-topology-and-security-thresholds.md) 第三部分（2026-08-16 定案）**：測試環境需求（Suite 1 一般 Linux runner／Suite 2 生產同規格節點；**gVisor 的 `systrap` 平台不需巢狀虛擬化**，待部署批第一台節點實測確認）、**10 個測項**與 45 項基線的覆蓋核對、通過判準（**45 項全數 pass、0 項 unknown**，任一 fail 或 unknown 即不得開放外部使用者提交 Skill 執行，無例外流程）、執行者與時機、證據存放於 `plans/mvp/m4/sec-009-acceptance/<日期>-<節點>/`（判定表與 `versions.txt` 進 repo，原始輸出留 CI artifact 並附連結）並保存 ≥ 1 年。
- **前置條件（缺一即判 `unknown` ＝ fail）**：受測 Runtime Image 已發佈至 **GHCR 且附 SBOM 與掃描 attestation**；`infra/nodes/gvisor-baseline.txt` 已填實際版本；`infra/egress/allowlist.yaml` 的 `tier: sandbox` 條目已填實際 `pinned_ip`，且該位址**不是控制平面節點**。
- **程序定案不等於測試通過**：本項於 M2 結束時仍未達成，維持未勾。

### SEC-010：安全事件回應與緊急停用 Provider

允收準則：

- 存在一鍵停用 `SelfHostedProvider` 的流程：停止派送新 Run、排空節點池、保留現場供調查。
- 觸發條件至少包含：逃逸疑慮、隔離技術的高風險 CVE 揭露、遺留資源持續超標、清理長期失敗。
- 流程以 runbook 形式產出，可被值班人員直接執行。
- 隔離技術「安全基準版本」的維護者與 CVE 應變 SLA **已定（[ADR-022](../../adr/ADR-022-sandbox-deployment-topology-and-security-thresholds.md) 第二部分 P-04，2026-08-16）**：維護者為平台維運負責人，基準檔 `infra/nodes/gvisor-baseline.txt`；逃逸類 CVE **24 h 內全池換版，做不到即依本需求停用 Provider**（此即本需求「觸發條件含隔離技術高風險 CVE 揭露」的具體判準），High 7 天，Medium 以下隨每月例行更新；24 h 自 `.github/workflows/gvisor-baseline.yml` 開出 issue 起算。
- **未涵蓋（待決策）**：安全事件的嚴重度分級與值班責任歸屬（誰接最高等級告警）尚未定案——ADR-022 已把「非 slot 類遺留資源連 3 輪撤銷失敗」與「P-02 探針偵測到連線」標為最高嚴重度作為輸入，但分級表本身仍缺；遮罩失敗的補救流程建議併入本項但尚未撰寫。

## 7. MVP 整體 Definition of Done

MVP 只有在以下條件全部成立時，才能視為完成：

- 一位新使用者能完成「意圖搜尋 → 詳情 → Fork → 試跑 → 評估 → 打包下載」。
- 至少一批精選 Skill 具備來源、License、摘要、靜態檢查及平台試跑證據。
- Cloud Sandbox 可在隔離環境完成、取消、逾時並清理 Run。
- UI 不誤導 Cloud Sandbox 可存取本機路徑（Local Runner 為後 MVP）。
- 所有 Run 都能追溯 Skill Version、Test Case、Provider、Runtime 與 Trace。
- 評估結果逐項對應驗收條件並附證據，改善建議可建立新版本後重新試跑。
- 下載套件通過格式驗證，不包含 Secrets，並保留來源與 License。
- 完成安全、隱私、權限、資料隔離及刪除流程測試。
- 完成至少一輪目標個人創作者的封閉測試，並記錄漏斗與質性回饋。
